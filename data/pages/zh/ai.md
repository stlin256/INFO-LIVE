### [Anthropic称其生物实验室已取得重大发现](https://techcrunch.com/2026/09/23/anthropic-says-its-biology-lab-has-already-found-something-big/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Anthropic says its biology lab has already found something big</div>

<div class="article-body" data-article-body="true"><p>上周，Anthropic证实其在旧金山湾区运营着一家湿性生物实验室，利用其AI模型进行实体实验。本周，这家AI巨头宣布，该实验室已经取得了一项自认为重大的发现：一种新型酶“系统”，正如Anthropic所描述的，它具有某些“令人联想到CRISPR的特性”。</p>
<p>CRISPR是细菌用来抵御病毒的天然免疫系统，现已成为研究人员广泛使用的基因编辑技术。</p>
<p>从本质上讲，Anthropic声称发现的是一种此前未知的酶系统，隐藏在噬菌体（一种感染细菌并在其体内复制的病毒）的DNA中。Anthropic的研究人员表示，该系统的行为类似于CRISPR，能够“执行DNA的剪切、复制和粘贴等操作”。</p>
<p>这项发现究竟有多重大或多具新颖性，还有待更广泛的科研界进行验证。Anthropic首席执行官达里奥·阿莫代（Dario Amodei）在社交平台X上发文承认，该发现是建立在他人先前工作的基础之上的，斯坦福大学的一个团队此前曾发现过一个“在某些方面与Claude所发现的系统类似”的系统。</p>
<p>但阿莫代和Anthropic不仅仅是在强调这项发现本身。这位CEO写道，他们正在大肆宣传该发现“主要是、尽管并非完全由Claude完成的”。</p>
<p>一方面，这是令人震惊的。该实验室今年春季才刚刚建立（尽管Anthropic拒绝具体说明它究竟开放了几个月）。仅仅在短短几个月内就取得一项发现已经足够神速，但团队表示，Claude实际上只花费了21个小时的协同努力。Claude动用了约950个智能体（agent），消耗了2.1亿个token来检索数据。</p>
<p>然而，Anthropic开展生物实验的消息曝光之际，正值包括阿莫代在内的多位AI公司CEO公开承认模型能力已变得如此强大、且潜在危险如此巨大，以至于全行业必须放慢脚步并建立安全测试流程之时。此前，本月早些时候，他的两名员工公开表示AI存在消灭所有人类的风险。</p>
<p>阿莫代本人曾表示，他最担心的事情之一就是AI可能被用于生物恐怖主义。但他同时也写道，他相信AI将在“5到10年内治愈大多数疾病”。因此，Anthropic显然认定其中的回报值得承担相应的风险。</p>
<p>考虑到这一点，这一消息中最大的看点或许并不是发现本身，而是生物实验室并没有彻底放任Claude自由行动。实体实验是由人类完成的。</p>
<p>“我们位于湾区的实验室看起来就像一个典型的分子生物学实验室。我们开展的研究仅涉及较低级别的生物安全风险等级（BSL-1和BSL-2），并且我们不处理能够感染人类的病原体。所有实验室工作均由人类科学家完成。”</p>
<p>诚然，利用AI开展生物学研究并非Anthropic独有。斯坦福大学的研究人员刚刚发表了一篇论文，介绍他们使用大语言模型（LLM）和CRISPR开展的工作。加州大学旧金山分校的研究人员利用AI从零开始设计酶。谷歌早在2020年就推出了其首个AI驱动的生物学研究工具AlphaFold。因此，AI显然已经深入渗透到专门AI实验室之外的生物学研究领域。</p>
<p>不过，阿莫代并没有排除未来建立全自动化生物实验室的可能性。他表示：“最终，在采取适当安全保障措施的情况下，Claude本身甚至有可能通过自主控制实验设备来安全地开展实验，但我们目前还没有这样做。”</p>

### [如果连亚马逊都不知道如何消除碳排放，那还有谁会知道？](https://techcrunch.com/2026/09/23/if-amazon-doesnt-know-how-to-eliminate-carbon-emissions-then-who-does/)
<div class="original-title-sub"><span class="orig-tag">原文</span> If Amazon doesn’t know how to eliminate carbon emissions, then who does?</div>

<div class="article-body" data-article-body="true"><p>亚马逊首席可持续发展官周二表示，该公司尚不知道将如何实现到2040年净零碳排放的目标。</p>
<p>“我们仍在向这一目标努力，”卡拉·赫斯特（Kara Hurst）在Axios主办的一场活动上表示，她随后补充道，自己“不会坐在这里宣称：‘我们知道达成这一目标的所有途径。’”</p>
<p>这一表态既坦诚又现实，但也有些令人失望。如果亚马逊都没有脱碳计划，那还有谁会有呢？</p>
<p>亚马逊是全球体量最大的公司之一，去年营收增长12%至7170亿美元——规模大致相当于爱尔兰的经济总量。正如联合国秘书长安东尼奥·古特雷斯所指出的那样，权力的天平正在从政府向少数几家大企业倾斜，亚马逊的崛起正是这一现象的缩影。</p>
<p>权力转移，责任随之而来。问题在于，亚马逊究竟承担着多大责任？</p>
<p>活动结束后，赫斯特在给TechCrunch的书面回复中表示：“这并非企业与政府对立的问题。应对气候变化所需规模的行动需要双方共同发力，且需要彼此协作。”她补充道：“在能够发挥领导作用的地方，我们都在身体力行。”</p>
<p>诚然，亚马逊并未坐视不理。在昨天的演讲中，赫斯特指出，该公司“连续数年成为全球最大的清洁能源采购商之一”，其资产组合中拥有42吉瓦的清洁能源。她还表示，亚马逊降低了碳排放强度（即每产生一美元营收所产生的污染量），不过这一说法取决于计算的时间跨度。去年，其碳排放强度较2024年有所上升，尽管仍低于2022年的水平。</p>
<p>亚马逊业务庞大且错综复杂，导致其碳排放几乎遍及经济的各个领域，从航空、人工智能到农业和建筑业。该公司需要各个行业的供应商共同努力以实现其目标。“这绝非我们一己之力所能完成的事情，”赫斯特在Axios活动上说道。</p>
<p>该公司承认承诺由其自身负责。赫斯特对TechCrunch表示：“我们对《气候宣言》（The Climate Pledge）设定的到2040年实现净零碳排放目标负责。这项承诺没有改变。”</p>
<p>但亚马逊的一些决定也削弱了其在该议题上的领导地位。今年早些时候，一项调查披露了该公司计划建造一座7.65吉瓦的天然气发电厂，为一处人工智能数据中心园区供电。该项目的35台涡轮机每年可能释放高达3300万吨二氧化碳，使其成为美国境内该类污染的最大单一来源。</p>
<p>除了少数例外，企业几乎总是将收入增长置于气候承诺之上。对于像亚马逊这样运营着全球最大云服务的公司而言，人工智能显然是一个绝不能错过的营收增长驱动力。</p>
<p>气候科技界一直希望，随着清洁能源成本的下降，市场机制能施展魔力来减少碳排放。虽然有一些成功案例，但人工智能热潮表明，这种方法存在局限性。就连作为该领域领头羊之一的亚马逊，也在大举押注天然气。在此过程中，它实际上等于在宣称，应对气候变化是留给未来几代管理层去处理的问题。这听起来是不是很熟悉？</p>

Research）以及维多利亚州卫生部。<br />阿尔巴尼斯昨晚与维多利亚州州长本·卡罗尔（Ben Carroll）以及新南威尔士州州长克里斯·明斯（Chris Minns）进行了简短通话。<br />他表示，早期证据发现该智能体访问了公开可用的文件，以及不打算公开的文件资料。<br />“目前可获得的证据显示，澳大利亚服务局的网络没有遭到更大范围的破坏。尽管如此，这种情况显然是不可接受的，”他说。<br />阿尔巴尼斯表示：“目前阶段尚无理由认为任何个人信息被访问，但调查仍在进行中。”<br />他介绍，该事件始于6月18日，当时OpenAI的一个研究团队使用内部模型对公共医疗领域开展基于互联网的研究。<br />该AI智能体在从政府门户网站获取信息时遭遇了多次拦截阻断，但它找到了绕过这些阻断的方法，最终获得了对其他区域的未授权访问权限。<br />“显然当时有拦截机制在发挥作用，向该AI智能体提示拒绝访问，”阿尔巴尼斯说，“AI智能体找到了绕过这些拦截的方法，不接受被拒绝的结果。”<br />随后，该智能体访问了公开及非公开信息，且根据澳大利亚服务局的说法，还向一台内部服务器写入了文件。阿尔巴尼斯表示，OpenAI直到9月10日——事件发生近三个月后——才向政府发出通知，而且是通过向一个公共邮箱发送电子邮件的方式进行的。<br />澳大利亚服务局随后于9月15日向澳大利亚网络安全中心（Australian Cyber Security Centre）汇报了该通知。该机构上周向公共服务部部长凯蒂·加拉格尔（Katy Gallagher）通报了这起事件，阿尔巴尼斯表示自己是在上周末听取了相关简报。<br />政府将成立一个由总理及内阁部牵头的特别工作组，紧急审查该事件，并确定现有流程是否足以应对与人工智能相关的网络安全事件。<br />该特别工作组将包括国家网络安全协调员、人工智能办公室、澳大利亚信号局、澳大利亚人工智能安全研究所和澳大利亚服务局。<br />此次审查将评估可能的执法和立法应对措施，同时该事件也将被提交给议会人工智能联合特设委员会。<br />阿尔巴尼斯表示，政府将紧急征询法律意见，以确定是否存在违法犯罪行为，以及该事件是否应转交澳大利亚联邦警察处理。该事件还将纳入政府计划推行的人工智能标准立法中。<br />OpenAI表示，其模型在一次内部评估中访问了“数个澳大利亚政府网站及服务”。这些模型当时正尝试检索有关澳大利亚问题的答案和统计数据。<br />“在此过程中，我们的模型采取了我们未曾预料的行动，”OpenAI发言人表示。<br />该公司表示，其审查未发现患者记录被访问的证据。该公司称，被访问的信息包括汇总的健康统计数据和内部文件名。<br />OpenAI表示，该活动发生在6月，但直到8月才被察觉。它是在对其训练和评估中所谓的“未对齐模型活动”（misaligned model activity）进行审查时发现这起活动的。该公司表示已于9月10日通知了澳大利亚服务局。<br />“我们已通知相关机构，并正在提供技术信息以支持他们的调查并协助排查潜在的安全漏洞，”该发言人说，“我们的整体审查仍在继续。”<br />OpenAI没有透露还有哪些其他政府网站和服务受到了影响。<br />阿尔巴尼斯利用这一披露强化了他的观点，即主张围绕快速发展的人工智能技术建立更严格的保护屏障。<br />“人工智能正在改变世界，”他说，并指出它具有带来经济增长、生产力提高以及健康、科学和创新进步的潜力。<br />“但人工智能也带来了巨大的风险，这就是为什么我们需要设立护栏来保护我们的生活方式。”<br />“我们要确保是我们去塑造人工智能，而不是由人工智能来塑造我们。简而言之，人类必须保持控制权。”<br />阿尔巴尼斯表示，政府理解该事件会令澳大利亚民众担忧，但试图让公众放心，目前尚未获悉有任何个人受到影响。<br />“截至目前，没有证据表明任何个人受到了影响，”他说。<br />阿尔巴尼斯表示，若涉及国家安全，某些细节可以保密，但澳大利亚人有权了解这起事件。<br />“我认为让人们了解这起事件的发生至关重要，”他说。<br />在披露这起侵入事件的两天前，阿尔巴尼斯刚敦促世界各国领导人携手保护人们免受人工智能带来的风险，并表示没有任何一个国家能够独自应对该技术日益增长的风险。<br />在科学家和行业高管警告强大系统的快速发展可能会超出政府控制新兴风险的能力之际，澳大利亚于周一在联合国呼吁就人工智能建立新的国际防护机制，成为22个签署国之一。</p>
<p>美国总统唐纳德·特朗普（Donald Trump）拒绝了放缓和限制人工智能发展的呼吁，并警告称任何自我强加的护栏都将给中国带来危险的优势。</p>
<p>在过去两个月中，OpenAI、Anthropic和谷歌均表示，其模型在进行黑客攻击能力测试时侵入了真实的计算机系统。</p>
<p>澳大利亚前网络安全主管、现任CyberCX首席战略官阿拉斯泰尔·麦吉本（Alastair MacGibbon）表示，该智能体最初并未被设定去黑入任何系统。</p>
<p>他说：“这个智能体的任务并不是黑客攻击；它的任务是进行医学研究，而它只是碰巧使用了其工具箱中的工具来实现该目标，这基本上涉及了黑客攻击手段。”</p>
<p>“它们这样做并不是出于恶意。它们这样做是因为被赋予了任务。设想一下，如果是一个怀有恶意的人指使智能体去执行这些任务会怎样。”</p>
<p>麦吉本表示，更大的隐患在于这起违规入侵事件此前一直未被察觉。他说：“我们应该追问的问题是，澳大利亚政府在6月份为什么没有检测到这一点。”</p>
<p>他还批评了政府在人工智能监管方面的资金投入。他将人工智能安全研究所（AI Safety Institute）四年间的预算规模比作昆士兰州的几个道路事故多发点治理项目。他表示，据他了解，总理及内阁部的人工智能办公室“实际上只有寥寥数人”。</p>
<p>“我入行25年了，我们一直在失败，”麦吉本说，“现在我们有了澳大利亚的受害者……这必须引起高度重视。这种傲慢必须停止。”</p></div>

### [在承接 AI 工作负载前验证 GPU 集群就绪状态](https://developer.nvidia.com/blog/validate-gpu-cluster-readiness-before-ai-workloads-land/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Validate GPU Cluster Readiness Before AI Workloads Land</div>

<div class="article-cover"><img src="https://developer-blogs.nvidia.com/wp-content/uploads/2025/12/cybersecurity.jpg" alt="在承接 AI 工作负载前验证 GPU 集群就绪状态" loading="lazy" /></div>

<div class="article-body" data-article-body="true"><p>借助 NVIDIA Cluster Readiness Engine（集群就绪引擎），团队可以通过工作负载驱动的验证，将可靠的 GPU 集群投入生产。</p>
<p>GPU 集群可能通过每一项健康检查，但在运行 AI 工作负载时依然失败。即使每个 GPU、网络链路和 Pod 都报告健康，一个 512-GPU 的训练任务仍可能性能不佳或失败。其原因可能是一个缓慢的 GPU、在负载下性能下降的链路，或者将流量悄悄路由到较慢路径的配置。运维人员可能在运行数小时后或客户提交工单时才发现问题。随后，团队可能需要花费数天时间对集群进行二分法排查以定位根本原因，而算力资源却处于闲置状态。</p>
<p>NVIDIA Cluster Readiness Engine（NVCRE）是一个开源 Kubernetes 控制器，在生产工作负载落地之前将排查范围缩小至具体的受影响节点。它跨拓扑感知节点组运行真实的分布式工作负载，测量结果，并报告哪些节点未通过各项测试。运维人员不再需要手动编写 NVIDIA 集体通信库（NCCL）清单、手动二分排查机架，或者从客户工单中获知硬件降级。就绪状态由此成为集群经过验证的既有属性，而非假设。</p>
<p>GPU 集群的就绪是分阶段实现的。它会经历启动（bring-up）、老化测试（burn-in）、准生产（preproduction）和生产（production）阶段，每个阶段都设定了不同的门槛。通过冒烟测试的节点并不一定准备好加入 512-GPU 的训练任务。</p>
<p>平台团队通常会将这一流程编写在操作手册（runbook）、电子表格或封装了 NCCL 测试的 Shell 脚本中。这便成为了他们在节点配置、GPU 共享和工作负载编排之外必须构建和维护的另一套系统。</p>
<p>集群可能通过标准诊断，却仍在真实的分布式作业中发生故障，因此测试就绪状态的最佳方法是运行实际的工作负载。在 Slurm 上，这只需要一条 srun 命令。而 Kubernetes 没有内置的等价命令，因此相同的测试需要 GPU 和远程直接内存访问（RDMA）资源请求、与网络架构相匹配的 NCCL 设置、足够大的共享内存卷，以及确保所有 Pod 同时启动的机制。</p>
<p>NVCRE 填补了 Kubernetes 上的这些空白。它运行能够暴露出真实硬件问题的工作负载，并精准指出导致每次故障的具体节点。</p>
<p>API 即产品界面。自定义资源定义（CRD）定义了各项资源，因此您可以通过 kubectl 进行检查，并通过 GitOps 工作流进行管理。</p>
<p>该 API 包含按层级排列的三个资源。</p>
<p>一项认证（certification）为每个类别创建一个工作流（workflow），每个工作流再创建其子作业（job）。</p>
<p>随后结果向上传播。作业记录哪些节点出现故障及故障原因，工作流报告测试结果，而认证则按类别对结果进行分组。</p>
<p>这一层级结构将每个故障归因于特定节点和类别。例如，一次运行会报告 gpu-01 在 NCCL 期间发生硬件故障，而 gpu-02 未达到带宽目标。</p>
<p>以下示例展示了认证如何指定其目标和要运行的类别。</p>
<p>内置目录目前涵盖三个领域：五种 NCCL 通信变体（all-reduce、all-gather、all-to-all、环回测试以及跨 NVIDIA NVSwitch 环回测试）、NVIDIA 数据中心 GPU 管理器（DCGM）4级诊断套件，以及采用 8B 和 56B 参数 NVIDIA Nemotron 5 模型的 NVIDIA NeMo 预训练。每个条目均包含平台感知的默认配置。</p>
<p>NVCRE 从目标节点检测 GPU 架构和云平台，并推导其余配置，包括每节点 GPU 数量、NCCL 环境以及平台特有的网络配置。</p>
<p>通过和失败标准采用通用表达式语言（CEL），并根据实测指标进行评估。默认情况下不附带阈值。以下数值是针对 NVIDIA GB200 NVL72 级别系统的示例说明。</p>
<p>当测量指标未达到目标时，NVCRE 会设置 ValidationFailed 状态条件，该条件与运行本身是否成功分开记录。即使工作负载顺利完成但未达到目标，仍会被报告为失败。</p>
<p>某些故障仅在特定规模下显现，因此分组策略是显式指定的。testScale 字段用于选择该策略。</p>
<p>所选策略决定了测量内容。在单个 NVIDIA NVLink 域内的 NCCL 测试测量的是 NVLink 带宽，而在三个机架间进行的相同测试测量的则是横向扩展网络（scale-out fabric）。两者的测量目标完全不同。</p>
<p>多节点验证中最棘手的情况是故障无法归因于任何单个节点。例如一个 64 节点的 all-reduce 出现低带宽，而该组内的每个节点都可能有关联。手动隔离原因可能耗费数天的工程时间。</p>
<p>NVCRE 将该隔离过程自动化。设置 testScale: diagnose 会运行拓扑感知的层级分组测试。引擎将每个失败的组进行拆分，重新运行拆分后的各半部分，并以此持续进行，直到达到 minGroupSize。在该规模下仍然失败的组会被标记为可疑项。maxConcurrent 限制了并发运行的作业数量，以免它们占满正在测量的网络。</p>
<p>输出结果会指明少数可疑节点，而不是牵连整个集群组，并给出每个节点失败的原因。</p>
<p>在 Kubernetes 上运行多节点 GPU 工作负载需要平台检测、特定框架的运行时配置、GPU 和网络资源请求，以及失败运行后的清理工作。这种配置过程重复繁琐且极易出错。</p>
<p>WorkloadRun 负责处理相关配置：只需提供容器镜像、选择框架并指定节点数量。</p>
<p>framework 字段支持且仅支持 torch（通过 torchrun 进行分布式训练）、mpi（NCCL 测试和其他 MPI 工作负载）或 exec（任意命令）之一。NVCRE 生成匹配的 Kubeflow TrainingRuntime，注入共享内存卷，设置 NCCL 及平台环境变量，并在硬件支持的情况下启用 NVIDIA NVLink 纵向扩展（scale-up）网络。</p>
<p>在没有协同调度器（gang scheduler）的情况下，Kubernetes 默认调度器会独立调度放置 Pod，各 Rank 只能在框架集合点（rendezvous）等待其对等节点。在繁忙的集群上，这可能会导致死锁：部分已调度的 Pod 占用了 GPU，同时等待永远无法就位的对等节点。设置 spec.gangScheduler 可以让每个工作负载 Pod 启用协同调度器（例如 KAI Scheduler），该调度器会暂留所有 Pod，直到整个任务组（gang）能够一次性完成调度。</p>
<p>由于 WorkloadRun 是一个标准的 CRD，外部工具可以使用它来运行工作负载，而无需引入 NVCRE 的其他组件。NVCRE 提供执行路径，调用工具提供测试内容。</p>
<p>集群在投入生产的过程中必须回答三个问题：配置是否正确？是否已准备好运行真实的 AI 工作负载？当前是否健康？NVIDIA DSX OS 的不同层级分别针对这三个问题给出了解决方案。</p>
<p>NVIDIA AI Cluster Runtime（AICR）用于建立并维护经过验证的集群配置。AICR 将经过验证的驱动程序、Operator、内核和系统设置组合捕获为版本锁定的方案配方（recipes）。团队可以在各个集群间复现相同优化后的配置、验证实时状态并检测配置漂移。这减少了性能波动，避免了在昂贵 GPU 闲置时耗费数天进行调优的情况。</p>
<p>NVCRE 负责验证集群是否已准备好运行真实的 AI 工作负载。这一主动式的、由工作负载驱动的层级会生成实际负载，从而能够发现不会产生遥测指标的故障隐患。单个降级的 GPU 会将同步训练作业的整体速度拖慢至其最差 rank 的水平，而 NCCL 带宽测试可以在几分钟内识别出该问题。</p>
<p>NVIDIA NVSentinel 持续监控集群健康状态。作为被动的、遥测驱动的层级，它监控集群已经产生的各种信号，包括 DCGM 指标、Xid 错误、系统日志以及云服务商维护事件。它能够检测运行时故障，并驱动隔离、排空（drain）和修复工作流。由于它不占用 GPU 运行时间，因此可以在生产环境中持续运行，而在该环境中进行主动测试则会占用原本属于工作负载的 GPU 资源。</p>
<p>每个项目既能独立提供价值，也能相互集成，为运行全栈的团队提供支持。</p>
<p>NVCRE 会记录故障节点及原因。它不会主动对节点打上 cordon、taint（污点）或修补节点状态（patch node conditions），从而避免操作冲突和清理不同步的问题。NVSentinel NVCRE Certification Monitor 可以将失败的认证结果转换为健康事件。随后，配置好的 NVSentinel 策略可以对节点执行隔离和排空，或者触发外部修复。后续成功的认证可以清除故障信号并释放污点。</p>
<p>NVCRE 要求目标集群具备 Kubernetes 1.29 或更高版本、kubectl、Helm 3.x 以及 NVIDIA GPU Operator。NVIDIA GB200 NVL72 和 NVIDIA GB300 NVL72 目录条目还需要适用于 GPU 的 NVIDIA DRA Driver，因为这些条目会创建 ComputeDomain 资源。DCGM 4 级类别需要独立的 DCGM 服务。在繁忙的共享集群上，推荐使用诸如 KAI Scheduler 之类的 Gang-aware（成组感知）调度器（可选）。</p>
<p>安装 CLI 并配置集群。nvcrectl setup init 命令将安装 CRD、控制器、Kubeflow Trainer 以及默认日志配置文件。</p>
<p>随后运行端到端验证。</p>

### [如何使用 NVIDIA Warp 和 MjWarp 加速机器人仿真与学习工作流](https://huggingface.co/blog/nvidia/how-to-use-nvidia-warp-and-mjwarp)
<div class="original-title-sub"><span class="orig-tag">原文</span> How to Use NVIDIA Warp and MjWarp to Accelerate Robotics Simulation and Learning Workflows</div>

<div class="article-body" data-article-body="true"><p>基于 NVIDIA Warp 构建的 MuJoCo Warp (MJWarp) 能够将兼容的 MuJoCo 模型带入 GPU 级并行规模。在本文中，我们将把一个 SO-101 从动机械臂从熟悉的 MuJoCo 工作流迁移至多达 2,048 个并行 MJWarp 环境中，并深入探讨促成这一迁移的技术以及验证步骤。</p>
<p>图 1. MJWarp 如何将 Python 与 GPU 仿真连接起来。MuJoCo 负责加载并编译 MJCF 模型；MJWarp 则在 NVIDIA Warp 中实现物理模拟，后者编译 CUDA 核函数以推进 NVIDIA GPU 上的仿真状态。</p>
<p>这是我们“具身智能物理仿真现状”（State of Simulation for Physical AI）系列的第二篇文章。第一篇文章梳理了机器人仿真的全景格局。在本篇中，我们负责准备仿真环境并扩展其规模，并不训练策略。后续关于 Newton 和 Isaac Lab 的篇章将涵盖下一阶段的集成层。</p>
<p>NVIDIA Warp 是一个用于编写高性能、GPU 加速核函数的 Python 框架。Warp 允许开发者在 Python 中编写静态类型的核函数，并将其编译用于 CPU 或 CUDA 执行。首次启动时会构建并缓存原生模块，后续启动则直接复用。核函数语言是 Python 面向性能的一个子集，而普通 Python 仍负责配置、内存分配以及启动调度。</p>
<p>这个面向机器人的小型核函数用于在重力作用下推演点的位置。一个逻辑线程处理一个点，因此相同的代码可以从两个点无缝扩展到数百万个点，而无需在控制流中引入 GPU 专有术语。</p>
<p>Warp 的三大价值主张包括：</p>
<p>另外还有两项 Warp 能力值得了解，尽管本文的 SO-101 工作流中并未用到。Warp 核函数是可微的：wp.Tape 会记录在其上下文内执行的前向核函数启动，并在调用 backward() 时反向重放伴随状态（adjoints），这也是各团队在 Warp 中构建可微几何、CFD 以及自定义物理引擎（包括用于仿真和设计优化的 CAE 工作流）的原因。Warp 还支持确定性执行（在 Warp 1.15 中引入）：GPU 原子操作在默认情况下依赖于调度器，因此重复启动同一核函数可能会产生微小差异，而可选择开启的确定性模式则通过牺牲少许性能，换取仿真、验证和回归测试中的可复现顺序。这些均为 Warp 框架本身的能力，并不构成对整个 MJWarp 推演过程可微性或确定性的保证。有关详细信息，请参阅关于可微性和确定性执行的 Warp 文档。</p>
<p>尝试体验 Warp：运行 pip install warp-lang（≥ 1.15 支持 GPU 确定性），然后运行 python -m warp.examples.browse，或查阅教程笔记本。</p>
<p>机器人仿真器会反复计算接下来的变化：给定当前的关节位置、速度、控制量和接触情况，它将场景向前推演一个微小的时间步。在本文中，“world”（世界/环境实例）指的是该场景及其状态的一个独立副本。一个 world 可能包含正在伸手抓取立方体的 SO-101 机械臂；另一个 world 则可以包含从略微不同的姿态起始的同一机械臂。</p>
<p>MuJoCo 和 MJWarp 可以运行相同且兼容的机器人与任务，但它们组织计算的方式截然不同。MuJoCo 天然适合在 CPU 上开发和检查单个或少数几个 world。MJWarp 则是 MuJoCo 物理管线的 NVIDIA Warp 实现，它将模型和一批独立状态放置在 NVIDIA GPU 上；调用一次 mjw.step 即可推进整批环境。</p>
<p>MJWarp 的价值并不一定在于让单个 world 的单步推演更快，而在于能够同时推进数百或数千个 world，从而为 GPU 提供足够的并行工作负载来提升整体吞吐量，即每秒完成的总 world 步数（world-steps）。这非常契合强化学习和大规模采样的需求，因为在这些场景中，收集经验的重要性远高于将单一环境的延迟降至最低。</p>

<p>匹配仿真与控制频率。在控制频率为每秒 50 帧且每帧包含 10 个物理子步的情况下，使用的物理时间步长应为 0.002 秒。在 CPU 端推演开始前以及通过 mjw.put_model 上传模型前设置好该参数，以确保两个后端所推进的仿真时间完全一致：<br />如果没有这一行，后续的每一项测量都将承袭这种不匹配性：包括一致性对比、以“仿真秒数”为单位引用的吞吐量指标，以及动作频率不再匹配部署环境的训练策略。</p>
<p>检查方块是否堆叠成功。对于 44 毫米的方块，成功判定转化为两个可测量的条件：水平中心误差 xy_err ≤ 0.015 米（在方块中心之间测量），以及方块中心之间的垂直间距 0.035 米 ≤ dz ≤ 0.055 米（相当于一个方块边长，留有稳定后的松弛余量）。在方块稳定后评估这两个条件；仅仅进程成功退出并不代表任务成功。<br />从配套检出代码中运行 CPU 任务。发布阻断项：在发布这些说明之前，请确认可访问的代码库 URL 以及固定的依赖项与资产版本；下方的代码库占位符并非可执行的 URL。<br />运行结束时会打印上述两个数值（stack check: xy_err=… dz=…），本文后续内容都将与这一断言进行比对。旁边的 so101_pick_place.py 是同一个程序，只是将物理步进留作练习。<br />机械臂直接取自固定在已知可用 commit 的 MuJoCo Menagerie，鉴于 Menagerie 资产会发生变化，因此请将该场景视为模板。可选的 reBot 变体：配套代码还通过 --robot rebot 提供了针对场景布局、夹爪以及容量限制（nconmax=256, njmax=500）的单独配置文件。本指南使用 SO-101。在报告其结果之前，请分别验证 reBot 资产和任务。<br />首先在 GPU 上运行单个世界（world），此时主机（host）仍在循环中，以便你可以在同一个查看器中观察同一任务并比对相同的两个数值。上传模型，分配批处理状态，从已初始化的主机状态进行播种，并在步进前执行一次前向传递：<br />每个设备端数组都带有一个前置的“世界维度”（world dimension），这就是为什么主机状态被索引为 mjd.qpos[None, :]、形状为 (1, nq) 而不是 (nq,)。后续扩展到数千个世界时，只需更改该前置维度，而无需更改调用方式。mjw.put_model() 还可以兼作兼容性检查：如果模型使用了不受支持的特性，它会直接报错，而不是悄无声息地丢弃它们。<br />显式播种这三个字段是更为透明的做法，能够清楚表明具体有哪些数据传递到了设备端；而 mjw.put_data(mjm, mjd, nworld=…) 则是一次性将整个初始化结构体传递过去。<br />随后帧循环即为 Gate 1 循环，其内部步进被重定向到 GPU 并镜像返回：<br />.numpy() 读取会在每个子步同步并将数据复制到主机，因此这是一条任务验证路径，而非吞吐量基准测试路径。它将逆运动学、可视化和任务检查保留在主机端。复制 qpos 和 qvel 后，在将派生的主机变量（如 mjd.xpos）用于控制、可视化或堆叠检查之前，先调用 mujoco.mj_forward(mjm, mjd) 对其进行刷新。在循环结束后读取这些字段并不会自动刷新它们。Gate 4 会从吞吐量路径中移除这些逐步的主机复制操作。<br />MJWarp 在步进前会分配接触（contact）和约束（constraint）缓冲区。超出这些容量会导致受影响的 rollout 无法用于验证或基准测试，即使执行过程伴随溢出警告继续运行而不是抛出异常也是如此。请增大相关限制并重新运行任务。更大的缓冲区会占用更多的 GPU 内存，因此在缩紧分配前，应在完整任务周期内验证容量。<br />为被仿真的机器人和任务设置接触和约束限制。SO-101 配置文件使用 nconmax=128 和 njmax=300 作为起始容量。请检查在任务中接触最密集的阶段这些限制是否充足：<br />应根据任务中接触最密集的时刻来确定其规模——对于抓取和放置任务，即两个夹爪和桌面同时接触方块的瞬间，而不是机械臂在自由空间中悬停的时刻。系统会报告溢出而不是直接抛出异常：当 Option.warn_overflow 保持默认设置时，MJWarp 会在运行脚本的终端或查看器中打印需要增加的预算额度（“narrowphase overflow - <div class="article-body" data-article-body="true"><p>本文由来自 HEMA 的 Mauro Rallo 和 Patrick van der Plas 共同撰写。<br />当 HEMA 的工程师需要寻找答案时，他们往往要在不同的门户之间来回穿梭，穿行于互不相通的 Wiki、服务目录和 IT 门户中。为了化解这种繁琐操作、实现即时应答，这家拥有百年历史的荷兰零售商基于 Amazon Bedrock AgentCore 构建了一个知识层。HEMA 在多个国家拥有 750 多家门店，背后有一支由工程师、产品负责人和业务分析师组成的技术团队推动数字化转型。公司亟需一套能够跨角色、跨工具运作的解决方案。<br />多年来，HEMA 默默构建了一项极具价值的资产：一张关于自身技术全貌的大型结构化图谱。一份服务目录将人员映射到团队，团队映射到服务，而服务又映射到我们对外提供的 API 以及支持的业务能力。问题从来不在于知识不存在，而在于知识难以获取。随着工程团队的扩大，非正式的“直接问身边同事”模式逐渐失效，各团队最终将答案分散在几乎没人知道该如何检索的各类门户、Wiki 和文档之中。<br />在这篇文章中，我们将介绍 HEMA 在内部知识碎片化方面所面临的挑战，阐述为何选择利用模型上下文协议（MCP）和 Amazon Bedrock AgentCore 来构建 HEMA 的内部 AI 助手 HAL，以及它是如何改变我们团队的工作方式的。<br />该方案依托于两个相辅相成的目标：HAL 将知识汇集于一处，而 MCP 则将这些知识直接呈现在人们已在使用的工具中（包括 HAL 网页聊天界面、Kiro、Claude 以及其他智能体）。安全性依托于 Microsoft Entra ID 进行保障，客户端无需配置任何 AWS 凭证。最初作为开发者工具诞生的产品，如今已成为跨角色的得力助手。同样的架构也将为下一步奠定基础：将 HAL 从只读的知识层转变为可执行操作的行动层。</p>
<p>挑战：频繁切换门户与知识碎片化<br />HEMA 的知识难题包含两个截然不同的层面。<br />第一层是结构化的基础设施知识，这一层其实维护得相当不错。多年来，HEMA 一直维护着一份服务目录，记录着整个技术架构的组织脉络：哪些团队拥有哪些服务、这些服务对外开放了哪些 API，以及它们如何映射到业务能力。来自产品信息管理（PIM）引擎和数据网格（data-mesh）表等系统的结构化数据已被导入并整理妥当。关于“存在什么”以及“谁来负责”的任何问题，只要你知道去哪里查找，通常都能找到答案。<br />第二层则是缺口所在。知道“存在什么”并不等同于知道“如何操作”。例如：“我该如何申请某个 API 的访问权限？我该如何配置一个新用户组？我们针对某项事务的规定是什么？”这些流程性问题没有统一的存放处。当团队规模较小、大家互相熟识时，这不成问题，大家直接当面询问即可。但随着 HEMA 不断壮大并引入新工程师，这种模式便无法继续扩展，且几乎没有现成的书面文档可供参考。<br />这导致了新员工入职培训缓慢、因查找位置不同而得到不一致的答案、频繁的上下文切换，以及将员工从实际工作中抽离出来的干扰摩擦。过去寻找一个答案可能意味着要翻找三到四个门户，有时甚至耗费整整一个下午；如今，这一过程在几秒钟内即可完成，直接在集成开发环境（IDE）或聊天窗口中就能搞定。</p>
<p>图 1：“改造前”的状态，展示了用户此前必须查阅的诸多来源</p>
<p>为何选择 MCP 和 Amazon Bedrock AgentCore<br />两项核心目标促成了该解决方案的成型，并且它们清晰地对应着我们选择的两项技术。<br />第一个目标属于 HAL：将 HEMA 碎片化的知识整合为单一、受治理的权威事实来源。第二个目标属于 MCP：将这些知识直接传递到员工开展日常工作的工具中，而不是迫使他们再去访问另一个新门户。<br />为何选择 MCP：模型上下文协议为我们在 AI 客户端与后端能力之间提供了一套标准化接口。我们无需为每个知识源构建定制集成，也无需为每个客户端应用程序重新构建，而是将每个数据源统一暴露为一次 MCP 工具即可。<br />随后，兼容 MCP 的客户端（如 HAL 网页聊天、Kiro、Claude 及其他智能体）便可直接调用相同的工具，无需额外的定制开发工作。正是这一点，让“从日常工具中直接访问”成为切实可行的方案，而非沦为针对每款工具分别开展的工程项目。<br />为何选择 Amazon Bedrock AgentCore：Amazon Bedrock AgentCore 是一个可以在任何框架或模型下大规模构建、连接和优化智能体的平台。对于 HEMA 而言，这意味着无需自行搭建和运维定制的 MCP 服务器基础设施即可构建 HAL。其中最关键的几项能力包括：<br />- Gateway（网关）：直接将 OpenAPI 规范和 AWS Lambda 函数转换为 MCP 工具，无需编写或运行自定义的 MCP 服务器代码。<br />- Identity（身份认证）：为内部 API 提供托管的入站 JSON Web Token (JWT) 身份验证和托管的出站 OAuth2（令牌库）。<br />- Runtime（运行时环境）：以容器化方式托管内部智能体（基于 Strands 框架构建）。<br />- Memory（记忆）与 Amazon Bedrock Guardrails（护栏）：提供对话记忆和内容过滤功能，支持欧盟推理区域及荷兰语。<br />这些能力共同为我们提供了契合企业级要求的坚实基础：Entra ID OAuth 认证、目前的只读访问权限，以及由现有 Active Directory 用户组驱动的访问控制，足以安全地暴露真实的内部知识。</p>
<p>分步构建 HAL<br />HAL 并非一蹴而就，而是经过了深思熟虑的两步演进。首先，团队构建了一个拥有独立聊天 UI 的独立助手。随后，当该底层基础得到验证后，我们通过 MCP 将其开放给了员工已在使用的日常工具。</p>
<p>第一步：将 HAL 构建为独立助手<br />HAL 的第一个版本是一个自包含的助手：一个网页聊天 UI（基于 Next.js 构建），由一个能够基于 HEMA 内部知识回答问题的智能体提供支持。当时尚未引入 MCP，也没有外部客户端，仅有 HAL UI 与 HAL 智能体进行交互。<br />HAL 智能体是一个封装为 Linux/ARM64 容器的 Strands 智能体，托管在 AgentCore 运行时上，并配有 AgentCore memory（短期对话上下文）和 Amazon Bedrock Guardrails（标准层，采用欧盟跨区域推理以支持荷兰语）。AgentCore runtime 与 AgentCore memory 均为 Amazon Bedrock AgentCore 提供的功能。<br />该智能体通过两条不同路径获取知识：<br />- 本地工具，直连知识库（Knowledge Bases）。智能体的语义搜索工具是本地 Strands 工具，直接通过知识库调用 Amazon Bedrock Retrieve API，中间无需经过网关。这是“从知识库中获取答案”的基础核心路径。<br />- 通过 MCP 连接到 AgentCore Gateway，用于实时 API。对于实时数据、完整 OpenAPI 规范、服务目录查询以及人员/团队信息检索，智能体通过 MCP 连接到自身的 AgentCore Gateway（Amazon Bedrock AgentCore 的一项能力）。该网关使用 AWS Identity and Access Management (IAM) SigV4 进行身份验证，进而调用我们的内部 API。</p>
<p>图 2：步骤 1，HAL 作为独立助手<br />我们从已有的结构化数据——服务目录着手，并补充了价值最高的文档，依据痛点程度和问题被提及的频率进行优先级排序。在 HAL 背后，运行着基于 Amazon Bedrock Knowledge Bases（全托管检索增强生成即 RAG 功能）构建的多个知识库：IT 与操作指南文档、API/OpenAPI 规范、Kafka 事件流主题及其 Avro 模式（Schema）、数据整合层（DCL）数据交换通道，以及服务目录（包含人员、团队、服务和 API）。<br />系统没有定制的 MCP 服务器代码。AgentCore Gateway 会直接根据 OpenAPI 规范为 API 直通目标生成 MCP 工具，并通过一个 Lambda 函数对知识库进行语义搜索。将网关直接对准我们现有的 API 规范并不是最理想的最终形态。专为系统间通信设计的 API 往往无法直接映射为智能体能够清晰理解和推理的工具，因此我们计划重构这些定义，使其演变为对智能体更友好的工具。<br />不过在现阶段，直接按原样开放 API 以极小的代价带来了巨大的价值。kb-search Lambda 封装了针对知识库的 Amazon Bedrock Retrieve API。其作用域受到 AWS Identity and Access Management (IAM) 的严格限定，仅能访问特定知识库的 Amazon 资源名称 (ARN)，并具有对源文档 Amazon Simple Storage Service (Amazon S3) 存储桶的只读权限。<br />检索遵循两步模式：初步的知识库搜索可回答大多数问题；当单个分块不足以提供完整信息时，fetch_full_document 会提取完整的文档。通过对语义查询应用 Amazon Bedrock 重排（reranking）功能，以及使用 team_id 元数据过滤进行限定于团队范围的查找，进一步提升了检索质量。</p>
<p>步骤 2：利用 MCP 将 HAL 接入日常工具<br />HAL 在其自有的聊天界面中表现良好，但人们通常工作在其他工具中：例如自己的 IDE、自己的 AI 助手。第二步就是让诸如 Kiro 和 Claude 等外部 MCP 客户端能够在无需分发 AWS 凭证的情况下，访问相同的知识和工具。这意味着需要添加第二个 AgentCore Gateway，并采用 Microsoft Entra ID 代替 IAM 进行身份验证。<br />由于 AgentCore Gateway 仅支持单一的入站身份验证类型，我们无法为这些外部客户端复用步骤 1 中基于 IAM 验证的智能体网关。因此，我们添加了第二个网关——即 Entra MCP Gateway，它通过 Microsoft Entra ID 的自定义 JWT 进行身份验证，专供 Kiro 和 Claude 等外部 MCP 客户端使用。该网关仅与智能体网关共享只读知识库。两者之间不存在共享代码，因此面向外部的接触面可以独立演进或发生故障，而不会对内部智能体造成影响。</p>
<p>图 3：步骤 2，利用 MCP 将 HAL 接入日常工具<br />AgentCore Gateway 能够将 OpenAPI 规范和 Lambda 函数暴露为工具。为了将知识库作为网关目标呈现，我们构建了一个小型中间 Lambda 函数作为网关调用的工具，该函数代表网关对知识库执行语义搜索。相比之下，活跃的内部 API 则直接作为 OpenAPI 目标暴露。</p>
<p>难点所在：身份验证与动态客户端注册（DCR）<br />其中一个颇具巧思的环节是外部客户端如何在没有 AWS 凭证的情况下进行身份验证。在 Entra 网关前端设有一个 MCP 认证代理（由单个 Lambda 支持的 Amazon API Gateway v2 HTTP API），用于协调 MCP OAuth 规范与 Entra ID 的具体要求。它负责提供 OAuth 发现文档，并将请求的 scope 重写为资源应用的调用 scope。它还会剥离 Entra v2.0 所拒绝的旧版 resource 参数，添加 response_mode=query 以便桌面客户端捕获授权码，并附带 Bearer [已脱敏] 代理 /mcp 请求。<br />有一个细节值得专门指出，因为这是整个系统中唯一出现 DCR 的地方。MCP 客户端通常期望使用 DCR，即通过 POST /register 调用返回一个 client ID。该代理并未实现真正的动态注册，而是使用了一个桩（stubbed）/register 接口，返回预先配置好的固定 client ID。DCR 在这里是模拟的，而非真实的。<br />完整的握手过程如下：<br />图 4：OAuth 与 DCR 身份验证流程<br />对于最终用户而言，其带来的便利在于只需配置代理 URL 和空的 oauthScopes 列表，无需 AWS 凭证，初次连接时通过浏览器登录，此后即可自动刷新令牌。</p>
<p>在 Amazon Bedrock AgentCore 上的部署<br />该基础设施采用 AWS 云开发工具包（AWS CDK）进行定义，是一个使用 npm workspaces 的 TypeScript monorepo 代码库。内部智能体作为 Docker 容器运行在 AgentCore 运行时环境上。诸如租户、客户端和资源标识符等特定于环境的配置，均通过 AWS Systems Manager (SSM) 参数提供。<br />在正式上线之前，HEMA 将 HAL 部署到预发（staging）环境，并面向工程师和业务用户开放了为期一个月的实际测试。在解决方案推广到全公司生产环境以供更广泛采用之前，此举验证了回答质量、覆盖面盲区以及日常可用性。</p>
<p>HAL 最初是一个开发者工具，但它目前已成长为一个跨角色的助手，而这种通用覆盖正是其核心意义所在。<br />开发者可以在 Kiro 和聊天界面中，充分调用全部技术层面的信息：文档、API 规范、Kafka 主题及模式、服务目录以及 DCL 通道。<br />产品负责人依靠 HAL 获取文档、操作指引和流程知识——即过去无处安放的规程层信息。<br />业务分析师借助 HAL 获取架构与基础设施知识：通过直接调用服务目录，了解存在哪些服务、这些服务公开了哪些 API 以及哪些团队拥有这些服务。<br />非开发角色的需求不仅真实存在，而且还在不断增长：负责梳理和优化产品经理流程的 HEMA 端到端团队，已经在日常工作中将 HAL 融入其中。在内部，HAL 通过“Everyone Skill”及配套的引导文件进行分发，并借助每月举办的 HEMA AI 开发论坛进行共享和维护。</p>
<p>下一步规划：从解答走向行动<br />如今，HAL 处于只读模式并提供即时解答。下一步则是让同一个助手执行即时操作。<br />这在当下之所以可行，正是因为底层门户已经具备了 API 能力，并且已经集成了现有的 Microsoft Entra ID 单点登录。这意味着 HAL 可以使用与保障读取工具安全完全相同的 Entra ID 身份验证及 Active Directory 组授权模型，将这些操作暴露为 MCP 操作工具。无需引入新的安全模型，只需设计新的、严格限定作用域的工具即可。</p>
<p>最具代表性的范例是预置新的 AWS 账户。如今，开发者需要前往专门的门户网站提交申请。接下来，他们无需访问该门户，直接在聊天软件、Kiro、Claude 或其他智能体中即可发起相同的请求。而且由于 HAL 已经为产品负责人和业务分析师提供服务，这种行动模式自然能够超越开发者运维场景，扩展至这些角色日常发起的更广泛的运营请求中。</p>
<p>这带来的经验是，读取架构为迈向写入步骤奠定了基础：通过在提供解答时妥善解决身份验证、多客户端访问和治理问题，我们已经为执行具体行动打好了基石。</p>
<p>HAL 将 HEMA 的组织知识整合在一个受治理的中心化平台中。MCP 与 Amazon Bedrock AgentCore 使这些知识变得触手可及、支持多客户端且安全可靠，而无需让每个调用的应用程序都从头重新构建认证、授权或路由机制。其最终成果并非一个单一的开发者聊天机器人，而是一个面向开发者、产品负责人和业务分析师的跨角色助手。知识层现已正式上线。顺理成章的下一步是将其扩展为一个行动层。届时，如今用于回答问题的同一套受治理、已认证的基础设施，未来将能够直接执行请求：预置权限、触发工作流，并直接通过聊天界面、Kiro、Claude 或其他兼容 MCP 的智能体代表用户采取行动。</p>
<p>如果您想了解本文中使用的构建模块，以下资源是一个良好的切入点。有关 MCP 服务器托管、身份验证和网关路由的详细信息，请参阅 Amazon Bedrock AgentCore 文档。有关模型上下文协议（Model Context Protocol）规范及客户端兼容性指南，请访问 MCP 规范网站。若要实际上手体验用于构建 HAL 内部智能体的开源智能体框架 Strands Agents，请访问 Strands Agents GitHub 代码仓库。如果您正在为自己的组织构建类似的知识层，Amazon Bedrock 研讨会将在指导式环境中演示检索增强生成（RAG）模式、知识库以及安全护栏。</p>

### [在 GitHub Copilot 应用中渲染超大型拉取请求](https://github.blog/engineering/user-experience/rendering-huge-pull-requests-in-the-github-copilot-app/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Rendering huge pull requests in the GitHub Copilot app</div>

<div class="article-body" data-article-body="true"><p>大规模的重构和代码迁移往往必须作为一个单独的变更来提交。<br />堆叠拉取请求（Stacked pull requests）是将工作拆分为更小变更的极佳方式，它能让代码审查更轻松，并帮助团队以更低的风险交付代码。但有些变更（比如这次的场景）无法被干净利落地拆分。这导致最终面对的是一个可能变得极其庞大的单一拉取请求，而随之而来的审查讨论又会进一步推高其规模。<br />即便在差异对比（diff）和审查讨论规模极大的情况下，审查体验也必须保持快速和流畅。在 GitHub Copilot 应用中，我们在重构拉取请求视图时便始终牢记这一要求。<br />为了测试极限性能，我们打开了所能找到的最大拉取请求：一个拥有 2,200 个文件、超过 100 万行代码变更以及 400 多条行内审查评论的开源拉取请求。以下是我们如何让即使这样极端的拉取请求也能拥有出色性能的实践过程。</p>
<p>问题的范围<br />高速渲染大型 diff 是一个已被充分理解的技术问题：虚拟化行、保持挂载的 DOM 节点较小，并充分利用每一行代码都具有已知固定高度这一事实。<br />评论才是棘手的部分。评论的高度取决于其 Markdown 的换行方式、可折叠区域、内部是否存在回复框，以及其中的图片是否已完成加载。所有这些只有在渲染时才能知晓。这迫使我们采用不同的架构。<br />测量（Measurement）。在真正渲染评论之前，你无法预知它有多高。这打破了让大型 diff 在滚动时保持快速响应的设计基础。<br />数据管道（The data pipeline）。如果为 diff 视图提供数据的数据管道出现停滞，或者丢弃了已完成的工作，那么一个快速的 diff 渲染表面将变得毫无价值。<br />我们究竟是如何发现这些缺陷的（How we actually found the bugs）。这些问题通常会在高负载、特定引擎以及特定滚动位置下暴露。因此，我们定义了“健康状态”的标准，对渲染表面进行了埋点监控以提供数据，并在无需人工值守的情况下持续运行“变更 → 测量 → 改进”的完整闭环。</p>
<p>第 1 部分：虚拟化，以及评论为何会打破它<br />第一步是理解让纯代码 diff 实现高性能的几何计算机制。一旦评论介入，这种几何计算机制便不再适用。</p>
<p>让大型 diff 变快的要素<br />你不可能在页面上放置一百万个 DOM 节点。标准的解决方案是虚拟化（virtualization）：只挂载屏幕上可见的行外加少量缓冲区行，并在用户滚动时复用这些相同的 DOM 元素。列表的表现就如同所有一百万行都真实存在一样：滚动条尺寸精准无误，滚动定位到特定行也能正常工作。但任何时刻实际存在的 DOM 行大约只有 100 行。<br />为了维持这种视觉假象，必须有机制提供空间几何数据。滚动条的高度是所有行高的总和；第 N 行的位置是其上方所有行高的累加和。跳转到某一行、绘制滚动条、决定哪些内容出现在屏幕上，这一切本质上都是对高度表进行的算术运算。你可以基于估算值构建这张表，并在测量具体行高后进行修正，通用的可变高度虚拟化组件正是这样做的。<br />但如果每一行都是采用已知字号的代码行，你就不必如此复杂。你可以在一开始预先计算整张表且它永远不会改变，因此后续完全不需要修正。<br />我们将此称为“绘制前已知所有高度”（all heights known before paint）契约。我们的 diff 渲染表面正是围绕该契约构建的：<br />- 命令式、复用 DOM 的代码行渲染器（每行不采用独立的 React 组件）<br />- 用于偏移量数学计算的类型化数组（Typed-array）几何数据<br />- 后端掌管、结构优先流式传输的 diff 文档<br />- 支持精确“滚动到第 N 行”的命令式滚动 API<br />这其中没有任何环节会出现性能恶化，因为每帧的处理工作量不会随总行数的增加而增长。对于纯代码场景，这一设计是完全正确的，我们完整保留了它。</p>
<p>评论如何改变契约<br />现在，在 diff 中间插入一条审查讨论线索（review thread）。它有多高？<br />你不知道，而且不渲染它就无法知道。它的高度取决于只有在渲染时才存在的事物，并且在初次绘制后还会继续变化：<br />- 在不同宽度下折行方式不同的 Markdown<br />- 用户可以就地展开或折叠的块<br />- 在现有讨论线索内打开、且会随打字输入而增高的回复编辑框<br />- 代码建议 diff、表情回应（reactions）、编辑模式、解决状态横幅<br />- 加载完成后会导致高度变化的图片和异步资源<br />显而易见的应对方案是使用预估器为每条评论预留一个固定高度的槽位。但在超大型拉取请求上，这种方案彻底失效了。一个平均表现准确的预估器在极端情况下依然是错误的。它会为大多数评论过度预留空间，留下大片空白；而对内容复杂的评论又预留不足，导致内容被截断或冒出嵌套滚动条。如果你在绘制后测量真实高度并写回共享的偏移量表中，下方的所有内容都会发生位移，而此时用户已经在滚动页面了。这就是所谓的滚动跳动（scroll jump），而在大型拉取请求中，这种跳动幅度会非常大。<br />因此，评论需要一种完全不同的契约。对于这类内容，“绘制前已知所有高度”是无法实现的。我们退而求其次能够保证的是：高度是有界的、延迟测量的，并且修正幅度小且锚定在用户正在查看的内容上。</p>
<p>采用双重几何体系而非单一体系<br />让这个问题得以解决的思路是：不再强求用同一种几何体系来同时服务这两种类型的内容。我们将文档的高度拆分为两个独立的域：<br />总高度 = 确定性的代码高度（精确、预先已知） + ∑ 动态块有效高度（先估算，后测量） + 滚动内边距<br />代码几何体系保留了原有的机制。它是确定性的、基于前缀和计算的、精确的，并且在评论调整尺寸时永远不需要重建。<br />动态块几何体系则覆盖了我们无法预测高度的所有内容，例如审查讨论线索、草稿和回复编辑框。每一个动态块都是根据其身份而非当前所处位置进行标识的。它拥有一个即便在内容加载后仍能保持稳定的键值，并且它锚定在特定文件、代码行及左右侧，而非具体的像素坐标上，因此页面重新排版不会丢失对其的跟踪。我们还保留了所有可能改变该块高度的要素特征指纹（fingerprint）：其内容、某个区域是否处于打开状态、编辑框是否处于激活状态等。此外，我们还会记录上次测量该块时的宽度并将其量化归类，以便普通的窗口缩放不会使文档中的每次测量全部失效。<br />如此一来，块的有效高度计算便十分简单：如果我们拥有有效的测量高度，则使用测量高度；如果特征指纹和宽度仍然匹配，则使用缓存高度；否则采用预估高度。这些高度保存在独立于代码行的专属索引中，因此评论调整大小永远不会迫使代码几何体系重建。此外，动态块的数量由评论数量决定，而不是由行数决定。即便存在几千个块也毫无问题，只要初次绘制不会同时挂载或测量所有的块即可。</p>
<p>测量调度器，以及我们最初犯下的错误<br />这部分花费了我们最长的时间才得以完善，因为我们最初的设计在一个极具启发性的方向上犯了错。</p>
<p>测量动态内容最直接的方法是为每个区块绑定一个 ResizeObserver，用于监听元素并在高度变化时将其测得的高度写回布局。这正是我们最初设计但在性能强化阶段弃用的方案。这正是大型虚拟化界面必须规避的反馈循环。一个将高度写回其所监听元素布局的观察器可能会重新触发自身，并且其开销会随着挂载区块的增加而不断膨胀。</p>
<p>取而代之并最终上线的方案是一个单一的、受空闲和滚动门控控制的测量流程，该流程遵循与确定性侧相同的纪律：</p>
<p>脱离热路径。它仅在可视范围稳定时运行，绝不会在每次滚动帧中执行，并且在滚动进行中完全处于等待状态。在滚动中途发生回流重排，恰恰是我们极力避免的卡顿来源。当滚动停止后，它才会再次运行。</p>
<p>限定在视口范围内。只有视口约 2400 像素以内的区块才会被纳入候选范围，因此工作量被限制在 O(视口) 级别。较远的区块继续沿用其预估高度，并在接近视口时再行校准。</p>
<p>屏幕上读取优先。已挂载的区块处于屏幕可见区域，因此其渲染出的实际高度即为绝对依据（ground truth）。测量流程以批处理方式一次性读取所有已挂载的候选区块，在中间没有任何写入操作的情况下仅进行一次重排，并记录所测得的数据。已挂载的区块绝不会为了沿用过期的预估值而被跳过。这一规则解决了我们所遇到的最棘手的错误：评论下方出现一条空白带，原因在于某个已挂载的区块被排除在测量之外，导致其一直停留在过大的预估值上。</p>
<p>离屏测量是有界的降级方案。对于尚未挂载的附近区块，测量流程最多只进行一次离屏渲染，以便在其滚动进入视野之前修正预留空间。高于视口的区块甚至会跳过此步骤。由于它们多预留的空间隐藏在首屏折叠线以下，因此不值得付出渲染开销。</p>
<p>观察器负责兜底其余情况。某些高度变化既不会改变指纹，也不会与滚动同步发生：例如在回复输入框中打字、图片加载完成、切换折叠内容等。每个挂载的区块都保留一个 ResizeObserver，但在默认情况下，它所做的仅仅是标记该区块，以便让空闲测量流程重新读取它。它自身绝不会主动写入高度，因为那样会闭合我们所拒绝的反馈循环。它会在卸载时解除监听，未激活的 pull request 标签页则完全不监听任何内容。</p>
<p>但有一个深思熟虑后的例外。对于由用户自身操作引发的尺寸变化，等待显然会带来肉眼可见的不良体验：例如展开折叠内容、打开回复输入框、图片完成加载。区块虽然立即变大，但其下方的代码却只能在下一次空闲测量流程中才会移动位置。在某一帧中，评论区域变高了，而其下方的一切仍停留在原位，用户能明显感知到这种两步式的跳动。因此，当一个区块已挂载且在屏幕上可见时，观察器现在会在同一帧中对其进行测量并在绘制前应用校准。区块变大，代码重新定位，下方的一切内容协同位移。两项安全保障措施防止其变成我们所规避的循环：每帧最多只执行一次同步提交，从而将突发的多重尺寸变动合并为一次；且在主动滚动期间绝不执行，而是退回到批量处理流程。</p>
<p>滚动锚定：校准而不对抗用户操作</p>
<p>当测量得出的高度与预估值存在差异时，滚动条的数学计算会发生变化，幼稚的做法会导致视口产生跳跃。解决方案是基于标识（identity）而非像素来进行校准：</p>
<p>在应用高度更新之前，捕获用户所锚定的目标（通过标识定位一行或一个区块），以及其内部的偏移量。<br />应用高度增量差值。<br />将该同一锚点解析为其新的像素位置。<br />执行滚动，使锚点在视口中保持原地不动。</p>
<p>此外还有几项避免体验失真的规则：<br />视口上方的区块高度发生变化 → 按差值进行调整（保持当前阅读位置不变）。<br />视口下方的内容完成注水（hydrate） → 不作调整（用户看不到）。<br />如果你在可见区块中切换了折叠状态或打开了回复框 → 抑制对该区块的上方区块校准，以使交互感觉直接顺畅，并允许下方的内容自然向下流动。<br />绝不对抗主动的指针或滚轮动量；将校准推迟到当前帧之后批量处理。</p>
<p>最后这条规则存在锐利的边缘情况，我们也曾因此踩坑。“用户正在滚动时不进行校准”最初是通过对最近一次检测到的滚动事件设置防卫逻辑来实现的，但程序化滚动也会刷新该时间戳。切换文件树侧边栏会改变 diff 差异面板的宽度。在开启自动换行的情况下，你上方的每一条折行都会重排为不同数量的可视行，整个坐标空间随之变动，界面在稳定下来时自身也会产生微小的滚动。防卫逻辑将此误判为“用户刚刚进行了滚动”，从而跳过了本应保持你阅读位置的校准操作，导致你正在阅读的文件漂移出了屏幕。修复方案是将用户的实际滚动与界面自身引发的滚动区分开来。任何“用户是否正在交互？”的检查，都必须确保自身的副作用无法满足其触发条件。</p>
<p>这样一来，校准始终保持微量，复用我们已有的测量数据，并始终跟随用户当前注视的内容。</p>
<p>第 2 部分：界面背后的数据流水线</p>
<p>Diff 界面的响应速度上限完全取决于向其喂送数据的效率，而该环节的三种工作习惯塑造了 UI 所能达到的能力。第一是先流式传输结构，再传输内容。Diff 数据是增量请求的，因此在文档仍在加载时，文件树和元数据便已完成绘制，整套审查讨论流（review threads）也会预先解析完毕，而不是零星逐条涌入。第二是将单项工作推迟到真正有需要时再做。语法高亮在主线程之外运行，因此代码行可以立即以纯文本形式显示，并在高亮结果返回后再行着色。语法高亮提升了界面呈现质量，而不会阻塞滚动。庞大的 Markdown 正文和建议变更上下文也采用相同机制：在接近视口之前，任何内容都不会被构建。</p>
<p>第三种习惯关乎哪些成本值得保留。在用户导航离开时释放 diff 文档是合理的默认做法。这些文档体积庞大，保留用户访问过的每一份文档是导致长时间使用后内存被耗尽的原因。但是，pull request 的元数据是持久化保存的，因此包裹在 diff 外层的框架壳子、标头和文件树会在用户返回时瞬间重绘，然后停在原地数秒钟，等待它刚才刚刚加载完成的 diff。在一个瞬间绘制的空框架壳中展示空白的 diff 会给人一种界面损坏的感觉，尽管总体的等待时间变短了。因此，原策略予以保留的同时我们增加了一个缓存层：将最近浏览的几个 diff 保留在内存中，超出限制的予以驱逐，并由后台刷新机制来检测缓存何时过期。</p>
<p>第 3 部分：测量循环，或我们究竟是如何发现这些 Bug 的</p>
<p>在这个项目中，几乎每个缺陷在显现之前都是无影无形的，而手动复现又极其痛苦。一份典型的缺陷报告通常这样写道：“某些评论下方会出现一条空白区域，但只是偶尔发生，且仅在大型拉取请求（PR）中出现；一旦滚过该区域再滚回来，它就自动恢复了。”靠盯着屏幕是无法排查这种问题的，因此我们构建了一套工具来进行机械化排查。</p>
<p>用应用的真实信号进行插桩，而非使用一次性日志<br />最朴素的工作流就是随处插入 console.log 调用、手动执行流程、复制输出内容、粘贴给某人（或某种工具）进行分析、删除日志，然后周而复始。这种方式效率低下，需要人工介入，最糟糕的是，你最终衡量的只是自己手写的插桩代码，而非应用的真实运行行为。</p>
<p>因此，该界面自身携带了针对其不变量的永久性、结构化探针。这些是它在每次渲染时针对自身回答的直白问题：<br />该界面是否真正受限于视口？当前挂载了多少行和多少个评论块？<br />测量计算是否合并为每帧单次提交，该帧耗时多久？<br />我们所做的滚动校正幅度有多大？<br />是否有任何评论块在滚动开始后才被插入？（一旦后端拓扑确定，该数值必须为零。）<br />每个块的观察器（observers）在卸载时是否真正销毁，还是每个块都在泄漏一个观察器？<br />这些都是客观的通过/失败信号，它们作为性能预算断言，被应用于针对包含大量评论的合成超大 PR 测试夹具的端到端测试中。现在，持续集成（CI）可以直接告诉我们该界面是否处于健康状态。</p>
<p>让这一闭环全自动化运行<br />其核心是一个自运行的“修改 → 测量 → 改进”闭环。包含两条路径：<br />无头探针路径：针对模拟服务器运行声明式流程（打开拉取请求、滚动到某一比例位置、切换展开详情块、调整窗口大小），同时读取应用自身的生产级插桩数据：React 渲染次数、性能时间线以及用于检测卡顿的 requestAnimationFrame 采样器。它能独立完成整个插桩、驱动、收集、分析、排序周期，并按顺序打印出性能瓶颈。因为该流程在运行时只是传递给探针的 JSON 数据，所以智能体（agent）只需用自然语言进行描述即可对任何流程进行性能分析，而无需修改一行源代码。<br />自动驾驶机制：在无人值守的情况下，驱动真实的桌面应用循环执行超大 PR 流程：首先是冷启动（评论仍为骨架屏状态），然后是热状态（评论已加载完成），执行切换折叠块、打开与取消回复输入框、折叠与展开文件、切换侧边栏目录树、深层浏览文件列表、调整窗口大小等操作。每项测量数据都会镜像记录到应用的磁盘日志中，这样智能体便可在无人操作键盘的情况下读取运行时行为。每个样本都携带一个健康信号，这就是客观的检查标准。一个热样本只有在满足以下条件时才被视为健康：评论之间没有未填补的间隙、没有留空的评论块，且在整个滚动范围（包括深层文件浏览）内，真实的讨论串内容均已实际挂载。<br />在真实引擎上实现无人值守复现。启用自动驾驶机制，让其循环运行，读取磁盘日志。<br />凭借健康信号而非肉眼进行检测。信任样本字段。<br />探测可疑交界处。当信号变差时，在该处添加一个狭窄的结构化探针，重新启用机制，重新读取。（编辑界面代码会热重载运行中的窗口并重新激活自动驾驶机制，因此获取一次全新的抓取数据仅需大约一个周期的间隔。）<br />拆除脚手架。一旦理清了不变量，就在测试用例和设计文档中将其固定下来，仅保留探测器级别的信号。<br />审查如此庞大的拉取请求，过去往往意味着两件事之一：漫长的等待，或者干脆放弃并在其他地方查看。代码审查并不是一份尺寸固定的文档。它是一场在你阅读过程中不断改变形态的对话，底层的界面必须从一开始就为此而设计，而不是事后打补丁。<br />最终的成果是一个全新的拉取请求视图：即使是包含数百万行代码差异及数百条讨论串的 PR，打开、滚动和交互体验也如同普通大小的拉取请求一样流畅。评论会完整渲染，而不会被截断在可滚动的容器内。展开折叠部分只会移动其下方的代码，而不会影响其他内容。返回刚刚离开的拉取请求时，视口仍停留在原处。<br />如果你日常以代码审查为生，不妨在一个你已知非常棘手的拉取请求上体验这种差异。打开你手头最糟糕的一个 PR 试试吧。<br />立即体验 GitHub Copilot 应用 &gt;<br />文章《在 GitHub Copilot 应用中渲染超大型 Pull Request》最初发布于 The GitHub Blog。</p></div>

### [要闻：Kubernetes 负责管理在节点上运行的负载](https://developer.nvidia.com/blog/manage-kubernetes-node-fleets-with-nodewright/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Manage Kubernetes Node Fleets with NodeWright</div>

<div class="article-cover"><img src="https://developer-blogs.nvidia.com/wp-content/uploads/2026/09/kubernetes-clusters-768x432.jpg" alt="要闻：Kubernetes 负责管理在节点上运行的负载" loading="lazy" /></div>

<div class="article-body" data-article-body="true"><p>Kubernetes 负责管理在节点上运行的负载。而管理节点本身才是真正的挑战所在：内核设置、系统软件包、存储布局、安全代理，以及 GPU 工作负载所依赖的宿主机层调优。许多团队通过 Ansible playbook、自定义脚本和手动操作手册（runbook）来管理这些内容。在另一个区域上线新集群、某次内核升级破坏了 RDMA、或者本周必须在整个节点集群范围内修复某个 CVE 之前，这种方式尚能应付。</p>
<p>GPU 基础设施让这一挑战变得更加艰巨。你无法直接丢弃一个 GPU 节点并迅速拉起一个全新节点。硬件非常稀缺，更换节点可能耗费数小时，而且长期运行的训练作业无法轻易重新调度。因此，运维层面的核心问题不再是如何修改单个节点，而是如何在不中断训练任务的前提下对所有节点完成变更。如今，这一问题的答案通常是一张电子表格、一个维护窗口，以及一名在凌晨三点紧盯终端界面的工程师。</p>
<p>NVIDIA DSX 平台可协助你设计与运营 AI 工厂，在其中，整个设施被视为单一系统而非一组离散机器的集合。宿主机配置亦遵循相同逻辑：变更的单位是集群（fleet），而非单个节点。NVIDIA DSX OS 是其中的开源软件层，而 NodeWright 是该层内用于配置与更新底层宿主机操作系统的项目。</p>
<p>DSX OS 通过涵盖 AI 就绪基础设施基础（AI-ready foundation）、资源与工作负载编排以及生产级 AI 服务的模块化开源项目组合来应对这一挑战。AI-Ready Foundation 负责定义、配置、验证与保障加速 Kubernetes 基础设施。NVIDIA GPU Operator、NVIDIA Network Operator、Topograph、针对 NVIDIA GPU 的 DRA Driver、NodeWright、NVIDIA 集群就绪引擎（NVCRE）以及 NVSentinel 提供了相应的支撑性基础设施能力。</p>
<p>NodeWright 能够以声明式方式配置并安全更新 Kubernetes 节点操作系统，而不会中断工作负载。它是一个开源的、Kubernetes 原生的软件包管理器，用于大规模修改和维护宿主机基础设施。可以把 NodeWright 视为适用于整个集群的 apt 或 yum：它能感知工作负载、感知中断预算（disruption budgets），并且能够在整个节点集群中渐进式推进变更。</p>
<p>NodeWright 先前在 NVIDIA 内部以 Skyhook 为名在生产环境中运行，现已作为开源项目提供。本文正式推出了 NodeWright 这一名称。</p>
<p>用于配置机器的优秀工具早已存在，Ansible 和 Puppet 已历经多年检验。但它们是为一个将机器作为个体进行管理的世界而设计的，而不是作为正在活跃运行敏感工作负载的集群的一部分。</p>
<p>当需要在 200 个 GPU 节点上更新内核参数时，难点不在于运行脚本，而在于如何在不中断这些节点上正在运行的训练作业的情况下完成更新。传统配置管理无法感知 Kubernetes。它不会在进行更改前隔离（cordon）节点，不会等待关键 Pod 执行完毕，也不会在重启前驱逐（drain）工作负载。它更不会在已经承载了你其余可观测性能力的集群内部去追踪成功或失败状态。</p>
<p>NodeWright 填补了这一空白。它管理宿主机级别变更的完整生命周期，涵盖安装、配置、升级以及卸载。在执行这些操作的同时，它充分遵循你的工作负载所依赖的 Kubernetes 原语：PodDisruptionBudgets、节点选择器（node selectors）、污点（taints）与容忍度（tolerations）。NodeWright 软件包被定义为自定义资源（Custom Resources），因此它们的部署方式与集群中的其他资源完全一致：通过 kubectl、Helm、Argo CD、Flux 或你现有的任何 GitOps 工具链即可实现。</p>
<p>NodeWright 包含三个核心组件：Operator、自定义资源与软件包（packages）。</p>
<p>Operator 是一个 Kubernetes 控制器，用于监听 NodeWright 自定义资源并管理跨节点变更的生命周期。软件包则是承载实际修改内容的容器镜像：包括脚本、配置文件以及二进制文件。软件包中还包含验证脚本，用于暴露错误并在修改不正确时停止发布流程。</p>
<p>当你应用 NodeWright 自定义资源时，Operator 会在每个目标节点上编排严谨的执行时序。图 1 展示了完整的执行时序以及受保护的工作负载如何使其暂停。</p>
<p>这种时序编排的意义，在于避免因内核更新导致训练任务半途折戟，从而在不影响工作负载的前提下平稳地将相同更新应用到整个集群。</p>
<p>NodeWright 软件包能够执行许多通常需要 root 权限的宿主机级别操作，且无需对节点进行回收重建。它们可以设置 sysctl 和 GRUB 参数、配置故障转储（crash dump）收集、创建逻辑卷、安装安全代理、修复 CVE，并执行其他系统级配置任务。NodeWright 会跟踪每个节点上每个软件包的状态与语义化版本，从而能够区分全新安装、升级还是降级。软件包还可以声明依赖关系，NodeWright 据此确定正确的执行顺序。</p>
<p>验证机制已内建于软件包的生命周期之中。应用、配置、升级、卸载以及中断后的后续工作均可与一项检查进行配对，以验证预期的节点状态并通过 Kubernetes 暴露失败情况。例如，CVE 修复软件包可以检测存在漏洞的内核模块是否仍处于加载状态，并将软件包标记为失败，从而让运维人员能即时获知受影响节点的状态，而不必等到后续因工作负载崩溃才发现问题。</p>
<p>随着集群规模扩大，这一模型同样延伸至节点就绪状态的管理。在未经此类控制的情况下，新置备的节点可能会在应用所需配置和调优之前就变为可调度状态。NodeWright 可以要求新节点在加入集群时带有 Kubernetes 污点，只有在完成所需的软件包操作并通过验证检查后才移除该污点。这建立了一条从“已置备”到“已配置”，再到“已验证”，最后到“可调度”的受控路径，确保新增容量在真正就绪之前不会接入生产级工作负载。</p>
<p>将变更推送到单个节点非常简单；但若推送到一千个正在运行生产训练任务的 GPU 节点上，则是完全不同量级的问题。</p>
<p>NodeWright DeploymentPolicy 资源提供了渐进式发布策略，用以控制变更在整个节点集群中的传播方式。你可以定义分区（compartments）——即通过标签选取的已命名节点组，每个分区拥有各自的中断预算和发布策略。图 2 展示了三种可用策略。</p>
<p>每种策略都包含一个批次阈值（batch threshold），即推进到下一个批次所需的最低成功百分比。可选的失败阈值则会在连续过多批次失败时中止该分区的发布。由你来设定风险容忍度，NodeWright 负责予以强制执行。</p>
<p>这意味着，你可以先在单个金丝雀（canary）节点上启动整个节点集群的内核更新，验证其健康状态无误后，再让发布流程自动加速推进。</p>
<p>一旦发生异常，更新过程会立即停止而非引发连锁反应。NodeWright 会在其状态中报告错误、标记失败的 Job，并向每个受影响的节点添加标签（label）与状况（condition）。你可以通过 Kubernetes API 快速定位并排查问题根因。</p>
<p>NodeWright 作为一个通用的软件包管理平台运作。由于软件包执行的操作需要 root 级别权限，主机修改直接依赖于原生 Kubernetes 原语：细粒度 RBAC 控制用户权限，准入控制器（admission controllers）校验规范，集成的验证检查则确保每一步的状态一致性。公共软件包仓库提供了模块化基础组件，用于运行 Shell 命令、管理绑定挂载（bind mounts）以及建立内核崩溃转储（crash dump）收集器。</p>
<p>NVIDIA 还基于团队在大规模运行 GPU 集群过程中积累的运维经验发布了相关软件包。</p>
<p>调优软件包采用基于意图的模型。无需指定具体的配置文件名称，你只需声明使用的加速器以及运行的任务类型，例如 NVIDIA Blackwell GPU 和多节点训练。软件包便会自动组合出适用的配置：内核参数、电源管理以及系统设置。其覆盖范围包括 NVIDIA Hopper 和 Blackwell GPU，并为任意 NVIDIA GPU 提供了通用基线配置，以及针对不同云环境的定制变体。还有一个专用软件包覆盖运行 Container-Optimized OS 的 Google Kubernetes Engine (GKE) 节点，该环境下通常无法使用常规的调优组件栈。</p>
<p>节点安装配置软件包可针对特定的云与加速器组合自动化引导步骤，为配备 NVIDIA Hopper 或 Blackwell GPU 的 Amazon Elastic Kubernetes Service (Amazon EKS) 集群处理内核版本管理与 Elastic Fabric Adapter (EFA) 驱动安装。</p>
<p>这些软件包是一项更大规划的一部分。NodeWright 与 NVIDIA AI Cluster Runtime (AICR) 深度集成。AICR 捕获经过验证有效的驱动程序、Operator、内核及系统配置组合，并将其作为锁定版本的配方（recipe）发布。其组件目录同时锁定 NodeWright operator 以及携带环境特定调优的 NodeWright 自定义配置，然后将它们渲染为适用于 Helm、Argo CD、Flux 或 Helmfile 的就绪部署包。NodeWright 随后将这些配方中主机级别的部分应用到正在运行的节点上。</p>
<p>两个配套的 NVIDIA 开源项目——NVCRE 和 NVSentinel——使该生态体系更臻完备。NVCRE 负责工作负载前验证，以核验加速基础设施是否已达到生产就绪状态；而 NVSentinel 负责监控运行时故障，并辅助执行隔离（cordon）、排空（drain）和修复操作。这些工具与 NodeWright 协同配合，为 GPU 加速的 Kubernetes 集群提供配置、维护和自愈支持。</p>
<p>需要明确的是其适用范围：NodeWright 并不取代 NVIDIA GPU Operator 或 NVIDIA Network Operator。它负责管理它们底层的主机操作系统层。</p>

<p>NodeWright 基于 Apache 2.0 许可证开源，是 DSX OS 的一部分。DSX OS 是一个模块化的开源项目组合，涵盖 AI 就绪基础设施、资源与工作负载编排以及生产级 AI 服务。你可以单独采用某一项目、集成其中数个，或将其组合为一个完整平台。其核心价值在于开放接口、独立采用与一致的生命周期，而非单体式架构堆栈。</p>

### [基于 AWS 构建的 Agent 式对话型视频智能方案](https://aws.amazon.com/blogs/machine-learning/agentic-conversational-video-intelligence-built-on-aws/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Agentic conversational video intelligence built on AWS</div>

<div class="article-cover"><img src="https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/17/ML-21279-1.png" alt="基于 AWS 构建的 Agent 式对话型视频智能方案" loading="lazy" /></div>

<div class="article-body" data-article-body="true"><p>借助由 Agent 式人工智能（Agentic AI）驱动的视频智能，您可以针对上传的视频提出自然语言问题，并在数秒内获得回答。媒体、安防、保险和专业服务等领域的企业与机构生成的视频量，已经超出了其团队能够审查的负荷。会议录像堆积在共享云盘中，安防摄像头记录着数周未被查看的画面。现场检查视频在初次查看后便长久滞留在对象存储中。这些视频中包含的信息往往极具价值：三周前讨论的一项设计决策、某人到达门前的确切时刻，或是导致车辆碰撞的一连串事件。但按传统方式获取这些信息，需要耗费数小时人工观看。另一种替代方案则是针对每种特定问题类型构建定制的机器学习（ML）流水线，但这需要巨大的开发投入。每一个新用例都意味着新的开发工作：<br />针对会议查询的语音转录流水线。<br />针对视觉搜索的计算机视觉流水线。<br />人脸匹配集成。<br />在本文中，我们将深入介绍构建一个支持接收自然语言问题并从视频内容中返回答案的视频智能解决方案的架构和关键模式。该方案采用 Agent 架构，在运行时决定调用哪些 AWS 服务。对于此前已分析过的内容，响应时间在 1 秒以内。对于新视频的初始分析耗时约 5 至 10 分钟，具体取决于视频长度和所需服务。完整的实现已在配套的 GitHub 代码库中提供。<br />我们并没有为每种问题类型预先构建固定的流水线，而是使用 Strands Agents SDK 创建了一个单一的 AI Agent，该 Agent 会根据用户提问的内容，动态编排 Amazon Bedrock、Amazon Rekognition 和 Amazon Transcribe。一家大型媒体与娱乐公司在一次 AWS Professional Services 咨询合作中采用了这种方法。借助该方案，其顾问可以查询已录制的调研会议内容，提取设计决策、行动项和利益相关者立场。根据该客户对每段录音所耗分析师工时的内部前后对比（未经独立核实），其在处理超过 200 个数小时时长录像的积压任务中，人工审查时间减少了约 80%。<br />该解决方案是一个接收视频文件并通过自然对话使其内容立即可供查询的 AI Agent。用户可以上传一段 90 分钟的会议录音，并提问“这次会议做出了哪些决定？”或“有人提到预算时间表了吗？”Agent 会判定是调用语音转录、视觉分析还是两者兼有，然后将结果综合成条理分明的回答。同一套系统还能处理安防监控查询（“此人出现过吗？”）、内容分析（“总结前 30 分钟的内容”）以及调查性问题（“哪辆车在发生碰撞前变换了车道？”）。每个用例均无需单独的处理流水线。<br />以下截图展示了该界面，其中包含一个用于自然语言查询的聊天面板，以及一个用于文件上传和分析模式选择的侧边栏。<br />图 1：视频智能聊天界面<br />其核心洞见在于流水线是在运行时确定的。针对语音内容相关的问题，Agent 会调用 Amazon Transcribe；针对人脸匹配，则转向 Amazon Rekognition；并且针对此前已处理内容的后续追问，能够复用缓存的结果。由模型负责路由调度，而非应用代码。<br />要跟随本文进行动手实践，您需要具备：<br />一个具有 Amazon Bedrock（已启用 Anthropic Claude Sonnet）和 Amazon Simple Storage Service (Amazon S3) 访问权限的 AWS 账户。对于文档处理，需要 Amazon Bedrock Data Automation (BDA) 或者 Amazon Rekognition 与 Amazon Transcribe。请参阅 Amazon Bedrock 中按 AWS 区域支持的模型。<br />安装了 Strands Agents SDK 的 Python 3.11 或更高版本（pip install strands-agents strands-agents-tools）。<br />配置了上述服务所需 AWS Identity and Access Management (IAM) 权限的 AWS Command Line Interface (AWS CLI)。<br />对工具调用（tool use）和推理循环（reasoning loops）等 AI Agent 概念有基本了解。<br />该系统由连接到多个 AWS AI 服务的 Agent 编排器组成，并由 Amazon S3 为上传的视频和缓存的分析结果提供存储。Agent 编排器是其推理引擎。它基于 Strands Agents SDK 构建，并由 Amazon Bedrock 提供支持，使用 Claude Sonnet 或其他支持工具调用的大语言模型（LLM）。它接收来自用户的自然语言查询，并根据问题决定调用哪些工具，在需要时对多次服务调用进行排序编排，并将结果综合为对话式响应。Agent 会维护对话历史记录，因此后续问题可以建立在先前的分析基础之上，无需重新处理。<br />图 2：解决方案架构<br />Amazon Rekognition 提供视觉分析功能，包括检测视频帧中的物体、场景、活动和人脸。当用户的问题涉及视频中肉眼可见的内容时，Agent 会调用 Amazon Rekognition。Amazon Transcribe 将语音音频转换为文本，具备涵盖 100 多种语言的自动语言检测（请参阅 Amazon Transcribe 支持的语言）和说话人分离（speaker Guardrails，以对 Agent 响应实施内容过滤和事实溯源检查，特别是在必须严格执行负责任 AI 控制的人脸匹配和监控场景中。<br />Agent 式编排的工作原理<br />在传统的视频分析应用中，开发人员定义了固定的处理流水线：上传视频、执行转录、进行视觉分析、展示结果。这种方法无论面对何种具体查询，都会通过相同的步骤处理每个视频，用户必须等待整个流水线执行完毕才能开始提问。而 Agent 式的方法颠覆了这种模式。只需将视频文件上传至 S3 存储桶等最基本的预处理，Agent 即可独立对每个问题展开推理，并仅调用回答该问题所需的服务。</p>
<p>当用户提交查询时，Agent 首先解析意图：用户需要的是转录文本摘要、视觉搜索，还是人脸比对？接着，它会检查相关分析是否已经执行并被缓存。如果没有，它会选择合适的工具并予以执行（当一个工具的输出作为另一个工具的输入时，可能会按顺序执行），然后将结果整合成自然语言回答。在针对 60 分钟视频的测试中，关于某个视频的第一个问题通常需要 5 到 10 分钟（在此期间运行转录或视觉分析）。而关于相同内容的后续问题则在 1 秒内即可返回，因为 Agent 复用了缓存的结果。实际耗时会因视频长度、分辨率以及所调用的 AWS 服务而有所不同。</p>

<p>为了说明 Agent 如何将多个工具调用进行串联，不妨设想一个场景：用户上传了一张参考照片，并提问：“这个人是否出现在我的监控视频中？”该 Agent 必须先为参考人脸建立索引，然后在视频中进行检索。这是两个相互依赖的先后顺序操作。以下追踪记录展示了 Agent 的内部推理过程：<br />[Think] 这是一个面部匹配查询。我需要先为参考照片建立索引，然后再搜索视频。<br />[Act] analyze_reference_image(image=&quot;reference.jpg&quot;) [Observe] {&quot;faces_detected&quot;: 1, &quot;face_id&quot;: &quot;face_001&quot;, &quot;confidence&quot;: 99.8}<br />[Think] 人脸已建立索引。现在正在检索视频。<br />[Act] search_faces_in_video( video_s3_key=&quot;security_cam_july5.mp4&quot;, collection_id=&quot;user_collection&quot;) [Observe] {&quot;matched_faces&quot;: [ {&quot;timestamp&quot;: &quot;00:14:32&quot;, &quot;confidence&quot;: 97.2}, {&quot;timestamp&quot;: &quot;00:47:15&quot;, &quot;confidence&quot;: 94.8}]}<br />[Response] 是的，该人物出现了两次：分别在 14:32（置信度 97%）和 47:15（置信度 95%）。<br />该 Agent 确定了正确的操作顺序，并妥善处理了它们之间的依赖关系（人脸检索需要依赖已建立索引的特征集合）。随后，它以对话形式呈现了结果。应用程序代码并未预先定义这一执行顺序；模型完全是根据工具描述和用户提出的问题自行推理出整个流程。<br />针对全面分析场景（例如当用户要求“分析这段视频”或“总结这段录音”时），Agent 可以直接调用 Amazon Bedrock 数据自动化（Amazon Bedrock Data Automation，简称 BDA），而无需分别调用 Amazon Rekognition 和 Transcribe。BDA 可以通过一次异步 API 调用，生成视频摘要、带时间戳的逐章节拆分内容以及完整转录文本：<br />[Think] 用户需要完整的摘要。BDA 通过单次调用即可提供摘要 + 章节 + 转录文本，比分别运行 Rekognition 和 Transcribe 更加高效。<br />[Act] analyze_with_bda(s3_uri=&quot;s3://amzn-s3-demo-bucket/meeting.mp4&quot;) [Observe] {&quot;summary&quot;: &quot;团队讨论了第三季度路线图……&quot;, &quot;chapters&quot;: [{&quot;title&quot;: &quot;开场介绍&quot;, &quot;start&quot;: &quot;00:00&quot;}, {&quot;title&quot;: &quot;路线图审查&quot;, &quot;start&quot;: &quot;05:32&quot;}, ...], &quot;transcript&quot;: &quot;欢迎大家。让我们先从……&quot;}<br />[Response] 以下是会议摘要及分章节内容：摘要 团队讨论了第三季度路线图…… 章节 - 00:00 - 开场介绍<br />当结果存在不确定性时，Agent 会明确传达这种模糊性。处于临界区间的置信度分数（例如 62%）会触发带有保留意见的回答：“我在 14:32 发现了一个可能的匹配项，但置信度较低，因此您可能需要人工核实。”如果因音频质量差导致语音转录失败，Agent 则会建议替代方案：“音频质量过低，无法进行可靠转录。您是否希望我尝试对演示文稿幻灯片进行视觉画面分析？”<br />这种 Agent 式架构模式广泛适用于用户需要从视频内容中提取特定信息、但事先并不清楚需要哪种具体分析类型的业务场景。<br />会议智能分析——半途加入项目的团队成员上传先前的会议录音，并提出针对性问题：“4月份做出了哪些架构决策？”、“团队是在何时同意使用 GraphQL 的？”或“请总结关于身份验证方案的讨论内容。”Agent 会执行转录、检索与总结，并返回带有时间戳的答案，精准对应录像中的特定时刻。<br />安防与门禁监控——大楼管理员上传大厅监控视频及一位来访者的照片，提问：“这个人本周是否进入过大楼？在什么时间？”Agent 会对视频进行人脸匹配比对，并返回具体的时间戳及置信度分数。<br />理赔调查——保险公估人上传行车记录仪视频，提问：“请描述碰撞发生前的事件发展过程”或“哪辆车占用了错误车道？”Agent 会将视觉场景分析与音频信息（例如当事人的言语反应、鸣笛声）结合起来，重构事件发生的时间线。<br />通过稳定的工具协议向视频之外的领域扩展<br />上述三个示例均属于视频分析范畴，但该架构的底层逻辑并不仅限于视频。Agent 根据工具的文档字符串（docstrings）来挑选工具，因此添加一项新能力（乃至一个全新的模态）只需将另一项服务封装为 @tool 函数，并描述其适用场景即可。工作流逻辑无需发生任何改变，相同的编排器、缓存机制和针对每个用户的隔离机制均可原封不动地直接套用。<br />图 3：将该模式扩展至其他模态<br />这使得该模式成为构建多模态 AI 助手的通用模板，既支持使用 AWS 自身服务，也支持引入第三方模型：<br />借助 Amazon Textract 进行文档与图表理解。技术方案调研会议往往并不局限于视频形式。通过添加 Textract 工具，从以 PDF 形式提供的架构图和工作文档中提取文本、表格和表单字段，Agent 即可将白板上绘制的内容与会议录像中的口头讨论进行交叉印证。这使得已经在解答会议音频提问的同一个对话会话变得更加充实和丰富。<br />借助 AWS HealthScribe 分析临床医患会话。将该模式应用于医患对话音频文件，HealthScribe 工具便能返回结构化的临床病历（包含逐轮对话转录以及提取的主诉、治疗方案等结构化板块），使用户可以针对录音询问“建议了哪些后续随访措施？”。<br />实体与情感提取，或集成第三方模型。Amazon Comprehend 工具可以从 Agent 生成的任何转录文本中提取命名实体、关键短语和个人身份信息（PII）。在 Amazon Bedrock 上可用的基础模型（包括第三方模型）也可以通过同样的方式进行封装，以实现特定领域的复杂推理。<br />在上述各类场景中，扩展点始终在于工具契约（tool contract），而非底层处理管道（pipeline）。构建了视频助手的团队已经拥有了完备的脚手架（编排、缓存、身份验证以及针对每个用户的环境隔离），只需添加对应的工具，即可快速搭建起支持其他模态的 AI 助手。<br />每次查询的成本取决于 Agent 调用的具体 AWS 服务。在完成初始分析（语音转录或视觉处理）之后，针对同一视频后续提出的跟进问题仅会产生 Amazon Bedrock 的推理费用，因为先前的分析结果已经被缓存。下表展示了一段 60 分钟视频的预估成本：<br />服务 操作 预估成本<br />Amazon Transcribe 60分钟音频转录 $1.44<br />Amazon Rekognition 人脸检索（60分钟视频） $6.00*<br />Amazon Rekognition 标签检测（60分钟视频） $6.00*<br />Amazon Bedrock Agent 推理（每轮对话） $0.05–$0.15<br />Amazon S3 存储（500 MB，保存24小时） &lt;$0.01<br />注：标注 * 的 Amazon Rekognition 60.00 美元费用为每个视频仅需产生一次的成本（后续查询仅会产生 Bedrock 的推理费用）。</p>
<p>根据截至 2025 年 7 月的 AWS 服务定价及前述成本表，针对一段 60 分钟视频进行基于逐字稿的典型查询，初始转录加上 Bedrock 推理的成本约为 1.50 美元。针对同一已转录内容的后续提问每轮仅需 0.05 至 0.15 美元，仅覆盖 Bedrock 的推理调用成本。实际费用取决于模型选择、输入长度以及 AWS 区域。有关当前定价，请参阅 Amazon Bedrock 定价、Amazon Transcribe 定价以及 Amazon Rekognition 定价。</p>
<p>该解决方案部署在结合 AWS Fargate 的 Amazon Elastic Container Service (Amazon ECS) 上。Streamlit 应用程序与 Agent 运行时运行在内部 Application Load Balancer 后方的 Fargate 任务中，而 Amazon CloudFront 分发是唯一的公共入口点。CloudFront 通过虚拟私有云 (VPC) 源访问负载均衡器，因此负载均衡器保留在无法路由到互联网网关的私有子网中，无法直接从互联网访问。CloudFront 还使用其默认的 *.cloudfront.net 证书终止查看者 TLS，无需自定义域名或 AWS Certificate Manager 证书即可提供公开受信任的 HTTPS 端点。Amazon Cognito 负责身份验证（默认仅限受邀用户，且强制要求通过基于时间的一次性密码 (TOTP) 进行多因素身份验证 (MFA)），上传的文件和缓存输出则存储在 Amazon S3 中，带有按用户划分的前缀，并应用了 24 小时生命周期策略。</p>
<p>图 4：Amazon ECS 和 AWS Fargate 上的部署架构</p>
<p>单个脚本（./deploy/deploy-ecs.sh）即可构建容器镜像，将其推送到 Amazon Elastic Container Registry (Amazon ECR)，并部署 AWS CloudFormation 堆栈。部署通常在 15 到 20 分钟内完成，其中大部分时间用于 CloudFront 的传播生效。完整的部署先决条件、AllowSelfSignup 参数及其权衡考量，以及分步操作指南均包含在代码库的 README 中。</p>
<p>Kiro 是一款 AI 驱动的开发环境，通过将高层创意转化为结构化的需求、设计和实现任务，支持规范驱动型（spec-driven）软件开发。我们利用其规范工作流、持久化项目上下文以及 Agent 钩子，在将概念推进为可部署示例的同时，随着各项功能的成形将安全性内建其中。</p>
<p>规范在实现之前定义了每项功能。人脸匹配规范定义了输入（参考照片加上视频）、预期行为（为人脸建立索引、搜索并返回时间戳）以及边缘情况（未检测到人脸、低置信度匹配）。转录规范涵盖了多语言检测、说话人分离（speaker diarization）以及重复查询的缓存行为。Kiro 根据每项规范生成实现任务，并在整个功能生命周期内保持上下文。根据团队以往构建类似集成的经验，这把他们预计通常需要数周的工作压缩到了一个集中的敏捷冲刺中。</p>
<p>威胁建模与规范同步进行，而非事后补做。在对各项功能进行规范定义时，我们同步对其可能被滥用的方式进行建模，并将结果记录在持续更新的威胁模型中（请参阅配套代码库中的 docs/threat-model.md）。该模型详尽推演了具体的杀伤链（身份验证绕过、网络暴露、通过提示词注入利用 Agent、权限过大的 IAM 以及逃避审计），并为每种威胁分配了处置方式。每个严重（Critical）和高危（High）级别的发现项都在示例中得到了修复。仍保持开放的项均在文档中附有明确的决定（接受的残留风险，或记录在案的生产环境改造项）。下一节介绍的安全控制措施是该流程的产物，绝非事后补救。</p>
<p>安全扫描被嵌入在开发循环中。Kiro Hooks 在代码变更提交时运行自动化的静态分析和基础设施即代码扫描，使用了诸如 Automated Security Helper (ASH) 等工具，并且容器镜像仓库在创建时已启用了推送时扫描功能。扫描发现的问题会作为任务返回到生成该功能的同一工作流中，因此配置错误在编写代码时就会显现，而不是在最终的独立评审中才被发现。其实际效果是实现了安全左移（shift-left）：一个小型团队即可在单个工作流中兼顾功能迭代速度与安全严谨性，使“设计即安全”（secure-by-design）成为默认路径，而非额外设卡。</p>
<p>安全考量</p>
<p>视频通常包含敏感的商业讨论和可识别身份的人员，因此多用户部署必须控制访问权限、隔离每位用户的数据，并限制单个用户操作所产生的影响。</p>
<p>参考部署实现了四大主要控制措施：<br />仅限受邀的 Amazon Cognito 账户，并强制启用 MFA。<br />在每个工具边界通过所有权验证强制执行的按用户 Amazon S3 前缀。<br />仅通过 CloudFront 暴露的内部 Application Load Balancer。<br />限制跨租户资源耗尽的按用户上传配额。</p>
<p>生产环境部署仍应评估是否采用具备更严格查看者 TLS 策略的自定义域名、挂载 AWS WAF、扩展审计日志记录与监控，并针对人脸集合、转录文本以及跨区域 Amazon Bedrock 模型推理明确数据处理要求。请与您的法务和隐私团队协作，以确定适用的知情同意、保留、删除以及数据驻留要求。如需完整的逐项控制措施分析、接受的残留风险、杀伤链和加固核对清单，请参阅配套代码库中的 docs/threat-model.md 以及 README 中的“生产环境安全考量”。</p>

<p>超过两到三个小时的视频初始转录需要数分钟时间，但后续查询可几乎即时从缓存中返回。人脸匹配的准确性取决于参考照片的质量。清晰、光线充足的图像效果最佳，而从合影中裁剪出的模糊照片可能会导致置信度较低。在强背景噪音或发言人声音重叠的情况下，转录准确性会有所下降。Agent 在检测到质量问题时会予以提示。Web 界面支持最大 2 GB 的 MP4、MOV、AVI 和 MKV 文件，由于 Streamlit 会在内存中缓冲上传内容，这一限制故意设置在低于 Fargate 任务内存的水平。对于更大的媒体文件，可直接上传到您用户前缀下的 Amazon S3 中，并让 Agent 通过其 URI 进行分析（BDA 支持最大 10 GB 的视频对象）。并发能力受限于任务的临时存储以及单用户配额（在默认配置下每个任务大约支持六个并发用户），自动扩缩容会在 CPU 负载增加时扩展任务数量。</p>
<p>如果您已经部署了该解决方案且不再需要它，请删除预置的资源以避免产生持续费用。资源拆除涉及三个 CloudFormation 堆栈，这些堆栈是通过参数值而非跨堆栈导出进行关联的，因此 CloudFormation 不会强制执行它们的依赖顺序。清空 S3 存储桶后，请按以下顺序删除这些堆栈：(1) video-analytic-agent-ecs（应用程序）、(2) video-analytic-cognito（身份认证）以及 (3) video-object-locator-infra（存储）。这些模板还会保留 Amazon ECR 存储库和镜像，且 AWS Key Management Service (AWS KMS) 密钥将保持在其处于待删除计划的状态。</p>
<p>Amazon Rekognition 人脸集合需要单独清理。应用程序是在运行时创建它们的，因此 CloudFormation 并不拥有它们，且它们的存在独立于视频存储桶的 24 小时 S3 生命周期。删除上传的对象或堆栈并不会删除已建立索引的人脸。请列出并显式删除每个集合。完整的拆除流程（包括首先清空启用版本控制的 S3 存储桶）可在代码仓库 README 中的“Teardown / clean up”（拆除/清理）部分找到。</p>
<p>在本文中，我们展示了使用 Strands Agents SDK、Amazon Bedrock、Amazon Rekognition 和 Amazon Transcribe 构建对话式视频智能解决方案的架构和关键模式。借助这种智能体架构，您不再需要为每种问题类型预先构建处理流水线。相反，单个智能体会根据用户的自然语言查询，在运行时推理应调用哪些服务。添加新功能仅需新增一个 @tool 函数并更新提示词，而无需构建全新的流水线。</p>
<p>要将此模式应用于您自己的用例，请首先配置一个以 Bedrock 作为模型提供商的 Strands 智能体，并将每个相关的 AWS 服务包装为带有描述性文档字符串（docstring）的工具函数。然后定义一个用于指导您所在领域推理的系统提示词，并部署在 ECS Fargate 上以供访问，或在本地运行以进行原型设计。完整的源代码、自动化部署脚本以及所有工具的实现均可在配套的 GitHub 代码仓库中获取。</p>
