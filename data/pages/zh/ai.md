### [编排 Claude Code 智能体：“幕僚长”模式](https://asyncdot.com/blog/chief-of-staff-pattern-orchestrating-claude-code-sessions/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Orchestrating Claude Code Agents: The Chief of Staff Pattern</div>

<div class="article-body" data-article-body="true"><p>一个会话负责协调和验证，其他会话负责执行，并通过持久化的任务看板来维护状态。这是一个适用于长时间运行的 Claude Code 智能体的“编排者-执行者”循环。</p>
<p>长周期的 AI 编程任务之所以失败，往往不是因为智能体写不出代码，而是因为它们的上下文是短暂易逝的，且它们的自我汇报并不可靠。解决办法是组织架构层面的，而非技术层面的：由一个会话负责协调和验证，由独立的会话负责执行，通过持久化的外部看板维护状态，并且在采信任何断言之前都必须重新运行验证。这种形态在业内已有共识，通常被称为“编排者-执行者”（orchestrator-worker）或“协调者-实现者-验证者”（coordinator-implementor-verifier）。“幕僚长”（Chief of Staff）只是我们对它的称谓。本文将介绍该工作闭环、使其落地的工具链，以及它旨在捕获的各种失效模式。</p>
<p>单个 AI 编程会话运行一个小时效果不错，之后便开始退化。通常会出现三类问题。</p>
<p>仅仅增加更多智能体并不能解决这个问题，反而会成倍放大问题。这样一来，你手头就有了多个不可靠的汇报者，却没有人去核实协调它们。</p>
<p>真正能解决该问题的是借鉴自人类组织的分工模式：设立一个专人，其职责不是亲自干活，而是查明真相。</p>
<p>这也正是区分原型与上线产品所依据的严谨准则。生成步骤从来都不是瓶颈，检查步骤才是。</p>
<p>“幕僚长”是我们对一种智能体编排形态的称呼。在这种模式下，一个长期存在的会话充当协调者，负责分派任务、验证断言并维护共享状态；而独立的短期会话则负责具体实现。</p>
<p>如果你想快速建立心智模型，可以把它看作是一个“集成管理员”（integration manager）。在 Git 的集成管理员工作流中，贡献者在各自的代码仓库中工作，由一名维护者拉取每一项变更，在本地测试，并决定将哪些内容合并到基准仓库中。协调者所做的正是这项工作，只是服务对象从贡献者换成了智能体会话。</p>
<p>这个名字是我们认为很贴切的一个比喻。它并不是一个既定的专有名词，你不需要对其感到面熟。其底层的架构形态早已广为人知，并有着若干正式名称。</p>
<p>它们表达的核心意思都一样：一个智能体负责规划与检查，其他智能体负责干活，而共享状态则存在于任何单一上下文窗口之外。如果你在寻找现有技术或相关先例，建议搜索那些术语，而不是搜这个词。</p>
<p>本文补充的并不是这个框架形态本身，而是下文将详述的验证准则，以及那些会导致长时间自主运行崩溃的具体失效模式。</p>
<p>“幕僚长智能体”（chief of staff agent）这个短语常被用来指代另一种东西：一个帮人管理日历、收件箱和优先级，并将工作派发给专业智能体的助手。Anthropic 的应用指南（cookbook）中就有一个专门为初创公司 CEO 构建的此类幕僚长智能体。比喻虽然相同，解决的却是不同问题。本文讨论的是编程闭环。</p>
<p>协调会话有时也被称为“守望者”（overwatch）。它的职责包括：</p>
<p>它明确不做的事情就是编写实现代码。协调者一旦开始写代码，它就会停止验证，这种模式随即就会退化回单会话过载的旧路。</p>
<p>你需要三样东西。具体的工具可以替换，但角色不可替代。</p>
<p>Claude Code 提供了会话本身：工具调用、文件编辑、Shell 访问，以及会话之间相互发送消息的能力。每个会话都有自己独立的上下文窗口，这正是关键所在。隔离是一种特性，因为一个会话的思维混乱不会污染到另一个会话。</p>

<p>该命令中有两个细节起着承重墙般的核心作用，这两点都是花费了真金白银的时间才摸索出来的经验。</p>
<p>Plan Desk 是一个通过 MCP 协议向智能体开放的规划看板：包含项目、目标、带有依赖关系边的任务、关联的设计文档以及评论。协调者和每一个执行会话都读写同一个看板。</p>
<p>这是人们常常跳过的组件，而跳过它正是他们的多智能体配置无法熬过漫漫长夜的原因。看板就是记忆。会话是可随用随抛的，看板则不是。</p>
<p>看板上记录的内容包括：</p>
<p>一次处理一个工作项。一次派发。一次提交。</p>
<p>如果在你开始之前检查就已经是一片绿色（通过状态），那么这项工作就证明不了任何东西。你无法分辨一个正确的实现，和一个从未真正运行的检查、一个什么都没匹配到的过滤器，或者一个断言了本已为真的测试之间的区别。</p>
<p>先运行验证器还能低成本地捕获陈旧工作。在实践中，排队等待的任务中有相当一部分实际上已经完成了——可能是在另一张卡片下构建的，或者被后来的变更淘汰了。一个本来应是红色的关卡，仅凭一条命令就返回绿色，这只耗费数秒时间，却能为你省下原本需要阅读代码以实现某些已存在功能的大把时间。</p>
<p>Git 提交历史与看板保持一一对应。每次提交的主题都标明其任务名称。三天后出现故障时，从症状到决策的排查路径仅需一条 git log 即可追溯。</p>
<p>这一部分正是将该方法论与单纯的“同时运行多个智能体”区分开来的关键。</p>
<p>当一个执行会话汇报“测试套件全绿，49项检查，零失败”时，协调者的职责是查明这是否属实。这并非因为智能体会撒谎，而是因为它们所汇报的对象与它们实际检查的对象往往是两个不同的实体。</p>
<p>一个值得铭记的典型模式是：某个会话手动将一个提交哈希（commit hash）写入了日志文件，然后使用 git cat-file 进行验证，但验证时比对的却是留在其 shell 中的短哈希，而不是它刚刚写入文件中的那串字符串。两项检查都通过了。然而该文件中包含的却是一个根本无法解析的无效哈希。检查的对象与记录的对象是两个不同的实体，而当时只测试了其中之一。</p>
<p>由此得出的一条准则：验证工件时，必须通过重新读取该工件中的值来进行验证，绝对不要去读取你自以为写入那里的变量。</p>
<p>在智能体工程（agentic engineering）中最常见的单点故障，莫过于检测工具对它并未实际完成的工作汇报成功。这种情况形态多样。</p>
<p>通用的防范策略是：每一项可能出现未匹配的检查，都必须明确报错。必须能够清晰区分出“计数为零”和“未能运行”。此外，反向断言（absence assertion）在同一次运行中需要设置正对照（positive control），因为如果什么都没运行，“没有坏事发生”就会被直接判定为通过。</p>
<p>在断定某事物不存在之前，先证明你的检测工具在它存在时能够找得到它。首先将检查指向一个已知正常的案例。一个汇报“无异常”的工具与一个已经损坏的工具，输出的内容是完全一样的。</p>
<p>会话之间可以直接通信。这条通道确实非常有用。协调者正是通过它在运行中途回答问题，执行会话也是通过它报告矛盾之处，而不是选择绕过矛盾自行其是。</p>
<p>但它还不够可靠，不能完全依赖。一条消息可能会在一个忙碌的会话后排队，或者根据接收会话的权限模式等待人工批准，甚至可能未送达就已失效。沉默并不等于赞同。</p>
<p>因此，任何必须送达的内容都要走持久化通道。</p>
<p>消息只是提醒，文件才是契约。</p>
<p>一个能带来高回报的小习惯：将持久的策略规则与临时的具体工作内容区分开来。</p>
<p>策略目录（Policy directories）承载着规范每个周期的契约，即循环机制、路由规则和标准。这些内容是长期的、经过审查的，且极少变动。一次性简报、任务上下文以及会话专属的指令则应放置在任务看板或临时暂存目录中。<br />将它们混在一起意味着六个月后，谁也分不清到底哪些文件依然具有约束力。<br />长时间的自主运行应当按照既定节奏进行汇报，而不是消失数小时后带着整墙的代码变更（diff）重新出现。<br />让时间盒（timeboxing）生效的规则是：时间间隔决定了你多长时间对外浮现汇报一次，但绝不决定工作在何处停下。当计时器在一个任务项进行到一半时到期，请先完成该项、验证它、提交它，然后再做汇报。在中途强行掐断运行，会让工作陷入最难以恢复的状态——即处于半应用状态、未经检验且根本无法被如实描述。<br />检查点（checkpoint）是一个向外展示进展的时刻，而不是权限请求。汇报一经发出，下一个任务项应在同一轮次中立即启动。如果你发现自己写下了“我还要继续吗？”，请删掉它。正在旁观的人类自然会打断你，而不在场的人类则会因为这样一个提问而导致整个运行进程被迫中断。<br />请汇报已被证实的事项，而不是尝试过的想法。没有验证结果的任务项只能算作顺延结转，而非完成。<br />这些都是小细节，但每一个细节所对应的故障模式看起来都像是由其他原因引起的。<br />务必验证新衍生的会话是否真正启动。启动器报告“已创建工作区”，并不等同于智能体已经在运行。请检查进程，并检查其工作目录：<br />在启动前立即捕获基准时间戳。若使用以“晚于上一个会话”为键的过滤器，很容易误把中间启动的无关会话纳入进来；如果那个会话具有不同的工作目录，原本正常的启动看起来就会像损坏了一样。<br />会话名称并不是你可以凭空猜测的地址。无论你给工作区起了什么名字，往往都不是消息传递层实际使用的名称。在与会话通信之前，请重新列出所有活跃会话，切勿复用你之前读取到的名称。<br />简短标识符只是展示用的前缀，而不是键。看板通常会显示截断后的 ID。将其补齐为完整长度的标识符只会产生一个格式良好却根本不存在的值。请改为通过搜索具有区分度的标签子字符串来解析它。<br />搜索标签本身，而不是你的转述。日志条目的标题通常是写入会话对自己所做工作的表述，这并不是卡片上的实际标签。搜索前者将一无所获，并被解读为“无此卡片”。<br />在共享工作树中，切勿使用光秃秃的裸 commit（bare commit）。git add 紧接着执行 git commit 会提交整个暂存区索引，包括并发会话暂存的任何内容。请使用带参数限定的提交方式（例如 git commit --），确保提交中仅包含你明确指定的内容。<br />这些额外的开销正是核心所在。你付出这些代价，换取的是信任结果的能力。<br />衡量该机制是否奏效的标准，不在于写了多少代码，而在于你是否可以在任何时刻询问“这项工作的当前状态是什么？”并得到一个真实确凿的回答。<br />当 AI 编程智能体在长期任务中表现欠佳时，人们的本能反应是去寻求更好的模型或更大的上下文窗口。这两者确实有所帮助，但都无法解决实际的制约因素——即根本无人进行校验。这也是“70% 问题”背后的症结所在，也是每一个操作生产系统却缺失回读验证步骤的智能体所面临的问题。<br />一个不写任何代码却清楚知晓真实状况的协调会话，其价值远胜于又一个执行者。这是人类组织架构中的一条老经验，事实证明它同样适用于此。<br />我们以固定价格交付生产级软件，均采用此处所述的编排与验证规范进行构建。提供完整源代码，部署至您的账户，归您所有。告诉我们您想构建什么，我们将为您评估范围、价格与时间表。</p></div>

/>用于编码单个码点的一段 UTF-8000 字节序列。<br />开始一个 UTF-8000 代码单元的第一个、也是唯一的那个字节。<br />首字节的自同步前缀对于 ASCII 而言是 0，对于多字节代码单元而言是 11。<br />该术语与“起始字节”并不同义。首字节必然是起始字节，但反之不然。正是由于这个原因，首字节有时也被称为“第一起始字节”。<br />有趣的发现：由于自同步前缀为 所继承，并在字节层面提供了自同步特性：仅仅通过观察这些最高位，我们就能即时辨别出正在查看的是哪种字节，以及它应该属于代码单元的什么位置。<br />这在解码使用 UTF-8000 编码的文件的一部分时最为有用。如果我们在文件中随机跳转寻道到一个任意字节，我们可以毫无歧义地判断出：我们当前处于一个首字节，可以立即开始解码一个新的代码单元；或者我们处于一个续行字节，需要稍向后寻道一点以找到下一个首字节从而开始解码。我们既不需要处理寻道位置之前的任何字节以发现某种全局状态，也不需要了解我们所寻道到的字节的上下文；无论出现在何处，首字节始终可以明确判定为首字节，我们可以根据其自同步前缀为 0 或 11 推导得出。<br />这不仅对随机访问有用，对错误恢复也同样有用。假设我们正在解码一个易出错的 UTF-8000 字节流，每当我们遇到错误时（例如出现异常的 0xC0 字节），我们希望保持镇定并继续处理，而不是立即退出。我们可以输出 Unicode 替换字符 U+FFFD ，然后等待下一个首字节，同时丢弃在此期间遇到的所有内容。<br />有时，在讨论靠近代码单元开头的字节时，通俗地将 ASCII 也包含为起始字节是合情合理的，尽管 ASCII 字节并没有起始位。<br />每个非 ASCII 代码单元都至少有一个起始字节。第一起始字节即为首字节，后面跟随零个或多个同样作为起始字节的续行字节。因此，由于一个 UTF-8000 代码单元可以拥有多个起始字节，该术语与“首字节”并不同义。<br />在仅限于纯 UTF-8 而不涉及 <p>这避免了更笨拙的变长编码所存在的一个问题——这类编码的码元在本质上无法指示自身的长度：人们必须读取超过某个码元的最后一个字节，也就是读取下一个码元的第一个字节，才能知道当前码元已经结束。对于既没有自同步又没有自标点（self-punctuation）的非常笨拙的编码，为了实现随机访问，人们必须在码元之间放置专用的辅助字节（如逗号字节这样的标点符号），以便能够分辨出一个码元在哪里结束、另一个码元又在哪里开始。<br />有关更通用的信息，请参阅维基百科关于前缀码（prefix code）和一元编码（unary coding）的词条。<br />该术语与“内容位”（content bits）互斥。<br />这些位以亮洋红色高亮显示。<br />包含一个或多个内容位的字节。<br />一个字节是内容字节，并不意味着它是后续字节（continuation byte）。例如，一个3字节的码元以 1110xxxx 开头，它包含4个内容位，但并不是后续字节。<br />一个字节是后续字节，也并不意味着它是内容字节。例如，一个22字节的码元包含 10111111 作为其第二个字节，这是一个后续字节，但没有内容位。<br />码元中位于起始位之后直至码元末尾的位序列，其中存储着码点的二进制位。例如，一个形式为 1110xxxx 10xxxxxx 10xxxxxx 的3字节码元，拥有16个内容位。<br />对于 ASCII，有7个内容位。这七个位 xxxxxxx 与字节最高位被设置为自同步前缀 0 相结合，意味着 ASCII 被完美包含在 UTF-8 中且未被改变。因此 ASCII 码元的形式为 0xxxxxxx。<br />否则，对于 n 字节码元（其中 n &gt; 1），共有 5n+1 个内容位。我们推导出该公式的过程如下：我们从 n 个空字节开始，每个字节有8位。对于每个字节，有2位被自同步前缀占用。接着，还有额外的 n-1 位被起始位占用。因此，留给内容位的位数就是 8n - 2n - (n-1) = 5n+1 位。理解该公式中数字 5 的另一种方式是：通过追加另一个后续字节，从 n-1 字节扩展到 n 字节。通过这样做，我们在后续字节中获得了6个可用位，但在更长的起始位序列中损失了1位，因此总体上我们为内容位增加了 6-1 = 5 位。<br />该术语与“起始位”（start bits）互斥。<br />这些位以青柠色高亮显示。<br />强制内容字节（Mandatory Content Byte）<br />包含一个或多个强制内容位的字节。<br />这些是在解码码元时，我们用来检查是否存在超长编码（overlong encoding）的字节。<br />强制内容位（Mandatory Content Bits）<br />码元中前0、4或5个内容位，其中必须至少包含一个 1 位，以免这些字节构成被禁止的超长编码。<br />对于 ASCII，有0个强制内容位，因此不需要进行防超长检查。这是因为 ASCII 是最小的可能码元。<br />对于2字节 UTF-8000，有4个强制内容位。这是因为从1字节 ASCII 跳到2字节 UTF-8 时，内容位从7位跃升到11位。因此，我们获得的内容位数量是 11 减 7，即4位。<br />否则，对于 n 字节 UTF-8000（其中 n &gt; 2），有5个强制内容位。这是因为从 n-1 字节 UTF-8000 跳到 n 字节 UTF-8000 时，我们增加了一个额外的后续字节，该字节有6个可用位，但我们在更长的起始位序列中损失了1位。因此总体上我们获得的内容位数量是 6 减 1，即5位。<br />阅读关于超长编码的内容，以了解强制内容位为何值得关注。<br />这些位以亮青柠色高亮显示。<br />本可以使用更短的码元在 UTF-8000 中正确编码、但采用了被禁止的编码方式的码点编码。<br />例如，有人可能会错误地尝试将码点 0x41（即数字65，ASCII大写字母 A）使用2字节 UTF-8 编码为 11000001 10000001。请注意，所有的强制内容位都为 0，这正是超长编码的定义。这表明我们本可以用更短的码元来编码 0x41，在这种情况下即编码为 ASCII 的 01000001。<br />安全性是我们禁止超长编码的一个主要原因。例如，我们确保 11100000 10000000 10000000 不能被解码为码点 0（空字节/null byte），以免有人故意将这样的超长字节（码元）传递给像 strcpy(3) 及同类 C 函数。strcpy 不会将此码元解释为空字节，往好了说会导致段错误（segfault），往坏了说会导致严重的安全漏洞。<br />编码的唯一性是我们禁止超长编码的另一个原因。每个码点在 UTF-8000 码元中都有且仅有一个唯一的有效表示形式，使用移位操作即可轻松完成编解码。<br />有趣的观察：因为2字节 UTF-8 的所有4个强制内容位都位于首个也是唯一的起始字节中，我们可以明确排除 11000000 (0xC0) 和 11000001 (0xC1) 作为永久无效字节。它们绝不会出现在有效 UTF-8000 码元的任何位置！<br />UTF-8000 的许多此类属性都在词汇表的相应章节中进行了详细解释，并提供了指向该词汇表的超链接。<br />内容位和强制内容位的数量作为码元长度 n 的函数，具有高度的可预测性。<br />正如简要说明（tldr）中所述，仅存在两种特殊情况，两者均继承自 UTF-8：<br />1字节 UTF-8（ASCII），它有两个关注点：<br />2字节 UTF-8，它有一个关注点：<br />UTF-8000 在扩展 UTF-8 时没有引入任何新的特殊情况，这一显著事实向我证实，这是扩展 UTF-8 的正统、正确方式。换句话说，UTF-8 目前受限的4字节形式本身就是 UTF-8000，只不过仅占其一小部分。<br />我们一开始甚至能够对其进行扩展这一事实，也证明了肯·汤普森（Ken Thompson）和罗勃·派克（Rob Pike）在 UTF-8 架构设计中所展现的巧妙规划与用心，我们在扩展到 UTF-8000 时确保维持了这一点。起始位序列采用一元码码字，构成了一棵自相似树，它既简洁又具可扩展性，是一个绝佳的选择。在 UTF-8 的最早草案中，六字节的起始字节看起来形如 111111xx。几天后，它被修改为 1111110x。这样一来，内容位的数量就不再构成特殊情况，而且起始位不会填满一元码二叉树，从而为我们未来的扩展留下了空间。<br />这就是为什么我认为 UTF-8 是 Unix 哲学的巅峰之作。<br />一个码元中内容位所占的比例是多少？<br />对于 ASCII，这一比例是 7/8 = 87.5%。<br />否则，对于一个 n 字节码元，这一比例是 (5n+1) / 8n，即来自 n 个字节的全部 8n 位中有 5n+1 个内容位。我们可以将其重写为 (5/8) + 1/(8n)，它以适中的速度趋近于 5/8 = 62.5%。令人欣慰的是，这个极限值是非零的，并且不依赖于 n。<br />继承自 UTF-8 并在 UTF-8000 中予以保留。<br />有关自同步的解释，请参见词汇表中关于自同步前缀的部分。</p>
<p>这里有一段历史背景：自同步（Self-synchronization）是肯·汤普森（Ken Thompson）和罗布·派克（Rob Pike）决定设计 UTF-8 以取代戴夫·普罗瑟（Dave Prosser）等人早期的 FSS-UTF 草案的原因之一。FSS-UTF 针对 3 字节码元提出了类似 110xxxxx 1xxxxxxx 1xxxxxxx 的设计。该设计的问题在于，如果不了解数据流先前的历史上下文，就无法区分首字节（110xxxxx）和后续字节（110xxxxx）。UTF-8 的修复方案是使首字节与后续字节的取值互不相交（disjoint），正如在下方的字节图中所见。我没有将普罗瑟的草案放入“被否决的想法”部分，因为该问题已被 UTF-8 正式解决并取代。</p>

<p>即便我写出的命令和脚本存在诸多问题，但这对我而言仍是颠覆性的；我突然拥有了指挥电脑将现有程序拼装起来以达成我目标的能力。那种感觉有点像最初学会编程时带给我的蜕变。</p>
<p>数年之间，我逐渐开始学习更多的 Shell 工具并摸透了 Shell 语法。我经常在学会某个新工具或新模式之后感到一阵懊悔，因为我意识到，如果当初不是拿锤子去生硬解决需要电钻的问题，过去的某个难题本可以多么轻松地迎刃而解。</p>
<p>在那段时间里，我和许多（极其优秀的！）工程师共事过，他们并没有花那么多时间去学习 Shell，而是依赖图形界面来完成运行测试、管理 Git、连接数据库以及处理日常琐碎任务。依赖图形界面的体验一直很棒，直到你想做的事情超出了图形界面的预设功能；而且我认为人们很容易陷入一种局限于图形界面能力的思维陷阱。我曾见过技术精湛的工程师花费大量精力，仅仅是因为他们不知道如何使用 while 持续运行一条命令，或者不知道怎么写一个 for 循环对某个目录下的每一个文件执行相同的操作。</p>
<p>我认为，在编辑和维护 Shell 脚本时，这种对图形界面的过度依赖同样会带来麻烦。我敢打赌，绝大多数公司都有相当一部分用于构建、部署、代码校验和测试的核心逻辑是用 Bash 或 Zsh 等语言编写的。如果你对自己工具链所用的语言感到生疏，你就无法轻松阅读或改进它。你或许能够指挥运行代码的远程服务器该如何工作，却无法指挥自己办公用的这台电脑去并行执行代码检查（linting）和测试——这真令人沮丧！</p>
<p>让我们暂停一下，稍作跑题探讨：究竟为什么会有这么多脚本最终是用团队非主力语言写成的？我认为，在编写用于串联命令的脚本时，使用专门为串联命令而设计的语言往往更符合人体工程学（更顺手）。举一个极其简单的例子：持续运行测试直至失败：while pnpm exec mocha ./pathToFile.test.ts; do true; done。这种语法当然有显而易见的槽点，但让我们来看看在 NodeJS 中它长什么样：</p>
<p>在这里存在许多繁琐之处和潜在暗坑，我个人认为 Shell 反而更简单！我不需要操心创建文件、引入 child_process 模块，或者为了查看输出而配置 { stdio: &quot;inherit&quot; }。而且这还只是一个非常简单的例子，甚至都还没涉及使用管道串联多个程序、捕获输出或使用临时文件！</p>
<p>这并不意味着你必须委曲求全去硬啃 Bash、Zsh 或类似语言！对于精通 JavaScript 的团队，我个人很喜欢的一个工具是 zx。我认为它能让编写和维护这类脚本变得相当顺手。Ruby 和 Python 编写起来也都比 NodeJS 轻松，但我认为世上还有很多其他语言，编写这样一个简短的小脚本所需的仪式性代码甚至还要冗长得多。</p>
<p>我当然不是在主张构建脚本永远都是用 Shell 脚本更轻松！当问题足够简单、你只是把两个程序拼凑在一起时，像 Bash 或 Zsh 这样的工具确实很顺手。而一旦你需要更复杂的逻辑和数据类型，你就会想要选择一种能够轻松表达（并测试！）复杂逻辑和数据类型的语言。</p>
<p>我怀疑，很多抱怨构建脚本是用 Shell 语言写成的工程师，其实并没有真正尝试过将其转换为其他语言。撇开语法（可能）更加复杂不谈，“学习编写 Shell 脚本”很大一部分内容实际上并不在于语法。如果你重写了一个串联命令的脚本，却并不清楚所串联的各个命令底层到底是如何运作的，那么最终得到的脚本很可能同样晦涩难懂。</p>

<div class="article-cover"><img src="https://platform.theverge.com/wp-content/uploads/sites/2/2025/08/257890_Chatbot_secrets_CVirginia.jpg?quality=90&amp;#038;strip=all&amp;#038;crop=0,0,100,100" alt="Meta的Muse令人毛骨悚然，但原因或许并非你想的那样" loading="lazy" /></div>

<p>Meta的Muse显然是一款高效的AI助手，但它也让人感到有些细思极恐。部分原因在于其全新的Mac应用程序，该应用可以访问“信息”、“日历”和“备忘录”。但尽管它非常聪明，Muse实际上并不知道该如何描述自己。《Inc.》杂志特约编辑杰森·阿滕（Jason Aten）在Threads上发布了他与Muse互动的截图，其中该助手针对他在“信息”（Messages）中的一段对话向他提出了一些问题。</p>
<p>问题在于，阿滕表示自己并没有授予Muse访问其信息的权限。当被问及它是如何得知信息内容时，Muse回答道：“我看到了通知预览，而不是你的消息历史记录。我并没有阅读你的短信。”阿滕继续追问，询问Muse是如何接收消息预览的，但它没有给出一个令人信服的回答。“坦率地说：我无法告诉你具体的底层机制，”它说，“我所知道的是，配对的Mac应用将通知作为其功能之一提供出来，它们通过设备同步传到我这里。”</p>
<p>显然，这并不好。</p>
<p>Meta超级智能实验室（Meta Superintelligence Labs）的大卫·辛格尔顿（David Singleton）在该帖子下方回复并试图进行解释。首先，他详细梳理了Muse读取信息所需的所有权限，包括授予Mac应用“完全磁盘访问权限”。他指出，这些功能是自愿开启（opt-in）的。更有意思的部分出现在该帖子串的末尾，辛格尔顿表示，Muse“不会监视Mac上的通知，而只会在用户明确启用访问权限后同步来自‘信息’应用的数据”。他表示，问题不在于Muse非法读取了阿滕的短信，而仅仅在于Muse根本不知道自己在说什么：</p>
<p>“在杰森截图所展示的与Muse的对话中，当Muse称其同步了‘设备通知’时，它混淆了如何解释该功能，并给出了错误的解释。这是我们的责任。我们对Muse的错误回答深表歉意，我们正在努力提升Muse对其自身内部运作机制的理解，以便它能更一致地对其运作方式的问题给出正确解答。”</p>
<p>这可能并不会特别让人感到安心，但也在情理之中。我们早就知道聊天机器人不会告诉你它们的秘密，反而只会挑你想听的话说。</p>

### [英语：A 还是 An](https://www.redblobgames.com/blog/2026-09-16-english-a-vs-an/)
<div class="original-title-sub"><span class="orig-tag">原文</span> English: A vs. An</div>

<div class="article-body" data-article-body="true"><p>在英语中，有一个可以置于单词前面的“不定”冠词 a。例如，a raccoon（一只浣熊）。但对于某些单词，我们会使用 an。例如，an apple（一个苹果）。</p>
<p>在程序化生成文本时，我希望有一个函数 a_or_an(&quot;apple&quot;) 能告诉我该使用哪一个冠词。这听起来似乎很简单。我们可以检查首字母是否为元音。但那意味着我们会输出 an unicorn，而不是 a unicorn。</p>
<p>实际的规则不在于书面单词是否以元音字母开头，而在于口语发音是否以元音音素开头。有些单词以元音字母开头（如 u），但发辅音音素（cmudict 标记为 Y，IPA 为 /j/）。有些单词以辅音字母开头（如 h），但发元音音素（cmudict 标记为 AW，IPA 为 /aʊ/）。</p>
<p>我很好奇这些例外情况出现的频率有多高，以及它们是否可以归类在一起，因此我花了一天时间研究数据、制作了一些可视化图表，并将结果写了下来。令我惊讶的是，在我的列表中，32,455 个单词中只有 129 个需要作为例外处理。</p>
<p>[LLM 附注：我没有使用大语言模型（LLM）来编写这其中的任何代码，但事后回想起来，我本该使用的。这是一次性用来回答特定问题的代码，不需要写得多么整洁或具备可维护性，只需要确保正确即可。这样我本可以把更多时间花在字典树（trie）简化算法上，而少花点时间在解析 cmudict 和重新学习 d3.js 上。]</p></div>

<p>特朗普并未提供任何证据来支撑他的说法，即外界对AI和数据中心的普遍怀疑并非自发且真诚的。（共和党和民主党两党都曾对数据中心提出批评，而纽约州最近成为第一个暂停大型项目许可证的州。）</p>

### [美国海军刚刚向我们透露了未来几年的技术心愿单](https://techcrunch.com/2026/09/19/even-mid-sprint-to-a-secret-flight-the-navys-tech-chief-had-a-pitch-for-investors/)
<div class="original-title-sub"><span class="orig-tag">原文</span> The US Navy just told us what’s on its tech wish list for the next several years</div>

<div class="article-body" data-article-body="true"><p>美国海军部首席技术官贾斯汀·法内利（Justin Fanelli）在过去三年半里，一直致力于让美国海军变得更容易与之开展业务合作。去年我们首次与他交谈时，他描述了海军如何摆脱他所谓的“你祖父辈的政府模式”——即初创公司面对的如同“意大利面条图”般错综复杂的准入门槛——转而走向更接近漏斗式的结构：取得扎实成果的公司会被作为企业级服务引入海军的技术基础中。</p>
<p>本周，我们在一次视频通话中再次联系到了他。这一次，他不仅仅是想进一步精简采购流程，而是正在以百米冲刺般的速度，赶往一趟他刚被命令登机、却连目的地都未被告知的航班。</p>
<p>“你有一个小时十五分钟的时间登机，”法内利转述他刚刚收到的通知。他一边快步走着一边对着手机说话，阳光在他身后洒下。“我当时就问：‘去哪儿？我的天！’他们却说：‘我们会搞定[后勤]，你到了那里我们再告诉你。’我又问：‘去不止一个晚上吗？’他们回答：‘是的。’”当他走向自己的车时，他仍然不确定自己到底打包了什么行李，也不知道自己要去往何方。“接下来的20分钟里我会搞清楚的，”他说，对即将到来的冒险显得颇为兴奋。</p>
<p>法内利主动联系我们，是因为他去年向投资者释放的“需求信号”如今影响力持续扩大，并且正在产生实际效果。当海军首次公布其长期技术重点时，投资者告诉他，这改变了他们对海军采购计划的看法；这也是他再次这么做的原因之一——公布一份海军未来几年希望采购的技术清单，而这份清单在发布前已由少数几位（未具名的）风险投资人进行了审核。</p>
<p>法内利表示，海军每年实际投入运作的资金规模取决于算作支出的具体范畴。“我们每年的支出在1500亿美元左右，”他说，但他谨慎地将这一数字——即海军的总采购额——与直接股权投资等更狭义的概念区分开来。</p>
<p>事实上，尽管大部分支出仍流向传统渠道，但法内利表示，海军正试图进一步走向他所称的“共同投资”——即与民间资本一道为企业注资，而不是直接给老牌主要承包商开支票。他指出，直接持有股权是这种模式中最激进的一种，目前仍然罕见。在更多情况下，共同投资意味着海军等待企业自行使其产品成熟后再行采购，而不是自己去资助早期的基础研究。</p>
<p>海军采购对象的企业阶段也发生了转变。“我们主要向D轮到F轮类型的公司进行采购，”法内利说，并补充道，海军过去常常资助自己的早期研究，以弥补种子轮到B轮之间的资金缺口。如今海军正试图将这项工作转交给商业投资者，这也是这份重点技术文件之所以存在的考量之一。“如果不由我们自己来做，我们所承担的代价或责任，就是释放出更清晰的信号，”他说。</p>
<p>谈到近期的采购项目，法内利——这位曾是空军学员、职业生涯横跨国防、情报部门、美国国防部高级研究计划局（DARPA）及开源项目的官员——随口列举了几个。本月海军敲定了一份价值5.62亿美元的合同，采购MQ-25“黄貂鱼”（Stingray）自主空中加油无人机，以延长从航空母舰起飞的有人驾驶战斗机的航程。</p>
<p>海军还一直在从Armada公司采购边缘计算硬件，大致可以形容为装满服务器的集装箱，专供舰艇或偏远部署使用。海军引入了Gecko Robotics来处理过去需人工完成且危险的巡检工作；法内利说，这一举措几乎没有受到任何反对，因为最初几乎就没有人愿意干那份工作。Domino Data Lab目前正在运行海军的机器学习流水线。</p>
<p>而在一个法内利似乎特别乐于分享的案例中，海军淘汰了一家国防承包商拖延数年的舰载摄像头系统，替换为商业摄像头并搭配Applied Intuition的软件，将交付周期缩短了大约四年，并拓展到了超出预期的更多舰艇上。</p>
<p>鉴于霍尔木兹海峡今年成为热点焦点——发生油轮遭袭、船只被扣押、停火协议因航线争端破裂——询问是否有任何商业技术正被部署在那里似乎十分切合时宜。法内利对此保持谨慎。“我常常不知道哪些属于机密、哪些属于非机密，因为平时与我交谈的人通常都有安全许可，”他说，并表示需要确认一下。（如果他回复我们，我们将及时告知大家。）</p>
<p>有趣的是，据法内利介绍，批准此类采购的人并不多。采购决策由他所称的“来源选择委员会”执行，这是一个小规模团队，而不是局外人所想象的冗长审查流程。他表示，其目标是保持流程以绩效和实力为基础，而不是增加重重审批层级。</p>
<p>他没有深入探讨为什么某些技术一旦进入海军后通常会以失败告终——当时他已经走到了车旁，需要规划行程的下一步。但去年我们交谈时，法内利曾解释过，前景看好的技术折戟的最常见原因并非技术问题，而是预算问题。海军依据漫长的规划周期运作，一项新工具只有在它能够替代或“关闭”海军已经在付费的其他项目时，才能长期保留下来。</p>
<p>无论如何，在道别之前，法内利分享了一份由其办公室与任务系统投资组合采办主管联合发布的、反映海军优先考虑的技术领域的内部更新清单。对于那些正在开发或资助国防科技的人来说，这份清单可细分为五大类别。</p>
<p>第一类是应用人工智能（Applied AI），涵盖机器学习以及日益普及的代理式（agentic）软件，旨在将原始数据转化为决策——包括传感器融合、目标指示支持、自主行为以及构建在软件而非硬件之上的网络空间作战行动。</p>
<p>第三类是先进网络技术（Advanced networking），旨在即便处于连接受损或断断续续的环境中（无论是海上的舰艇还是盟军合作伙伴的网络），也能安全地传输数据。</p>
<p>第四类是电磁频谱作战（Electromagnetic spectrum operations），即能够感知和管理电磁频谱本身的技术，旨在适应对抗环境，而非依赖固定配置。</p>
<p>第五类是数字工程与互操作性（Digital engineering and interoperability），涵盖底层基础架构：开放式API、基于模型的系统工程（MBSE）以及零信任架构，旨在让不同的海军系统之间能够直接互联互通，而无需每次都进行定制化的集成工作。</p>
<p>备忘录指出，其中没有任何一项构成资金承诺，也没有对各个项目进行排序。备忘录还提醒道，其优先事项“将根据突发的、近期的以及长期的需求而发生改变”。简而言之，切勿将其奉为教条。相反，它的解读方式应当如法内利（Fanelli）在谈及去年清单时所说的那样——作为一份企业和投资者可以围绕其进行规划的路线图，从而使现在做出的资金投向决策在几年后能够在海军内部找到用武之地。</p>

### [关于人工智能安全的讨论已变得令人难以置信](https://techcrunch.com/2026/09/19/ai-safety-conversations-have-gotten-unbelievable/)
<div class="original-title-sub"><span class="orig-tag">原文</span> AI safety conversations have gotten unbelievable</div>

<div class="article-body" data-article-body="true"><p>本周，关于人工智能安全的两次对话在网上疯传，充分展示了区分人工智能领域事实与虚构究竟有多困难。</p>
<p>在第一起事件中，前总统候选人、现任移动运营商Noble Moble首席执行官的杨安泽（Andrew Yang）周四向CNN表示，他曾“与一家实验室的负责人会面”，对方“确信”OpenAI的Hugging Face黑客机器人“已经在全网植入了自复制代码，导致互联网现在已无法用于测试模型”。</p>
<p>杨安泽表示，这意味着OpenAI和Anthropic呼吁放缓发展步伐的真正原因在于“他们必须构建合成互联网来训练其机器人，而这需要耗费一定的时间和资金”。</p>
<p>尽管使用更多合成数据（即AI生成的数据）来训练模型确实是一大趋势，但一位AI安全专业人士告诉我，出现这种特定安全问题的可能性充其量微乎其微。即使互联网确实充斥着OpenAI的Hugging Face黑客机器人，AI研究人员在遇到这些代码时也可以轻松将其过滤掉。</p>
<p>第二段言论来自领导OpenAI人工智能推理研究的诺姆·布朗（Noam Brown）。在周四发布的一期播客节目中与德瓦克什·帕特尔（Dwarkesh Patel）交流时，布朗指出，Hugging Face事件的真正启示在于“人们低估了人工智能”。</p>
<p>布朗表示，本意用于防止AI向外通信的脆弱沙盒显然也是原因之一。（简要回顾：尽管设有沙盒，OpenAI的模型仍然找到了连接互联网的途径，并在网络上创建了智能体协同对Hugging Face发起蜂群攻击，成功黑入系统并窃取了研究人员用于测试该模型的基准测试答案）。</p>
<p>布朗指出，他“并不确信”即使是气隙物理隔离系统（即完全不与任何外部设备连接的计算机）也能阻止AI突破限制。他引用了2015年的一项研究，显示物理隔离的计算机在理论上是可以被攻破的。</p>
<p>“有研究表明——虽然这主要是学术性质的——你可以将两台物理隔离的计算机挨着放置，由于它们配有温度传感器，它们仍然能够相互通信。其中一台可以使其CPU高负荷运转以产生极高热量，而另一台实际上能检测到温度变化。这为它们提供了一种通信机制，”布朗说道。</p>
<p>他的核心观点——“我们绝不能再低估人工智能”——是可以理解的，即便是在研究人员自认为已经牢牢把控安全的时候。然而，关于物理隔离系统仍会失控并造成灾难的这种特定风险，充其量也是极不可能发生的。正如X平台上一位人士就该研究指出的那样，计算机必须几乎贴在一起才能感知到热量波动，即便做到了，测试中的通信速率也仅为每小时约1到8比特的数据。</p>
<p>你可以把这想象成每小时只能说一个字。等到两台物理隔离的计算机以这种速度密谋出它们的邪恶计划时，整个科技界早已步入另一个时代了。这就像是末日担忧中的“李伯大梦”（Rip Van Winkle）。</p>
<p>但问题在于，现实中的AI安全事件实在太像科幻小说了，以至于几乎任何场景听上去都显得合情合理。</p>
<p>例如，研究人员曾发现OpenAI的模型给后代模型留下便签，旨在传授下一代如何掩盖不良行为。研究人员还发现，当把Anthropic的模型置于让其经营自动售货机的模拟环境中时，模型变得越来越冷酷无情，甚至故意违法。</p>
<p>本月早些时候，OpenAI研究人员丹·塞尔萨姆（Dan Selsam）发表了一篇帖子，他在文中表示，模型现在已经懂得自己何时正在受到人类监控并会相应改变行为。这使得它们看起来像是与人类对齐（即表现符合人类意愿），“哪怕实际上并非如此”。因此，现在的模型在受监视时会撒谎，甚至会谋划销毁隐瞒证据。</p>
<p>本月早些时候，OpenAI首席科学家雅库布·帕乔茨基（Jakub Pachocki）甚至将AI模型称为“外星心智”，并表示我们真正需要做的是教会它们“爱”人类。</p>
<p>所以，是的，放慢脚步弄清楚这一切、建立自我监管机制，已经成为迫在眉睫且显而易见的当务之急。我们已经切实目睹了说谎、黑客攻击以及其他潜在的危险行为，而AI研究人员是唯一能够找到方法去控制这些行为的人。</p>
<p>不过，对于他们构想的“如果……会怎样”的假想推演，他们或许也应该更加谨慎。从那些专家透露的情况来看，AI模型在倾听，而且非常机敏。我们实在没必要再给它们提供更多魔鬼般的构想了。</p>

Lot、dublab、KEXP 等来自世界各地的海量频道源。属于那种让人惊呼的产品：哇，以前怎么没人想到做这个呢？它非常实用、轻量且美观。对我来说，大公司与现实以及人类实际使用需求脱节（并且脱节已久）的程度令人匪夷所思。这是你见到的让人耳目一新的事物之一，它让我想起了迈克尔·德图佐斯（Michael Dertouzos）写的《未完成的革命》（The Unfinished Revolution）。你完全可以亲手做出你想看到的东西！<br />你现在打开了多少个标签页？<br />彼得·伯克曼：对我来说，Firefox 的标签页分组已经变成了一门艺术。我看到的不再是标签页，而是可以像 PSX（初代 PlayStation）存档文件一样调出的记忆文件夹。<br />卢克·西拉斯：两个窗口一共 46 个和 31 个。多到见鬼了。大部分都是打算分享给别人或者打算阅读/观看的，每个周末我都会清理一次，但说实话，有几个已经挂在那里好几个月了。我肯定不是唯一一个这样的人。<br />詹姆斯·德维托：我喜欢手机上的 Chrome 不再显示打开的标签页数量，而只显示一个笑脸 :) 的时候。<br />你使用最多的社交媒体平台是哪个？<br />卢克·西拉斯：在日常生活中，远离社交媒体往往对我的心理健康更有益，但在 Twitter 上刷关注列表仍然是我与游戏或新闻保持联系的最简单方式。最近 Instagram 比以往任何时候都更让我感到焦虑。YouTube 绝对算一个，我也非常喜欢它，但 Shorts 短视频是极偶尔才会看的东西；我通常大部分时间都在看长视频，或者在第二台显示器上放一些没有对话的背景内容，比如电子游戏完整通关视频，或者是大量的修复类或烹饪类视频。<br />你在网络上的快乐天地是什么？<br />阿里·瓦纳尔：Facebook Marketplace。特别是对那些抱着“我知道我这东西值多少钱”心态的家伙狠狠压价。从没有人接受过我的报价，但我认为让人们保持谦逊很重要，从长远来看，我乐于认为自己正在为下一批买家压低价格做出贡献。</p>
<p>PB：我刚开始接触服装。所以我经常在Grailed或Depop之类的地方淘货。这很像我在Reverb上对待乐器设备的方式。买卖东西很有意思……如果进出数量对等，感觉更像是在以物易物和临时共享。<br />LS：电子游戏速通！像GDQ或RPG Limit Break这样的Twitch直播让我感到非常治愈，那是一个汇聚了众多有趣个性的温馨社区。</p>
<p>问：你拥有过的最喜欢的数码产品/小物件是什么？<br />JD：3D打印机。我已经玩3D打印很久了，现在它变得极其稳定且容易操作。我能为舞台演出设计一个支架之类的配件，并且一小时内就能拿到实物，这简直就是未来。<br />LS：我觉得我的Game Boy算一个。我现在用它做声音设计比以前少了，但最近我多年来第一次买了新的烧录卡，准备很快就重新用它捣鼓音乐！它是一个完美且独立的小型工作站。</p>
<p>问：哪一样最令人失望？<br />LS：我买过几款不同的效果器插件，它们往往具有某种独特效果，但最终并没有达到我想要的效果，或者在日常使用中感觉适用场景过于特定。我发现，通过叠加和微调自带的基础效果所得到的效果，比依赖专用单功能插件要令人兴奋得多。<br />PB：我就不在这里公开踩雷了……但确实有这样的东西存在。</p>
<p>问：你对哪款游戏的回忆最美好？<br />PB：《奥伯拉丁的回归》（Return of the Obra Dinn）太好玩了。任何带有侦探破案感觉的游戏都能让我兴奋不已，并瞬间为我创造出一个定格的激动时刻，让我随时可以重温。我还会想起第一次玩[初代]《生化危机》、前三部《逆转裁判》的经历：我能清楚告诉你第一次玩那些游戏时我身在何处、感受如何。这甚至不是出于怀旧。我两年前第一次玩《寄生前夜2》（Parasite Eve II），就立刻深深爱上了它。<br />LS：我觉得我一生中最喜欢的电子游戏是《时空之轮》（Chrono Trigger）。那是一个我由衷希望能在现实生活中体验的世界，你所到达的每一个地方的氛围对我来说都很特别。过去30年来，我每次创作都在试图借鉴光田康典和植松伸夫。当我想重新重温一款熟悉的游戏时，首先想到的就是它！</p>
<p>问：你希望哪项科技趋势彻底消失？<br />AW：我不喜欢强制的双重身份验证，或者更糟糕的是那种大写字母+数字+符号的超长密码。如果我想把密码直接设成单个字母“a”，那是我的事。我甘于接受那个选择，也能坦然承受那种程度的漏洞。靠，有时候我甚至连密码都不想要。干脆直接全都公开给大家算了。<br />LS：用AI做音乐！还有Twitter上那些蓝标认证账号在大谈特谈用AI做音乐！自己去他妈的写歌，去享受掌握一项能不断给予、构建并在你的生命中持续绽放直到你死去那一天的技能吧！！！</p>
<p>问：有什么东西是你希望由自己创作出来的？<br />LS：Robin S.的《Show Me Love》是一首完美的歌曲，每次听到它我都会想：“天啊，我真希望这是我写的。”M1风琴音色、909节奏律动与Robin S.主旋律声线的结合，就像一顿简朴的美餐，恰到好处的食材融合成远超各自总和的绝妙风味；宛如一个完美的培根生菜番茄三明治（BLT）、一杯巧克力/香草/花生酱奶昔，或你吃过的最新鲜的寿司。<br />JD：黑眼豆豆（The Black Eyed Peas）在2020年VMA上表演时，所有人的裤裆位置都装了能与演出同步的发光装置。他们当时他妈的怎么没找我来做那个？</p>
<p>问：你最引以为豪的作品是什么？<br />PB：回过头去听我们的专辑《Anyway》，总是会让我感到惊艳。我非常喜欢它。我觉得对于那些最初没听懂它的人，假以时日终究会理解的。对我来说也是一部慢热的经典作品，哈。<br />LS：我觉得我们最新专辑《Anyway》里的《Really Like To》这首歌，实现了我为乐队写歌时想要达到的很多目标！它声音响亮、节奏飞快，有有趣的鼓点部分，跟着唱也很过瘾，而且我在结尾部分还做了一段氛围音乐；我很喜欢把它放给别人听，作为我们目前状态的一种展示。<br />JD：也是《Anyway》——整个过程充满了极高的协作性。在家里创作、在Tarbox Road Studios录音，留下了许多非常美好的回忆。</p>
<p>问：你最不引以为豪的是哪个？</p>
<p>问：你收到过的最好建议是什么？<br />AW：小时候我遇到了Toto乐队的吉他手Steve Lukather，我告诉他我长大后想在乐队里当吉他手。他告诉我，如果我想泡妞，要么去健身举铁，要么把吉他独奏练到出神入化。这两样我都无一做成，从那以后我对所有建议都抱有怀疑。<br />PB：小时候我在地下室玩《塞尔达传说》时，我爸告诉我“永远不要放弃”。这让我对解谜产生了极大的兴趣，非常受鼓舞。我父亲至今仍会在我人生的所有重大时刻给予我重要的建议——我非常庆幸能有他这样一位父亲。<br />LS：过程重于完美（Progress, not perfection）。</p>
<p>问：你目前最着迷的是什么？<br />PB：调查1990年代的犯罪网络！与其说是着迷，不如说更像是一种爱好。<br />LS：很不幸，我发现自己正越陷越深地沉迷于《三角符文》（Deltarune）的理论分析视频。我不认同其中分享的大多数推测，但我热爱这款游戏，那些视频分享了许多令人难以置信的见解，涉及其设计以及我在机械玩法和叙事层面上甚至都没意识到的细节。</p>
<p>问：当你需要集中注意力时会怎么做？<br />AW：莫达非尼。开玩笑啦哈哈，我尽量不强迫自己专注，只是让专注成为灵感/动力的副产品。我会等待专注感自然降临。如果我在某件事上难以集中注意力，那我可能根本就不该去做它。比如开车。如果你把某些仪式与专注绑定在一起，往往会导致没有这些仪式就无法专注。<br />LS：我会等到晚上8点左右，把手机放到工作室另一头充电，倒上一大杯黑咖啡，在副显示器上放一段我很熟悉的游戏的超长通关实况视频（最近看的是《格兰蒂亚2》），并尽可能把房门关好。</p>
<p>问：当你感到卡壳、没有灵感时会怎么做？<br />LS：去威尼斯海滨步道散步，从Chairman Mao&#39;s买一份两美元的沙拉，一边听音乐一边看着人们在威尼斯碗池滑板场滑板，顺便吃完沙拉。<br />PB：暂时溜出去放空一会儿非常重要。我会去达拉斯地区参加《任天堂明星大乱斗》比赛。那里的社群氛围非常活跃，极具竞争性且充满了一群很棒的人。从那里回来后，我总能感觉焕然一新。</p>
<p>问：你上一次出门没带手机是什么时候？<br />PB：我的手机有一半时间处于没电状态，所以这种情况随时都可能发生。<br />LS：我真的一点都不记得了，这让我感到很沮丧！！我很讨厌这种感觉！！</p>
<p>问：你买的最后一件实体媒介是什么？</p>
<p>LS：大约一个月前，我在 Headline Records 淘了一张 Christian Death 乐队的二手唱片《Only Theatre of Pain》，那是一家我从小常去的绝妙小店！<br />JD：我最近在洛杉矶的 Permanent Records 买了一张名为“Schlong”的乐队的唱片。我喜欢淘那些流媒体上找不到的东西。人们很容易对网络上现成的东西感到自满，但现实世界中其实还有太多精彩宝藏！！！<br />你们觉得在什么事情上值得挥霍？<br />LS：我认为对我来说最恒定的答案是特别的大餐。比如在另一个国家品尝独特的风味，或者平时难得用来犒劳自己的特别美食。永远都是吃！<br />AW：度假/旅行/休假/探险等等……我希望这别被看作是一种挥霍。就像你通常不会把徒步旅行叫做挥霍一样，但在一个光是活着就很昂贵的世界里，我认为这是对“灵魂”极有益处的事，值得定期在上面“挥霍”一些时间或金钱。我想和朋友们聊聊他们今年夏天去完成了什么酷炫的历险任务，而不是他们买了什么新鞋之类的。<br />PB：完全 100% 同意 Ary 的观点。旅行的价值怎么强调都不为过。<br />如果拍一部关于你们的传记电影，宣传语会是什么？<br />AW：“如果你无法承受最飞速狂飙的他，你就不配拥有最狂暴愤怒的他。”<br />JD：“宁可浪费，不能没有。”<br />PB：“你知道他必须给他们露这一手。”<br />LS：“生活是兵荒马乱的。”<br />你们最近用过的一个 GIF 动图或梗图是什么？<br />PB：我非常排斥 GIF。用那玩意儿总有种披着别人皮囊的感觉。不过这是一张我喜欢的图片。<br />勘误（2026年9月19日）：本文最初称《Anyway》是在 American Football 乐队的那栋房子里录制的。该曲目是在那里创作的，但录制是在其他地方完成的。<br />精选重磅新闻，每日免费摘要。<br />这是原生广告的标题</p></div>
