### [AI计算初创公司Lambda将在拟议IPO前筹资40亿美元](https://techcrunch.com/2026/10/06/ai-computing-startup-lambda-to-raise-4b-ahead-of-planned-ipo/)
<div class="original-title-sub"><span class="orig-tag">原文</span> AI computing startup Lambda to raise $4B ahead of planned IPO</div>

<div class="article-body" data-article-body="true"><p>据《华尔街日报》报道，云服务提供商Lambda正以145亿美元的投前估值筹集至多40亿美元，这可能是该公司计划于2027年进行首次公开募股（IPO）前的最后一轮私募融资。Coatue Management和贝莱德集团（Blackstone）牵头本轮融资。</p>
<p>《华尔街日报》查阅的一封致投资者信显示，Lambda的积压订单金额从6月的150亿美元增至9月的500亿美元。虽然这看起来像是需求大幅增长，但其中相当一部分增幅似乎来自一家公司的350亿美元承诺：Anthropic于8月底与Lambda签署了一项协议。</p>
<p>这意味着，自2025年融资以来估值已大幅攀升的Lambda，其估值可能严重依赖Anthropic持续付款的能力。不过，鉴于可靠的GPU算力供应极其稀缺，投资者显然仍愿意押注提供这类算力的公司，尤其是那些与大型人工智能实验室签有大额合同的公司。</p>
<p>对于Lambda这类新型云服务商而言，需求本身与满足需求的成本相比，并不是更大的问题。数据中心建设在很大程度上依靠债务融资，而Lambda上周刚刚额外筹集了10亿美元债务；放贷方也越来越谨慎，开始挑选向哪些对象、在什么情况下提供资金。Lambda此时决定进一步融资，不仅为其IPO定价定下基调，也让公司能够在公开市场审视到来之前获得更多资本。</p>
<p>如果Lambda最终进行IPO——据报道，该公司原计划今年上市，但因市场不确定性而推迟——它将加入其他由英伟达支持的新型云服务商行列，例如CoreWeave和Nebius。这些公司如今都依赖自身股票的表现，为数据中心建设提供资金。英国新型云服务商Nscale上月提交了IPO申请，预计很快开始交易。</p>
<p>Lambda、Coatue和贝莱德集团未立即回应置评请求。</p>

<div class="article-cover"><img src="https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/10/06/ml21227_.drawio.png" alt="基于 AgentCore 与 OpenClaw 构建具备上下文感知能力的 AI 助手" loading="lazy" /></div>

<div class="article-body" data-article-body="true"><p>现成的 AI 助手在回答单个问题时表现出色，但在另一个维度上却存在不足：连续性。如果你今天向一个无状态的助手询问关于花园的问题，它完全不会记得你三周前提到过排水良好的高架苗床、你只使用有机肥料，或者你的矮牵牛花曾在热浪中难以存活。每一次对话都是从零开始，重新解释上下文的负担落在了用户身上。</p>
<p>问题并不在于回答的质量，而在于助手对你毫无记忆。本文展示了如何构建一个能够积累上下文的个人助手，该助手使用运行在 AgentCore 运行时（Amazon Bedrock AgentCore 的一项功能）上的开源智能体系统 OpenClaw。AgentCore 记忆（同样是 Amazon Bedrock AgentCore 的一项功能）将一次性对话转化为持久的知识。你还将看到如何使用结构化元数据为这些记忆打上标签，以便检索出与当前问题密切相关的记录。</p>
<p>我们的实际示例是 Sprout（一个园艺助手），但该架构与具体领域无关。只要更换人设和技能清单，相同的流水线即可用于客服机器人、健身教练或内部服务台。整个系统包含在单个 AWS CloudFormation 模板中，只需一条命令即可部署，并基于按量计费模式运行，轻度个人使用每月仅需几美元。在此过程中，我们还将分享可应用于在此技术栈上构建助手的设计准则。</p>
<p>AgentCore 是一个能够使用任何框架或模型大规模构建、连接和优化智能体的平台。下图展示了端到端的请求流，涵盖从入站的 Telegram webhook 到 AgentCore 运行时及其支撑的 AWS 服务。</p>
<p>图 1：Telegram webhook 和 Amazon EventBridge 定时任务均调用相同的 AgentCore 运行时智能体，该智能体负责协调 OpenClaw 网关、AgentCore 记忆和 Amazon Bedrock</p>
<p>两个入口点汇聚至同一个智能体。Telegram 消息通过 Amazon API Gateway 和一个处理 webhook 的 AWS Lambda 函数到达，而早间浇水提醒等定时任务则通过 Amazon EventBridge Scheduler 和一个定时任务 Lambda 函数到达。两者都调用 AgentCore 运行时上的 InvokeAgentRuntime API，其中一个轻量级的 server.py 进程负责协调 OpenClaw 网关、AgentCore 记忆以及 Amazon Bedrock Converse API。Amazon Simple Storage Service (Amazon S3) 提供工作区存储，AWS Key Management Service (AWS KMS) 负责加密，AWS Secrets Manager 存放机器人令牌，Amazon CloudWatch 捕获日志和指标。</p>

<p>命名空间解决了某条记录归属于谁的记忆的问题，而元数据则解答了它具体关于什么内容。在 sprout/{chat_id}/long_term 内部，对“我的矮牵牛花正在枯萎”进行语义搜索，会返回所有含义接近的内容。对于园艺爱好者而言，这意味着三月份的肥料偏好以及无花果树修剪笔记，会与真正相关的记录排在一起。而结构化元数据则有助于我们在记忆进入提示词之前缩小其范围。</p>
<p>每个条目指定一个键（key），该键必须与索引键匹配才能被过滤，并将 extractionType 设置为 STRICTLY_CONSISTENT（直接从事件中透传）或 LLM_INFERRED（从对话中提取）。对于推断出的键，提取配置可以将值限制在固定列表中。Sprout 正是这样做的，因此两条写入路径都会生成相同的词汇表，无论是由哪一部分创建的记录，过滤器的含义都完全相同。</p>
<p>在模型生成回复之后，server.py 会将用户轮次和助手轮次一同传入并调用 CreateEvent。该新事件会输入到提取策略中，进而为下一次对话丰富长期存储的内容。</p>
<p>代码片段 3：持久化轮次，以便提取策略能够异步丰富长期记忆。</p>
<p>提取是异步进行的，因此在当前会话中提及的事实通常要在后续会话中才变得可检索。需要针对这种延迟进行设计：短期会话事件覆盖当前对话，而长期记录则覆盖在此之前的所有内容。</p>
<p>以下是整套流水线端到端协同工作的过程。在几次对话中，你用简明的大白话一次一种植物地登记了整个花园。每一次提及都会变成一个事件。提取策略会提取有关该植物、其所在位置及其光照情况的信息，并存入 sprout/{chat_id}/long_term。今天早晨，用户提出了一个问题：“你还记得我花园里的其他植物吗？”检索系统拉取回这些记录，组装逻辑对它们进行排序，随后它们被纳入系统提示词中。助手在回答时涵盖了用户的位置、日照暴露情况、花坛构造、土壤特性以及植物清单——而这些内容在当前消息本身中均未出现。</p>
<p>图 2：Sprout 通过召回存储的植物清单和生长条件来回答有关花园的问题</p>
<p>通过使用 Amazon EventBridge → Cron 路径上的调度器技能（scheduler skill），Sprout 还可以将该计划转化为主动提醒（例如“跳过草本植物，昨天的土壤仍然潮湿”），并在降雨或热浪即将来临时根据天气技能（weather skill）对其进行调整。</p>
<p>记忆和视觉能力还能相互叠加增益。当用户发送一张植物枯萎的照片时，图像会被发送给 Claude Sonnet 4.5，而系统提示词中仍然携带着记忆层所知晓的一切信息。助手将照片与用户已保存清单中的墨西哥矮牵牛花进行匹配，并结合上下文诊断出枯萎应激反应，而不是冷冰冰地单独分析一张匿名的植物照片。</p>
<p>图 3：视觉与记忆协同工作。照片被发送至视觉模型，而系统提示词中则携带了用户存储的花园上下文信息</p>
<p>视觉模型并非万无一失。在之前一次没有植物清单上下文的交互中，同样的植物被极其自信地识别成了牵牛花（morning glory）——一种同样开着漏斗状紫色花朵的物种。正是用用户自身存储的清单对视觉模型进行了落地约束（grounding），才将看似合理的猜测转变成正确且个性化的诊断，这生动地证明了为什么记忆不仅能改善语气，还能切实提高准确性。</p>
<p>在每一轮对话中注入记忆会导致系统提示词变得庞大，如果采用朴素的实现方式，则在每次请求时都需要为这些 Token 付费。Amazon Bedrock 上的提示词缓存（Prompt caching）解决了这个问题。助手对提示词进行了结构化处理，使稳定的前缀（即人设和组装好的记忆块）置于最前，而易变的用户消息置于最后。Bedrock 会跨请求缓存已处理的前缀，因此对话内重复的轮次无需对未变更的部分重新计算。对于受支持的模型，提示词缓存可将成本降低高达 90%，并将延迟降低高达 85%。</p>
<p>排序规则比任何单一设置都更重要：将稳定内容置于最前，易变内容置于最后，并保持记忆块内部排序的确定性（前面的组装函数有助于实现这一点），以确保前缀在请求之间切实匹配。</p>

### [DOCA GPUNetIO 如何统一 NVIDIA 软件栈中由 GPU 发起的网络通信](https://developer.nvidia.com/blog/doca-gpunetio-gda-ki-unified-gpu-networking/)
<div class="original-title-sub"><span class="orig-tag">原文</span> How DOCA GPUNetIO Unifies GPU-Initiated Networking Across the NVIDIA Software Stack</div>

<div class="article-cover"><img src="https://developer-blogs.nvidia.com/wp-content/uploads/2026/10/image9-768x432.png" alt="DOCA GPUNetIO 如何统一 NVIDIA 软件栈中由 GPU 发起的网络通信" loading="lazy" /></div>

<div class="article-body" data-article-body="true"><p>GPU 应用程序越来越需要将网络和数据传输视为一等的 GPU 控制操作，而非由主机驱动的服务。当 CPU 处于每次网络事务的中间环节时，它就会成为关键路径上的瓶颈，增加延迟并限制分布式应用程序实时响应的效率。</p>
<p>NVIDIA DOCA GPUNetIO 作为专为实时数据包处理和数据传输设计的以 GPU 为中心的网络 SDK 层，直接解决了这一问题。它融合了 GPUDirect RDMA、GPUDirect Async Kernel-Initiated (GDA-KI) 和 GDRCopy 等技术，使 CUDA 内核能够直接驱动以太网（Ethernet）、RDMA、Verbs 和 DMA 操作，同时将 CPU 排除在应用程序的关键路径之外。</p>
<p>具体而言，DOCA GPUNetIO 提供了以下两者：</p>
<p>自 NVIDIA 首次通过 DOCA GPUNetIO 推出以 GPU 为中心的数据包处理以来，该框架已取得显著成熟，从一种将 CPU 移出关键路径的高效方式，演变为了一个统一的 GDA-KI 基础架构，广泛集成于 NVSHMEM、NCCL、Aerial 5G SDK、UCX/NIXL、带有 Holoscan Sensor Bridge 算子的 NVQLink、Holoscan Advanced Network 算子、DeepEP/HybridEP 等项目中。</p>
<p>本文介绍了最新进展：开源库、统一架构，以及这些集成在实践中是如何工作的。</p>
<p>在 GPUNetIO 成为通用底座之前，每个通信库都构建了各自独立的 GDA-KI 风格、由 GPU 发起的 RDMA 实现。每一个库都是独立运作的，拥有各自的假设、代码和维护负担。它们彼此之间没有任何共享。</p>
<p>将不同的 GDA-KI 风格实现汇聚到 GPUNetIO 框架下带来了一个巨大的优势：各个库无需再自行构建和维护基于 GDA-KI 的 RDMA 通信路径，而是可以收敛到一个统一的 GPUNetIO GDA-KI 实现上，所有人都能在一个地方对其进行使用、改进和扩展。</p>
<p>这为功能开发、优化和问题修复创造了一个共同的投入切入点，减少了跨 SDK 的重复工程，并使为某一框架开发的创新能够更快地惠及其他框架。</p>
<p>换句话说，GPUNetIO 成为了多个通信库赖以构建的通用 GDA-KI 基础底座，而不是一组并行且部分重叠的实现。这种统一方法对于 NIXL/UCX、NCCL 和 NVSHMEM 等更高级别的库尤为有价值。它们正协同丰富 GPUNetIO，各方都能从中获取并受益于整个技术栈的改进。从生态系统的角度来看，这意味着更少的重复代码、更少的行为碎片化，以及更稳健的长期演进路径。</p>
<p>NVIDIA 以两种紧密相关的形式提供 GPUNetIO，因为生态系统既需要广度，也需要开放性。完整的 DOCA SDK 版本是一个超集：它是 DOCA 编程指南中记载的 GPUNetIO 实现，涵盖更广泛的 DOCA 技术栈，包括（但不限于）Verbs、以太网、DMA 和通信通道（Comm Channel）集成，同时保留了将控制路径移近 GPU 并将 CPU 移出应用程序关键路径的核心 GPUNetIO 模型。</p>
<p>与此同时，NVIDIA 还发布了一个开源的 GPUNetIO 项目，作为更轻量级、专注于 RDMA-Verbs 的实现，专为希望在网络传输层集成方式上保持完全开源的框架而设计。目前，开源版本是较小且面向 Verbs 的子集，而 DOCA SDK 版本则是增加了更丰富 RDMA 支持、以太网和 DMA 等更广泛能力的超集。</p>
<p>这种划分并不是为了制造两个分化的软件栈。其目的是为 GPU 发起的 RDMA 通信提供通用的开源基础，同时在存在 DOCA SDK 时仍保留通往更高级功能的途径。事实上，开源实现可以在运行时检测 DOCA SDK 的存在，并在可用时通过 dlopen 调用选定的闭源 DOCA SDK 函数；如果缺少该 SDK，它将继续使用开源实现运行。</p>
<p>这就是核心的架构优势：无需每个通信库都构建和维护其私有的 GDA-KI 风格 RDMA 管道，GPUNetIO 成为了多个框架和库可以共同采用、强化和改进的共享实现切入点。</p>
<p>在 CUDA 设备端，对于 Verbs 路径而言，两者的差距刻意保持得很小：开源和 SDK 变体均公开了一个面向设备的 API，这使得即使主机端实现从轻量级开源路径扩展到更广泛的 DOCA SDK 功能集，GPU 编程模型也能基本保持一致。</p>
<p>本节涵盖了适用于任何 GPUNetIO 应用程序的核心概念和编程模型要素。</p>

<p>对于以太网和 RDMA Verbs 传输，DOCA GPUNetIO 提供了两个不同级别的 API：高级和低级。</p>
<p>高级 API 提供了复杂和复合操作的实现。例如，在 Verbs 方面，doca_gpu_dev_verbs_put_signal() 提供了一种预先实现的线程安全组合，将 RDMA 写工作队列条目（WQE）与按每个线程作用域或按每个 warp 作用域执行的 RDMA 原子 Fetch &amp; Add WQE 相结合（warp 中的所有线程协同操作，提交 WARP_SIZE 个 RDMA 写操作，并在最后仅提交单个 RDMA 原子操作）。该函数负责处理来自同一网络队列上其他 CUDA 线程的 WQE 并发提交，并触发网卡门铃（doorbell）以避免竞态条件。</p>
<p>类似地，在以太网方面，另一个示例是 doca_gpu_dev_eth_txq_send()，它提供了在网络队列上提交以太网发送 WQE 然后在线程、warp 或 block 作用域触发门铃的线程安全组合。这同样适用于接收端。</p>
<p>相比之下，低级 API 提供的是应用程序可用来创建自定义复合操作的基础构件，例如使用不同操作码提交 WQE、敲响网卡门铃，以及轮询完成队列并等待完成队列条目（CQE）。这些 API 不具备线程安全性，因此，如果多个线程并发访问同一个网络队列对象，应用程序需要负责进行适当的同步。</p>
<p>WQE 提交到网络队列后，必须通知网卡，以便网卡执行这些操作。这一步称为“敲响门铃”。在 GPUNetIO 中，它指的是 CUDA 内核通知网卡有新的工作已准备好执行。</p>

<p>NCCL GIN（GPU 发起网络通信）为 CUDA 内核提供设备端通信抽象层，暴露出 put、get、signal、wait 和 flush 等原语。自 NCCL 2.27 起，GIN 已将 GDA-KI 集成为后端，并利用开源的 GPUNetIO Verbs 路径。该架构使 NCCL 算法和设备 API 应用程序能够直接从 GPU 驱动 RDMA 操作，同时通过 GIN 接口将底层队列管理和工作提交的复杂性抽象掉。</p>
<p>该工作流始于通信器初始化期间由 CPU 执行控制路径。在此阶段，CPU 负责创建 RDMA 队列对、注册内存，并将传输描述符导出到 GPU 内存中。配置完成后，数据路径完全转移到 GPU。GIN 操作会映射为 GPUNetIO Verbs 调用，由后者负责 WQE 准备、敲响门铃以及轮询完成情况。对于每一次网络事务，这种模式都能成功将 CPU 从应用程序的关键路径中移除。</p>
<p>通过将通信语义与传输实现解耦，NCCL 可以专注于集合通信算法，而 GPUNetIO 则提供经过强化的 GDA-KI 底层支撑。NCCL 利用 GIN 层面的控制机制管理线程、CTA 或整个 GPU 范围内的资源共享，从而实现请求聚合和队列管理优化。这些能力与 GPUNetIO 的优势相契合，使系统能够实现低延迟、高吞吐路径，同时避免 RDMA 实现彼此割裂。最终，GPUNetIO 成为一个共享基础，使性能增强和网卡支持能够开发一次，并在整个 GPU 通信生态系统中复用。</p>
<p>如需了解 NCCL GIN 接口的功能实现，开发者可以访问 NCCL tests GitHub 代码仓库，获取参考代码。</p>
<p>NVSHMEM 是一种基于 PGAS 的编程模型，为 GPU 集群提供可扩展的点对点和集合通信原语，例如 put、get、原子操作、屏障和归约。它支持多 GPU 应用程序在 CUDA 内核中实现细粒度的 GPU 到 GPU 数据移动与同步，从而显著提升应用工作负载的强扩展能力。</p>
<p>在网络通信方面，NVSHMEM 根据可用的网络能力和应用需求提供多种传输方式。NVSHMEM 提供 IBGDA 传输，该传输使用 MLX5 直接 verbs 实现 GDA-KI。</p>
<p>随着开源 GPUNetIO 库的发布，NVSHMEM 3.7 引入了新的基于 GPUNetIO 的传输方式。通过构建在这一通用实现层之上，NVSHMEM 可以受益于 GPUNetIO 的优化，以及通过 DOCA SDK 提供的先进网卡功能。新的 GPUNetIO 传输支持 GDA-KI 通信，也支持通过 RDMA 发起的主机通信（又称 CPU 通信；在后一种场景中，GPUNetIO 仅用于控制路径，以配置网络元素，而数据路径则通过 NVSHMEM 原生函数在 CPU 上执行）。用户可以通过设置 NVSHMEM_REMOTE_TRANSPORT=gpunetio 来选择 GPUNetIO 传输，并通过设置 NVSHMEM_GPUNETIO_ENABLE_GDAKI=1 启用 GDA-KI。</p>
<p>NVSHMEM 中 GPUNetIO 传输的 GDA-KI 部分遵循 IBGDA 传输的结构，但将较大部分的底层代码替换为对 GPUNetIO 库的调用。例如，如上文“敲响门铃”一节所述，门铃的构造和敲响代码已完全外置到 GPUNetIO 库中。在实现与 IBGDA 相同功能和性能的同时，GPUNetIO 传输显著降低了传输实现的复杂性，体现了整合 GDA-KI 实现中通用功能的价值。</p>
<p>根据具体的通信模式，启用 GDA-KI 可能会显著提升小消息规格下可实现的带宽。以下实验使用了 NVSHMEM 性能测试套件中的 shmem_put_bw 基准测试，并在不同消息大小下调用 nvshmem_double_put_nbi。该实验在每个 CTA（协作线程阵列，cooperative thread array）中使用 1 个线程和 1 个 QP，并逐步增加 CTA 的数量。下方的两张图表展示了 GPUNetIO 传输层所实现的带宽，其中第一张展示了禁用 GDA-KI（即使用 CPU 通信）的结果，第二张展示了使用 GDA-KI 的结果。</p>
<p>如上文图 5 所示，当 NVSHMEM 使用 CPU 通信时（控制 CPU 路径配置为 GPUNetIO 函数，而 CPU 数据路径为 NVSHMEM 原生路径），由于 CPU 代理瓶颈的存在，在扩展到更多 CTA 和 QP 时，小消息规格的带宽受到了限制。而在图 6 中，同样的基准测试是在启用了 GDA-KI 特性的 GPUNetIO 后端下执行的（数据路径由 GPU 通过 GPUNetIO CUDA 函数执行）。</p>
<p>该实验证实，使用 GDA-KI 消除代理瓶颈后，带来了更优的 CTA 和 QP 扩展表现。与非 GDA-KI 变体相比，GDA-KI 变体可以在更小的消息规格下达到更高的峰值带宽，并且在消息尺寸维度上更早达到峰值带宽。此前对比 IBRC 与 IBGDA 带宽性能的实验也显示出了类似的结果。</p>
<p>总体而言，GPUNetIO 在保留 IBGDA 和 IBDEVX 功能与性能的同时，大幅降低了 NVSHMEM 的实现复杂度及维护成本。</p>
<p>NVIDIA NVQLink 是 NVIDIA 用于将量子处理器控制系统连接至 GPU 计算的低延迟参考架构，通过与 NVIDIA CUDA-Q 的紧密集成，支持诸如量子纠错（QEC）、前馈以及自适应校准等实时量子-经典混合工作流。Holoscan Sensor Bridge（HSB）通过使用 RoCE、轻量化 FPGA IP 以及主机端控制软件，为该方案提供了网络基础；而 NVQLink 将这种基于 HSB 的模型推向了更低的延迟区间，使其适用于实时 QPU 控制，而非传统的传感器数据摄取流水线。</p>
<p>NVQLink 所使用的 HSB 网络算子被称为 GPU RoCE Transceiver（收发器）。它构建在 DOCA GPUNetIO 和 DOCA Verbs 库之上，专为尽可能降低流量转发延迟而设计。在独立运行模式下，该算子提供了一条流量转发执行路径，用于网络健康检查与性能分析。</p>
<p>该算子启动一个常驻 CUDA 核心（persistent CUDA kernel），利用 DOCA GPUNetIO CUDA 函数持续接收来自远端对等节点的数据包，并在无需任何 CPU 干预的情况下将其发回。在此配置中，远端对等节点是一块 FPGA，负责测量数据包从发出到被接收回来的时间间隔。</p>
<p>为了测量 HSB 2.7.0 GPU RoCE Transceiver 算子的网络转发延迟，我们使用了一台配备 Blackwell GPU 和 ConnectX-7 网卡的 NVIDIA IGX Thor 平台。</p>
<p>在另一侧，通过 OSFP 线缆进行背对背直连，我们使用了 Xilinx RFSoC 4×2 板卡上的 FPGA 来发送、接收并测量往返延迟。</p>
<p>测得的报告最低延迟（即 FPGA 发送数据包与接收到数据包之间的时间）约为 2.6 微秒，中位数延迟为 2.7 微秒。</p></div>

### [我们对 Googlebook 的五点初步印象——令人兴奋，但尚显粗糙](https://www.theverge.com/tech/1005745/google-googlebook-android-laptops-dell-acer-asus-lenovo-hp-impressions)
<div class="original-title-sub"><span class="orig-tag">原文</span> Our first five impressions of Googlebooks — exciting but underbaked</div>

<div class="article-cover"><img src="https://platform.theverge.com/wp-content/uploads/sites/2/2026/09/268755_Google_event_Asus_Googlebook_14_ADiBenedetto_0001.jpg?quality=90&amp;#038;strip=all&amp;#038;crop=0,0,100,100" alt="我们对 Googlebook 的五点初步印象——令人兴奋，但尚显粗糙" loading="lazy" /></div>

<div class="article-body" data-article-body="true"><p>该主题的帖子将被加入你的每日电子邮件摘要和首页信息流。</p>
<p>谷歌的新款笔记本电脑操作系统对 Android 手机用户展现出诸多潜力，但前方仍有很长的路要走。</p>
<p>该作者发布的帖子将被加入你的每日电子邮件摘要和首页信息流。</p>
<p>查看 Antonio G. Di Benedetto 的全部文章</p>
<p>Googlebook 来了。首批机型于 10 月 4 日星期日开售，而我们大约在 24 小时前收到了全部五款 Googlebook 的评测机。自那以后，我们一直在争分夺秒地测试这些设备，了解使用这些 Android 笔记本电脑究竟是什么体验。</p>
<p>乍看之下，Googlebook 很有 Chromebook 的感觉，有时还显得有些毛糙。不过，谷歌在笔记本电脑与手机交互方式上提出了一些很棒的新思路。你现在已经可以将手机连接到 Windows 笔记本电脑，同步通知，也可以在 macOS 上镜像整个 iPhone。但 Googlebook 允许你直接通过笔记本电脑操作手机，其体验十分自然。当然，前提是相关功能能够正常运行。</p>
<p>以下是截至目前我们对 Googlebook 的所有认识、感受和想法——好的、坏的，以及奇怪的地方。</p>
<p>Googlebook 的核心在于与 Android 手机配合使用，而谷歌在这方面的实现非常出色。用 Android 手机设置 Googlebook 简单且毫不费力。开箱体验相当直观：系统会提示你扫描二维码配对手机、登录 Google 账户，然后下载一些你已经在手机上安装的应用。这与最新款 Chromebook 的体验相似，但整个过程更加直观。</p>
<p>将手机应用投射到 Googlebook 上、只需点击一次就把手机上的任务迁移到笔记本电脑、在笔记本电脑上访问手机文件，以及在笔记本电脑上接收手机通知，这些功能都运行良好。这些都是很聪明的设计，让你工作时可以继续专注于笔记本电脑，但其中一些功能仍显得不够成熟——有些地方甚至是字面意义上的粗糙。</p>
<p>应用投射功能允许你直接在 Googlebook 上使用手机应用。与镜像整个手机屏幕相比，直接从笔记本电脑上的应用抽屉启动应用，感觉更加自然。但这也意味着，Googlebook 上的两个独立应用抽屉里可能会出现重复的应用。而且，系统不会阻止你同时运行桌面版和移动版应用——即使是 Chrome 也一样。通常情况下，这应该很容易被忽略，但点击同步过来的通知（例如 Slack 通知）时，可能会打开投射版应用，而不是 Googlebook 上的网页应用或原生应用。投射版应用有时还会出现文字像素化或用户界面比例异常的问题。与原生桌面应用相比，它们在动画和滚动方面看起来、用起来也稍微有些迟滞。</p>
<p>谷歌的“继续使用”（Continue On）功能会将你正在手机上使用的应用临时固定到 Googlebook 的任务栏上，这个功能非常妙。如果我在手机上打开一个电子表格，只需点击一下，就能轻松将它转移到笔记本电脑上。太棒了！不过，我试用的大多数应用都无法通过这一功能同步到 Googlebook 上——甚至 Google 地图和日历也不行。目前看来，它主要适用于 Google 文档和 Google 表格，而对这两个应用来说确实非常好用。</p>
<p>最后，直接通过笔记本电脑读取手机上的文件确实能正常工作。太棒了！</p>
<p>我喜欢华丽的灯光秀。这些笔记本电脑上的谷歌 Glowbar 灯带赋予 Googlebook 独特的风格，但实际作用不大。它位于机盖上，朝向远离用户的一侧；使用笔记本电脑时，通常会亮起白光。与 Gemini 交谈时，它会交替变换颜色；合上机盖后，它会暂时显示一道谷歌风格的彩虹，然后进入休眠状态。</p>
<p>它最实用的功能是显示笔记本电脑的电量。不过，我原本希望在合上机盖充电时，能够看到一些酷炫的动态灯效，展示电量逐渐增加的过程。实际上，在插入或拔出电源线时，它只会以绿色、黄色或红色灯光闪烁几次，用来大致表示电量。至于联想可选配 AI 鼠标上那条真正朝向用户的 Glowbar，它不过是一条可以自行选择颜色的 RGB 灯带，并不会与机盖上的灯光同步。</p>
<p>这些小灯带实在太让人想动手改造一番了。我希望谷歌能在这方面做得更多。至少可以先从显示持续电量开始，让灯带随着充电进度缓慢亮起。</p>
<p>我很喜欢谷歌现在会为 Play 商店中的应用标注桌面端评级。在 Googlebook 上浏览应用时，应用会被归入五类：为桌面端打造、针对桌面端优化、兼容桌面端、更适合在网站上使用，以及专为移动端打造。除了核心的 Google 应用和 CapCut Pad、BandLab 等少数其他应用外，我们还没有发现多少被标记为“为桌面端打造”的应用。</p>
<p>像 Slack 这样被标注为“更适合在网站上使用”的应用，最适合以渐进式网页应用（PWA）的形式安装——这与 ChromeOS 上的情况一样。不过，按照我在 Chromebook 上熟悉的常规流程操作时，一开始并不能安装该网页应用。尝试了几次，并从头开始直接加载 slack.com 后，Chrome 最终提示我进行安装。</p>
<p>如果我从未听说过 Googlebook，而你把我直接带到其中一台笔记本电脑前，我大概会以为 ChromeOS 刚刚进行了一次不错的升级。它们非常像 Chromebook。这并不算坏事，因为我一直很喜欢 Chromebook 相对省心的网页使用体验。但这也意味着，Googlebook 仍带有 ChromeOS 的一些陈旧特征。</p>

### [制药商称：减肥药显现减缓生物衰老的迹象](https://www.technologyreview.com/2026/10/06/1145836/weight-loss-drugs-glp1-lilly-novo-aging-clocks/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Weight-loss drugs show signs of slowing biological aging, say drugmakers</div>

<div class="article-body" data-article-body="true"><p>风靡全球的减肥药带来的益处或许不仅限于帮助人们减重，它们可能还能消解岁月的痕迹。</p>
<p>根据分子“衰老时钟”的读数，制药巨头礼来（Eli Lilly）与诺和诺德（Novo Nordisk）表示，服用其旗下药物的患者衰老速度有所减缓。</p>
<p>这类时钟通过观察随时间累积的 DNA 变化来评估一个人的生物学年龄；而在更新的版本中，则是通过追踪关键蛋白质的水平来进行评估。</p>
<p>两家公司均发现，与服用安慰剂的患者相比，服用这些被称为 GLP-1 药物的超重或糖尿病患者其生物学年龄有所降低，尽管这种差异因所使用的时钟类型以及测试的器官不同而存在较大差异。</p>
<p>诺和诺德全球项目负责人尼古拉·勒德（Nikolaj Roed）表示，总体差异大约在“两到三年”左右。他表示，公司在“跨试验以及跨不同组织的研究中，都看到了患者生物学年龄的改善”。</p>
<p>这些发现加剧了科学家们的广泛推测，即这些被称为 GLP-1 的药物正在对衰老的根本原因发挥作用，并且可能成为一种名副其实的长寿疗法。</p>
<p>“在我看来，两年的效果是相当显著的，”被公认为衰老时钟发明者的加州大学洛杉矶分校教授史蒂夫·霍瓦特（Steve Horvath）表示。霍瓦特指出，新出现的这些数据可以提供“证据，表明这些 GLP-1 药物实际上就是所谓的‘衰老保护剂’（geroprotectors），即能够减缓甚至可能逆转生物学衰老的药物”。</p>
<p>上周末，两家公司在“衰老研究与药物发现”（Aging Research &amp; Drug Discovery）会议上分享了他们的发现。该会议致力于为衰老寻找科学治疗方案。尽管这一探索尚未取得任何明确突破，但一些科学家现在认为，诺和诺德的司美格鲁肽（商品名为 Ozempic 和 Wegovy）正在接近这一目标。</p>
<p>“在非健康人群中，我确实认为它是一种抗衰老药物，”协助诺和诺德进行分子测量的哈佛大学生物学家瓦迪姆·格拉德舍夫（Vadim Gladyshev）表示，“但在健康人群中，目前还没有人知道。”</p>
<p>这些药物通过刺激 GLP-1 受体来实现减重，该受体会向你的大脑发出不饿的信号。然而现实世界中的研究显示出了更为广泛的益处：这些药物可以改善肾功能、降低血压，甚至大幅降低整体死亡风险。</p>
<p>丹麦制药巨头诺和诺德的高级科学总监亚历杭德罗·阿瓜约-奥罗斯科（Alejandro Aguayo-Orozco）在会议期间表示：“如果问题是‘司美格鲁肽能否应对与健康寿命和衰老相关的多种疾病？’我们知道答案是肯定的。”</p>
<p>他表示，下一个需要回答的问题是，这些效果是否伴随着生物学衰老分子测量的变化：“当你使用司美格鲁肽进行干预时，它真的会让时钟朝某个方向转动吗？答案也是肯定的。”</p>
<p>该公司发现，随着时间推移，这些药物会导致衰老时钟广泛放缓——以检测心脏蛋白质的时钟为例，放缓幅度高达4年。“我认为器官年龄发生改变这一点是非常明确的，”阿瓜约-奥罗斯科说。</p>
<p>这些研究对衰老时钟科学也是巨大的推动。尽管这些指标反映了一个人的年龄，但它们是否能作为真正的生物标志物此前仍未确定。现在，时钟研发者们获得了证据，表明当人们服用具有广泛且已被充分证明有益的药物时，其读数显示出年龄有所下降。</p>
<p>曾从事该领域研究、现经营初创公司 Reflector Bio 的生物学家姬玉阁（Yuge Ji，音译）表示：“时钟研究领域的人员十年来一直在推动开展此类研究。这对他们来说意义重大。”</p>
<p>作为其研究的一部分，诺和诺德采集了 10,052 人的血液样本，其中一半服用该药，另一半服用安慰剂。在研究开始时以及数月后采集的血液随后通过“蛋白质组学时钟”进行测量，该时钟利用关键蛋白质的水平来预测个人的年龄和死亡风险。</p>
<p>礼来公司的科学家对其 GLP-1 药物替尔泊肽（tirzepatide）开展了类似研究，使用的是所谓的“表观遗传”时钟，这种时钟通过计算 DNA 中累积的变化来评估年龄。礼来的研究规模较小，但也发现用药者体内的分子时间在很大程度上走得更慢。</p>
<p>礼来公司负责衰老研究的副总裁凯文·达芬（Kevin Duffin）在会议上表示：“所有的时钟都在传递一个一致的信息，那就是我们看到了年龄的降低。这并不是说我们要让年龄逆转30年之类，但这是一个显著的减少。”</p>
<p>这些分子已成为世界上最畅销的药物，其中礼来的替尔泊肽（用于糖尿病的商品名为 Mounjaro，用于肥胖症的商品名为 Zepbound）去年为公司贡献了超过360亿美元的收入，高居榜首。诺和诺德同样拥有多个商品名的司美格鲁肽则紧随其后。</p>
<p>波士顿会议的组织者、英矽智能（Insilico Medicine）创始人亚历克斯·扎沃龙科夫（Alex Zhavoronkov）表示，若全球人口的寿命哪怕仅延长一年，就相当于数千万个人的完整寿命。</p>
<p>上个月，扎沃龙科夫展示了他公司一款治疗肺部疾病的药物也逆转了衰老时钟的信号。尽管该药处于实验阶段，但扎沃龙科夫一直致力于推广人类正进入长寿药物新时代的理念。他还在会议期间透露，尽管自己并不超重，但他一直在“微量使用”现有的减肥药物。</p>
<p>“我正在使用替尔泊肽，同时也是司美格鲁肽的使用者，”扎沃龙科夫说。</p>
<p>这是直接提出“首款大众市场抗衰老药物是否已经问世”这一问题的一部分努力。</p>
<p>“你认为一个理性的人应该开始服用司美格鲁肽吗？”他在挤满听众的现场向诺和诺德科学家阿瓜约-奥罗斯科发问。</p>
<p>“我不是医生。我无法回答这个问题，”阿瓜约-奥罗斯科回答道。</p>
<p>多名人士提醒称，GLP-1 药物确实存在副作用，包括肌肉流失。霍瓦特表示，这也是为什么它们可能对大多数人并不适用的原因之一。霍瓦特称自己虽然考虑过，但目前尚未准备好亲自使用这些药物。</p>
<p>“显然，这些药物对肥胖人群有很多好处，但我还没有看到足够的证据表明它们对消瘦人群有益，”他说，“我想我们还得等等看。”</p>
<p>答案可能在一两年内开始浮现。今年1月，美国高级健康研究计划署（ARPA-H）投入3800万美元用于德克萨斯州的一项研究，该研究将尝试确定司美格鲁肽是否对60岁以上的健康人群具有抗衰老作用。该研究将考察认知能力、行动能力以及感官敏锐度的变化。</p>
<p>该项目还旨在帮助确立抗衰老药物的监管路径，并围绕长寿打造一个“全新的治疗产业”。</p></div>

### [Mirror Particle 正在构建人类行为的“世界模型”](https://techcrunch.com/2026/10/06/mirror-particle-is-building-a-world-model-of-human-behavior/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Mirror Particle is building a ‘world model’ of human behavior</div>

<div class="article-body" data-article-body="true"><p>致力于预测人类行为的初创公司迎来了高光时刻。在过去一年中，Simile 以20亿美元的估值筹集了2亿美元；Aaru 以10亿美元的估值筹集了8800万美元；而在1月份以44.8亿美元估值宣布完成4.8亿美元巨额种子轮融资的AI初创公司 Humans&amp;，则推出了用于建模人类行为的 Persimmon。</p>
<p>如今，人类行为预测的现状严重依赖大型语言模型（LLM），通过提示工程或微调来让它们角色扮演目标受众群体。但成立两年的旧金山初创公司 Mirror Particle 认为，这种方法从根本上就是有缺陷的。</p>
<p>“这就像拿着一把强力水枪去对抗尼亚加拉大瀑布，”Mirror Particle 联合创始人兼首席执行官阿比维亚克蒂·阿胡贾（Abhivyakti Ahuja）表示。该公司为品牌提供一种能够预测消费者行为及其背后原因的AI引擎。“LLM 已经在数千亿个数据点上进行了训练。通过如此少的数据量进行[微调]，你能在多大程度上影响它的行为？它仍然停留在过去。”</p>
<p>Ahuja 认为 LLM 并不能像人类那样看待世界。“LLM 建模的是书面语言，但人类是由视觉感知、空间推理和社会智力构成的。”她表示，依赖它们意味着获取的洞察是建立在人类未注意到的事物之上的，而在尝试预测人类行为时，这完全脱离了重点。</p>
<p>Mirror Particle 正在采取另一种方法：构建一个基础模型，或者正如 Ahuja 所描述的那样，一个从零构建的、模拟人类为何做出某种行为以及人类行为如何随时间变化的世界模型。</p>
<p>“我们不想捕捉静态的人，”Ahuja 说。“我们想捕捉变化中的人。这意味着要捕捉关于人们如何改变、什么诱因在改变他们以及改变到何种程度的纵向数据。”她补充道，如果他们没有改变，“那也是一种信号。”</p>
<p>Mirror Particle 已经完成了一轮天使轮融资，并表示即将完成首轮风险投资。该公司下周还将参加 Startup Battlefield 200，这是 TechCrunch 著名的初创公司竞赛，将于10月13日至15日在旧金山举行的 TechCrunch Disrupt 2026 上展开角逐。</p>
<p>这家初创公司依靠专有的数据组合——包括客户的消费者数据、时事、流行文化、社交媒体等——来对一个人群细分市场进行建模，将其视为一个随时间演变的系统，并追踪其在经历各种体验时的动机转变。其中的大部分重点在于“显示偏好行为”（revealed behavior）——即人们实际做了什么，而非自我报告的问卷调查答案。</p>
<p>与其竞争对手一样，Mirror Particle 最初的商业化策略集中在对这类洞察已有预算需求的领域：市场调研、品牌及产品策略。例如，Mirror 不仅可以帮助美妆品牌为吸引Z世代撰写更好的化妆品广告文案，还能判断该受众群体是否真的想要这款产品。</p>
<p>“如果[目标受众]根本不想要眼影盘呢？”Ahuja 说。“如果你想向这个市场销售产品，也许腮红是一个更好的选择。”</p>
<p>Mirror Particle 的预测引擎还为客户提供当前或未来行为背后的“原因”——为其推荐提供合理解释的动机、制约因素和额外背景信息，从而帮助品牌做出更明智的决策。</p>
<p>在一个早期的试点项目中，一家知名宠物食品品牌想知道在包装上放什么图案才能促进销售。鸡肉？牛肉？还是蔬菜？Mirror 的技术发现该品牌问错了问题。图案并不重要。问题在于该品牌知名度太高，以至于被认为是大众化且廉价的品牌，在解决这一认知问题之前，销售额将陷入瓶颈。</p>
<p>“我们认为我们模型的演进方式就像婴儿认知世界一样，”Ahuja 说，并指出婴儿是从视觉走向语言，再到身体意识，最后到社会智力。</p>
<p>对人类大脑建模的这种根本性兴趣源于 Ahuja 学习神经科学和计算机科学的背景。她来自印度，最终在多伦多大学求学，并在那里受到了AI先驱杰弗里·辛顿（Geoffrey Hinton）在神经网络领域贡献的启发。</p>
<p>毕业后，Ahuja 加入了亚马逊机器人公司（Amazon Robotics），从事制造其他机器人的机器人研发工作。正是在那里，她遇到了联合创始人威尔·宋（Will Song）和汤姆森·严（Thomson Yen）。Song 职业生涯中的相当一部分时间都在构建销售个性化引擎，而 Yen 则专注于利用深度学习来研究AI代理如何理解人类行为。</p>
<p>这家初创公司的长期愿景是成为“预测人类行为的通用层”，并从更广泛的群体层面分析走向个体层面的洞察。</p>
<p>“如果我们想与AI协同工作并彼此合作，我们只需要一个更好的人类模型，”Ahuja 表示。</p>
