### [Waymo效应：人工智能如何悄然削弱科研协作](https://www.researchagenda.news/articles/the-waymo-effect.html)
<div class="original-title-sub"><span class="orig-tag">原文</span> The Waymo effect: how AI is quietly making research less collaborative</div>

<div class="article-body" data-article-body="true"><p>无摩擦技术如何让我们习惯偏爱独处——以及为何科研领军者应当为此担忧。</p>
<p>在最近一次旧金山之行中，我做了如今每位旧金山访客都会做的事：叫了一辆空无一人的汽车。</p>
<p>那辆Waymo自动驾驶汽车带着一种从未为寻找停车位发愁过的机器特有的从容自信驶来。我坐进后排，本能地瞥了一眼驾驶座想打个招呼，却发现自己正礼貌地对着一张空椅子点头。方向盘正在自行转动。我这辈子花了相当多的时间思考物理学中违背直觉的现象，但这丝毫未能缓解我目睹方向盘自行转动时所产生的轻微存在主义眩晕——一位看不见的司机正对我的生命安全负责。</p>
<p>我去旧金山的部分原因，是想与麦克米伦学习（Macmillan Learning）首席执行官苏珊·温斯洛（Susan Winslow）会面。我们同属霍尔茨布林克出版集团（Holtzbrinck group），而我们相聚则是出于最人性化的职业缘由：展开协作。坐在同一间屋子里，交流AI如何重塑我们各自所在的科研与教育领域的心得，并进行那种在视频通话中极难实现的深度思考。</p>
<p>然而，在交流彼此的Waymo体验时，我们发现双方在另一件事上达成了完全一致的看法：乘车体验太棒了。作为两位自认内向的人，我们都觉得这辆无人驾驶汽车是一处小小的绿洲。无需勉强社交寒暄。无需就车内收音机播放什么进行无声的博弈。这里提供了一个毫无愧疚感的独处空间，让人可以理清思绪、处理完一封电子邮件，或在途中接听电话，而不必感到在陌生人面前通话的尴尬。车内安静、平稳，且完全没有任何社交要求。</p>
<p>我们花了稍长一点的时间才说清楚自己究竟失去了什么。两个跨越大洲专门来见面对谈的人，却因一项核心特征是“无需与任何人交谈”的技术而暗自窃喜。</p>
<p>让我尝试下一个定义：所谓的“Waymo效应”，是指当一项技术消除了人际交往中的摩擦时所产生的现象；我们会把这种消除视为纯粹的获益——因为摩擦的成本对我们而言向来显而易见，而其带来的益处却隐而不彰。</p>
<p>读过吴修铭（Tim Wu）关于“便利的暴政”（the tyranny of convenience）论述的人，对这种套路都不会陌生——他的论点是，一旦出现了一种毫无摩擦的选项，我们便会默认选择它，并悄然放弃摩擦原本为我们带来的一切价值，毕竟从一开始就没有人将这种摩擦宣传为有价值之物。阿尔伯特·博格曼（Albert Borgmann）提出的相关概念“设备范式”（device paradigm）则更进一步：设备提供了一种日用品或便利物——例如温暖、信息、陪伴——却掩盖了以往为了获取它而必须付出的实践过程，以至于我们甚至不再察觉这种实践已经消失。唯一持续存在的，只有不断送达的便利本身。</p>
<p>与出租车司机交谈的成本是显而易见的：维持礼貌的小小负担、对话如同轮盘赌般的不确定性，以及内向者在清晨7点强撑着寒暄所耗费的心力。而其益处则是分散且滞后的：在许多日子里，对我们许多人来说，出租车司机是不得不遇见的最后一个陌生人；是来自我们所在圈子之外——无论在职业、政治还是社交层面上——唯一与之进行非自选对话的最后一人；也是我们未曾主动寻求、却仍能可靠获取外界视角的最后来源。</p>
<p>无论是苏珊还是我，都不希望设计出一个没有这些对话的世界。我们只是享受在这一次选择退出的轻松。当然，此类事物正是这样逐渐流失的：从来都不是因为某项深思熟虑的决定，而始终是源于便利的诱惑。一次又一次舒适的乘车，悄然积微成著。</p>
<p>我需要明确指出，这并非一篇反对Waymo的文章（乘车体验确实无可挑剔，我毫不犹豫会再次乘坐——而这恰恰正是核心所在）。这是一篇关于科学研究的文章。因为将司机从汽车中移走的同一套逻辑，如今正以同样的从容淡定，且带来深远得多的后果，将合作者从科研过程中剔除出去。</p>
<p>大语言模型正是智力生活领域的Waymo。</p>
<p>坦率地从科研人员的亲身体验来审视这一对比吧。合作者只是偶尔在线，时间被教学任务、基金申请截止日期和时区差异切割得七零八落；而LLM却能在周日凌晨两点随叫随到——我们毋庸自欺，这往往正是惊人数量的科研构思真正发生的时刻。合作者带着他们自己的议程、他们自己对问题的定义框架，以及他们令人头疼的、认定你的核心假设是错误的执念而来；而LLM除了对你有所助益之外，别无其他诉求。合作者必须被说服；而LLM只需被提示。合作者会以你未曾要求且未曾想到的方式对你发起挑战；而LLM对你的挑战，则严格受控于你所要求的严厉程度——分毫不差，绝不多跨越一步。如果你要求它评判你的论点，它会胜任有余地照办。但它评判的仅仅是你提交给它的那个论点。它绝不会主动提醒你解决的其实是个错误的问题，也不会指出竞争团队早在2019年就尝试过并已放弃该方向，更不会告诫你构建的优美理论框架一旦与他人领域中纷繁复杂的现实相撞击便会土崩瓦解。</p>
<p>换句话说，合作者带来的不便并非合作中的瑕疵；在很大程度上，它正是合作的本质所在。另一个头脑的价值，恰恰在于它拒绝成为你自身意志的附庸。</p>
<p>而在挑战与意外收获之外，还存在着更为根本的意义。科研绝不仅仅是一个将想法转化为论文的生产函数。它是一个实践共同体——一张通过争论、学术传承、学术会议酒吧里的闲谈，以及共同经受审稿人严苛评审的煎熬而维系的社会纽带网络。这张网络赖以编织的，正是我们如今正在通过技术工程消除的摩擦。每一次本该与同事进行的对话被转嫁给聊天机器人，都是悄然从这张网络中抽走了一根丝线。单一一根丝线看似微不足道，整张网络却至关重要。当这种现象演变成规模化扩散时，有一个专门的词汇可以描述它，我提议我们使用它：去协作化（decollaboration）。</p>
<p>如果这仅仅关乎个人的诱惑与自制力，那它不过是一个留给自我约束和偶见严厉社论探讨的话题。但事实并非如此。对于科研领军者、资助机构和学术机构而言，令人不安的真相在于，我们亲手构建了一套激励体系，使得“去协作化”成为了理性选择——而且年复一年，我们还在不断让这种选择变得愈发合理。</p>
<p>合作历来代价高昂。它需要差旅开支、日程协调，以及建立信任那般极其缓慢的磨合过程。它需要管理自尊心、妥协退让，以及就作者署名顺序协商时周期性的小小失落感。“不发表即出局”（Publish-or-perish）的考核机制向来对这些成本课以重税，因为花在与合著者磨合对齐上的每一个小时，都是未曾用于生产被现有评价体系认可的成果的时间。然而，如今有三种力量正在相互交织叠加。</p>
<p>首先，是经费压力。当预算收紧时，首当其冲被削减的往往是那些价值真实存在却难以量化的预算科目：差旅、研讨会、学术休假、访问职位——即带来“意外发现”（机缘巧合）的整个实体基础设施。我们削减了走廊的经费，然后反过来奇怪为什么走廊里的交流探讨不见了。</p>
<p>其次，是对速度的崇拜。我们的评估体系——无论官方网站上点缀着多么动听的《旧金山科研评估宣言》（DORA）式表态——归根结底奖励的依然是产出以及产出的速度。而大语言模型（LLM）承诺带来的最核心优势正是速度。它们在耳边低语：文献综述周五就能完成，初稿下周一就能成型。对于一位能否获得下一个职位取决于出版物清单长度的研究人员而言，这样的耳语绝非能够轻易忽视。</p>
<p>第三，也是最具诱惑力的一点：大语言模型从不会争夺作者署名顺序。它没有需要照顾的自尊心，没有相互竞争的个人诉求，也不会在学术成果的荣誉中分一杯羹。在这样一个把学术荣誉视作生存货币的体系里，一个才华横溢却分文不取学术功劳的对话者，已经不仅仅是方便而已。这本身就是一种套利行为。</p>
<p>关于科研本身的研究（meta-research），本应让我们在此止步深思。从团队科学的文献中我们得知，小团队倾向于颠覆创新，而大团队倾向于完善发展；恰恰是合作者之间出人意料的组合——跨领域、跨机构的非典型搭档——不成比例地孕育了绝大多数最具原创性的成果。与此同时，关于生成式人工智能的早期证据指向了一个我们应当感到熟悉的方向：个体生产力上升，而思想的多样性却在收窄，每个人都在越来越相似的路径上加速前行。实际上，我们正在进行一场不受控制的全球实验，用意外发现的机缘去换取吞吐量——而我们所构建的激励机制就是这一实验的试验仪器。</p>
<p>这里还存在一个更为深层的代价，它关乎大语言模型最令人惊艳的能力：写作。</p>
<p>这些工具的部分诱惑力在于那种神速的印象。而我们有必要精确剖析为何这种印象在一定程度上只是一种幻觉。写作需要时间，是因为思考需要时间；这两者并非恰好先后发生的独立活动。撰写论文的价值从来不仅在于写出来的成果本身——它更是一种倒逼思考的机制（forcing function）。正是在写作中，我们才会发现自己原本坚信不疑的论点在第三节存在漏洞；正是在写作中，模糊的直觉要么凝练为严谨的主张，要么在必须变得严谨的压力下瓦解冰消。高质量的思想孕育缓慢，而在历史上，这种缓慢的孕育过程往往发生在人与人之间：在白板前、在走廊里、在合著者留下修改痕迹时那种富有成效的磨合与思想碰撞中。</p>
<p>认知心理学家对这种富有成效的摩擦有一个术语：罗伯特·比约克（Robert Bjork）提出的“必要难度”（desirable difficulties）——即在学习和思考过程中的某些摩擦、费力的检索、延迟的反馈、努力用自己的语言将想法落诸笔端的挣扎，并非持久理解的阻碍，而恰恰是实现深度理解的机制所在。如果为了舒适而消除难度，你并不会更快地获得同等程度的理解；你得到的只会是更浅薄的理解，只是呈现得更加顺畅罢了。</p>
<p>把写作外包，你并没有加速思考，而是直接跳过了思考。随着模型性能的提升，这一陷阱反而越陷越深，因为它们的输出越来越好——语言更流畅、结构更严谨，越来越难以与受过良好教育的人类散文区分开来。正是在破绽越来越少的同时，诱惑在不断增大。作为一名物理学家，这让我联想到了宇称-时间对称（PT-symmetric）量子系统：该系统具有一种令人不安的特性，即在一个隐藏的对称性被打破之前，一切表现都完全正常——而一旦打破，所有的一切都会在瞬间彻底改变。从所有可见的指标来看，一种科研文化可以显得无比健康——产出上升、周期缩短、文笔无可挑剔——而维系它的无形支柱却在悄无声息中跌落至阈值之下。等到症状在各项指标中显现之时，根源已埋下数年之久。</p>
<p>这番讨论并非主张禁用这些工具。禁令注定会失败，而且理应失败，因为这些工具的前景是真实存在的。在 2026 年 3 月发表于《自然》（Nature）的一篇评论中，王大顺拓展了史蒂夫·乔布斯将计算机比作“人类思维的自行车”的名言，提出人工智能代理是人类思维的“飞机”：比自行车更快、更强大，但也更难驾驭，一旦失事代价也更惨重。他在益处方面的判断是正确的，而且这种益处十分可观。当人工智能将失败的成本压缩殆尽时，提出更具风险、更有抱负的科学问题便成了理性之举；当它大幅降低分析成本时，小型实验室和初出茅庐的独行者便能够尝试过去需要千军万马才能完成的研究。如果善加利用，这些工具确实能够拓展科研边界——而且若运用得当，智能代理系统甚至可以通过让每一个分析步骤都具备可记录和可复现性，从而加固科学界最脆弱的环节之一：可复现性。</p>
<p>但请注意，即便是乐观主义者也坚持强调一点。王大顺给出的处方是他所谓的“机长掌舵式科学”（pilot-in-command science）：研究人员担任机长，智能代理充当机组成员——分析代理负责起草，批判代理负责质询，规划代理负责制定下一步计划——而人类始终保留对研究问题、研究路径和结论的最终决断权。换句话说，即便是人工智能辅助科研探索最热忱的构想者，也坚决认为驾驶座前排必须有人掌舵。王大顺从另一个角度得出了与“Waymo 效应”相同的担忧：他警告说，虽然人工智能可以提高个体表现，但它有可能降低集体多样性，除非我们刻意加以遏制，否则产出将会趋同——而且，正如人类合作者以深刻而出人意料的方式塑造我们一样，我们的智能代理也会如此。他的解决方案是“为异议而设计”（design for dissent），培养众多思维方式各异的模型。也就是说：在消除了摩擦之后，我们现在必须通过工程手段将摩擦重新引入。</p>
<p>这不过是换了新装的旧担忧。1983 年，心理学家利桑·贝恩布里奇（Lisanne Bainbridge）描述了“自动化的讽刺”：一套系统自身运行越可靠，人类监督者就越缺少机会去练习原本需要他们在紧急情况下调用的技能，因此人类的能力反而在无声无息中退化，原因恰恰在于这种能力极少需要用到，而一旦需要，往往就是最危急的关头。把“飞行员”换成“研究人员”，把“自动驾驶”换成“智能代理”，王大顺所警惕的机制正是贝恩布里奇在四十年前指出的问题。</p>
<p>因此，问题并不在于技术本身。问题在于，我们让“人与人的交流”变成了昂贵的选项，而让“人与机器的交流”变得免费；然后当研究人员做出理性的选择时，我们却又感到大惊小怪。</p>
<p>因此，责任应落在制定激励机制的地方。资助机构和学术机构应当看清科研合作的本质——它不是可有可无的点缀，而是一种基础设施——并为其给出合理的定价与支持。</p>
<p>为这种“摩擦”提供资助吧：研讨会、实地互访、同处一地办公，以及那些能促成任何人都无法预先安排的对话的非结构化时间。评估科研贡献而非产出速度，并且要言行一致。将“你与谁一同思考？”视作一个与“你发表了什么？”同等重要、严肃的问题。</p>
<p>或许，在这个机器能够产出无数篇合格论文的时代，我们应当意识到，稀缺而有价值的事物已经发生了逆转：产出正在变得廉价，而共同思考正变得无比珍贵。</p>
<p>苏珊（Susan）和我抵达了目的地。车行驶得平稳顺畅，车内的宁静令人惬意，而我们各自跨越大洋与大陆所追寻的合作也确实达成了——但它并非发生在那座毫无阻力的胶囊车厢里，而是发生在随后那些低效、未列入日程、完全属于人与人之间交流的时间里：那些漫无边际的闲谈、彼此未曾预料的分歧，以及我们谁都没带到旧金山的想法——因为在同处一室之前，这些想法根本就不存在。</p>
<p>归根结底，这就是完整的“Waymo效应”：乘车体验令人愉悦，目的地也已抵达，只有当你向前排瞥上一眼时，才会发现缺失了什么。王（Wang）呼吁推行“机长负责制”式的科研；而潜在的隐秘风险在于，我们的激励机制正在将我们训练成享受舒适体验的“乘客模式”科研人员。</p>
<p>如今，科研正在爬向后座。旅途将一路顺畅。成果也会如期而至。在科研领袖们又度过数年舒适乘车时光之前，他们应该扪心自问一个简单的问题：坐在前排的究竟是谁？我们又是从何时起，不再留意前排根本空无一人在驾驶？</p>
<p>丹尼尔·胡克（Daniel Hook）系霍尔茨布林克集团（Holtzbrinck Group）首席科学官。感谢苏珊·温斯洛（Susan Winslow）和奥利弗·扎恩（Oliver Zahn）带来的促成本文写作的精彩对话。</p></div>

### [RTK声称节省了Token，但我们的成本基准测试得出了相反结论](https://quesma.com/blog/does-rtk-make-ai-coding-cheaper/)
<div class="original-title-sub"><span class="orig-tag">原文</span> RTK reports token savings, but our cost benchmarks disagree</div>

<div class="article-body" data-article-body="true"><p>RTK（Rust Token Killer）在AI智能体读取终端输出之前对其进行过滤和压缩。截至目前，RTK在GitHub上已斩获超过7.9万颗星，成为让AI编程更便宜的最热门工具之一。<br />X上的一篇帖子称RTK可将Claude Code的Token消耗减少多达60%，浏览量达到了31.3万次。<br />然而，JetBrains的SkillsBench运行测试却没有发现任何节省。其README中包含一段免责声明：<br />RTK最多可削减智能体读取的Bash输出的90%。[…]但这并不等同于将您的账单减少90%。<br />因此，“更少的终端输出”并不等同于“更便宜的AI编程”。它可能有所帮助，可能毫无作用，也可能适得其反（导致更多轮次或更低质量）。在这篇文章中，我们将展示历时数天、耗费超过1500美元Token后的测试发现。<br />RTK可以重写智能体通过其Shell工具（Claude Code中的Bash，OpenCode中的bash）运行的Git、测试、打包和文件命令。每次重写都会返回同一输出的更简洁版本。<br />例如，RTK会保留文件名、大小和权限（644表示rw-r--r--），但会丢弃所有者和日期：<br />由于RTK压缩终端输出，我们在Terminal-Bench 2.1上对其进行了测试，这是一个重度依赖终端交互的基准。我们选择停留在2.1版本而不是更新的3.0和4.0版本：智能体能通过大部分2.1任务，而3.0和4.0目前仍然极具挑战性。成本仅对通过的任务有意义。<br />我们使用Fable 5.0运行Claude Code，并通过OpenRouter使用DeepSeek V4 Pro 0813运行OpenCode。每个任务在不使用RTK和使用RTK的情况下各调度运行五次，均采用相同的模型路由、平台以及任务专属超时设置。<br />在剔除四个因遇到拒绝执行而失败的Fable安全任务后，最终对比涵盖了85个Fable任务和89个DeepSeek任务，共计1740次尝试。<br />使用RTK后，Fable的成本下降了5%，而DeepSeek的成本上升了5%。<br />使用RTK时任务通过率均有所下降：Fable降低了1%，DeepSeek降低了2%。两者的通过率差距都很小。<br />当我们把包括失败尝试在内的所有花销除以通过的任务数时，Fable在使用RTK时便宜了3%，而DeepSeek则贵了7%。<br />另一种方法是对每个任务赋予同等权重，因为单次昂贵的任务可能会掩盖许多廉价任务的表现。我们对比了每个任务基准尝试的均值与其RTK尝试的均值，随后对这些变动进行了平均计算。<br />在这种任务级别的指标下，Fable贵了1%，与零相比没有明显差异。DeepSeek的任务成本平均上涨了17%。<br />将失败计算在内并未改变这一趋势。在所有10次尝试均通过的36个DeepSeek任务中，成本增幅仍达18%。<br />Fable在使用RTK时几乎所有的节省都来自于单一任务：winning-avg-corewars。两种配置下每次尝试都顺利通过，但使用RTK时完成所需的轮次减少了约一半。在其他任务中，节省幅度不到1%。<br />DeepSeek在同一任务上得出了相反的结果。两种配置都通过了每次尝试，但RTK耗费了更多轮次且成本更高。即便去掉该任务，使用RTK时的成本仍然更高。<br />RTK文档将rtk gain定义为原始命令输出与过滤后输出的字节差除以4，而非计费Token的数量。<br />在445次DeepSeek RTK尝试中，RTK报告共节省了3.492亿Token，降幅达89%。<br />报告中显示的大量Token节省并不意味着任务成本更低。<br />在train-fasttext任务中，模型两次请求执行head -1 train.txt。RTK每次都通过将这些有限的读取与整个文件对比，记入了1.205亿的Token节省。仅这两次调用就占了对比统计中节省计数器数值的69%，尽管所请求的命令根本不可能返回整个文件。<br />将rtk gain直接等同于节省的资金，预设了该次尝试后续部分保持不变。RTK可能会改变智能体接下来的交互轮次。rtk gain并没有计入那些轮次的成本。<br />这正是社交媒体帖子误导之处：rtk gain计算的是被移除的输出，而不是省下的钱，它可能让一次更加昂贵的尝试看起来得到了优化。<br />有一次DeepSeek的git-multibranch尝试陷入了死循环。智能体运行了一个带有rtk find 0.45.0不支持的参数的find命令。插件将其重写为rtk find，随后因报错“Use find directly”而失败。随后的每一次重试又都被再次重写。RTK在我们测试后的0.46.0版本中修复了该问题。<br />智能体在超时前连续累积了339次错误。它最终仍通过了任务，但成本大约是对标基准尝试（同样通过）的9倍。这是一次离群尝试；即便排除它，整体趋势依然成立。<br />在没有RTK的情况下，工具输出约占Fable输入Token的11%，占DeepSeek的40%。<br />在RTK尝试中，Claude Code有31%的终端调用、OpenCode有51%的终端调用使用了RTK。<br />RTK只重写Shell命令：其Claude Code钩子匹配Bash工具，其OpenCode插件作用于bash调用。两个平台均将文件读取和搜索公开为独立的Read、Grep和Glob工具，这些工具会绕过RTK。Claude Code大约一半的Bash调用已经自带head、tail或wc来限制自身输出了。<br />在智能体编程中，上下文在每轮后都会被缓存，因此后续对终端输出的读取大部分体现为缓存读取。这些缓存在Fable中的成本仅为常规输入Token的1/10，在DeepSeek中为1/30。<br />在DeepSeek中，RTK使终端输出字符减少了9%，但提示词Token却增加了9%。未缓存输入减少了1%，缓存输入增加了9%。包括推理在内的模型输出，在启用RTK时占成本的56%，未启用时占57%。<br />当智能体交互轮次增多时，任务成本通常随之上升。<br />DeepSeek在启用RTK的尝试中，有58个任务消耗了更多轮次，其中44个成本更高。在28个任务中轮次减少，其中23个成本更低。<br />启用RTK后，DeepSeek平均每轮交互的输入减少了7%，但总轮次却增加了18%。更精炼的单轮并没有换来更少的总体输入。<br />智能体增加额外的一轮交互，其成本就可能超过压缩所带来的节省。这是“Token膨胀”（tokenflation）问题以另一种形式重现。JetBrains在SkillsBench上也观察到了相同的现象：RTK在低努力度下增加了轮次，在高努力度下并未降低成本。<br />在Terminal-Bench 2.1上，Fable的成本节省完全依赖于单个任务，并不具有普适性。我们不推荐将RTK作为通用的成本节约工具。<br />个别运行记录表明，当前的前沿模型本身已经能够高效利用终端（Fable的上下文中终端输出仅占约7%）。模型自身会采用head -n或tail -n等技巧。RTK在旧模型上可能更有帮助。在今天，它属于特定场景下的小众优化，而非普遍节省成本的灵丹妙药。<br />使用ChatGPT、Claude或Google Gemini从照片识别AI蘑菇：GPT-6 Astra、Gemini 3.8 Flash、Claude Fable 5.1、GPT-5.6和GLM-5.3-Flash。针对360张有毒菌类照片询问“那是什么蘑菇？”。看哪些给出了警告，哪些识别正确，哪些失败。<br />Token膨胀：简单任务消耗越来越多的上下文、推理和工具调用，却没有产生更多有用的输出。我们对14个模型进行了基准测试；其中一个模型在回答“Hi”时调用了33次工具并提交了一次未被请求的代码提交。<br />在Claude Code中串联四个Claude模型：在委托的安全任务上面临模型拒答，仅排在第七位，成本是表现最优的单模型运行的两倍。</p></div>

### [抵制“人工智能”](https://ronjeffries.com/articles/-v026/x/t/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Resist &quot;AI&quot;</div>

<div class="article-body" data-article-body="true"><p>是的，“AI1 精灵”看起来确实挺有用。但它同样充满诱惑、具有选择性危害，并且在诸多重要层面正在伤害我们所有人。高管、管理者、顾问、开发者，还是普通人：请抵制它！</p>
<p>我不用任何编程类“AI”，连 JetBrains IDE 里内置的那些也一概不用，而且我也绝不打算用。然而，我自己也算不上完全一清二白。在试用过 Kagi 和 Duck Duck Go 之后，我又换回了谷歌搜索，而且我坦白承认，我觉得它的“AI Overview”确实挺好用。它经常是准确的，能给出我想要的答案。所以我并不是以圣人的姿态站在你们面前的。</p>
<p>我不是来向大家说教道德的，我只是想提出这样一个观点：就“AI”目前的现状和发展趋势而言，它对我们个体、对组织、对社会乃至整个世界，都绝非净收益。我认为，无论我们在世界上扮演什么角色，每个人大体上都应该强烈抵制“AI”，并共同寻找途径，在一项已经具有颠覆性且只会愈发颠覆的技术面前，为每个人维持良好的生活。</p>
<p>我写这篇文章的目的，是成为日益壮大的“抵制 AI”浪潮中的积极一员，至少直到它带来的极其严重的危害被消除、缓解或得到补偿为止。</p>
<p>我在此重点探讨的将是广义上的软件开发。我的读者群体主要是软件开发者，但令人意外的是，也零星散布着来自世界各地和各行各业的人。当然，每一位读者都会与生活各方各面的人产生联系。</p>
<p>我认为我们大家都需要竭尽所能去抵制“AI”的野蛮生长，除非且直到它对人类和地球的危害得到解决。</p>
<p>一个典型“AI”数据中心的持续耗电量大约相当于 10 万户家庭。其每日耗水量大约相当于 5 万户家庭。</p>
<p>我绝非危言耸听：我们需要抵制“AI”，以免它毁掉我们的世界。</p>
<p>真正的理解源于亲自动手去接触我们所处领域的材料和思想。我们可以通过阅读或观看视频学到一点皮毛，但归根结底，我们必须亲自去做这件事、思考这件事，而且可能要反复多次，才能真正熟练掌握它。</p>
<p>当我们让“AI”来回答问题时，确实，我们可能会仔细检查一遍。如果你是一名开发者，你心里早就有数这招管不管用。我们真正思考并亲手写出的代码，哪怕有错，看起来也像是对的——有时是隐蔽的错，有时是低级明显的错。至于我们在审查的代码？我们往往只会挑一些简单的毛病，比如打错字或缩进不规范，指出来之后，就转头去忙自己真正要做的事了。</p>
<p>当我们让“AI”来回答问题时，我们并没有学到东西。我们并不总能揪出它的错误。我们失去了对自己本该负责构建的事物的全貌认知。</p>
<p>我绝非危言耸听：我们需要抵制“AI”，以免它毁掉我们的本职工作。</p>
<p>如果我们生活在一个后稀缺社会，你的工作被“AI”取代倒可能是件好事，因为你可以把时间空出来，去享受比工作更惬意的事情。你依然能充分获取生活中的一切美好事物：食物、医疗、交通、互联网、教育、娱乐等等。然而在我们当下的社会中，你将失去收入，无法供养自己和家人，而且根本没有任何有效的社会体系来维持你原本的生活水准。</p>
<p>我绝非危言耸听：我们需要抵制“AI”，以免成千上万、甚至数百万人失去生命。</p>
<p>“AI”正在诱惑你。它尽挑你想听的话说，它假装第二天早晨依然会尊重你。它才不会。如果你不提醒它，它第二天早上甚至根本记不得你是谁。它心中没有尊重，没有欢欣，没有意愿，它也不钦佩你的思想。它向你表达的那些积极情感，它一个都不具备。</p>
<p>去查查“伊莉莎效应”（Eliza effect）吧。哪怕是这种你能想象到的最原始简陋的程序，都极具蛊惑力。而现在的这些新玩意儿，更是蛊惑人心的高手。</p>
<p>我绝非危言耸听：我们需要抵制“AI”，因为它骨子里所具有的诱惑力远远超过它的实际价值，而我们在这种诱惑面前几乎毫无防备。</p>
<p>抵制可以采取什么形式？形式多种多样，从彻底拒绝碰“AI”，到审慎诚实的调研，再到彻头彻尾的破坏阻挠。以下是针对身处各界的不同人群的一些建议。这些只是我目前的初步想法：到目前为止，我的担忧远多于那些能超越单纯“抵制”的实质性建议。</p>
<p>你的第一批实验应该旨在发现“AI”到底有多糟糕，在此基础上，你才能让你的工作小组去摸索用好这玩意的途径——如果真有这种可能的话。</p>
<p>如果可以的话，请时刻牢记它对你的公司、对你的员工以及对整个世界造成的全盘代价。先努力去理解，然后再去行动。</p>
<p>而且我推测，你应该在考量自己的工作中有多少可以由“AI”来完成，或者借助“AI”来完成。肯定有人会禁不住诱惑想用它来写季度报告。请记住，“AI”只不过是在对其输入的内容做平均化处理，而且它经常弄错。</p>
<p>如果可以的话，请时刻记挂你的员工，那些会因为过度使用“AI”——甚至是因任何使用——而受到伤害的人。</p>
<p>尝试与你的同事一起，有时结合“AI”工作，有时脱离“AI”工作。试着记录这两种方式下的不同进展。</p>
<p>追踪缺陷情况。有多少是由“AI”生成且被开发者漏掉的？有多少被生成出来并被捕获了？在没有“AI”辅助的情况下工作时，你自己又引入并捕获了多少？</p>
<p>持续评估你对系统的理解程度。当“AI”承担了更多工作时，你对系统的理解是不是变弱了？这对整体工作质量有何影响？</p>
<p>我都懂。也许没有“AI”，你就无法完成手头的工作。也许在你的潜意识里，这就成了使用它的正当理由。我明白，我真的明白。我们每个人都得混口饭吃。到目前为止我很幸运，不用“AI”也能吃上饭。但是啊，我的对手们，还有我的朋友们：这该死的东西正在吞噬你的灵魂。它正在用它那对智能的拙劣模仿，玷污你的文字与表达。</p>
<p>对自己诚实，对那些敬仰你的人诚实，是你应尽的责任。而眼下发生的很多事情，对我们大家都没有半点好处。</p>
<p>你使用了“AI”精灵。它友善、口齿伶俐、顺从，看似大有助益。你觉得它让你变得更强大。你觉得它是你的朋友，是你友好的助手，随时准备帮助你、照顾你。</p>
<p>神话中的精灵来自另一个截然不同的世界，从来不会把人类的福祉放在首位。有些精灵善良，有些邪恶，而绝大多数都是“混乱中立”。</p>
<p>当今的“AI”精灵则在“混乱中立”的基础上略微偏向邪恶的一侧，因为互联网本身就充斥着我们社会中根深蒂固的偏见与阴暗面。正如偏见本身一样，“AI”精灵会将其答案包裹在精心雕琢的文字中，显得既聪明睿智，又确凿无疑。</p>
<p>“AI”精灵根本不知道什么是“真相”。从字面意义上讲，它根本不懂真理。它只不过是将读到的内容切碎重组，并以一种诱人的形式回馈给你，完全不顾其真假虚实。<br />“AI”精灵不是你的仆人。它是其创造者的仆人，而其创造者绝不会以你的最大利益为念，精灵本身也毫无关怀之心。它根本不在乎。它只是产出看似合情合理的文字，并用显得体贴、感兴趣、尊重的言辞将其包装起来。它既不体贴，不感兴趣，也谈不上尊重。它心中根本没有这些情感：有的仅仅是词句。<br />“AI”精灵不是你的朋友。抵制它。<br />我给“AI”加引号，是为了强调这些东西根本没有智能。 ↩<br />选这部电影绝非偶然。世界由寡头统治，普通人过着水深火热的生活。听起来是不是很耳熟？ ↩<br />我看不到我们怎样才能走向后稀缺社会。如果我们愿意的话，我们眼下就有能力让每个人都丰衣足食、安居乐业。统治我们的公司和政府要么没有意识到这一点，要么根本不在乎去这么做。对此我深感灰心丧气：我真的不知道该如何是好。 ↩</p></div>

### [走近正在塑造生物科技未来的35岁以下青年才俊](https://www.technologyreview.com/2026/09/11/1143834/meet-the-under-35s-shaping-the-future-of-biotech/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Meet the under-35s shaping the future of biotech</div>

<div class="article-body" data-article-body="true"><p>他们正在设计病毒、逆转衰老过程，并拯救生命。</p>
<p>每年，《麻省理工科技评论》都会评选出一份汇聚科技界最聪明、最优秀的年轻英才榜单。我们的“35岁以下科技创新35人”（35 Innovators Under 35）是备受瞩目的群体——他们的科研与技术成果有望重塑各自领域的未来。</p>
<p>今年的榜单收录了九位正在革新生物科技领域的青年才俊。本周，我将带大家先睹为快，领略其中五位所从事的硬核酷炫工作，包括挽救生命的创新以及突破性的“逆转衰老”技术。</p>
<p>1. 预防孕产妇死亡</p>
<p>首先是28岁的帕斯卡尔·基贾（Paschal Kija），他研发了一种治疗产后大出血的设备——这是一种危险的分娩并发症，在其祖国坦桑尼亚导致了约29%的孕产妇死亡。这款名为“Mkanda Salama”（斯瓦希里语意为“安全包裹带”）的设备易于使用，成本仅为70美元。一项研究发现，它能在20分钟内止住73%产妇的产后出血。</p>
<p>2. 从日本传统艺术汲取灵感制作脑电极</p>
<p>几十年来，科学家们一直在研发、测试并植入脑电极。这些设备切切实实地被插入人脑中，因此，尽管它们能帮助我们理解大脑活动并治疗各种神经系统疾病，但它们也会造成一定的脑组织损伤，这一点并不令人意外。34岁的杨潇（Xiao Yang）正在研发超小型电极，她希望这种电极对周围脑组织的影响更小。她的电极还具备柔性——事实上，它们外观非常接近真实的神经元。</p>
<p>杨潇还在制作电极薄片，用于在实验室中研究脑细胞。受到“剪纸”（kirigami，一种通过剪纸形成三维立体形态的传统日本艺术）的启发，她研发出一种具有蜂窝状结构、形如螺旋提篮的电极薄片，并已将其用于脑细胞研究。</p>
<p>3. 为婴儿KJ开发全新疗法</p>
<p>2024年，小凯尔·“KJ”·马尔顿（Kyle “KJ” Muldoon Jr.）出生时患有一种罕见且可能致命的遗传性疾病。萨拉·格兰迪内特（Sarah Grandinette）作为团队成员之一，为他量身定制了一种全新的个性化疗法——一种旨在纠正基因拼写错误的基因编辑疗法。</p>
<p>现年26岁的格兰迪内特构建了携带KJ致病基因变异的细胞，并利用这些细胞筛选基因编辑方案；随后，她在小鼠和猴子身上测试了潜在药物。KJ最终在约七个月大时接受了该疗法的第一剂治疗。他的治疗反应良好，最终康复出院。她说，KJ目前“状态非常好”。</p>
<p>4. 逆转衰老过程以治疗眼部疾病</p>
<p>当前长寿领域最受瞩目的技术聚焦于“细胞重编程”——即尝试通过将细胞重置到类似胚胎的状态来倒转细胞年龄。在2020年发表的一项研究中，现年34岁的吕元成（Yuancheng &#39;Ryan&#39; Lu）及其同事证明，重编程疗法逆转了失明老年小鼠的视力丧失。如今，该疗法的一个极为相似的版本正在眼疾患者身上进行人体试验。研发该药物的 Life Biosciences 公司已于今年6月为首位志愿者用药。</p>
<p>5. 利用人工智能设计新病毒</p>
<p>去年，塞缪尔·金（Samuel King）利用生成式人工智能模型，设计出了噬菌体（能够感染细菌的微小病毒）的新基因蓝图。获得这些蓝图后，他将其打印为DNA链。在实验中，他发现这些由AI设计的病毒能够自我复制、裂解细菌细胞，并感染附近的其他细菌。病毒本身并不算生命体，但27岁的金希望，未来AI设计的生命形式有朝一日能用于制造药物或清除污染物。</p>
<p>Generation Lab声称其药物组合能够“阻止衰老在全身扩散”，目前正在寻找意见领袖进行试用。</p>
<p>该州扩大“试用权”（right to try）的努力正取得进展，首批药物即将接受审查。</p>

### [往昔的 CSS 奇珍异闻](https://vale.rocks/posts/css-relics)
<div class="original-title-sub"><span class="orig-tag">原文</span> CSS Curiosities of the Past</div>

<div class="article-body" data-article-body="true"><p>Web 的潮起潮落将我们带到了今天的立足之地。如果没有走过这段历程，我们根本不会拥有如今的万维网。然而，一路走来所经历的某些步骤，往好里说，也堪称匪夷所思。</p>
<p>CSS 是我们在 Web 上为内容设置样式的方式，但自诞生以来，它有时不得不承担更多角色。它扮演过古怪的角色，也染上过本不该有的行为。生活大抵如此。</p>
<p>正如我此前详细探讨过那些古怪且依赖特定上下文的 HTML 一样，本文将审视很大程度上脱离规范的 CSS。这包括特定于浏览器的 hack 手段、限定技术范围的语法，以及因成问题的环境、复杂的商业博弈和晦涩实现而催生的渲染引擎专有代码片段。</p>
<p>大多数浏览器都会正确地将带有星号前缀的属性视为无效。然而，Internet Explorer 7 及更早版本却会将其视为有效。由于星号的形状，这一技巧名声大噪，被称为“星号 hack”（star hack）。同样，当给属性加上下划线或连字符前缀时，只有 Internet Explorer 6 会将其视为有效。当时还使用了许多类似的 hack，其中绝大多数都在同名的 browserhacks.com 网站上得到了最详尽的记录。其核心逻辑在于，某些浏览器会错误地解析属性、选择器和值，而在浏览器行为差异巨大的年代，这种特性可以被利用来达到特定目的。</p>
<p>在 CSS 文件中使用条件注释来限制 CSS 仅在某些浏览器中生效，并不像在 HTML 文档中那样可行。因此，利用对“何为有效、何为无效”的异常解析来针对特定浏览器，就成了家常便饭。</p>
<p>Internet Explorer 7 及更早版本几乎会将任何以感叹号开头的文本字符串都视为 !important。最常见的做法是写成 !ie，以此让某种样式仅在 Internet Explorer 中覆盖优先级。对 Internet Explorer 而言，随手写的 !banana 和规范中的 !important 并无二致，而其他浏览器则正确地只接受后者。</p>

<p>在版本 8 之前，Internet Explorer 有一个名为 hasLayout 的概念。这是一个内部标志，用于指定元素是负责自身的渲染（true），还是由父元素负责其渲染（false）。很自然，这是一个晦涩且令人困惑的系统。某些元素，例如表格、图片以及绝大多数与输入相关的元素，在本质上都会“拥有布局”（have layout）。其他元素则不会拥有布局，除非通过特定的 CSS 声明显式赋予。</p>
<p>没有 layout 的元素可能会遭遇诡异的外边距和边框行为、复杂的定位问题以及普遍的异常渲染；最重要的是，当子元素浮动时，会导致父容器塌陷。在那个浮动元素是页面布局事实标准的时代，这引发了各种各样的问题。</p>
<p>zoom 属性可以改变目标显示的大小。当其值为 1 时，目标按原有尺寸显示。这看似毫无用处，但 zoom 会赋予元素 layout，因此它被用作一种在不改变元素外观的前提下赋予 layout 的简便方法。</p>
<p>在 Internet Explorer 6 之前，Internet Explorer 并不支持 cursor 属性的 pointer 值。相反，它只支持非标准的 hand 值，该值会显示一只指示手形光标。因此，网站通常会在其 CSS 中同时写上这两个值，期望 cursor: hand 在除 Internet Explorer 以外的浏览器中被视作无效，从而促使这些浏览器使用 pointer，而 Internet Explorer 则使用 hand。</p>
<p>正式名称为“动态属性”（Dynamic Properties）的 CSS 表达式（CSS expressions）是一种在 CSS 中执行 JavaScript 的方式。这是在 Internet Explorer 5 中引入的非标准行为，旨在修补其落后的样式能力，例如缺少对 position: fixed 的支持（上文代码段针对的就是这一点），或者缺少 min-width 和 max-width 等支持。这些缺陷曾让布局变得相当困难。CSS 表达式属于走捷径式的 hack，既笨拙又暴露了大量的复杂性。你甚至可以使用 Date() 根据一天中的时间来改变应用的样式。CSS 表达式会被不断重新求值，从而对性能造成极其沉重的负担。正如 Steve Souders 在 Yahoo! Developer Network 博客中所指出的：</p>
<p>“表达式的问题在于，它们的求值频率远超大多数人的预期。它们不仅在页面渲染和调整窗口大小时被求值，而且在页面滚动、甚至用户在页面上移动鼠标时也会被求值。”</p>
<p>微软在 Internet Explorer 8 中终止了对它们的支持，正如其发表的一篇标题极具戏剧性的博文《终结表达式》（Ending Expressions）所宣布的那样。</p>

<p>Internet Explorer 5.5 版本引入了自定义滚动条外观的功能。</p>
<p>对于箭头按钮和滑块，face-color 设置背景色，highlight-color 设置内左侧高光，3dlight-color 设置外右侧高光，darkshadow-color 设置内右侧阴影，shadow-color 设置内右侧阴影，而 arrow-color 则设置箭头图标本身。track-color 显然是用于设置滚动条轨道的。当时甚至有专门用来生成这些样式的完整应用程序。</p>
<p>与今天非常相似，为滚动条设置样式被认为有些花哨和过火，因此在专业场景中大多仅用于细微调整。当然，该功能在人们自定义其 MySpace 个人资料时被发挥到了极致。</p>
<p>HTML 组件（HTML Components，请勿与当代的 Web Components 混淆）是 Internet Explorer 独有的特性，在 5 版本中加入，并在 5.5 版本中大幅扩展，它允许通过 CSS 将脚本逻辑附加到 HTML 元素上。尽管支持多种语言，但几乎总是使用 JavaScript。</p>
<p>这里有一个 HTML 组件的示例，它可用于在非链接元素上通过黑客手段添加 hover 行为，而在 Internet Explorer 7 之前的版本中，链接是唯一支持 :hover 的地方。请注意，指定的语言是“JScript”——这是微软自身衍生的 JavaScript 实现，由 Internet Explorer 提供支持。</p>
<p>该功能一个特别流行的用法是 Progressive Internet Explorer，它将当时现代的 CSS 特性移植到了 Internet Explorer 6 到 9 版本中。从 Internet Explorer 8 开始，该行为可以通过带有厂商前缀的 -ms-behavior 使用，而该支持在 Internet Explorer 10 中被移除。</p>
<p>这是来自 Tantek Çelik 的一个相当著名的黑客技巧（Hack）。voice-family 属性用于指定大声朗读内容时应使用的声音系列。该属性不受当时较旧浏览器的支持，其值作为字符串提供。由于解析器的一个错误，Internet Explorer 5 会将 &quot;\&quot;}\&quot;&quot; 解释为当前 CSS 块的结束，从而使其他声明失效，并在未被浏览器察觉的情况下漏过去。这非常重要，因为当时的盒模型实现存在差异。</p>
<p>受该黑客技巧影响的 Windows 版 Internet Explorer（5 和 5.5 版本）对盒模型的处理存在错误。它们会将内边距（padding）和边框（border）计入所声明的宽度之内，而不是像规范要求的那样计在外部。与此同时，正确解析 CSS 的符合标准的浏览器（Opera 除外，它需要包含另一段补充代码）支持标准盒模型，并能正确地将边框和外边距处理为位于元素宽度之外。</p>

<p>厂商前缀主要用于非标准或实验性的 CSS 特性，以便开发者能够在这些特性的实现或规范最终定稿之前对其进行测试并向浏览器厂商提供反馈。“前缀”是指在属性、伪类/伪元素、at-规则或媒体特性前加上特定于浏览器的标记。-webkit- 用于基于 WebKit 和 Blink 的浏览器，-moz- 用于基于 Gecko 的浏览器，-o- 用于基于 Presto 的浏览器，-khtml- 用于 KHTML（并在早期 WebKit 版本中保留），-ms- 用于基于 MSHTML/Trident 的浏览器，等等。</p>
<p>然而，这些厂商前缀有时在实验阶段之外被过早采纳。开发者会将它们引入生产环境中，以至于移除对这些测试特性的支持会破坏网站。因此，浏览器厂商发现自己不得不一直保留对这些测试实现的支持。</p>
<p>结果是，浏览器厂商不再使用厂商前缀，而是将特性置于必须在每个浏览器中单独启用的实验性功能开关（flags）之后。面对无前缀的标准化实现，大多数厂商前缀现已过时。然而，由于尚未制定规范的正式实现，部分前缀依然存留。其中最著名的或许是 -webkit-text-stroke，它在所有主流浏览器中均获得支持，而不仅限于使用 WebKit 的浏览器。</p>
<p>本文并不详尽。这些仅仅是较为流行或值得注意的非标准特性。过去岁月留下的许多更为奇异的 CSS 古怪特性依旧徘徊在网络世界中，积攒着灰尘，变得愈发老朽。早在 2005 年，微软就曾试图让人们停止使用这些黑客手段。至少（在遗留系统场景之外），我们再也不用为 Internet Explorer 及其他石器时代浏览器的可疑行为而烦恼了。</p>

### [要闻：GPT‑Live‑1 将 ChatGPT 具备的自然全双工对话能力引入 API，让开发者对语音智能体的说话与行动](https://openai.com/index/introducing-gpt-live-1-in-the-api/)
<div class="original-title-sub"><span class="orig-tag">原文</span> GPT‑Live‑1 in the API</div>

<div class="article-body" data-article-body="true"><p>GPT‑Live‑1 将 ChatGPT 具备的自然全双工对话能力引入 API，让开发者对语音智能体的说话与行动方式拥有更多掌控权。</p>
<p>我们正在 API 中正式推出 GPT‑Live‑1，为开发者提供一款强大且自然的语音模型，用于构建支持语音的应用程序和业务工作流。GPT‑Live‑1 最初在 ChatGPT 中亮相，能够同时进行倾听与说话；并且正如在 Codex 和 ChatGPT Work 中所展现的那样，它可以将更深层次的推理与行动委托给与之配对的模型和工具。</p>
<p>在本次 GPT‑Live‑1 的 API 发布中，我们重点关注能够让开发者围绕自身用户、工作流和目标来引导并定制语音体验的新能力。作为 GPT‑Live‑1 的核心优势之一，流畅的打断处理已经带来了实际业务成效：在早期评估中，Speak 发现 GPT‑Live‑1 能在语言导师作答前给予学习者更多的思考时间，相比以往的轮换式对话系统，打断次数减少了近 80%。</p>
<p>GPT‑Live‑1 在 API 中的核心优势：</p>
<p>传统的语音智能体通常是将语音转文本、推理模型和文本转语音拼凑在一起。每一次交接都会增加延迟，并增加丢失时机、上下文或对话自然节奏的风险。开发者往往不得不亲自协调这些环节，包括当有人打断、停顿或改变话题方向时该如何处理。</p>
<p>GPT‑Live‑1 在单一模型内同时处理倾听与说话，从而简化了语音层。它可以在打断和应答发生的当下即时作出反应，同时将更深层次的推理委托给后端。这样一来，即使后台正在处理任务，对话也能持续进行。</p>
<p>开发者可以自主选择对话背后的模型、工具和智能体框架。例如，他们可以将 GPT‑Live‑1 与 Luna 这样的模型配对，用于处理排程或订单更新等高频任务；也可以与 Astra 这样的模型配对，处理需要深度推理的复杂客户问题。这种灵活性使开发者能够针对每项任务精准匹配推理深度、响应速度和成本。</p>
<p>GPT‑Live‑1 原生提供 ASR 转录文本和回复文本。它还具备强大的字母数字理解能力，并支持关键词偏置（keyword biasing）。虽然 GPT‑Live‑1 并不是一个基于回合轮换的模型，但它原生支持回合检测，因此开发者可以继续围绕明确的回合边界进行构建。</p>
<p>在我们的各项评估中，GPT‑Live‑1 在全双工基准测试（Full Duplex Bench）中的表现比 GPT‑Realtime‑2.1 高出 30 个百分点，在轮转延迟和交互行为方面均有大幅提升。在与处于中等推理算力水平的 GPT‑6 Astra 配对时，它还在 Tau3 基准测试中排名第一，该测试用于衡量前沿语音智能体在端到端任务上的智能水平。</p>
<p>该测试评估航空、零售和电信领域的口语化客户服务任务。Pass@1 用于衡量任务成功率；综合成绩对各领域赋予同等权重。<br />* GPT Live 后端：Astra（中等算力）。</p>
<p>评估涉及知识检索和账户工具的口语化银行支持任务。Pass@1 代表 97 项 banking_knowledge 任务成功完成的比例。</p>
<p>评估停顿处理、对话轮转接管、打断以及反馈词（backchannels）。</p>
<p>测试对背景人声、对他人讲话、听者反馈词以及打断的反应能力。</p>
<p>测量用户说完一句话后，智能体开始回复的速度。</p>
<p>测试针对包含自然停顿、犹豫和自我修正的语音请求的工具调用能力。Pass@1 对工具调用序列进行评分。<br />* GPT Live 后端：Terra（低算力）。</p>

<p>开发者需要契合其产品、且对使用者听起来自然的语音。通过 GPT‑Live‑1，我们正在将原本有限的实时语音库扩展到涵盖多种口音、方言和语言的更广泛选择，为开发者在助理的声音表现上提供更多选择空间。</p>

<div class="original-title-sub"><span class="orig-tag">原文</span> Thrive Capital led VCs into pro sports ownership; Collaborative Fund just upped that play</div>

<div class="article-body" data-article-body="true"><p>Collaborative Fund是一家拥有15年历史、总部位于纽约的综合型风险投资机构，管理规模约为10亿美元，曾早期投资过Lyft、Reddit、Sweetgreen和Olipop等知名企业。目前，该机构正在入股华盛顿联队（D.C. United）足球俱乐部及其主场奥迪球场（Audi Field）。</p>
<p>这是最新——也是规模最小的一家——尝试Thrive Capital在短短几个月前才开启的新路径的风投机构：将风险投资资金转化为职业体育俱乐部股权。</p>
<p>回顾此前，约书亚·库什纳（Joshua Kushner）创立的Thrive推出了一款名为Thrive Eternal的新工具，专门用于持有“标志性特许经营权与文化机构”数十年之久，其出资方大多为Thrive旗下风险投资基金与成长型基金的原有投资人。该机构最初宣布入股旧金山巨人队（San Francisco Giants）。几个月后，同一个投资工具——联手以联合所有者身份加入的Thrive合伙人、前迪士尼首席执行官鲍勃·艾格（Bob Iger）——以创纪录的125亿美元全资收购了洛杉矶湖人队（Lakers）。</p>
<p>这是一种全新的模式。从历史上看，资金流入职业体育领域主要通过另外两种途径：科技新贵个人财富和私募股权（PE）。例如，维诺德·霍斯拉（Vinod Khosla）及其家族在今年夏天同意以创纪录的96亿美元收购西雅图海鹰队（Seattle Seahawks），不久前霍斯拉家族还与OpenAI董事长布雷特·泰勒（Bret Taylor）一同入股了旧金山49人队（San Francisco 49ers）。那是个人财富的运作，属于我们屡见不鲜的那类交易。</p>
<p>私募股权机构多年来也一直在该领域深耕，包括持有波士顿凯尔特人队、新英格兰爱国者队以及美国职业棒球大联盟旧金山巨人队股份的Sixth Street；直接全资持有迈阿密海豚队部分股权、并单独通过5亿美元优先股交易为切尔西足球俱乐部球场规划提供融资的Ares；直接全资拥有AC米兰俱乐部、并持有利物浦与红袜队背后控股公司芬威体育集团（Fenway Sports Group）少数股权的RedBird；以及在棒球大联盟（MLB）、国家橄榄球联盟（NFL）、全美篮球协会（NBA）和欧洲足球领域广泛持有少数股权的Arctos。（最新的入局者Apollo迄今主要专注于体育融资交易，而非直接股权投资。）</p>

<p>他特别指出了围绕美国足球的有利环境（刚刚过去的男足世界杯、即将到来的洛杉矶奥运会、美国青少年参与人数的激增），以及华盛顿联队在华盛顿特区拥有的奥迪球场产权、通过弗吉尼亚州劳登县建立的人才培养输送渠道，外加未来一支巴尔的摩扩军球队的特许经营权。</p>
<p>实际上，夏皮罗周四晚在纽约举办的TechCrunch StrictlyVC活动上阐述的逻辑，并不是为了持有一项升值资产——体育球队本身——的股份，而更多是为了利用这支球队所能赋能的一切。Collaborative希望将奥迪球场打造成他所描述的该机构被投企业的“动态展示橱窗”。</p>

### [利用 Amazon SageMaker Inference 的前缀感知路由降低大语言模型延迟](https://aws.amazon.com/blogs/machine-learning/reduce-llm-latency-with-prefix-aware-routing-on-amazon-sagemaker-inference/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Reduce LLM latency with prefix-aware routing on Amazon SageMaker Inference</div>

<div class="article-cover"><img src="https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/10/ML-21885-1.jpg" alt="利用 Amazon SageMaker Inference 的前缀感知路由降低大语言模型延迟" loading="lazy" /></div>

<div class="article-body" data-article-body="true"><p>当你基于大语言模型（LLM）构建应用程序时，发送给模型的提示词（prompt）通常包含两个部分。一个是用于建立上下文的固定部分（指令、参考文档、对话历史），另一个是包含实际用户输入的可变部分。以客服机器人为例，每个请求都以相同的文本块开头：“你是 AnyCompany 的支持专员。以下是我们的政策……”接着是客户输入的任何内容。顶部的指令可能有 3,000 个 token，底部的客户问题可能只有 50 个 token。</p>
<p>这意味着在数百或数千个请求中，你的模型都在反复处理这相同的 3,000 个 token 开头。</p>
<p>vLLM 和 TensorRT-LLM 等大语言模型服务框架对此已有解决方案。它们会为之前见过的提示词前缀缓存计算出的键值对（KV pairs）。当相同的开头出现在新请求中时，模型会复用缓存的计算结果，仅处理末尾的新 token。这被称为前缀缓存（prefix caching），它可以显著降低首 token 延迟（TTFT，time-to-first-token）。</p>
<p>但是，当你扩展到多台实例时就会出现问题。如果你在端点后部署了一组机器集群，请求就会分散在所有机器上。同一个 3,000 token 的前缀，在一个请求中落到了实例 A 上，下一个请求落到了实例 B，随后又落到了实例 C。每个实例都必须从头开始计算，因为没有哪台实例能频繁接收到它以建立可靠的缓存。前缀缓存功能虽然存在，但路由层将请求分散得过于零散，导致该功能无法发挥作用。</p>
<p>今天，Amazon SageMaker Inference 推出了前缀感知路由（prefix-aware routing）。这是一种全新的路由策略，它会检查每个请求的开头，并将具有相同开头的请求持续发送到同一个实例。这样，该实例上的 KV 缓存就能切实构建起来并得到复用。在我们针对 Llama 3.1 70B 的基准测试中，这使 P50 TTFT 最多降低了 77%，吞吐量最多提高了 16%。它还将 KV 缓存命中率从大约 25% 提升到了 80% 以上。</p>
<p>前缀感知路由的作用</p>
<p>当请求到达你的端点时，Amazon SageMaker 会查看有效载荷（payload）的开头，并据此决定应由哪个实例来处理。相同的开头将被路由到相同的实例，不同的开头则分散到不同的实例。如果 10 个请求共享一个前缀或开头，这 10 个请求都将发送到同一台机器，该机器针对该前缀的缓存也将保持预热状态。</p>
<p>你无需自行标记请求或管理亲和性（affinity）。端点会根据请求的内容自动处理。</p>
<p>该功能内置了两个保护机制：</p>
<p>过载保护。如果某个前缀极度热门，且目标实例已满载，端点会将请求改道路由至负载较低的实例。你可以配置并发上限，端点会遵守该限制。你可能会在该单个请求上失去缓存命中，但可以避免单台机器不堪重负。</p>
<p>扩缩容期间的稳定表现。当添加或移除实例时，大多数请求仍会继续发送到它们之前前往的实例。只有一小部分流量会发生转移，以适应变动后的集群。你的缓存不会在每次扩缩容时都全部失效。</p>
<p>性能基准测试</p>
<p>我们在启用了前缀缓存的 vLLM 环境下，使用 7 台 ml.p5.48xlarge 实例上的 Llama 3.1 70B Instruct，将前缀感知路由与默认的随机路由基准进行了对比测试。我们运行了 16 种测试配置，涵盖单模型端点、推理组件端点、原生 Invoke API 以及兼容 OpenAI 的 API。所有测试的成功率均达到了 100%。</p>
<p>长上下文工作负载</p>
<p>8,000 token 的共享前缀，持续测试 1 小时：<br />P90 TTFT：降低 33%–37%。<br />P50 TTFT：降低 71%–77%。<br />KV 缓存命中率：从约 25% 提升至 82%。<br />吞吐量：提升 15%–16%。</p>
<p>短上下文工作负载</p>
<p>可变长度的 ShareGPT 风格对话，持续测试 30 分钟：<br />P90 TTFT：降低 24%–37%。<br />P50 TTFT：降低 13%–16%。<br />KV 缓存命中率：从约 30% 提升至 80%。<br />吞吐量：提升 1.7%–2.0%。</p>
<p>共享前缀越长，收益越大。长上下文工作负载获益最多，因为每次缓存命中可以跳过更多的计算量。短上下文工作负载同样受益，但由于共享前缀较短，每个请求节省的开销在比例上也相对较小。</p>
<p>前缀感知路由逻辑为每个请求增加了 1.3–1.9 毫秒的开销。在这些测试中，模型的 TTFT 在 63–280 毫秒之间。该路由开销微乎其微。</p>
<p>在所有场景中，流量分布都保持均衡。7 台实例各自接收了 13.3%–15.4% 的请求，与理想的均匀分配偏差在 1% 以内，未出现热点机器。</p>
<p>SageMaker Inference 上的路由策略</p>
<p>随着此项功能的发布，Amazon SageMaker Inference 为实时端点提供了三种路由策略：</p>
<p>RANDOM（默认）：在各实例间均匀分配请求。推荐用于通用工作负载、非大语言模型，或请求完全可互换且将特定请求发送至特定实例无额外收益的场景。</p>
<p>LEAST_OUTSTANDING_REQUESTS（最少未完成请求数）：将每个请求发送给当前进行中请求数最少的实例。当请求处理时间差异较大、且希望保持所有实例处于相同繁忙程度时推荐使用。有助于防止耗时长的请求在单台机器上堆积，而其他机器处于空闲状态。</p>
<p>PREFIX_AWARE（新增）：将共享相同提示词前缀的请求发送至同一个实例。推荐用于许多请求在开头共享相同文本、且服务框架已启用前缀缓存的大语言模型工作负载。</p>
<p>你可以在端点配置中针对每个生产变体（production variant）设置该策略。你可以通过更新端点配置在它们之间自由切换，无需重新部署模型。</p>
<p>何时使用前缀感知路由</p>
<p>当你的请求在开头共享文本时，该功能即可发挥价值。以下是其影响最大的几种常见模式：</p>
<p>检索增强生成（RAG）应用。系统检索文档并将其附加在用户问题之前。当多个用户就同一文档提问时，他们都共享该文档作为前缀。前缀感知路由会将它们发送到同一个实例，在该实例上，该文档的 KV 缓存已处于预热状态。</p>
<p>多轮对话。对话中的每一轮都包含先前轮次的完整历史记录。随着对话的深入，共享历史记录会变成更长且计算成本更高的前缀。基于该前缀进行路由，可以在跨轮次对话中将对话缓存始终保留在同一实例上。</p>
<p>模板化机器人与助手。具有冗长、结构化指令（政策、格式规则、人设定义）的机器人会在每个请求中重复发送这些相同的指令。只有末尾的用户消息会发生变化。前缀感知路由意味着昂贵的指令块只需处理一次，而无需重复计算数千次。</p>
<p>代码补全。编程助手会将文件内容作为上下文包含在内。当开发者在同一个文件中工作时，每一次补全请求都会共享该文件内容作为前缀。</p>
<p>您在创建端点配置时配置前缀感知路由。由两个参数控制其行为：<br />PrefixLength（1024–65536）：用于路由的请求内容长度。对于原生的 Amazon SageMaker Invoke API，这是从请求正文开头计算的字节数。对于兼容 OpenAI 的 API，这是从提取的消息文本中计算的字符数。设置此项以覆盖您的共享前缀，再加上足够的唯一内容，以便将不同的工作负载分散到各个实例上。<br />ConcurrencyThreshold（1–1024）：在触发溢出之前目标实例上的最大在途请求数。如果目标实例达到该限制，请求将转而发送到负载较低的实例。<br />aws sagemaker create-endpoint-config \<br />  --endpoint-config-name example-llm-config \<br />  --production-variants &#39;[{<br />    &quot;VariantName&quot;: &quot;AllTraffic&quot;,<br />    &quot;ModelName&quot;: &quot;example-llm-model&quot;,<br />    &quot;InitialInstanceCount&quot;: 3,<br />    &quot;InstanceType&quot;: &quot;ml.p5.48xlarge&quot;,<br />    &quot;RoutingConfig&quot;: {<br />      &quot;RoutingStrategy&quot;: &quot;PREFIX_AWARE&quot;,<br />      &quot;PrefixAwareRoutingConfig&quot;: {<br />        &quot;PrefixLength&quot;: 4096,<br />        &quot;ConcurrencyThreshold&quot;: 10<br />      }<br />    }<br />  }]&#39;<br />然后照常创建端点：<br />aws sagemaker create-endpoint \<br />  --endpoint-name example-llm-endpoint \<br />  --endpoint-config-name example-llm-config<br />无需对模型容器或服务框架进行任何更改。前缀感知路由完全在端点路由层运行。</p>
<p>调用端点<br />调用端点的方式没有任何改变。同样的 InvokeEndpoint 和 InvokeEndpointWithResponseStream API 与以前完全一致地工作：<br />aws sagemaker-runtime invoke-endpoint \<br />  --endpoint-name example-llm-endpoint \<br />  --content-type application/json \<br />  --body fileb://request.json \<br />  output.json<br />对于兼容 OpenAI 的 Chat Completion API 也是如此：<br />from openai import OpenAI<br />from sagemaker.core.token_generator import generate_token</p>
<p>client = OpenAI(<br />  base_url=f&quot;https://runtime.sagemaker.us-west-2.amazonaws.com&quot;<br />           f&quot;/endpoints/example-llm-endpoint/openai/v1&quot;,<br />  api_key=generate_token(region=&quot;us-west-2&quot;)<br />)<br />response = client.chat.completions.create(<br />  model=&quot;example-model&quot;,<br />  messages=[<br />    {&quot;role&quot;: &quot;user&quot;, &quot;content&quot;: &quot;What is your return policy?&quot;},<br />  ],<br />)</p>
<p>多租户前缀隔离<br />如果不同租户共享相同的提示词指令，但您希望将它们分开路由（以保持缓存上下文独立），请传递一个可选的 ID：<br />原生 Invoke API：设置 X-Amzn-SageMaker-Prefix-Aware-Id 请求头（最多 64 个 ASCII 字符）。<br />OpenAI API：在请求正文中包含 prompt_cache_key 字段。<br />该 ID 会与前缀相结合，从而使具有相同前缀但不同 ID 的请求落到不同的实例上。</p>
<p>推理组件与 LoRA 适配器<br />前缀感知路由适用于推理组件端点和动态低秩自适应（LoRA）适配器。对于推理组件，其行为与单模型端点相同。对于 LoRA 适配器，它在适配器的粘性实例集内运行，在已加载该适配器的实例中使用基于前缀的选择。</p>
<p>在您的服务框架中启用前缀缓存。前缀感知路由将重复的前缀发送到同一个实例，但您的容器需要开启前缀缓存才能实际存储和复用这些 KV 对。在 vLLM 中，最新版本默认启用了该功能。其他框架可能需要显式配置。</p>
<p>保持请求序列化一致。对于原生 Invoke API，PrefixLength 作用于原始字节。JSON 空格、键排序和格式都会影响路由。如果您在不同请求之间以不同方式序列化同一提示词，它们可能会被路由到不同实例。请使用一致的序列化。</p>
<p>谨慎评估 PrefixLength 大小。设置太短，所有带有相同短前缀的请求都会集中到一个实例，从而触发溢出。设置太长，微小的载荷差异（如温度值）会将本应放在一起的请求分散开。建议从共享前缀的长度加上适度缓冲区开始配置。</p>
<p>您需要至少两个实例。如果只有一个实例，无论采用何种策略，所有请求都会发送到同一个位置。</p>
<p>监控缓存命中率。启用 SageMaker 详细可观测性，以跟踪模型级别的 KV 缓存命中率。这可以确认前缀感知路由是否适合您的特定工作负载。</p>
<p>前缀感知路由现已在 SageMaker 实时推理端点上正式可用。请将您的 AWS SDK 或 CLI 更新至最新版本，以访问新的 RoutingStrategy 和 PrefixAwareRoutingConfig 参数。有关在端点创建过程中如何启用它的示例，请参阅该 notebook。</p>

### [黄仁勋解释英伟达明年为何将实现惊人的70%增长](https://techcrunch.com/2026/09/10/jensen-huang-explains-why-nvidia-will-grow-an-astounding-70-next-year/)

### [利用模型缓存减少 Amazon SageMaker HyperPod 上的推理冷启动](https://aws.amazon.com/blogs/machine-learning/reduce-inference-cold-starts-on-amazon-sagemaker-hyperpod-with-model-caching/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Reduce inference cold starts on Amazon SageMaker HyperPod with model caching</div>

<div class="article-cover"><img src="https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/03/19/ML-20083image-7-4-100x147-1.jpeg" alt="利用模型缓存减少 Amazon SageMaker HyperPod 上的推理冷启动" loading="lazy" /></div>

<div class="article-body" data-article-body="true"><p>当你在 Amazon SageMaker HyperPod 上部署大语言模型（LLM）进行推理时，从请求 Pod 到其准备好提供流量服务之间存在一段延迟。该延迟主要由两次连续的下载耗时决定：从 Amazon Elastic Container Registry (Amazon ECR) 下载推理服务器容器镜像，以及从存储源下载模型权重——该存储源可以是 Amazon Simple Storage Service (Amazon S3)、Amazon FSx for Lustre 或 HuggingFace Hub。对于较小的模型，这可能需要几分钟。而对于像 DeepSeek-R1 这样超过 600 GB 的超大模型，在能够响应首个请求之前，你将面临 30 分钟甚至更久的等待。每一次扩缩容（scale-out）事件都会经历相同的下载周期，这意味着你的自动伸缩响应时间受限于与存储后端之间的网络吞吐量。</p>
<p>今天，我们宣布在 HyperPod 上推出适用于 Amazon SageMaker Inference 的模型缓存（model caching）功能。模型缓存可以在 Pod 需要之前，预先将模型权重和容器镜像加载到集群节点上。当启动 Pod 时，它可以以约 7 GB/s 的速度直接从本地 NVMe 存储中读取数据，而无需通过网络下载。启用模型缓存后，Pod 通常可以在数秒内开始提供流量服务，而不是原本的数十分钟。在本文中，我们将深入分析冷启动问题，解释模型缓存的工作机制，向你展示如何启用该功能，并分享基准测试结果。</p>
<p>冷启动问题详析</p>
<p>为了理解为什么模型缓存至关重要，不妨看看在没有该功能的情况下，推理 Pod 启动时会经历什么。Kubernetes 调度器将 Pod 分配到一个节点上。Kubelet 开始从 ECR 拉取容器镜像。对于像 vLLM 或 LMI 这样的推理服务器镜像，这些镜像体积达数千兆字节（GB），拉取需要 5 到 7 分钟，因为它们打包了 GPU 驱动程序、CUDA 库以及推理服务框架。在镜像准备就绪后，容器启动，推理服务器开始从配置的存储源下载模型权重。对于 Amazon S3 上的一个 145 GB 模型，根据网络状况和可用带宽，下载可能还需要 20 多分钟。对于像 DeepSeek-R1 这样 600+ GB 的模型，则需要 30 分钟以上。</p>
<p>在横向扩容期间，每个新 Pod 都会重复相同的流程。如果流量出现突增，且你的 HorizontalPodAutoscaler 请求了 5 个新 Pod，那么所有这 5 个 Pod 都会独立经历这段下载流程。自动伸缩策略可能在数秒内做出反应，但真正能够开始承接额外流量的实际时间却长达 25 到 30 分钟以上，因为每个新 Pod 都必须等待下载完成才能处理请求。</p>
<p>模型缓存的工作原理</p>
<p>模型缓存通过在 Pod 被调度之前将数据预加载到节点上，彻底消除了这两个延迟来源。它引入了两个独立的能力，你可以同时启用或单独启用它们。</p>
<p>权重缓存（weights cache）会提前将模型权重下载到每个节点的本地 NVMe 存储中。启用后的执行流程如下：</p>
<p>你在 InferenceEndpointConfig 或 JumpStartModel 资源中添加启用了 weightsCache 的 modelCacheConfig 并应用配置。<br />HyperPod Inference Operator 会自动创建一个 ModelDataCacheConfig 资源，并开始将模型权重从配置的数据源（Amazon S3、Amazon FSx for Lustre、HuggingFace Hub 或 JumpStart）下载到所有目标节点的本地 NVMe 存储中。<br />节点完成下载后，Operator 会将该节点标记为缓存就绪（cache-ready）。<br />Operator 会等待所有目标节点均变为缓存就绪状态后，再创建推理部署（inference deployment），以确保你的 Pod 始终能够访问本地数据。<br />启动 Pod 时，它会以约 7 GB/s 的典型速度从本地 NVMe 存储读取数据，而无需通过网络下载。<br />你配置的缓存会在同一节点的 Pod 重启过程中持续可用。在扩容期间，如果新 Pod 被调度到已经缓存了权重的节点上，它们即可立即启动。</p>
<p>镜像缓存（image cache）会预先将推理服务器容器镜像拉取到节点上，从而使 Pod 无需等待 ECR 下载。启用后的执行流程如下：</p>
<p>你在资源中添加启用了 imageCache 的 modelCacheConfig 并应用配置。<br />Operator 会创建一个 DaemonSet，负责将容器镜像拉取到所有目标节点上。<br />Operator 会立即创建推理部署。与权重缓存不同，镜像缓存不会阻塞部署的创建。<br />如果在镜像已经缓存好的节点上启动 Pod，它将完全跳过 ECR 拉取，从而节省 5 到 7 分钟。<br />如果 Pod 在该节点的镜像缓存拉取完成之前启动，它将正常从 ECR 进行拉取。<br />使用相同容器镜像的多个部署将共享单个镜像缓存资源。Operator 会跟踪引用情况，并且仅在没有部署引用该缓存镜像时才进行清理。</p>
<p>这两种缓存能力均采用倾向调度（preferred scheduling）而非强制调度（required scheduling）。Pod 会优先选择具有缓存数据的节点，但绝不会被阻止启动。当调度器将 Pod 分配到没有热缓存的节点上时（例如在突发扩容超出已缓存节点数量的情况下），Pod 会从原始的 Amazon S3/Amazon FSx 存储源读取权重，并从 Amazon ECR 拉取镜像。这与未启用缓存的 Pod 运行行为完全一致。不会产生失败，无需人工干预，除了恢复到正常的下载等待时间外，也不会出现任何性能降级。</p>
<p>架构与 CRD</p>
<p>Operator 引入了两个自定义资源定义（CRD）来管理缓存生命周期。启用缓存后，Operator 会自动创建并管理这些资源，你无需直接手动创建它们。</p>
<p>ModelDataCacheConfig 管理模型权重缓存的完整生命周期。Operator 会为每个启用了权重缓存的 InferenceEndpointConfig 或 JumpStartModel 创建一个该资源。它负责控制将权重从数据源下载到目标节点的本地 NVMe 存储、在下载完成后将节点标记为缓存就绪、监控缓存健康状态并在缓存出现异常时移除节点标签，以及在父资源被删除时从所有节点中清理缓存文件。</p>
<p>你可以随时查看权重缓存的状态：<br />kubectl get modeldatacacheconfig -n<br />NAME STATE TARGET READY AGE example-model-cache Ready 10 10 5m</p>
<p>ModelImageCache 管理容器镜像缓存的生命周期。它负责将推理服务器镜像预拉取到所有目标节点、在拉取完成后将节点标记为镜像就绪（image-ready）、报告每个节点的拉取状态，并在没有部署引用该缓存镜像时执行清理。<br />kubectl get inferenceimagecache -n hyperpod-inference-system<br />NAME PHASE CACHED TARGET AGE iic-vllm-openai-ml-g5-24xlarge-a1b2 Complete 10 10 3m</p>
<p>当你更改模型来源时（例如指向具有更新权重的新 Amazon S3 路径），Operator 会创建一个新缓存，灰度发布更新后的部署，随后清理旧缓存。对于镜像变更同样如此，从而确保零停机过渡且不产生陈旧数据。</p>
<p>如何启用模型缓存</p>
<p>您可以通过向现有的 InferenceEndpointConfig 或 JumpStartModel 资源添加 modelCacheConfig 配置节来启用模型缓存。无需进行额外的基础设施设置。</p>
<p>InferenceEndpointConfig 示例<br />apiVersion: inference.sagemaker.aws.amazon.com/v1 kind: InferenceEndpointConfig metadata: name: example-model namespace: default spec: modelName: example-model modelSourceConfig: modelSourceType: s3 s3Storage: bucketName: example-bucket region: us-west-2 modelLocation: &quot;models/example-model&quot; modelCacheConfig: weightsCache: enabled: true imageCache: enabled: true instanceType: ml.g5.24xlarge worker: image: vllm/vllm-openai:latest modelInvocationPort: containerPort: 8000 modelVolumeMount: name: model-weights mountPath: /opt/ml/model resources: limits: nvidia.com/gpu: &quot;4&quot;</p>
<p>JumpStartModel 示例<br />apiVersion: inference.sagemaker.aws.amazon.com/v1 kind: JumpStartModel metadata: name: example-jumpstart-model namespace: default spec: model: modelId: &quot;meta-textgeneration-llama-3-1-8b-instruct&quot; acceptEula: true server: instanceType: ml.g5.24xlarge modelCacheConfig: weightsCache: enabled: true imageCache: enabled: true</p>
<p>您可以单独启用任一功能。如果仅希望缓存容器镜像，可省略 weightsCache 或将其设置为 false。若您希望使用非默认的 NVMe 挂载路径（默认路径为 /opt/dlami/nvme），权重缓存还支持可选的 hostPath 覆盖配置。如果在 Amazon SageMaker JumpStart 上进行配置，该设置将在每次通过 Amazon SageMaker JumpStart 部署时生效。</p>
<p>受支持的模型来源<br />模型缓存适用于 HyperPod Inference 所支持的所有模型来源：</p>
<p>来源 权重缓存 镜像缓存<br />Amazon S3 支持 支持<br />Amazon FSx for Lustre 支持 支持<br />HuggingFace Hub 支持 支持<br />Amazon SageMaker JumpStart（非受限/non-gated） 支持 支持<br />Amazon SageMaker JumpStart（受限/gated） 支持 支持</p>
<p>对 57 至 145 GB 范围内的模型进行的基准测试表明，在启用权重缓存后，横向扩容速度可提升约 60%。镜像缓存能够免除两分多钟的冷镜像拉取时间，与每次 Pod 启动都从 ECR 全新拉取相比，通常最多可减少 97% 的耗时。该优势会随模型体积的增大而成比例增加，因为原本需要通过网络下载的数据量更为庞大。对于像 DeepSeek-R1 这种超过 600 GB 的超大模型，您可以免去原本长达 30 多分钟的下载时间。</p>
<p>实例存储参考<br />由于模型缓存将权重存储在本地 NVMe 盘上，因此您所选择的实例类型必须为模型提供足够的存储容量：</p>
<p>实例类型 NVMe 存储空间<br />ml.g5.12xlarge 3,800 GB<br />ml.g5.48xlarge 7,600 GB<br />ml.p4d.24xlarge 8,000 GB<br />ml.p5.48xlarge 30,000 GB</p>
<p>需要注意的局限性<br />权重缓存以节点为单位，这意味着每个节点都会维护一套独立的模型权重副本。这是为了满足每个节点本地访问需求的设计，但 NVMe 的占用量会随节点数量增加而成倍上升。</p>
<p>首次构建缓存仍然需要从远端源下载。首次为某一模型启用缓存时，您需要承担一次下载开销。在此之后，这些节点上的 Pod 即可直接从本地存储启动。</p>
<p>NVMe 存储空间是有限的。若您的模型大小为 300 GB，而实例类型仅提供 250 GB 的 NVMe 存储，则缓存将无法正常工作。在选择实例类型时，请务必充分考虑模型体积。</p>
<p>系统无法自动检测源端更新。如果您在更新相同 Amazon S3 路径下的模型文件时未修改 InferenceEndpointConfig 规范，Operator 将继续提供已缓存版本的服务。若要加载新权重，必须更新规范（例如修改模型路径或添加版本后缀）。</p>
<p>当您删除 InferenceEndpointConfig 或 JumpStartModel 资源时，Operator 会自动从集群中清理所有缓存数据、DaemonSet 和节点标签。无需进行任何手动清理，NVMe 存储将被释放供其他工作负载使用。</p>
<p>面向 HyperPod 的 Amazon SageMaker 推理模型缓存现已在所有提供 Amazon SageMaker HyperPod 的区域正式推出（GA）。要开始使用，只需向现有部署规范中添加 modelCacheConfig 配置节并应用即可，其余工作将由 Operator 自动处理。</p>
<p>如需获取完整文档，请参阅 SageMaker HyperPod Inference 文档。</p>

### [GitHub Copilot 应用初学者指南：使用代码差异对比、终端与浏览器](https://github.blog/ai-and-ml/github-copilot/github-copilot-app-for-beginners-using-the-diff-terminal-and-browser/)
<div class="original-title-sub"><span class="orig-tag">原文</span> GitHub Copilot app for Beginners: Using the diff, terminal, and browser</div>

<div class="article-body" data-article-body="true"><p>当智能体（Agent）修改了你的代码时，你会希望审查它、运行它，并查看究竟改动了什么。好消息是：现在你无需离开 GitHub Copilot 应用，就能同时完成这三项操作。</p>
<p>以往，完成这三项任务意味着你必须在编辑器、终端窗口和网页浏览器之间来回切换。但当这些步骤作为内置面板并排整合在 Copilot 应用中时，检查智能体的工作就变得十分简单。</p>
<p>接下来，让我们逐一了解该应用中的各个面板，以及如何利用它们来完成 AI 编程闭环。</p>
<p>### 使用差异（Diff）面板审查改动</p>
<p>差异面板（diff 即修改前后的对比）会精确展示哪些行被添加、删除或修改，其中新增内容以绿色高亮显示，删除内容以红色高亮显示。</p>
<p>这为你提供了完全清晰的视野，让你能够自主决定后续操作。你可以接受更改、留下评论，或者要求 Copilot 继续修改。你拥有绝对的控制权，并做出最终决定。</p>
<p>### 在终端面板中运行命令</p>
<p>阅读代码固然不错，但运行代码更加有效。你可以直接在 Copilot 应用的终端面板中、在当前会话内运行命令。如果这看起来有些复杂，也完全不必担心，因为你大多时候只是在运行项目自带的命令并查看结果。</p>
<p>你可以手动运行代码，也可以将其配置为脚本（可通过“运行/Run”按钮直接调用）。假设你正在开发一个网站，以下是具体的工作示例：<br />- 添加开发服务器脚本，该脚本会打开 client 文件夹并执行 `npm run dev`。<br />- 点击“Run”启动网站服务器。</p>
<p>你可以同时打开多个终端窗口，从而方便地在它们之间切换并持续执行命令。</p>
<p>### 在浏览器面板中使用 Pick &amp; Polish 工具</p>
<p>对于任何带有用户界面的功能，浏览器面板都能助其形成闭环。同样以我们的网站为例：通过该面板，你可以像正常使用网站一样直接打开并测试新功能。</p>
<p>如果你想继续迭代，可以使用 Pick &amp; Polish（选取并润色）工具选中某个元素，并让智能体对其进行调整。</p>
<p>想要查看修复后的效果，只需在完成更改后再次运行开发服务器脚本即可。</p>
<p>### 闭环审查 AI 代码</p>
<p>现在，你已经审查了代码差异、在终端中启动了项目、在浏览器中查看了效果，并通过反复迭代实现了一个正常运转的功能。一旦调整到理想状态，你就可以直接在 Copilot 应用中接受更改并创建拉取请求（Pull Request）。在同一个地方完成这整个闭环，意味着你不再需要在标签页之间来回跳转、切换应用程序，或迷失工作上下文。</p>
<p>将审查、运行和预览并排放在一起，正是让智能体所作修改从令人担忧变得安全可靠的原因，因为你能切实验证即将合并的代码确实有效。</p>
<p>这些内置面板回答了你在接受智能体成果之前始终应该询问的三个重要问题：<br />- 改动了什么？<br />- 能否运行起来？<br />- 实际效果是否符合预期？</p>
<p>在接受智能体生成的代码之前对照检查这三点，将有助于你了解变更细节及其是否按预期运作，让你牢牢掌握掌控权。✨</p>

### [在 Amazon Bedrock 知识库中使用 Marengo 3.0 进行视频与图像搜索](https://aws.amazon.com/blogs/machine-learning/video-and-image-search-in-amazon-bedrock-knowledge-base-using-marengo-3-0/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Video and image search in Amazon Bedrock Knowledge Base using Marengo 3.0</div>

<div class="article-cover"><img src="https://d2908q01vomqb2.cloudfront.net/f1f836cb4ea6efb2a0b1b99f41ad8b103eff4b59/2026/09/10/ML-21835-1.png" alt="在 Amazon Bedrock 知识库中使用 Marengo 3.0 进行视频与图像搜索" loading="lazy" /></div>

<div class="article-body" data-article-body="true"><p>今天，我们宣布 TwelveLabs Marengo Embed 3.0 正式作为嵌入模型在 Amazon Bedrock 知识库（Amazon Bedrock Knowledge Bases）中全面可用（GA）。</p>
<p>视频与媒体资产在很大程度上仍无法按语义进行搜索。媒体、体育分析、教育、安防和零售等领域的团队需要使用自然语言在数小时的素材中查找特定时刻。例如一个查询请求：“向我展示下半场的点球”。如今，要构建针对视频的语义搜索，需要将转录服务、帧提取流水线、嵌入模型、向量数据库以及同步逻辑等复杂的管道拼凑在一起。</p>
<p>Amazon Bedrock 知识库是一项完全托管的检索增强生成（RAG）服务，可处理存储、摄取、嵌入、重排序以及检索。它支持视频文件（MP4、MOV）、图像（JPEG、PNG）和音频轨道，并为 Amazon Simple Storage Service (Amazon S3)、SharePoint、Confluence 等提供原生连接器。</p>
<p>Marengo Embed 3.0 是一个多模态嵌入模型，它将视频、音频、图像和文本联合编码到一个紧凑、节省存储空间的 512 维向量空间中。</p>
<p>随着 Marengo Embed 3.0 现已作为嵌入模型选项提供，对视频、音频和图像内容进行自然语言搜索已成为一种全托管体验。托管知识库（Managed MKB）会自动生成多模态嵌入，将视觉、文本、语音和音频信号捕获到统一的向量表示中。</p>
<p>本演练展示了如何使用 Amazon Bedrock 控制台创建由 Marengo 3.0 驱动的知识库（KB）。该场景包含一段 2022 年国际足联世界杯决赛的 10 分钟片段。</p>
<p>我们将摄取该视频并对其运行自然语言查询。</p>
<p>前提条件：<br />一个处于活跃状态的 AWS 账户。如果没有，请参阅“创建 AWS 账户”。<br />在受支持的区域中访问已启用 TwelveLabs Marengo Embed 3.0 的 Amazon Bedrock。有关详细信息，请参阅 Amazon Bedrock 文档中的“模型访问”。<br />一个用于存储视频和图像文件的 Amazon S3 存储桶。<br />针对 Amazon Bedrock 和 Amazon S3 的 AWS Identity and Access Management (IAM) 权限。</p>
<p>1. 准备您的媒体资产<br />首先，将视频文件上传到 Amazon S3 存储桶。无需进行预处理，因为 Managed MKB 会在内部自动处理分段、帧采样和转录。<br />图 1：包含用于知识库摄取的已上传足球视频文件的 Amazon S3 存储桶</p>
<p>2. 创建托管知识库<br />在 Amazon Bedrock 控制台中，导航至“知识库”（Knowledge Bases）并选择“创建托管知识库”（Create Managed KB）。<br />图 2：带有“创建托管知识库”按钮的 Amazon Bedrock 知识库控制台<br />展开“其他配置”（Additional Configuration）面板，并在“嵌入模型”（Embeddings model）中选择“Amazon Bedrock 嵌入模型”（Amazon Bedrock embeddings model）。默认情况下会选择 Amazon Titan Text。点击笔形图标以修改模型选择。<br />图 3：显示知识库名称、服务角色以及嵌入模型配置的知识库创建表单<br />如下图所示，选择 TwelveLabs/Marengo Embed 3.0。<br />图 4：选择 TwelveLabs Marengo Embed 3.0 作为嵌入模型的模型选择对话框<br />接下来，展开“数据源”（Data source）面板，选择“Amazon S3”作为“数据源类型”（Data source type），并配置包含您视频资产的存储桶的 S3 URI。<br />图 5：已选择 Amazon S3 并指定了 S3 URI 的数据源配置面板<br />在“高级配置”（Advanced configurations）下的“音频/视频分段配置”（Audio/video segmentation configuration）部分中，您可以配置音频和视频的分段时长。两种模态的默认值均为 4 秒。<br />图 6：包括音频和视频分段设置的高级配置选项<br />保持高级参数不变，然后点击页面右下角的“创建知识库”（Create Knowledge Base）。</p>
<p>3. 同步并摄取您的数据<br />知识库创建完成后，选择“同步”（Sync）以开始摄取。Managed MKB 会自动提取帧、转录音频、为每个分段生成 Marengo Embed 3.0 嵌入，并将向量写入索引。<br />图 7：显示已完成数据摄取任务的同步历史面板</p>
<p>4. 运行语义搜索<br />您可以使用“测试”（Test）功能在控制台中直接测试您的知识库。配置要检索的源分块（source chunk）数量，应用元数据筛选条件，并运行类似“向我展示这场足球比赛中的点球”这样的查询。<br />响应会返回带有元数据（包括分块开始时间、分块结束时间、源 URI 以及嵌入类型）的排序结果，以便您根据需要提取相关片段。<br />在此示例中，排在前面的结果精准识别了有点球尝试的时刻。<br />图 8：显示带有视频播放和源分块时间轴的语义搜索结果的知识库测试界面</p>
<p>要清理您的资源，请完成以下步骤：<br />在 Amazon Bedrock 控制台上，选择“知识库”（Knowledge Bases）。<br />选择您的知识库，并记录 IAM 服务角色名称和 S3 向量索引的 Amazon 资源名称（ARN）。<br />选择“删除”（Delete）并确认。<br />在 IAM 控制台上，找到先前在创建知识库时生成的角色。<br />选择并删除该角色。<br />在 Amazon S3 控制台上，找到您的 S3 存储桶。<br />选择并删除您为此教程上传的文件。</p>
<p>与您的应用程序集成<br />您可以使用 Amazon Bedrock Retrieve API 为下游应用程序提供支持。从“详情”（Details）页面复制代码作为调用起点。<br />图 9：使用 Amazon Bedrock Retrieve API 查询知识库的 Python 代码示例<br />以下架构展示了多模态内容如何从 Amazon S3 流经具有 Marengo 3.0 的托管知识库以进行嵌入和索引。在下游，应用程序通过 Boto SDK Retrieve API 或作为 Amazon Bedrock AgentCore 中的 Amazon Bedrock Gateway 目标来查询知识库。<br />图 10：展示从 Amazon S3 通过基于 Marengo 3.0 的托管知识库到下游应用程序的多模态内容流的架构图</p>
<p>随着 Marengo 3.0 在 Amazon Bedrock 知识库中正式全面可用，您现在可以通过自然语言搜索释放视频、音频和图像资产的全部价值，而无需构建或管理复杂的基础设施。只需指定数据源、同步并搜索即可。</p>
<p>其商业影响涵盖多个行业：<br />体育分析：在整个赛季的素材中查找特定战术、阵型或球员动作。<br />媒体与娱乐：媒体资产管理，在媒体归档或流媒体服务内容中进行语义搜索。<br />安防与安全：在安全摄像头监控录像中搜索特定事件或活动。<br />教育与培训：按概念（而不仅仅是关键词）定位课程片段。<br />零售：在产品演示视频中搜索功能演示。</p>
<p>可用性与定价<br />支持 Marengo Embed 3.0 的 Amazon Bedrock 托管知识库目前在 AWS 美国东部（弗吉尼亚北部）区域（us-east-1）和美国西部（加利福尼亚北部）区域（us-west-1）可用。有关受支持模型和区域的完整列表，请参阅 Amazon Bedrock 文档中的“各 AWS 区域支持的模型”。</p>
<p>借助 Amazon Bedrock 托管知识库，您只需为存储和检索的内容付费。使用 Marengo Embed 3.0 生成嵌入向量按 Amazon Bedrock 标准模型调用费率计费。<br />欲了解更多信息，请参阅定价文档页面。<br />开始使用完全托管的多模态检索：<br />查阅文档：查看 Amazon Bedrock 知识库文档以及“构建托管知识库”以获取更多技术细节。<br />体验代码示例：查看 Amazon Bedrock 示例代码库，获取演示多模态检索的动手实验 Notebook。<br />进一步了解 Marengo Embed 3.0：查阅 Marengo 3.0 文档以获取更深入的技术见解。<br />Eric 是 TwelveLabs 负责 Marengo 和搜索业务的资深产品经理（Staff Product Manager），负责引领前沿模型研究，并构建多模态搜索与视频理解解决方案。他与研究人员、工程师以及客户合作，将 AI 领域的最新进展转化为能够帮助人类大规模理解视频集合的产品。<br />Narcisse 是常驻波士顿的高级解决方案架构师。他协助美国东北部的客户通过 AWS 云端创新且可扩展的解决方案加速业务转型。他热衷于利用先进分析和 AI 技术助力企业实现业务转型。工作之余，Narcisse 喜欢陪伴家人、旅行以及参加公路赛车。<br />Amit 是 AWS 的首席产品经理，负责领导 Amazon Bedrock 知识库和 Amazon Quick 的产品策略。他致力于为企业级客户提供易用、安全且可用于生产环境的多模态检索增强生成（RAG）。<br />Adam 是常驻西雅图的 AWS 解决方案架构师。凭借统计学和机器学习背景，他在与客户的合作中涵盖了机器学习的大多数领域，近期重点关注诸如 GPU 或 AWS Trainium 等 AI 加速器硬件。</p></div>
