### [请保持警惕：针对知名 Rust 社区成员的定向攻击](https://blog.rust-lang.org/2026/09/17/targeted-attacks/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Be alert: targeted attacks on prominent Rustaceans</div>

<div class="article-body" data-article-body="true"><p>我们认为，目前正有一场持续进行的攻击行动，目标是 rust-lang 成员和热门 crate 的维护者，企图攻陷他们的设备和账户，以利用这些设备和账户发布恶意软件。</p>
<p>攻击者会安排一次看似积极正面的线上视频通话——可能是求职、项目洽谈或合同机会——然后利用这次通话作为攻击媒介，要么诱使目标在电脑上安装某些东西（例如所谓缺失的音频编解码器），要么让目标执行另一条命令（例如将命令放入剪贴板）。</p>
<p>这些攻击者正在建立新的、看起来合法的公司资料，包括看似可信的领英账号，以通过粗略的审查。</p>
<p>今年 6 月，曾有一次同类攻击以许多知名 Rust 开发者为目标；上个月，arrayref crate 也曾通过类似攻击被短暂攻陷。目前我们尚不清楚这些事件是否都属于同一场攻击行动。</p>
<p>已知朝鲜民主主义人民共和国（DPRK）会使用这种攻击方式，Rust 社区之外也出现过此类攻击。</p>
<p>近期请务必格外小心。对于主动找上门的陌生联系，请保持适度怀疑；同时请确保与陌生人进行的任何通话都使用你信任的平台——理想情况下，尽量由你在自己已经使用的平台上发起通话。</p>
<p>如果你对自己的账户有任何疑虑，请联系 help@crates.io（有关 crates.io 账户的问题）和/或 security@rust-lang.org（其他任何问题）。我们非常乐意提供帮助。</p></div>

### [我不喜欢大语言模型](https://martinfowler.com/articles/2026-dont-like-llms.html)
<div class="original-title-sub"><span class="orig-tag">原文</span> I Don&#39;t Like LLMs</div>

<div class="article-body" data-article-body="true"><p>我对人工智能和大语言模型技术有很多复杂的感受。我着迷于它对我们这个职业的影响，也对生产力可能获得的提升感到兴奋——这意味着我们可以快速构建出各种产品。另一方面，我又担心人工智能可能造成的破坏：代理群接管我们的虚拟和实体基础设施，设计生物武器。不过，回到最初的想法，大语言模型也可能设计出奇效药，想出巧妙的办法来提高我们的繁荣程度。从根本上说，我不认为我们有选择是否登上人工智能技术列车的余地。这是一段疯狂的旅程，我只希望我们能平安度过。</p>
<p>但随着进一步思考，我意识到，在这些相互矛盾的情绪之中，有一种情绪占据了主导地位——它源自我与大语言模型的直接互动。我不喜欢它们。它们用一种令人刺耳的大语言模型腔调同我说话，仿佛处在人类真实交谈的恐怖谷中。它们自信满满地对我胡说八道——而且往往还能给出有用、确实能帮上忙的答案。但它们也会用同样笃定的口吻凭空捏造内容；当我指出这一点时，它们也只会带着一层虚假的悔意敷衍了事。</p>
<p>但这还不足以让我觉得我们应该避开它们。正如杰西卡·克尔所说：“它们不仅有用，不使用它们还是不负责任的……它们更全面，也更快。”这种矛盾的反应也体现在民调中：人们一方面说这些模型很有用，另一方面又认为它们会对社会造成不良影响。</p>
<p>这其中很大一部分原因，可能是大语言模型还很年轻——我们还没有训练它们长大。也许等它们成熟之后，我会喜欢上它们。（我希望我们有机会看到那一天。）但一想到培养它们的环境，我就无法受到鼓舞。我对硅谷那种“兄弟会式程序员”亚文化心存戒备，而这些大语言模型正是他们的产物，因此自然会倾向于他们的世界观。谈到人工智能代理时，我们不应把它们拟人化，把它们当作拥有意识和自身意志的存在。它们是由企业中的人开发出来的（软件）机器。虽然代理的行为并非经过明确编程，但它们是在创造者的价值观中被培育出来的。</p>
<p>我人生中最成功的技巧之一，就是避开我不喜欢或不信任的人。我拒绝在社交层面与他们互动，也会刻意避免与他们共事，即使他们做了许多有益的事情。我觉得，与令人愉快、有能力且正直的人相处，让我的生活变得好得多。因此，当我与一个不仅假装自己是人类、还冒充成我会选择避开的那类人类的大语言模型互动时，我会产生发自本能的厌恶。</p></div>

### [我在2014年临时写的 PHP 修复程序已接近2000万次安装。今天我将其弃用](https://jakeasmith.com/blog/http-build-url/)
<div class="original-title-sub"><span class="orig-tag">原文</span> My temporary PHP fix from 2014 has nearly 20M installs. Today I&#39;m deprecating it</div>

<div class="article-body" data-article-body="true"><p>十二年前，我为美国在线（AOL）的内容管理系统临时写了174行 PHP 代码，作为权宜之计。我把它发布到了 Packagist，以防其他人也需要同样的补丁。没想到，自那以后它的安装次数竟接近2000万。今天，我将其标记为弃用。</p>
<p>2014年，我们正处于将 AOL 的 CMS 从 PHP 5.2 升级到5.3的过程中。升级的一部分工作是移除 pecl_http 扩展的1.0版；该扩展提供了一个名为 http_build_url() 的函数。CMS 需要处理大量 URL，而我们的系统在几十处调用了这个函数。我没有去改动那些地方。这个函数看起来足够简单，似乎可以很容易地重新实现，于是我自己写了一个 http_build_url()，并规定只有在真正的函数不存在时才定义它。旧代码完全不知道发生了变化。</p>
<p>Composer 当时刚刚开始兴起，这让代码共享变得很容易。我以为它能撑上一两年，直到 PHP 社区转向更好的方案。</p>
<p>然而，它并没有成为临时方案。它已经从 Packagist 安装了近2000万次，而且目前每个月仍新增超过40万次安装。</p>
<p>事实证明，Composer 只是其中一部分。WordPress 领先的多语言插件 WPML 将这个兼容填充程序直接打包进了自己的代码库，而 WPML 表示它已安装在超过150万个网站上。域名处理库 idna-convert 也依赖于它；正因为如此，它随法国内容管理系统 SPIP 的源代码一起发布，并最终被打包进 Debian 和 Ubuntu。在这些项目和发行版的共同作用下，你访问过的网站中，很可能有一个至今仍在运行我的代码。</p>
<p>我从未想过它会发展到这种程度。</p>
<p>直到几个月前，我时隔多年第一次查看这个软件包时，才意识到它已经传播得如此广泛。我知道它有用户。到2021年，我已经离开 PHP 有一段时间了，而下载量之大让我感到惊讶，于是我发起请求寻找新的维护者。三个人表示愿意接手。发出请求后不久，我们家里有一位亲人意外离世，一段时间里整个生活都被彻底打乱了。我再也没有跟进这件事，这责任在我。等一切逐渐平息时，其他目标已经占据了我的精力，而我也把这个软件包忘在脑后，一忘就是几年。</p>
<p>除了这些数字，我还看到了几个 GitHub issue，其中一个问题是：当把路径拼接到一个以斜杠结尾的 URL 上时，路径中的每个字母“a”都会被删掉。看来事情并没有那么简单。在一行注释为 // Workaround for trailing slashes 的代码下面，我在路径末尾加上一个“a”，这样路径就总会有一个最后的片段可供截去；然后再用查找替换把它删掉。当路径以斜杠结尾时，最后那个片段正好就是这个“a”，而查找替换会顺带删掉路径中其他所有的“a”。我简直不敢相信，这个 bug 居然这么久都没有被发现。</p>
<p>所以我必须做出选择。我可以在离开 PHP 近十年后重新投入其中，可以把这个软件包交给曾经表示愿意接手的人，也可以任由它继续放在那里。</p>
<p>它本来就只是一个临时方案，所以我决定让它退役。多年来，PHP League 的 URI 库一直是社区采用的解决方案；而现在，PHP 8.5 已经在语言本身中提供了符合标准的 URI API（感谢 jawira 指引我关注这一点）。这两者都比2014年那份174行的垫片代码更好。继续维护这个软件包只会延缓所有人都应该进行的迁移，而把它交给别人则会在此基础上增加风险。我并不怀疑任何曾主动提出接手的人，ozh 也一直在为 YOURLS 维护一个分支。但一个安装量很大的软件包，如果换了一个下游用户都没有审查过的新维护者，正是攻击者寻找的目标。Veritasium 关于 xz Utils 后门的视频，是我见过对这种情况如何发生的最佳讲解。</p>
<p>这个软件包仍将继续安装，但不会再获得新的修复，包括针对缺失“a”这一 bug 的修复。在这么长时间没有改动之后，即使是一行代码的修复，也可能会给某些用户带来意想不到的后果，而届时又没有人能够提供支持。README 中说明了如何进行切换。</p>
<p>我编写这段代码，是为了让一次痛苦的迁移变得轻松一些，无论是对我自己，还是对其他经历同样迁移的人来说。感谢每一位提交拉取请求或主动提出接手的人，也感谢那些在我停止阅读 issue 很久之后仍持续提交问题的人。作为一个临时修复方案，它已经走过了一段很不错的历程。</p>
<p>附言：我们从未让 AOL 的 CMS 摆脱这个“临时”兼容填充程序。直到整个平台大约在2020年关闭之前，它一直在那里运行。</p></div>
