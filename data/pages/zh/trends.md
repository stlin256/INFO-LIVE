### [一份可持续的网络职业生涯，等这一切过去之后](https://dbushell.com/2026/10/07/sustainable-web-career/)
<div class="original-title-sub"><span class="orig-tag">原文</span> A sustainable web career, for when all this blows over</div>

<div class="article-body" data-article-body="true"><p>2026年10月7日，星期三</p>
<p>不管是好是坏，网络行业正经历一个阶段。原因在很大程度上是不理性的。人们仍然需要网络，这一点没有任何改变。然而，这门生意的财务状况举步维艰，长期职业前景也显得不容乐观。</p>
<p>由于我公开反对那股意图摧毁我所从事职业的力量，并因此得罪了一些人，我经常会私下收到志同道合同行的求建议。我只能给出一个不太振奋、但很实际的回答：不要在没有退路的情况下辞掉一份有收入的工作。去温彻斯特酒吧，喝上一杯冰啤酒，等这一切过去吧。</p>
<p>《僵尸肖恩》（2004年）中的人物在温彻斯特酒吧喝酒。西蒙·佩吉饰演的角色举着一品脱啤酒，做出干杯的姿势，并朝镜头眨眼。</p>
<p>我相信情况会好转。在那之前，我们能专注于什么，来加速走出这场智力低迷，并在一切平静下来后让自己处于更有利的位置？</p>
<p>要想拥有一份可持续的网络职业生涯，还有什么地方会比那些极度短缺的关键技能更值得关注？我关注的是前端开发，但这些知识领域与所有从事网站制作的人都有关。</p>
<p>无障碍一直是网络开发的基础，但它从未像现在这样需要每个人积极倡导。理解为什么无障碍服务于所有人。学会如何围绕真实需求和实际实施来讨论无障碍。</p>
<p>遗憾的是，无障碍已经成了某些科技群体用来表达立场的工具。（有人告诉我，LinkedIn上充斥着错误信息。）无障碍不是可以像装饰一样，在网站上最后临时添加的一项功能。无障碍问题无法在最后通过自动化流程解决。网络从业者必须从第一天起就在所有决策中尊重无障碍，以此对抗这种思维方式。</p>
<p>学习并采纳相关指南，把它们作为你的基准。与真实的人交流并进行测试。对于那些愿意让你了解现实情况的专业人士，应当听取他们的意见。</p>
<p>CSS是前端标准中最有活力、发展最快的一项。要设计出良好的样式表架构，需要深入理解这门语言的特性。级联层以及能够降低特异性的选择器等新特性，让这件事变得容易得多。</p>
<p>CSS一直具备处理组织良好样式的能力，但一些拒绝学习和尊重这门语言的开发者，试图使用简化抽象或“CSS-in-JS”等方案，把复杂性转移到别处。这些方案本质上存在局限，会导致性能不佳，而且实际上并没有解决它们声称要解决的问题。</p>
<p>沟通是一项供不应求的“软技能”（原因显而易见）。如果你希望以专家身份脱颖而出，或者只是在嘈杂的环境中让别人听见你，这是一项很棒的技能。学会简洁，专注于重要的观点。不要害怕提问。</p>
<p>以恰当的方式尽早处理疑虑，避免事态升级。不要相互指责，但要“保护好自己”——项目中的每个人都应朝着同一个目标努力，只是有些人采用的方法可能存在偏差。保持积极，不要正面迎击消极情绪。</p>
<p>如果你善于沟通，就会在自己的岗位上受到高度尊重。</p>
<p>你可能没想到这一点，但我们确实要谈谈它。</p>
<p>“不谈政治”的特权已经不复存在。极右翼政治意识形态正在抬头，科技行业中沉睡的仇恨也在苏醒。法西斯科技的中心是马斯克的“X”；David Heinemeier Hansson等人在那里散播种族主义，并在社区中滥用权力来推动某种议程；而Guillermo Rauch则与一名战争罪犯自拍。DigitalOcean等大型科技巨头正在为这场夺权行动提供资金。对于那些否认这一威胁的人，要保持警惕。</p>
<p>如果你不想被迫离开这个行业，就要在法西斯主义找上你之前认清并拒绝它。不要保持沉默。</p>
<p>我已经谈到了有助于我们应对未来的话题，但我们应该忘掉什么？</p>
<p>Facebook的实验如今已变成一种货物崇拜式的遗留框架，但今天已经没有理由再学习它。React已经牢牢确立为代码生产者之间的通用语。React代码的生成速度，快到任何人都不可能读完。简单地说，尽管过时的招聘信息仍然要求相关经验，但React不值得投入时间。高薪React开发的日子已经屈指可数。</p>
<p>GitHub如今成了一项负担。对于私有代码仓库，请使用自托管的Git代码托管平台。我推荐Forgejo。许多类似Tailscale的服务都可以轻松控制远程访问。不要把东西公开，任由死互联网来攻击！CI/CD也采用本地方案，或者使用不隶属于科技巨头的独立服务。花时间学习基本的Git命令。一点技术和基础设施知识，就能带来很大帮助。</p>
<p>这些人外表英俊、魅力十足、非常善于与人交往。我说的是：开发者关系从业者、YouTuber、初创公司创始人等。过去，科技行业愿意与我们各让一步时，影响者很有娱乐性，在派对后的聚会中聊上几句也很愉快。现在游戏规则变了，我们不应允许虚假叙事主导一切，并决定一个封闭网络的未来。普通人仍在使用网络。能负担影响者兜售的新奇玩意儿的人少之又少。他们所处的注意力经济已不再是我们需要关心的事。</p>
<p>这就是我对可持续网络职业生涯的关注重点，等这一切过去之后。</p>
<p>请牢记最重要的一点：网络是人类为满足人类需求而创造的。这些需求不会消失。丢掉在繁荣时期积累下来的沉重负担。回归基础，为职业需求回归之时做好准备。</p>
<p>所有观点仅代表我个人，不代表任何大型语言模型。我写下的一切百分之百出自人类之手。因为我在乎！</p>
<p>我创办了Valley Fold，就是为了帮助你，所以让我们一起实现你的网站吧。无论你已经明确了需求，还是完全没有头绪，我们都可以在任何阶段与你合作。</p></div>

<p>依赖注入（Dependency Injection，DI）框架已经存在了很长时间，但 Ruby 开发者传统上一直对其敬而远之，这很可能是因为大家认为它带来了不必要的复杂性。</p>
<p>然而，正如本文试图阐明的那样，不采用依赖注入所换来的“简单性”其实会带来负面效应。与 Java 等语言相比，Ruby 的灵活性使我们能够以一种友好得多的方式来实现 DI。</p>
<p>在很多情况下，传递给对象的参数往往混合了初始化参数与方法参数，两者之间缺乏明确的界限。</p>

<p>如果我们看一下该类在控制器中的使用方式，会发现：</p>
<p>从该类的调用方式可以看出，@email 和 @password 均来自用户输入，因此每次注册时都需要初始化新值。而一旦计算完成，UserRegistration 的实例就会立即被废弃。</p>
<p>该类使用了几个外部接口：EmailValidator、BCrypt::Password、UserRepository 以及 ConfirmationMailer。这些都是常量，因此在多次调用之间不会发生改变。它们就是依赖项（Dependencies）。</p>
<p>这些常量在实现代码中被直接引用，无法在测试环境中轻易替换。因此，为了为其编写测试，我们必须基于对对象内部细节的了解来对全局 API 进行打桩（stub）。</p>
<p>如果 EmailValidator 更改了规则，导致我们的测试邮箱无法通过验证怎么办？突然之间，我们的测试可能会因为与被测行为完全无关的原因而失败。我们需要一种更好的方法来将它们替换为测试替身（test doubles）。</p>
<p>依赖项（Dependencies）是在对象生命周期内可能被多次使用的引用。参数（Arguments）则是与单次请求相关的单次入参。</p>
<p>Ruby 在设计上是面向对象的；你所交互的每一个实体都是对象。类的存在是为了定义构建特定类型对象的可复用模式，但这些类实例本身是作为独立个体对待的。</p>
<p>当一个对象与另一个对象发生交互时，它们之间便建立了依赖关系。我们称这些为协作对象（coordinating objects）。管理系统复杂性主要就是要限制这些依赖关系。</p>
<p>如果协作对象可以在一个对象内部的任意位置被引用，那么从视觉上直观判断其所有依赖就会变得更加困难。</p>
<p>将所有协作对象作为显式依赖在顶部统一声明，能使通过视觉直观判断类的依赖关系变得非常容易。</p>
<p>现在，我们只需看一个地方，就能一目了然地确定该类依赖于 EmailValidator、BCrypt::Password、UserRepository 和 ConfirmationMailer。在这个小例子中这看起来变化不大，但你肯定见过依赖散布在各处的更大规模的类。想一想这两种模式将如何扩展，以及哪一种会更难理解。</p>
<p>设想出现了一个新需求：员工邮箱需要使用更强大的摘要算法。在以前，这需要修改实现代码。但现在，我们所需要做的仅仅是传入一个不同的依赖项。</p>
<p>这种结构允许我们将类的初始化与其具体使用分离开来。</p>

<p>除了冗长的参数列表之外，它还要求将每个关键字参数赋值给实例变量，因此你不得不将每个参数重复输入两次。</p>

### [关于俄罗斯鼠疫研究所工作人员之死我们了解多少？是否存在更大风险？](https://www.theguardian.com/world/2026/oct/06/what-do-we-know-death-darya-shipilova-anti-plague-institute-russia-wider-risk)
<div class="original-title-sub"><span class="orig-tag">原文</span> What do we know about death of anti-plague institute worker in Russia and is there a wider risk?</div>

<div class="article-cover"><img src="https://i.guim.co.uk/img/media/462785441d219322c6970ad4fcf8cbeb444cc616/171_0_1706_1365/master/1706.jpg?width=140&amp;quality=85&amp;auto=format&amp;fit=max&amp;s=35c3178db8ed9e8f5a0629df5cd0e862" alt="关于俄罗斯鼠疫研究所工作人员之死我们了解多少？是否存在更大风险？" loading="lazy" /></div>

<div class="article-body" data-article-body="true"><p>俄罗斯否认达莉娅·希皮洛娃（Darya Shipilova）在工作期间发病后死于鼠疫，但专家表示仍有诸多疑团待解。</p>
<p>在上周据报道一名28岁的实验技术员在俄罗斯一家鼠疫研究实验室发生事故后身亡，我们在此梳理目前关于该事件的已知信息。</p>
<p>具体细节目前仍不明确，但来自俄罗斯的报道显示，伊尔库茨克市鼠疫研究所的雇员达莉娅·希皮洛娃在工作中感到身体不适两天后，于10月2日死亡。</p>
<p>据俄罗斯卫生监管机构——联邦消费者权益保护和人类福祉监督局（Rospotrebnadzor）称，希皮洛娃死于“病因不明的肺炎”。</p>
<p>然而，也存在其他说法：相邻的布里亚特共和国行政长官阿列克谢·齐德诺夫（Alexey Tsydenov）最初表示希皮洛娃死于鼠疫，随后修改了他的社交媒体发帖，改称她“可能”死于该疾病。</p>
<p>俄罗斯当局已向世界卫生组织（WHO）否认了这一情况，称：“俄罗斯联邦伊尔库茨克市未记录到任何此类危险疾病的病例。”</p>
<p>我们所讨论的是一种由鼠疫耶尔森菌（Yersinia pestis）引起的疾病，该细菌通常存在于小型哺乳动物及其寄生跳蚤中。在14世纪席卷欧洲的腺鼠疫或“黑死病”正是由同一种微生物所致。</p>
<p>然而，腺鼠疫与一些人推测导致希皮洛娃死亡的肺鼠疫有所不同。</p>
<p>前者更为常见，会导致被称为横痃的淋巴结肿大，并通过受感染跳蚤的叮咬传播；而后者则属于肺部感染。肺鼠疫的致死率更高，且可在人与人之间传播。</p>
<p>媒体的一篇报道称，希皮洛娃是在从泰国归国后因该病入院的；而另一篇报道则称，她在实验室打破试管后感染。联邦消费者权益保护和人类福祉监督局已否认研究所发生过任何此类事故。</p>
<p>值得注意的是，鼠疫并非只是过去的疾病。</p>
<p>“全球每年通常在地理受限的区域报告几百例鼠疫病例，特别是在马达加斯加和刚果民主共和国——尽管在美国西部、中亚、蒙古等地也有少量病例，”伦敦帝国理工学院的马利克·吉巴尼（Malick Gibani）博士表示。</p>
<p>这听起来或许令人不安，但我们不再需要依赖中世纪的医疗手段。</p>
<p>雷丁大学的西蒙·克拉克（Simon Clarke）博士表示：“与许多病毒性呼吸道疾病不同，鼠疫是由细菌引起的。如果及早使用氟喹诺酮类和氨基糖苷类等抗生素，对这种病原体非常有效，并且在暴露后通常会作为预防性用药。”</p>
<p>然而，伦敦卫生与热带医学院的布伦丹·雷恩（Brendan Wren）教授表示，目前正在出现多重耐药菌株，“如果实验室正在研究此类菌株，那么治疗选择可能会受到限制”。</p>
<p>还有报道称，与希皮洛娃可能存在接触的近200人目前正处于医学观察中，并且多家医院已实施隔离措施。</p>
<p>“隔离和监测是明智的策略，”雷恩表示。</p>
<p>墨尔本大学的爱丽丝·休斯（Alice Hughes）教授补充说，肺鼠疫的潜伏期仅为一到三天，目前尚未有人表现出症状。</p>
<p>雷丁大学的伊恩·琼斯（Ian Jones）教授也表示无需过度恐慌：“此处的案例看起来是一起罕见的实验室事故，不太可能进一步扩大扩散。”</p>
<p>然而，克拉克表示仍存在未知因素。“在更多细节浮出水面之前，很难评估这究竟是一起孤立病例、一次职业暴露，还是存在更广泛传播的迹象，”他说。</p>
<p>联合国卫生机构发言人克里斯蒂安·林德梅尔（Christian Lindmeier）表示，对其他人的风险很低。“根据现有信息，世卫组织的初步风险评估估计，伊尔库茨克面临的风险为中等至偏低，整个俄罗斯联邦面临的风险为低，而世卫组织欧洲区域面临的风险极低，”他表示。</p>
<p>伯明翰大学病毒免疫学副教授兼生物安全3级实验室学术负责人扎尼亚·斯塔马塔基（Zania Stamataki）博士表示，英国用于危险生物的控制系统行之有效，这意味着实验室获得性感染极为罕见。</p>

<p>而在 Zig 中，声明函数的唯一方式就是对其命名。如果你想将一个函数赋值给某个东西，你需要先跳出到容器作用域。我们稍后会看到一个这样的例子。</p>
<p>正如在 Lua 中变量可以是全局的或局部的（其中全局是默认情况），Zig 中容器作用域的值（称为声明）也是如此。在这里，“局部”是默认行为，意味着该声明仅对同一文件内的代码可见。因此我们必须将 main 标记为 pub，因为这个函数是由未包含在我们文件中的 Zig 代码调用的！通常，那段代码来自于 Zig 标准库的 start.zig 文件，不过这种行为也可以被覆盖。与 Rust 类似，Zig 使用 fn 而不是 function 或 C 语言的……什么都不写，并将返回类型放在参数列表之后。</p>
<p>对 std.debug.print 的调用除了 .{} 之外可能都很眼熟。这种 .{} 语法是 Zig 中初始化结构体、数组或联合体等容器的典型方式；你可以通过编写 .field = value 来填充其中的字段。这个小点的普遍存在起初往往会让一些人感到不适。它的存在是为了让 Zig 的语法（在语言理论意义上）更容易解析。</p>

<p>这是一个泛型函数的例子。Zig 中的所有普通函数（至少在原则上）都是对其 comptime 参数、其 anytype 参数的类型以及它们所闭包捕获的任何容器作用域 comptime 值进行泛型化的。fmt 字符串被标记为编译期已知（comptime-known），以便验证 args 的类型并在编译期生成必要的代码。（顺便说一句，[]const u8 表示不可变字节切片。在 Rust 中类似的类型可能是 [&amp;]u8。Zig 字符串字面量以 UTF-8 编码并以 null 结尾，但 Zig 没有更专用的“string”类型。）这里我们没有打印任何内容，所以我们传递了 .{}，在这种情况下它被视为空元组。</p>
<p>极客同好们可能会感到惊讶且高兴地发现：std.debug.print 以及其他字符串格式化函数完全是在用户空间使用 comptime Zig 实现的，而不是依赖宏或特殊的内建特权。</p>
<p>最后，值得注意的是，我们的程序并没有完全按照预期的设想工作：“Hello World!” 被输出到了 stderr，而不是 stdout。这是 std.debug.print 符合预期设计的特性。写入 stdout 需要稍多一点的样板代码，等我们配置好 Lua 后我再加入这些代码。</p>
<p>目前为止一切顺利。为了与 Lua 配合使用，我们还需要用到 Zig 的构建系统。我们将首先添加一个 build.zig 脚本来运行我们的 hello.zig 文件。</p>
<p>该脚本将通过在其所在目录下调用 zig build 来编译并执行。函数名称 build 以及单个参数都是必填的。</p>
<p>接下来两行通常如下：</p>
<p>目标选项指定了诸如操作系统、机器架构以及代码编译所针对的 ABI 等内容。传入 .{}（在这里会强制转换为选项结构体的默认值）允许用户在命令行中通过 -Dtarget= 前缀传入他们期望的目标，并默认使用本机原生目标。optimize（优化）选项可以是 debug（默认）、fast、safe 或 small。后几个选项是“发布”构建变体，分别优先考虑执行速度、诸如溢出和边界检查等内存安全特性，或者磁盘上的代码体积。</p>
<p>接下来，我们将把 hello.zig 代码放入构建系统所谓的“模块”（module）中。模块可以成为可执行文件、C 风格的库，或者被编译进更深层的 Zig 模块（可能存在于依赖项目中）。模块需要一个根源文件，我们的模块将接收我们的目标和优化选项。</p>
<p>顺便提一下，如果你省略了 optimize 之后的那个末尾逗号，Zig 的自动格式化工具 zig fmt 会将整个函数调用放在同一行。如果你写在同一行但在 optimize 之后包含了逗号，zig fmt 会将其排版成上述的样子。如果你在使用 LSP 支持，该自动格式化工具很可能会在保存时运行。某些类型的语法错误会阻止 zig fmt 执行任何操作，因此你需要先自行解决这些错误。</p>
<p>调用 b.path() 是 Zig 构建系统处理文件系统的方法。这层额外的间接抽象使得构建系统能够统一处理可能属于依赖项、或者可能由构建过程中更早步骤生成的文件路径。这应该是一个相对路径。顺便提一下 @import() 的两个限制：除了诸如 std 这样的命名模块外，@import() 还可以接收相对路径。这些相对路径不能超出包含当前模块根源文件的目录子树之外。此外，每个文件至多只能属于一个模块。</p>
<p>因此，在包含 A/root.zig、B/main.zig 和 B/utils.zig 的情况下，root.zig 文件不能使用 @import 引入 main.zig 或 utils.zig，而 main.zig 和 utils.zig 则可以随意相互引入（甚至可以同时互相引入）。如果 main.zig 和 root.zig 都想要导入 utils.zig，那么同时包含它们的任何项目都必须进行组织，使 utils.zig 成为一个由这两个项目共同导入的模块。</p>
<p>接下来，我们将把模块编译为可执行文件。</p>
<p>这是一个（暂时的）完整构建脚本；使用 zig build 运行它将把 hello.zig 编译为一个名为 hello-lua 的可执行文件，并将其放置在相对于运行 zig build 位置的 zig-out/bin 目录下。构建系统在编译完成后还可以运行编译出的产物，但需要我们明确告知它去运行。</p>
<p>新增的第一行在我们的构建图（Build graph）中创建了一个名为“run”的新命名“步骤”（step）。该步骤可以通过调用 zig build run 来运行。第二个参数是帮助文本，当用户运行 zig build -h 时，会显示在步骤旁边供用户查看。</p>
<p>第二行在构建图中创建了一个运行程序 exe 的步骤，第三行则将用户在 zig build run 之后通过 -- 参数传入的任何命令行参数传递给对 exe 的调用。第四行和第五行初看有些奇怪。第四行表示我们的命名步骤 run_step 依赖于 run.step。这意味着 zig build run 需要 run 执行，这符合我们的预期。</p>
<p>&amp; 运算符与 C 语言中的完全相同：Zig 拥有指针，但没有更复杂的指针魔法。step 是 run 上的一个字段，如果你运行了 LSP，就会发现它是一个指针。. 运算符根据左操作数的类型自动发挥 C 语言中 . 或 -&gt; 运算符的作用。因此 &amp;foo.bar 获取的是 foo（或者当 foo 是指针类型时为 foo.*）上 bar 字段的地址。</p>
<p>最后，末行表示我们的可执行文件将在运行前完成安装。严格来说这并不是必需的，但会在下一篇文章中为我们提供便利。</p>
