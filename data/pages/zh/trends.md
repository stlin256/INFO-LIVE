### [人工智能没有智慧，你也不会有](https://alexn.org/blog/2026/09/22/ai-has-no-wisdom-and-neither-will-you/)
<div class="original-title-sub"><span class="orig-tag">原文</span> AI Has No Wisdom and Neither Will You</div>

<div class="article-body" data-article-body="true"><p>2026年9月22日｜5分钟｜评论</p>
<p>仅在过去一个月里，我就听到了这些说法：</p>
<p>“毫无疑问，这个行业正在转型；然而，那些掉进不再阅读和编写代码这一陷阱的人和组织，终将自食其果。”</p>
<p>“事实是，凭感觉编写的项目会随着时间推移，逐渐沦为一团无法维护的乱麻。原因很简单，却很难解决：代码的可维护性和良好架构没有我们可以采用的有效衡量指标，因为糟糕架构或不可维护代码所造成的影响，往往要经过数月、甚至数年才能显现。”</p>
<p>我们当然可以定义什么是糟糕的代码：难以阅读、难以理解，也难以应对未来各种变化而演进的代码。这类代码中，改动一个地方可能以极其不可预测的方式破坏整个程序，或者破坏远离改动点的其他地方的逻辑，近似于“蝴蝶效应”。这类代码中，添加一个功能意味着一项艰巨的工作：需要在多个地方修改代码，却仍可能漏掉某些补丁，从而造成不一致。这样的代码，其设计中的不变量并不清晰；而它的作者可能已经不在了，无法防止违规情况、确保整体协调。这样的代码也很难测试，需要使用模拟对象并暴露实现细节，最终导致脆弱的测试，反过来阻碍有意义的重构。</p>
<p>然而，我们知道一个事实：发现糟糕的代码需要时间——数月，甚至数年。当然，经验丰富的软件工程师有一种能够察觉代码异味的直觉，在糟糕后果显现之前很久就能采取行动。</p>
<p>熟练的开发者、专家们，依靠的是用汗水和泪水铸就的直觉。他们长时间工作，努力调试并修复生产环境中的问题，发誓再也不会愚蠢到重蹈覆辙。这种直觉实际上无法被整理成一套僵化的规则，因为一切都取决于具体情境。专家与那些能让初学者提高生产力的同一套规则和配方并不相容。专家不遵循规则，他们制定规则。</p>
<p>于是，我们遇到了一个问题……</p>
<p>首先，人工智能并没有接受关于代码“可维护性”意味着什么的训练。比如，任何强化学习都需要一个能够立即衡量的奖励信号，而不是要等数月或数年才能衡量。人工智能从面向初学者的规则手册中学习规则。人工智能从现实世界中的代码里观察模式，而坦率地说，现实世界中的大多数代码都相当糟糕。你无法为可维护代码定义一个适应度函数，至少目前还无法定义一个我们能够辨识的适应度函数；否则，它早就已经被纳入代码检查工具中了。</p>
<p>你有没有注意到，人工智能在“简化”代码方面有多糟糕？没错，我说的是最先进的模型。它甚至无法恰当地定义函数，只会选择把函数拆分成更小的函数，而这些小函数实际上并不可复用。如果为了理解一个大函数，还必须阅读被提取出来的小函数的实现，那么从大函数中提取小函数就是一个非常糟糕的选择。定义出可复用且能澄清意图的函数是一门艺术，是需要精通的艺术。按照德雷福斯模型，大多数开发者仍处于“高级初学者”阶段，他们无法定义出优秀、清晰且可复用的函数；目前的人工智能也同样做不到。</p>
<p>如果人们仍然掌握控制权，并能从这些错误中学习，这本来不会是多么糟糕的事。但我们正在看到一种趋势：人们开始依赖人工智能来编写代码，甚至阅读代码。</p>
<p>这些人永远无法达到精通境界，因为他们不再做出选择，不再为编码中的错误承担责任，也不再从这些错误中学习。现在犯错的是人工智能；人工智能不会从这些错误中学习，而那些依赖人工智能编程的人也不会从中学习。</p>
<p>别误会我的意思，我认为大型语言模型是很棒的工具。我不是卢德分子；我已经把人工智能整合进日常工作，同时也在实际教同事们我所学到的东西。我很乐意让大型语言模型替我们处理那些不得不面对的、无聊而且耗尽灵魂的破事。我也很享受由此带来的效率提升。但归根结底，它只是一种工具；和所有其他革命一样，它的光芒也会逐渐消退。依我看，它已经开始消退了，因为如今的科技新闻坦率地说相当无聊。</p>
<p>人们实际上很不擅长做预测。我相信，未来会让我们所有人感到意外。不过，我要做出一个属于自己的预测……</p>
<p>未来，我们会看到越来越多的公司骄傲地把“禁止使用人工智能”政策当作竞争优势进行宣传。而且，它们会是对的。</p>
<p>人们会说：“自动化流水线总是更高效。”但软件行业很特殊，因为我们一直在大规模地进行自动化；我们所做的一切都是自动化，人工智能并不是实现自动化的唯一手段，而且根据具体情境，它实际上可能成为一种干扰。“编程已经被解决”——这句话在任何有意义的层面上都不成立。当然，你可以指示大型语言模型为你构建一个 C/C++ 编译器；但你也可以直接克隆 GCC 或 LLVM，这样你会得到一个更好的 C/C++ 编译器，而且还是免费的。也许，与其重新发明同样的 CRUD 应用，我们还有更好的方式来投入时间和资源（人类的需求和欲望是无限的，我们不缺新的目标去努力实现）。</p>
<p>如果人们和企业不开始对人工智能的使用负责，就会承担后果。</p></div>

### [要闻：我刚刚发布了 Extralite 3.1.0 版本](https://noteflakes.com/articles/2026-09-22-extralite-3-1-0)
<div class="original-title-sub"><span class="orig-tag">原文</span> Extralite 3.1.0 is Here</div>

<div class="article-body" data-article-body="true"><p>我刚刚发布了 Extralite 3.1.0 版本。这一新版本实现了参数化查询的自动缓存，并将内置的 SQLite 升级至 3.53.4 版本。</p>
<p>Extralite 是一个快速且富有创新的 Ruby 语言 SQLite 封装库，功能丰富。它提供了从 SQLite 数据库检索数据的多种方式，使在多线程和多纤程（fiber）Ruby 应用中使用 SQLite 数据库成为可能，并包含了一整套用于管理 SQLite 数据库的工具。</p>
<p>Extralite 现在会自动为任何参数化查询缓存底层的 sqlite3_stmt 对象。此前，当你使用不同的参数通过 Database#query_xxx 运行相同的 SQL 时，每次执行查询 Extralite 都会创建一个新的 sqlite3_stmt，这会导致 SQLite 反复解析相同的 SQL。现在，在调用 Database#query_xxx 系列方法（或 Database#execute）之一时，Extralite 会自动缓存底层的 sqlite3_stmt 对象，并在后续重复调用时复用它，从而减少内存分配并最大程度降低解析开销，让你能从基于 SQLite 的应用中挤出更多性能。</p>
<p>此前，我曾撰文讨论过通过直接执行原生 SQL 查询而非使用 ORM 来操作关系型数据库的优势。Extralite 的核心目标就是让你轻松做到这一点的同时最大化性能。以下是一个实现该操作的简单代码示例：</p>
<p>有了自动查询缓存，你无需再显式创建预编译查询（通过 Database#prepare）。你只需执行相同的参数化 SQL，Extralite 就会替你完成底层查询的缓存工作。</p>
<p>Extralite 旨在让你充分发挥 SQLite 数据库的潜力。它会自动配置你的数据库以启用预写式日志（WAL）并强制执行外键约束（对于旧有数据库你可以将其关闭）。它提供了诸如参数化查询批量执行、保存点、备份以及变更集等高级特性。此外，它速度飞快！</p>
<p>Extralite 还允许你使用结构化转换从查询结果中生成带有标识映射（identity map）的对象图，这使你只需一次查询就能检索实体及其所有关联对象，完全无需使用 ORM！</p>
<p>我对 Extralite 的目标是将其打造成一个在不使用 ORM 的情况下基于 SQLite 数据库构建应用的全面工具。我希望它既快速又易用。在推出自动查询缓存之后，我其实想移除封装了预编译查询的 Extralite::Query 类，因为在我看来，自动查询缓存已经实现了预编译查询的大部分价值。如果你认为这种抽象对你的使用场景仍是必需的，请告诉我，我可能会改变主意。</p></div>

### [要闻：Git 2.56 版本包含 700 多个非合并提交](https://lwn.net/SubscriberLink/1094575/2385e98583715c2b/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Looking forward to Git 2.56 - and 3.0</div>

<div class="article-body" data-article-body="true"><p>Git 2.56 版本包含 700 多个非合并提交；它带来了许多不错的改进，但对于大多数用户而言，并不会从根本上改变 Git 的使用体验。在这方面颇具潜力的一项特性，是在（仍处于实验阶段的）git history 工具箱中新增了 drop 子命令：</p>
<p>该命令将使指定的提交从当前分支的历史记录中被移除，并重新重放其后添加的所有提交。它为移除有问题的提交提供了一种更简便的方式。不幸的是，如果历史记录中包含合并提交，它仍然无法工作，这使得它在许多（或绝大多数）代码仓库中无法使用。</p>
<p>git status 命令现在会建议使用 git pull 命令来更新落后于其跟踪分支的本地分支。不过，即使分支落后于（尚未拉取的）远程跟踪分支，它仍然会显示分支处于“最新状态”（up to date）。</p>
<p>git refs 命令用于在底层操作引用；在 2.56 中，它增加了一系列新的子命令。这些命令包括 create、delete、update 和 rename，或许出乎 Git 的一贯常态，它们的功能正如其名称所示，名副其实。</p>
<p>新版本还带来了许多细节上的可用性调整。git branch 新增的 --delete-merged 选项将移除已合并到其远程跟踪分支的本地分支。如果某个分支正在被用于二分查找（bisect），尝试使用 git branch -d 删除该分支将会失败，并显示一条有用的提示信息。在锁定配置文件失败时将会进行重试，避免在多个命令同时尝试修改该文件时造成困扰。git add 新增了一个 --resolved 选项，该选项只添加已解决合并冲突的文件。</p>
<p>除此之外，还有常规的大量错误修复、重构和性能改进。总的来说，2.56 看起来是一个坚实稳定的版本，但它也显露出该项目正将许多更重大的工作留待将来的迹象。这就引出了一个问题：接下来会是什么？</p>
<p>9 月初，Git 维护者滨野纯（Junio Hamano）询问社区下一个版本应该是什么。是发布社区为之努力了一段时间的 3.0 版本、以此为这一年画上圆满句号最好？还是说，在 3.0 版本发布之前，仍需要发布一个或多个 2.x 版本？</p>
<p>这是一个重要的问题，因为 3.0 将包含许多破坏向后兼容性的改动，可能会让一些用户在升级前犹豫不决。在这些改动中，最重要的或许是默认改用 SHA-256 哈希函数，而不是 Git 从一开始就使用的 SHA-1 哈希。长期以来，SHA-1 一直被认为是不够安全的，这对于像 Git 这样的应用程序来说令人担忧。哈希值用于标识 Git 仓库中的每一个对象（文件、目录树、提交），并用于验证导向任意特定节点的提交链。如果 SHA-1 可以被破解，那么可以想象它可能被用来篡改仓库的历史记录，而且这种篡改将难以甚至无法被察觉。</p>
<p>Git 长期以来一直包含针对已知 SHA-1 攻击的防御机制，目前似乎很少有人严重担心仓库被篡改的潜在风险。尽管如此，转向更安全的哈希函数仍然十分有意义。</p>
<p>自 2023 年的 2.42 版本以来，Git 就已经具备了对 SHA-256 的非实验性支持，不过与旧仓库互操作的一些胶水层支持花费了更长时间。一段时间以来，阻碍 Git 开发者将 SHA-256 设为默认的最大顾虑，是主要代码托管平台（forge sites）的支持情况（或者说缺乏支持）。GitLab 自 2024 年起就提供了支持，Forgejo 也提供了支持。然而，房间里那头依然缺席的大象是 GitHub；发布一个会创建与 GitHub 不兼容的仓库的 Git 版本，是一个令人担忧的前景。目前尚不清楚 GitHub 何时可能会添加该支持，但值得注意的是，GitHub 员工、同时也是 SHA-256 转型背后的关键开发者 brian m. carlson 在回复滨野纯的问题时表示，关于该主题的消息即将到来，并将下一个版本定为 3.0 可能是最佳选择。</p>
<p>话虽如此，carlson 还提出了他希望在 3.0 发布之前添加的另一项变更。尽管 Git 一直将十六进制数（具体指对象 ID）作为小写字符串管理，但它也接受大写 ID。这导致了两个看似不同的 ID（例如 f00f00 和 F00F00）实际上是相同的情况。显然，这种模糊性引发了一些漏洞和安全弱点。因此，carlson 希望更改 Git 的行为，使其仅接受小写 ID。这一变更表面上看应该不会对太多用户造成困扰，但几乎可以肯定，某些地方一定有人依赖于这一行为。</p>
<p>另一个一直在等待 3.0 发布的重大变更是切换到“reftable”机制。Git 中的引用（通常称为“ref”）是名称与仓库中对象之间的关联；例如，分支、标签和远程跟踪分支都是引用。目前，Git（默认情况下）将每个引用作为文件存储在仓库的 .git/refs/ 目录下。如果仓库包含一个名为 foo 的分支，就会存在一个文件 .git/refs/heads/foo，其中包含该分支顶端提交的 ID。此外还有一种将所有这些引用汇总到 packed-refs 文件中的机制，这在一定程度上提升了性能。</p>
<p>这种机制能够正常工作，但随着引用数量的增加，其效率变得越来越低。在某些项目中，引用数量确实大幅攀升。根据该项目的 reftable 文档，Android 仓库包含超过 800,000 个引用。在如此庞大的规模下，查找引用或确定是否存在指向特定提交的引用，可能是一项极其昂贵的操作。开发速度变慢是一种黄牌警告级别的困扰，从而催生了对引用机制进行改造的愿望。</p>
<p>Git 2.45 版本引入了 reftable，作为一种更高效的引用存储方式。它是一种针对空间效率和快速访问都进行了优化的二进制文件。从那时起，创建使用 reftable 而非旧的文件机制的仓库已经成为可能，但这从未成为默认设置。对于 Git 本身的用户来说，切换到 reftable 应该不会产生可见的影响（除了更好的性能），但对于访问 Git 仓库的其他软件包的用户来说，这可能会成为一个问题。carlson 在其邮件中提到了 libgit2 这一潜在的顾虑点。</p>
<p>事实证明，libgit2 在这里不会成为阻碍；Patrick Steinhardt 透露，他已经为 libgit2 添加了 reftable 支持，并且 SHA-256 支持已在 8 月份默认启用。因此，libgit2 应该已经为 Git 3.0 的过渡做好了准备。</p>

### [正确设计你的编程语言（2024）](https://blog.veritates.love/design-it-right)
<div class="original-title-sub"><span class="orig-tag">原文</span> Design your programming languages right (2024)</div>

<div class="article-body" data-article-body="true"><p>我只是觉得，我们应该为新的编程语言及其配置制定一些基本规则。你懂的吧？</p>
<p>这只是一些杂乱的想法，列举了我认为你应该加入的特性，或者至少应该深思熟虑、别把自己未来加入这些特性的可能性给堵死的地方。还有一些是我正在思考、但尚未得出确切答案的话题。</p>
<p>当你准备在代码中嵌入一段多行字符串时，却发现必须闭上眼睛假装当前的缩进层级根本不存在，眼睁睁看着原始文本内容挤满代码编辑器的左侧边缘，这实在太难看了。</p>
<p>这是一个早已解决的问题。Dhall 在这方面做得相当不错（尽管我不太喜欢那里的转义规则），Nix/Lix 也有类似的规则。</p>
<p>我在 Ve.dedent 中为 JavaScript 模板字面量实现了类似的逻辑，效果让我非常满意。我也在 PureScript（以及 Python？）中竭尽全力尝试过，但由于缺乏源码文本与转义/插值文本之间的区分，这变得困难得多；最终它充其量只是一个在某些场景下能用的工具，而无法成为一种如同语言内置特性那样系统化的方案。</p>
<p>带缩进的多行字符串纯粹是一件可以在早期多花几个小时精力解决的事，何必等到它变成用户的痛点、让你陷入若不破坏向后兼容就无法更改的窘境呢。</p>
<p>文件路径应该相对于其所在文件，或者相对于定义明确的项目根目录。这主要适用于配置文件，对正在运行的程序影响较小（对于后者，使用工作目录通常就足够了），但话说回来……导入行为应该是可预测的。</p>
<p>值得注意的是，Docker Compose 和 Rust 的 Cargo 的配置文件在这点上都做错了。</p>
<p>再说一次，你必须从一开始就把它做对，或者构想出坚实的版本管理方案。（不过当然了，那些从一开始就没花心思把它做对的编程语言，通常也没有足够好的版本策略来应对这个问题。）</p>
<p>选定一两个文件扩展名，然后坚持用下去！请记住，如果你是一门新语言，你只是一位承蒙现有生态系统厚爱才得以进入的客人，理应按照既有规则行事。</p>
<p>无论在 IDE 还是在线代码查看器/Git 代码托管平台上，语法高亮主要都是基于文件扩展名来实现的。如果你的语言没有一个可识别的文件扩展名，你的用户就得付出更多折腾的代价。</p>
<p>举个例子，Bazel 在名为 WORKSPACE、BUILD 以及扩展名为 .bzl 或 .bazel 的文件中使用 Starlark。Starlark 恰好能复用 Python 的语法高亮，这一点确实很不错。</p>
<p>但如果存在多种不同的扩展名以及没有扩展名的文件名，你就很难说服你的 IDE 对它们进行高亮。（如果这些名称还可以自定义配置，那就更难了，不过我觉得 WORKSPACE 和 BUILD 应该不可配置吧？）如果你在 grep 检索文件时必须囊括所有可能出现的形式，搜索也会变得更难。诸如此类。</p>
<p>另一个早已解决的问题：允许尾随逗号（trailing commas）！（如果你喜欢的话，也可以允许前置逗号……甚至是真正的项目符号列表点号。）</p>
<p>许多语言在数值字面量（想要添加更多前缀或后缀，但前进的道路却被向后兼容性阻断）、字符串/正则转义（请使用带定界符的转义，比如 &quot;\u{XXXX}&quot;！），或关键字方面都犯过错误。</p>
<p>这更多是我个人的看法，但我讨厌无修饰的裸关键字（bare keywords）。我认为关键字应该自带某种指示符号（sigil），以明确标明它是关键字，这样既能方便日后扩展更多关键字，又不会破坏那些将这些词用作标识符的旧代码。你真的以为自己第一次就能把一整套关键字设计得完美无瑕吗？……你能找出一门真正做到了这一点的编程语言吗？</p>
<p>在开发过程中对代码进行迭代，与拥有一个整洁、无可挑剔的正式发布版本……这是截然不同的两码事，我认为这些不同的工作流理应受到尊重！</p>
<p>例如，在开发时，我们经常把 Web 服务器部署在不同的端口和/或局域网主机上，使用 HTTP 或自签名 HTTPS（或者在少数允许偷懒的情况下甚至直接用 file:///！）；而在生产环境中，它可能位于特定路由下的反向代理之后，等等。</p>
<p>版本控制包含很多层面的含义。</p>
<p>其中一个我从未真正见过被妥善解决的问题，就是如何处理跨版本的代码。</p>
<p>比方说，我想为已发布软件的不同版本之间编写一个迁移脚本。那么，这段代码显然必须存放在较新的版本中——毕竟之前的版本不可能预知未来的变化。但你该如何测试它呢？你差不多得从源码版本控制系统中把之前的版本检出，让两个版本并行存在。（这也是“开发”模式与“发布”模式截然不同的地方之一！）</p>
<p>总的来说，如果你希望人们用你的编程语言编写库，请给他们提供一种合理的版本交流方式。这方面比较酷的工具之一，是那些能够检查库的 API（尤其是带类型系统的语言！）以判定它应该是一个补丁（patch）、次要（minor）还是主要（major）版本的工具。</p>
<p>然而，我必须强调：版本号永远都取决于主观决断。它们是一种不完美的沟通工具，而非数学上精确的抽象。</p>
<p>噢，还有另一个我常挂在嘴边的话题：发布版本号时请务必附带日期！它不一定非要写在版本号本身里，但应该容易获取，比如展示在版本号旁边、工具提示（tooltip）中，或者权威官方网页上。如果对所有软件的发布日期毫无概念，你几乎不可能在跨软件（包括语言、运行时、软件包、依赖项）之间进行版本比对。</p>
<p>这是围绕构建系统等更大话题的其中一部分，不过：</p>
<p>我发现，对于原本没有细粒度文件监听（file watching）功能的构建系统，事后想要补丁式地添加这一功能是绝不可能做到的。除非你专门写一个完整的 Python 程序去解析文件、重建其依赖树、确保弄清每个文件是如何被使用的以及它到底是否相关、在配置更改时重载整个监听器，诸如此类。</p>
<p>就像 find/grep 一样：如果你可以直接让构建工具告诉你需要检索的所有文件，然后由你决定是否包含依赖项，体验就会好得多。（此外，列出这些文件/通配模式（globs）也是迈向文件监听的第一步，尽管话说回来，你确实需要进行适当的系统级集成，才能兼顾新增文件、配置变更等各种情况！）</p>
<p>如果你还想加入真正到位的代码搜索功能，能够区分搜索词究竟出现在标识符还是字符串中，或者出现在类型还是表达式项（terms）中等等，那就更棒了。没错 ^.^</p></div>
