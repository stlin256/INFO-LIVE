### [减少 C 语言中的未定义行为](https://lwn.net/Articles/1095811/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Reducing undefined behavior in the C language</div>

<div class="article-body" data-article-body="true"><p>为什么在 2026 年还要关注 C 语言？他说，它仍然是一门优秀的语言。C 语言具备可移植性，长期保持稳定，编译速度极快，生成的二进制代码执行效率也很高。“所见即所得”；看着 C 代码，你很容易就能明白计算机实际会执行什么操作。围绕这门语言有大量成熟的工具，而且在必要时 C 语言也不会横加干涉。</p>
<p>他说，C 语言确实历史悠久，而这影响了它如今的面貌。C89 标准必须应对种类繁多的硬件，包括采用原码或反码整数表示的机器、分段内存、奇特的指针表示方式以及令人意想不到的类型大小。例如，某些霍尼韦尔（Honeywell）机器采用 9 位字节。这使得制定一个能够编写可移植代码的标准变得异常复杂。</p>
<p>当时采取的做法是根据“抽象机”来定义该语言的语义。所有操作都应当像是在那台抽象机上运行一样来执行，而这台抽象机可能与实际硬件并不完全吻合。程序的可观察行为（observable behavior）必须符合抽象机的行为方式。“可观察”这一部分至关重要：对 volatile 变量的访问被定义为可观察的，必须严格按照抽象机进行；而其他所有操作只要能产生相同的最终结果即可。</p>
<p>该标准赋予了编译器实现者极大的自由度；只需保留可观察行为即可。而该行为中有许多方面要么是未定义的（undefined），要么是由实现定义的（implementation-defined）。这些都不属于可观察行为，因此不会限制编译器实现者可以做什么。当然，在 C 标准未作限制的地方，还有其他规范可以约束编译器开发者；这些规范包括 ABI 要求、POSIX 等标准，或者向后兼容性的需要。</p>
<p>当程序执行了不可移植或标准根本未作定义的操作时，就会出现未定义行为（undefined behavior）。在这种情况下，C89 标准规定它对实现“不提出任何要求”。未定义行为的存在有多种原因：它允许实现支持扩展，处理与基于硬件的安全机制之间的交互，并执行激进的优化，同时允许忽略难以检测的错误。它明确赋予了编译器忽略整类难以检测错误的权利。</p>
<p>Uecker 表示，问题在于标准允许编译器对未定义行为做出任何反应，甚至达到“鼻中飞出恶魔（invoking nasal demons）”的荒谬地步。在编译器编写者看来，如果一个程序包含任何未定义行为，那么它就没有任何预期的语义。C++23 标准更进一步，明确规定标准对此类程序不施加任何要求。这导致开发者之间对于这门语言到底能提供何种预期产生了广泛的分歧。</p>

<p>“时间旅行”类 bug 最终应该会消失，但在许多其他情况下，即使标准很明确，编译器编写者也往往存在分歧。这些情况包括读取未初始化的变量（这几乎总是有定义的），以及指针的相等性比较（这始终是有定义的，但 Clang 和 GCC 都曾对其进行过错误编译）。</p>
<p>为了尝试解决所有这些乃至更多问题，C 语言委员会设立了三个专门针对内存对象模型、内存安全和未定义行为的研究小组。目前 C 标准中大约有 100 处未定义行为，但正在推进中的 C2y 草案已经移除了其中的 45 处。情况确实正在好转。</p>
<p>用于发现问题的工具库正变得越来越丰富：编译器警告、静态分析器、Sanitizer、基于大语言模型的工具、形式化验证等。当检测到潜在的未定义行为时，编译器发出警告的场景正在不断增加；最近的例子包括针对整数溢出和潜在的释放后使用（use-after-free）场景提供了更好的警告。静态分析器不仅可以作为独立工具使用，也越来越多地被直接内置到编译器本身中；例如，GCC 现在可以针对许多潜在的缓冲区溢出情况发出警告。Sanitizer 则通过插入运行时检查来工作；它们可以捕获大量的未定义行为，并在陷阱模式（trapping mode）下用于安全加固。</p>
<p>内存安全从来都不是 C 语言的强项，但 Uecker 想强调的是，它是可以改进的。该问题可拆解为三个子问题：类型安全、空间内存安全和时间内存安全。</p>
<p>他说，C 语言拥有强大的类型系统，剩下的问题是可以修复的。例如，无标签联合体（tagless unions）可能会导致类型混淆，但编译器可以通过一些额外的注解来强制实施类型检查。新的诊断工具可以捕获从 void 进行的不安全类型转换。跨翻译单元的类型检查在传统上对 C 语言来说并不是大问题，因为头文件被用来确保类型一致，但通过链接时检查器，这种情况还可以得到进一步改善。</p>
<p>空间内存安全——即边界检查——是一个已被部分解决的问题；编译器目前已能在许多场景下执行数组边界检查。在某些情况下，需要进行一些代码改动才能充分发挥此类检查的作用。例如，使用 counted_by 属性可以实现对柔性数组（flexible array members）成员的检查。</p>
<p>Uecker 表示，时间内存安全——即避免释放后使用（use-after-free）及类似漏洞——难度更大，而 Rust 在这方面无疑具备优势。尽管如此，实现更完善的时间内存安全强制保障仍然是可能的。像 CHERI 这样的架构在这方面也能提供帮助。Fil-C 则能够发现大量时间安全漏洞。</p>
<p>所有这些工具和语言层面的改进能否让我们达成完全的内存安全？他表示，彻底解决这一问题要么需要代价高昂的运行时检查，要么需要形式化验证。在不久的将来，最完备的成效将来自于受限语言与形式化验证工具的结合。</p>
<p>总的来说，他总结道，C 语言仍然是一门充满活力的语言，并且仍在持续演进。C23 标准移除了诸多存在问题的特性，包括旧式（K&amp;R）函数定义、对原码（sign-magnitude）和反码（one&#39;s-complement）机器的支持，以及三字符序列（trigraphs）。它还增加了精确位宽整数类型、带检查的整数运算等。C2y 将走得更远，增加 case 范围匹配、具名 for 循环、用于确定数组长度的 _Countof() 宏，以及大量的“去心魔”（demon removal）工作。它不会让 C 语言实现完全的内存安全，但这终究是一种可能性，并且随着时间的推移会变得越来越切合实际。在演讲的最后，他鼓励有兴趣的人士积极参与工作组。</p>

<p>使用 .chain() 对大型系统组进行排序很方便，但可能过于严格。如果系统集 X 链式排在系统集 Y 之前，那么 X 中的每个系统都必须运行完毕，Y 中的任何系统才能开始，即便涉及的系统根本没有触及相同的数据。这往往会导致工作线程处于空闲状态，等待系统集末尾的少数落后者，这种模式在渲染领域中经常出现。</p>
<p>新的 chain_weak()、before_weak() 和 after_weak() 函数提供了一种更宽松的替代方案。与常规对应函数一样，它们请求相连元素之间的执行顺序，但该顺序仅在数据访问实际发生冲突的系统之间保留。不冲突的系统则不作顺序约束，可以按任意顺序运行，包括并行运行。</p>
<p>当两个弱排序系统的数据访问实际发生冲突时，它们之间会保持常规顺序，因此排在前面的系统仍会先运行。两个仅通过链中处于它们之间的非冲突系统而产生冲突的系统也会保持有序。然而，非冲突系统可以自由地以任意顺序运行并重叠执行，从而提高并行度！</p>
<p>有两类系统被视为始终冲突，因此它们的顺序始终保持：产生延迟效果（如 Commands）的靠前系统（以便靠后系统能观察到它们，并照常插入 ApplyDeferred 同步点），以及排他性系统（exclusive systems，无论如何都不能与任何系统重叠）。</p>
<p>因为调度器只能感知其追踪的访问，所以通过只读访问上的内部可变性、全局状态或其他未追踪方式表达的依赖关系将不会被遵循。仅在系统不依赖此类隐式顺序时才使用 chain_weak，否则请继续使用 chain。</p>

<p>主题上下文（theme context）与一种名为 SemanticToken 的新型设计令牌结合使用。颜色的查找流程现在分为两个阶段：ThemeToken 首先被转换为 SemanticToken，随后结合使用 SemanticToken 与 ThemeContext 来查找颜色。<br />除了允许针对特定上下文进行颜色选择之外，这也使得设计新主题变得更加容易！用户不再需要繁琐地为上百个不同的主题令牌单独挑选颜色，语义令牌的集合要小得多，而且令牌与颜色之间的关系也直观得多。<br />Bevy UI 现在支持将 em 和 rem 作为尺寸单位。em 代表当前字体大小（由 EmSize 组件表示），rem 代表全局“根”字体大小（由现有的 RemSize 资源表示）。<br />当同一实体上存在 TextFont 时，EmSize 会从中派生；将其沿层级向下传递则由你的应用程序决定。<br />如果你希望在构建好 UI 后调整文本大小，这会特别有用，例如用于实现无障碍功能，或者仅仅为了改善 UI 在不同设备上的呈现效果。<br />默认字体大小现已改为 rem(1)，而非 px(20)。如果你不修改 RemSize，这不会产生任何影响；但这意味着当你修改它时，文本将在默认情况下按比例缩放。<br />组件现在可以选择启用“列摘要变更刻（column summary change ticks）”：<br />启用后，除了“每个实体的变更刻”外，系统还会存储一个“列变更刻”。这允许在查询变更时以较低开销跳过整列实体，而无需检查每个实体的组件以确定其是否发生了变更。<br />这使得变更操作（mutation）的开销更高，因为它们需要同时写入列变更刻和实体变更刻；但对于那些变更查询频繁但实际变更并不频繁的实体而言，这种权衡是完全值得的！我们已经看到变更刻在 GPU 网格提取代码中带来了 132 倍的加速！<br />FixedNode 是 Bevy UI 的一个新标记组件。<br />带有 FixedNode 组件的 UI 节点实体是相对于目标相机的视口进行定位的，而不是相对于其父元素。FixedNodes 不继承父级的布局、裁剪或变换上下文。它们的行为类似于“根节点”。<br />Bevy UI 现在可以绘制带有椭圆边框几何形状的节点。<br />BorderRadius 的字段现在改为了 CornerRadiuss，以便能够为每个轴设置不同的半径。<br />在调度器运行（并随之运行你的系统）之前，它首先会根据系统的顺序约束（.before()、.after()、.chain()）和系统集（system sets）计算系统的运行顺序。然而除此之外，调度器还必须解决冲突——如果系统 A 和系统 B 都修改组件 C，且 A 和 B 之间没有明确的顺序，调度器就需要挑选一个先运行。到目前为止，这一规则一直是非确定性的（non-deterministic）。<br />但在实践中，调度器对这些冲突系统所选择的顺序往往是“确定性但随意的”。简而言之，你的系统可能碰巧处于正确的顺序，但对图进行一次毫不相关的修改可能会突然使其处于错误的顺序。这种问题可能非常难以察觉。<br />隆重推出调度随机化（schedule randomization）！这将在保持任何显式系统顺序约束的同时，将系统的运行顺序随机化。一旦启用了调试特性，ScheduleBuildSettings 将包含一个 shuffle_seed 字段，用户可以设置该字段来将其调度随机化。例如：<br />这可用于“基于属性的测试（property testing）”，以验证系统即便处于不同的执行顺序下，是否依然满足某些属性。<br />不过也有一些注意事项。目前，当使用 auto_insert_apply_deferred 时，包含命令（commands）的系统总是会被放置在它们所能使用的最早同步点之前。这意味着即使你的系统可能没有正确的顺序，它们也可能由于其使用的同步点而“碰巧”具备正确的顺序。我们希望在未来修复这一问题。<br />此外，多线程执行器会贪婪地执行系统：它会寻找第一个尚未执行、依赖项已完成且没有其他冲突系统正在运行的系统。其结果是，即使洗牌后的顺序是 (A, B, C)，如果 A 和 B 发生冲突，C 仍可能会在 B 之前运行。这在测试中可能正是所期望的，但也可以考虑使用单线程执行器来避免这种情况。<br />该工具是互补的</p></div>

### [纳维-斯托克斯迷失在翻译中：为何人工智能自动形式化的 Lean 验证无法保证自然语言证明的正确性](https://arxiv.org/abs/2610.08144)
<div class="original-title-sub"><span class="orig-tag">原文</span> Navier-Stokes lost in translation: Why Lean verification of AI autoformalisation does not guarantee correct natural language proofs</div>

<div class="article-body" data-article-body="true"><p>自动形式化（Autoformalisation）正日益被用于验证数学文本，包括人工智能生成的文本，正如 OpenAI 宣称的纳维-斯托克斯方程解的爆破解（blow-up）证明中所展示的那样。在这一过程中，AI 系统将文本从自然语言（NL）翻译为诸如 Lean 之类的形式化语言。一旦完成这种翻译，以形式化语言表达的论证便能轻松实现机械化验证。本文的主旨在于阐明，由于在进行语义忠实翻译时存在诸多困难，这一过程可能完全无法为最初的自然语言论证提供置信度保证。特别是，我们着重指出，要实现语义保真的翻译，必须解决数学自然语言文本中的歧义问题，而该问题在可解性复杂度指数（Solvability Complexity Index, SCI）谱系/算术谱系中处于任意高的层级（SCI = ∞）。因此，通俗来说，提供语义保真的 AI 自动形式化比包括停机问题（其 SCI = 1）在内的任何计算问题都要困难。为了展示这一结果的影响，我们在实践中列举了若干 AI 将自然语言陈述及证明错误翻译为 Lean 语言的实例，这些错误导致了自然语言证明与其 Lean“验证”之间的脱节。其中包括 OpenAI 宣布的纳维-斯托克斯证明。特别是，我们展示了形式化后的 Lean 证明与纳维-斯托克斯方程解爆破的自然语言证明并不相符。</p></div>
