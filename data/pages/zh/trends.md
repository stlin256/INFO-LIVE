### [调优服务器以进行基准测试](https://david.alvarezrosa.com/posts/tuning-a-server-for-benchmarking/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Tuning a Server for Benchmarking</div>

<div class="article-body" data-article-body="true"><p>优化代码始于对其进行测量，而测量只有在具备可重复性时才有意义：在 5% 的噪声干扰下，2% 的提升是根本看不出来的。然而在未调优的机器上，相同的二进制程序在多次运行之间很容易出现几个百分点的速度浮动。在本文中，我们采用一个微型基准测试，一步步对机器进行调优，并在每次更改后重新测量，直到运行结果变得具备确定性。1 1 请注意，针对基准测试的调优与针对性能的调优不同：基准测试要求机器具备可重复性，即使以牺牲部分峰值速度为代价。然而，生产环境机器则追求榨干每一分极致速度。</p>
<p>我们的示例以短突发方式对双精度浮点数数组求和。实际服务很少会持续压满 CPU：它们处理一个请求，进入空闲，然后再被唤醒处理下一个。这里的每个计时迭代都在 2 毫秒的空闲间隔后执行一次 256 次求和的突发操作，该空闲间隔不计入测量时间2 2 PauseTiming / ResumeTiming 用于将休眠排除在测量时间之外，而 DoNotOptimize 用于防止优化器消除结果；如果没有它，编译器会删掉整个循环。</p>
<p>在发布模式下使用全部优化编译它：-O3，以及 -march=native -mtune=native -flto -ffast-math。然后运行十次重复并汇总结果。</p>
<p>最值得关注的一行是 cv（变异系数）：标准差除以均值。接近 3% 的批次间噪声——任何小于该幅度的优化都将无法察觉。让我们把它降下来。</p>
<p>在调整任何参数之前，先看看你在调优什么。lstopo 可以将整台机器呈现在一张图中：缓存、核心、SMT 配对，以及挂载在它们之上的 PCIe 设备。先从我的笔记本电脑看起：</p>
<p>图 1：我的笔记本电脑（Intel Core Ultra 5 135U）。三种核心：两个性能核（P-core），各带两个硬件线程（点状虚线）；八个能效核（E-core），以四个一组共享 L2 缓存；以及两个低功耗能效核（左下角），完全位于 L3 缓存之外。</p>
<p>在这里，核心的选择会直接改变你的测量结果：落在 CPU 4 上，你会得到一个时钟频率较低的能效核；落在 CPU 12 上，你甚至还会失去 L3 缓存。现在将其与我的家庭实验室服务器进行对比：</p>
<p>图 2：我的家庭实验室服务器（AMD Ryzen 7 PRO 8700GE）。八个完全相同的核心，配备完全相同的缓存；NVMe 硬盘和网卡（NIC）挂载在右侧的 PCIe 上。</p>
<p>在服务器上，每个核心都完全一致：同构机器是更好的基准测试平台。一旦基准测试涉及 I/O，PCIe 侧就变得至关重要：它展示了你正在使用哪个 NVMe 或网卡，以及在多插槽机器上它挂载在哪个 NUMA 节点下。</p>
<p>调度器可以自由地在核心之间迁移基准测试任务，而每一次迁移都会丢弃预热好的缓存。在混合架构 CPU 上情况更糟：性能核与能效核运行相同代码的速度大相径庭，因此结果会因进程落点的不同而呈现双峰分布。将基准测试绑定到单个核心（在混合架构上绑定到性能核）：</p>
<p>均值下降到 55.3 µs，变异系数（CV）降幅超过一半，来到 1.06%。这一收益比单纯的迁移成本所体现的还要大：现在每次突发都会唤醒同一个核心，因此该核心的时钟频率在各次突发之间根本没有时间回落。3 3 核心绑定将基准测试固定在核心上，但并未阻止其他任务使用该核心。在繁忙的机器上，可以更进一步，仅为基准测试保留该核心，可以通过内核命令行（isolcpus=2 nohz_full=2 rcu_nocbs=2），也可以在运行时通过 cpuset cgroup 来实现。</p>
<p>默认情况下，Linux 会随负载动态调节 CPU 频率，因此基准测试会在较冷的低频状态下启动，而在较热的高频状态下结束。将频率调节器（frequency governor）切换为 performance 模式以将频率锁定在高位：</p>
<p>并验证其是否生效：</p>
<p>重新测量得出的均值为 54.9 µs，CV 为 0.79%。这一增益看似不大，只是因为核心绑定已经让我们的核心时钟保持在温热状态：单独使用 performance 调节器，就能将未绑定的基线从 99.6 µs 直接拉升到 54.5 µs。无论哪种方式，突发都不会再在冷时钟下被唤醒。</p>
<p>CPU 仍然与其 SMT 同胞核心共享执行单元和 L1/L2 缓存：调度器放置在那里的任何任务都会干扰我们的测量。完全禁用 SMT：</p>
<p>CV 降至 0.26%，改善了三倍：该核心现在完全独占其执行单元和缓存。</p>
<p>即使使用了 performance 调节器，睿频频率也会随温度和功率预算而波动：同一程序在温热机器上的运行频率要低于冷机器。禁用睿频以获得稳定的时钟频率：</p>
<p>在这台机器上没有任何变化，因为我们的短突发本来就没有给芯片足够的时间来提升睿频。在睿频确实生效的机器上，均值反而预计会上升：你放弃了峰值性能。这种权衡完全可以接受，因为在进行优化时我们关注的是相对数值，而这些数值现在在多次运行之间具备了可比性。4 4 低延迟生产环境调优则做出截然相反的抉择并保持睿频开启：在那里，每一纳秒都至关重要。对延迟最敏感的量化交易机构甚至更进一步，运行超频服务器，锁定在高于出厂规格的固定全核频率上——通过更强的散热来换取速度与稳定的时钟。</p>
<p>以下表格展示了整个过程，每一行都在之前所有更改的基础上增加一项变动。我们把噪声从接近 3% 降低到了 0.26%，同时整体速度提升了 1.8 倍；半个百分点的差异现在变成了真实、可测量的有效信号。5 5 欢迎使用我 CppPlayground 仓库中的基准测试在你的机器上进行复现。</p>
<p>在更繁忙的机器上，还有一系列长尾参数值得尝试：禁用地址空间布局随机化（ASLR）、不可屏蔽中断看门狗（NMI watchdog）或透明大页（transparent huge pages）。bench-remote.sh 脚本应用了所有这些设置。重启后没有任何配置会被保留，但这正是你想要的：调优、测量，然后重启恢复成一台普通机器。</p>

### [要闻：自去年以来取得了很大进展，而我也参与贡献了一部分](https://shnatsel.github.io/state-of-simd-rust-2026/)
<div class="original-title-sub"><span class="orig-tag">原文</span> The state of SIMD in Rust in 2026</div>

<div class="article-body" data-article-body="true"><p>自去年以来取得了很大进展，而我也参与贡献了一部分！<br />在去年的调研之后，我开始向看起来最有前景的 SIMD 库贡献代码。接二连三的发展下，我现在成了 Fearless SIMD 的维护者之一。<br />为了避免利益冲突，我邀请了其他库（std::simd、wide、pulp、macerator）的作者来审阅本文草稿并提供反馈。不过，我依然保留了编辑把控权，所有疏漏均由我个人负责。<br />今年的调研比我之前的文章更加深入。所以系好安全带，让我们……从头开始！<br />执行算术运算的硬件很便宜，因此本世纪制造的任何 CPU 都配备了充足的算力单元。但你仍然只有一个指令解码模块，而且很难让它跑得飞快，这就导致算术硬件被严重低估和未充分利用。<br />为了绕过指令解码瓶颈，你可以一次性给 CPU 输入一批数字来进行单次算术操作（例如加法）。这也正是其名称的由来：“单指令多数据流”（Single Instruction, Multiple Data），即 SIMD。<br />与其将两个数字相加，不如将两批数字或两组“向量”相加，而所花费的时间与仅做一次加法大致相同。<br />在近期的 x86 芯片上，这些批次的大小最高可达 512 位，因此理论上你可以让 f64 类型的数学运算提速 8 倍，或者让 u8 运算提速 64 倍。但在实践中，它的运行速度可能更慢，也可能更快。<br />从历史上看，SIMD 指令是在 CPU 架构已经设计完成之后才添加的，因此在每个架构上，SIMD 都是一个拥有自己营销名称的扩展。<br />ARM 将其命名为“NEON”，所有 64 位 ARM CPU 都具备该扩展。<br />WebAssembly 没有市场营销部门，因此他们就直接称其为“WebAssembly 128 位紧缩 SIMD 扩展（WebAssembly 128-bit packed SIMD extension）”。<br />64 位 x86 出厂时配备了一个名为“SSE2”的扩展，它具有用于 128 位向量的基础指令；但后来他们在此之上添加了一大堆扩展，SSE 4.2 添加了更多操作，AVX 和 AVX2 添加了 256 位向量，而 AVX-512 则添加了 512 位向量以及更多操作。<br />上面这段话里的“后来”二字引发了一个问题。<br />如果你在一台 x86_64 CPU 上运行程序，并不能想当然地认为该 CPU 就拥有特定的某个 SIMD 扩展。因此在默认情况下，编译器不允许使用超过 SSE2 的指令，因为那些指令无法在所有 x86_64 CPU 上正常工作。<br />解决这个问题有两种途径。<br />如果你在一家只在自己的服务器或公有云上运行二进制文件的公司工作，你完全可以直接断言它们的设备都足够新，至少支持 10 多年前推出的 AVX2；一旦程序在任何不支持 AVX2 的设备上运行，就让程序直接崩溃或报错异常退出：<br />但是，如果你要分发二进制文件供其他人运行，这就不算是一个可行的选择了。<br />相反，你可以采用一种称为“函数多版本化”（function multiversioning）的做法：针对不同的 SIMD 扩展将同一个函数编译多次，而在程序实际运行时，检测 CPU 支持哪些特性，并据此选择合适的版本。<br />幸运的是，这个问题只存在于 x86 上。<br />ARM 在其 64 位 CPU 上强制普及了 NEON，并且在此之后并没有真正添加过有用的 SIMD 扩展（后文会详述）。<br />WebAssembly 则要求你编译出两个不同的二进制文件，一个带 SIMD，一个不带，并使用 JavaScript 来检测浏览器是否支持 SIMD。<br />利用 上，并且需要进行基准测试或紧盯汇编输出来验证它是否生效。详情请参见《你能信任编译器来优化你的代码吗？》（Can You Trust a Compiler to Optimize Your Code?）。<br />这是使用起来最简单的选项，不需要引入任何依赖项，并且会自动支持编译器所支持的所有指令集，无论该指令集多么冷门。<br />缺点是这种方法不是非常可靠。你的函数越大越复杂，编译器无法对其进行向量化的概率就越高。性能也可能随着编译器版本的变化或周围代码的更改而发生大幅波动。<br />浮点类型也需要特别注意。<br />浮点数很古怪。即便是像以合理的精度对浮点数数组求和这样琐碎的事情，其复杂程度也令人惊讶，参见《驯服浮点数求和》（Taming Floating-Point Sums）。<br />此前，自动向量化对浮点类型并不起作用，因为这会改变结果的精度（通常是变得更好，但编译器不允许改变任何可观察到的结果）。<br />这种情况在 Rust 1.98 中得到了改变，该版本稳定了代数运算（如 algebraic_add()），这些运算允许编译器改变可观察的结果，就像是一个危险性更低的 -ffast-math。在大多数情况下，你仍然必须重写代码来使用它们，代码才有资格获得向量化。<br />而且你仍然需要通过某种方式实现多版本化。既然谈到这里……<br />下面讨论的多合一 SIMD crate 也提供了多版本化功能，但让我们先快速浏览一下 multiversion，因为它对自动向量化最有用。<br />它使用起来非常简单：你只需在函数上添加 #[multiversion(targets = &quot;simd&quot;)] 注解即可。<br />但这种易用性掩盖了一个未在文档中说明的陷阱：调用带有 #[multiversion] 注解的函数会有少许开销。开销非常小——不到十几条指令，但如果你给它加上注解的函数本身就很微小，这就会显现为显著的开销。<br />作为一个经验法则，如果你的函数内部包含循环，请添加 #[multiversion]；如果它只处理少量数值，请添加 #[inline(always)]，只要在调用链的上游某处存在 <p>最大的缺点是它仅限 nightly 版本，且仍会偶尔发生破坏性 API 变动。因此某天你升级了编译器，代码突然无法编译，你就必须去修复它。但只要你能接受这一点，且只需要固定宽度的向量以及可能的多版本机制（multiversioning），那它其实相当不错！</p>
<p>std::simd 的存在意义在于它直接构建在 LLVM 之上，可以面向 LLVM 所能支持的任何平台，包括只有大型银行才会使用的奇特 CPU，或是只有中国政府才会使用的奇特 CPU。反过来说，如果 LLVM 内部没有完美匹配的操作供 std::simd 使用，那就没有备选方案（Plan B），实际上也不会使用任何 SIMD。</p>
<p>这种情况发生的频率令人不安。拿它的 sin() 来说再贴切不过了：打着 SIMD 的幌子交付标量实现简直就是大忌（原罪）。而且 reduce_sum() 不知何故在性能和精度两方面都是最糟糕的情况。所以千万别费心在浮点数上使用任何非基本的函数。</p>
<p>我们拥有的最接近正规三角函数的东西是 sleef crate，它是 SLEEF 移植到 std::simd 的部分实现，只是有一点微小的 bug。而这也是我通篇文章中能拿出来的最好的三角函数实现了！</p>
<p>在多版本机制方面，std::simd 具有独特的灵活性。你可以使用 multiversion crate，或者本节中任何其他 SIMD crate 提供的多版本机制。所有其他 crate 都只能配合自身内置的多版本机制工作。</p>
<p>它的 Simd API 看起来非常优雅，如果你能直接对 N 进行数学运算的话效果会很好，但你不能。即使在 nightly 版本中，该特性也非常不完整。没有它，使用 Simd 来获取硬件尺寸的向量虽然行得通，但要丑陋得多。</p>
<p>尽管在许多情况下你可以直接使用 std::simd 并且性能尚可，但零散地通过第三方 crate 拼凑特性收效有限。例如，sleef crate 无法与 multiversion crate 配合使用，你必须自行 fork sleef 并将它们缝合在一起。第三方扩展各自独立工作，却无法组合使用。</p>

<p>AVX-512 仅在不会造成性能损耗的较新型 CPU 上使用（见下文硬件部分）。你可以手动配置 multiversion 以实现此行为，但这并不是默认行为，且需要大量的样板代码（见上文）。而所有其他 SIMD 抽象 crate 都仅仅检查是否存在 AVX-512。</p>
<p>它最近发布了 v1.0 版本，并附带了安全政策等一切完备的配套。</p>
<p>最大的缺口是三角函数。目前还没有将类似 SLEEF 的库移植到 fearless_simd 机制中的成果。</p>
<p>wide 拥有诸多优势：良好的平台覆盖率、大量已实现的操作，并且它已经是 v1.0 版本了。它甚至拥有三角函数，不过其精度被明确声明为未作规定。</p>
<p>最大的缺点在于它从根本上与多版本机制不兼容。如果你不面向 x86，或者始终针对已知硬件使用 -C target-cpu= 进行构建，那倒无所谓，否则它会严重削弱性能。唯一的变通方案是 cargo multivers，但它仅适用于长时间运行的程序，否则其启动开销会让 SIMD 带来的性能提升相形见绌。</p>
<p>另一个缺点是不支持任何类型的泛型，无论是针对元素类型还是向量宽度。不过，你可以使用宏来绕过这一限制。与其将函数写成泛型，不如将其包装在 macro_rules! 中，并写成 $type::from_slice 而非 T::from_slice。这增加了一些样板代码，但也省去了泛型约束的样板代码，因此有得有失。我实践过这种做法，感觉还不错，特别是当你引入像 paste 这样的 crate 时。</p>
<p>如果你只针对少数几种类型（例如 f32 和 f64），无论如何你可能都想采用宏的方式，即使在具有泛型的库中也是如此，因为这还允许你拥有“泛型”大小的数组。实际的泛型数组大小是一项仅限 nightly 且不完整的特性。但你也可以使用 generic-array crate，或者干脆创建一个具有最大可能 SIMD 大小的数组来绕过这个问题。</p>
<p>pulp 的构建初衷是为 faer 线性代数库提供支持。这决定了它的优先级：已实现的操作大多是数学运算（例如没有 swizzle 操作），并且其 API 偏向于原生宽度向量。</p>
<p>固定宽度向量在技术上是可行的，但完全没有文档记录，用起来相当别扭。我在调研它们的过程中贡献了一些修复，包括针对一个健全性（soundness）漏洞的修复。</p>
<p>它原生不支持对元素类型进行泛型化，但我为 wide 描述的宏技巧在这里应该同样适用。</p>
<p>它的多版本机制是我见过的最冗长的。虽然有一个宏可以减少样板代码，但与其他替代方案相比，即使是那个宏也相当繁琐。</p>
<p>macerator 是 pulp 的同门近亲，采用了类似的设计。它的构建初衷是为 burn 提供 CPU 后端。</p>
<p>与 pulp 相比，它增加了对针对元素类型的泛型代码的支持，但移除了对内部函数（intrinsics）的安全访问以及绝大部分文档。它完全没有对固定宽度向量进行尝试。</p>
<p>它还默认启用了 SSE4.2，并为龙芯（LoongArch）添加了优化代码路径。</p>
<p>这是除 std::simd 之外唯一一个提供部分可移植 f16 数据操作的库，尽管支持的操作列表非常有限。将其与 AVX-512 一起使用需要 nightly 编译器，而在 NEON 上可以在 stable 版本运行。这仍然相当别扭，因为标准库的 f16 仅限 nightly，而这个 crate 必须在没有它的情况下勉强应付。</p>
<p>在 crates.io 上除了 burn 之外，没有任何项目使用它。</p>
<p>我排除了为单一特定项目构建的 SIMD crate（例如 jxl_simd、pathfinder_simd），因为它们不是面向大众的。我也排除了主要由 AI 驱动开发的 crate（例如 magetypes、simdeez、thermite），因为我无法推荐将它们用于生产环境，尤其是后两者存在令人担忧的 bug。</p>

<p>不支持 32 位 x86（你总是会回退到标量版本），但这在 2026 年并不是什么大问题。<br />fearless_simd 通过其 kernel! 宏，基本上为你提供了与 archmage 相同的工具。<br />这是一个声明式宏，而非过程宏。这改善了构建时间，但与 archmage 不同的是，它不支持用其修饰泛型或常量泛型（const-generic）函数。反正内在函数（intrinsics）和泛型本来也难以融合，所以通常这不是什么大问题。<br />它没有捆绑 safe_unaligned_simd，因为可以通过其可移植 SIMD 抽象来完成安全加载；但如果你真想把加载写成 _mm256_loadu_epi64()（通常是为了移植以此类方式编写的现有代码），你也可以自己引入它。<br />其 SIMD 级别与可移植 SIMD 抽象相同。因此，即便你非常清楚自己在做什么，你也无法选择启用早期、缓慢的 AVX-512，或者访问 NEON 的非基线扩展（如 aes 或 bf16）。<br />好的一面是，你可以轻松地混合搭配可移植 SIMD 和内在函数。这让你能够用可移植 SIMD 编写大部分算法，并仅在真正需要的地方使用少量内在函数。<br />在这方面，pulp 出人意料地强大。<br />如果你想使用不属于任何 SIMD 级别的内在函数，比如来自 aes 特性的 _mm_aesenc_si128，这是在不自行实现 SIMD 特性标记（tokens）的情况下安全做到这一点的最佳（且唯一）方法。<br />遗憾的是，它并未记录如何做到这一点。<br />如果你查阅文档，会发现以各种 CPU 特性命名的结构体（例如 Avx512ifma），以及构建该结构体的方法，该特性对应的内在函数就位于其上。所以你会以为只要构建它并调用该函数就行了，对吧？错了。<br />你可以这么做，而且也能运行，但性能糟糕透顶。你是在一个不能保证拥有额外 CPU 特性的函数中调用一个需要额外 CPU 特性的内在函数（请记住，CPU 特性检测可能会失败），因此该内在函数必须位于其独立的函数中。这样一来，你为了调用一条指令，就必须付出函数调用的开销——好几条指令。“好几条指令”可比一条指令多得多，因此函数调用开销占据了主导地位，导致性能暴跌。<br />相反，你必须做的是创建一个启用了所有所需特性的上下文，然后从该上下文中调用一系列内在函数。像这样：<br />请参见此处获取一个你可以实际运行的更完整示例。<br />为了完整起见，我应该提到 fearless_simd 仓库曾提议将类似功能作为一个单独、独立的 crate。它已经完全实现，但没有人站出来真正维护它，因此从未被合并。如果 pulp 有什么让你不爽的地方，不妨尝试那个方案，看看你是否愿意接手它。<br />除了 std::simd 和自动向量化之外，SIMD 内在函数是所有 SIMD 代码的基石。它们也非常直观：内在函数应当明确映射到特定的 CPU 指令。鉴于它们如此简单且重要，你会期望它们工作得非常出色。<br />事实并非如此。无论在 Rust、C++ 还是 C 中，都是如此。<br />在“给我这条确切的指令”与编译器优化之间，存在着根本性的张力。如果你让编译器将 SIMD 内在函数视为纯粹的黑盒，最终就会在其他地方产生低效。<br />例如，我在 ARM 上遇到的一个真实错误是 u32x4::from([1,2,3,4]) 运行缓慢。这实际上就是加载一个常量，而且 u32x4 的内存布局与四个 u32 组成的数组完全相同，所以它应该极其轻量——仅仅是一次加载。<br />解决方案是弃用针对 vld1_u32_x4 的黑盒实现，将其转换为编译器可以妥善优化的常规加载的兼容包装层。非常感谢 Rust stdarch 的维护者 Folkert de Vries 协助排查该问题并实现了修复。<br />那么，我们把所有内在函数都变成常规编译器操作的包装层不就行了吗？但愿真有那么简单。<br />那个 vld1_u32_x4 并不真正算是一个黑盒。它是一个还没有人为其编写优化 pass 的硬件操作。而如果你想把某些特殊的操作转换为编译器能够理解的基本块（或者仅仅是将略有不同的硬件指令的通用行为抽象出来</p></div>
