### [Git之后将走向何方](https://ersc.io/blog/what-comes-after-git)
<div class="original-title-sub"><span class="orig-tag">原文</span> What comes after git</div>

<div class="article-body" data-article-body="true"><p>East River Source Control 成立已有一年多了，但我们此前并未公开过多讨论我们正在做的事情。我们目前尚未发布任何具体产品，不过很快就会发布；在此之前，我们想先分享一些我们关于版本控制及未来走向的思考。</p>
<p>构建软件从根本上来说是一项协作任务。项目起步时往往规模不大，最终却会演变成为极其庞大复杂的系统。但无论 cargo new 生成的文件，还是包含数十亿行代码的单体仓库（monorepo），其本质都是一样的：源代码。安全可靠地存储这些代码、管理其随时间的变化，并确保开发人员随时可用，是任何技术机构最关键的核心职能之一。</p>
<p>过去，你可能通过一台共享服务器来存放代码。学术界随后是工业界逐步开发出了如今被称为源代码管理（SCM）和版本控制系统（VCS）的技术。即便是只在版本控制系统领域，多年来我们也见证了无数工具的兴衰：CVS、SVN 和 Git 统治了开源领域，但也存在许多其他工具，如 Perforce、ClearCase、Fossil、Mercurial、SCSS、Monotone、BitKeeper 等等。这些工具成为了存储代码以及团队协作修改代码的标准方式。</p>
<p>智能体开发（Agentic Development）的兴起改变了我们开发软件的许多方面，但也对版本控制系统施加了前所未有的压力。团队以有史以来最快的速度产出更多代码，导致代码仓库体积急剧膨胀，活跃分支数量激增，并在合并新工作时产生严重的冲突。智能体非常适合与单体代码仓库（monorepo）配合使用，因为它们能更容易地获取更多上下文，但这同时也加剧了上述问题。它们还将开发环境迁移到云端的隔离环境中，这意味着需要极快的克隆时间。所有这些问题过去通常只属于大型组织的烦恼，但智能体正把大公司的难题带给我们所有人。</p>
<p>我们相信，随着各机构不断扩大其雄心壮志，它们将需要下一代版本控制工具。然而，在这个领域采纳新工具时，人们表现得保守谨慎是完全在情理之中的。正如我前面所言，源代码是一个组织拥有的最珍贵的资产之一，变革不仅带来收益，也伴随着风险。我们深切理解这些顾虑，因此正在搭建一座从当下通往未来的桥梁。</p>
<p>不过，现存的 Git 服务器已经有很多了。是什么让我们与众不同？</p>
<p>从高层架构来看，绝大多数托管 Git 代码仓库的服务大致是这样的：<br />你的 Git 客户端通过 Git 协议连接到它们的服务。在服务内部，它们将你的代码仓库存储在磁盘上，并用一个服务层连接这两端。</p>
<p>当然，这种描述略微有所简化：系统背后会存在许多服务器，代码仓库前端也会有一个复杂的微服务层。存储会有副本冗余，系统内部在发生各种各样的事情。我们在此关注的是整体架构，但切勿将图示的简洁误以为是系统的简单。系统背后做了大量工作，但那些细节在此时此刻并不直接相关。</p>
<p>基于这种思路，以下是我们正在做的事情的示意图：<br />它看起来非常相似！这也是简化后的示意，例如架构中完全没有画出 GraphQL API 接口。但其中的区别至关重要：虽然你仍然可以使用普通的 Git 客户端通过 Git 协议连接到我们的存储，但我们的服务器上并不存储传统的 Git 代码仓库。取而代之的是，我们拥有一个自主研发的定制存储引擎。</p>
<p>简而言之，我们不认为 Git 代表了源代码管理的未来。Git 忠实地服务了开发者多年，但它是围绕 2005 年的约束条件设计的，而不是 2025 年，更不用说 2035 年了。例如，它是专为 Linux 内核打造的——一个开源项目。开源对我们的行业固然重要至极，但这意昧着它缺失了一些对于不公开代码的商业组织非常有用的关键特性。此外，尽管 Linux 内核绝非小型代码仓库（在 7.2 版本时约有 4300 万行代码），但业内各大主要公司在多年前就拥有以数十亿行代码计的单体仓库。在如此庞大的规模下，技术选型至关重要。</p>
<p>与此同时，考虑换用另一种版本控制系统也是极其困难的。Git 已经深度嵌入到了我们的工具链中：现在的规范不是 SvnOps，而是 GitOps！有太多工具原生支持 Git 协议，这使得我们很难考虑替代方案。在 Git 诞生之初，同时间段还涌现了其他几个项目，尤其是 Mercurial 和 Bazaar。但网络效应导致最终几乎所有人都转向了 Git。</p>
<p>那么该怎么做？那就是在保留 Git 协议的同时，重构底层的存储层。虽然这无法解决我们预见的未来所有问题，但确实大有裨益。与以单一 Git 仓库作为唯一真实数据源的系统相比，我们的系统能够实现水平扩展。而且由于这并非一个全局统一的中心化平台，其他公司的使用情况不会影响到你，因为它们都是独立的部署环境。这为你带来了可靠性和控制力——在谈论基础设施时，这是至关重要的两点。</p>
<p>那么对于未来那些可能性又当如何？如果你需要的扩展能力超越了 Git 协议的承载上限，或者需要 Git 无法提供的功能，该怎么办？支持该协议的策略具有一个优势：你可以同时支持多种协议。</p>
<p>这正是 Jujutsu（jj）发挥作用的地方。在 ERSC，我们是 jj 的忠实拥趸，部分原因在于它堪称支持渐进式采用的技术典范。虽然 jj 本身是一个独立的版本控制系统，但它具备对接多种不同后端的能力。大多数开发者使用带有 Git 后端的 jj 来直接操作本地 Git 代码仓库，但 Google 内部也开发了对接其 Piper 版本控制系统的后端。这使得单个开发者可以在工作中有权选择使用 jj，即使他们的同事仍在使用普通的 Git 客户端：对于服务器而言，它只是 Git 协议的又一个常规用户。我们将在服务端复现这一策略：</p>
<p>这为通往版本控制的未来铺平了一条平滑的道路：你可以在一开始继续使用常规的传统 Git，享受可靠且可扩展的源代码管理服务。单个开发者可以按照自己的节奏选择采用 jj；当你准备好更进一步时，jj 能够通过不同的协议与同一个底层引擎直接通信。</p>
<p>关于这一点需要重要说明的是：这是未来的工作，目前尚未推出。上游目前并没有“jj 原生”协议，我们也没有声称这就是我们正在构建的内容。如果这作为上游特性是有价值的且上游愿意支持，我们将与社区在此方面展开合作。并且该协议将会有详尽的文档说明，任何用于支持该协议的客户端修改都将开源。我们不会理所当然地认为，仅仅因为我们构建了这样的东西，上游就一定会采用它，毕竟 Git 协议在当今已经能够满足其绝大多数用户的需求。无论最终形式如何，我们都致力于成为 jj 生态系统中的优秀参与者。</p>
<p>存储解决方案只是团队进行代码协作所需的一部分。代码审查、CI（持续集成）、问题跟踪等等，不一而足。虽然传统的软件代码托管平台（forge）通常将所有功能打包为一个统一方案，但我们相信软件正在进入一个更具可定制性的时代。因此，我们的产品形态更像是积木组件，而不是一个单一的托管平台。存储是基础，因此它排在首位。但你可以确信，我们希望让我们的存储解决方案与你的其他软件栈协同工作，而不是与之冲突。虽然我们将在版本控制系统（VCS）领域提供多款产品，但如果你想在技术栈的其余部分采用自己的软件，完全没有问题。或者，如果你想采用我们的一些第一方组件并搭配你自己的软件，这也同样很好。</p>
<p>尽管这些目前都尚未正式推出，但我们很快就会逐步开放。与此同时，下周的 JJ Con 见！</p></div>

### [这并不是 YAML 规范的错，但是……](https://slugcat.systems/post/26-09-10-yaml-spec/)
<div class="original-title-sub"><span class="orig-tag">原文</span> It&#39;s not the YAML spec&#39;s fault, but</div>

<div class="article-body" data-article-body="true"><p>我又偶然读到了一篇痛骂 YAML 的博文。作者一边洋洋得意地反复提及“挪威问题”（The Norway Problem），一边散布着不实言论。于是我自己做了一番调查，以下是我的发现。</p>
<p>YAML™（发音与“camel”押韵）是一种人类友好的、跨语言的、基于 Unicode 的数据序列化语言，围绕动态编程语言的常见原生数据类型设计。它广泛适用于从配置文件、互联网消息传递、对象持久化到数据审计和可视化的各类编程需求。</p>
<p>多年以来，YAML 在许多领域变得非常流行。根据你作为程序员的经验资历，你很可能在配置文件或其他地方见过它。与此同时，它也引来了大量批评。通常存在三大问题，而且它们往往以不同方式相互交织：</p>
<p>这些批评中有一部分是合理的，但也有些是用词不当或错位的。至少在我看来是这样。让我们一探究竟。</p>
<p>在我的编程生涯中，我曾在许多项目中用过 YAML、TOML、JSON 等格式。我对所有这些格式都有一些微词，但我将专注于 YAML 的部分。</p>
<p>我制作的第一个真正使用 YAML 的项目，是 9 年前我自制的 Python Discord 机器人。这大概是我第一个不是给《太空空间站 13》（Space Station 13）做贡献的“大”项目，所以很多事情都得靠我自己。我最终决定将 YAML 用于配置文件。我没有遇到任何关于 YAML 常见的槽点问题，但我意识到这纯属走运。当时我只是在用 yaml.safe_load()，仅此而已。</p>
<p>这并不意味着使用 YAML 就毫无问题。关于我配置文件工作方式的一件傻事是，我实际上有两个文件：config.yml 和 override.yml。这是因为我总是需要加载 config.yml 来提供基本结构和默认值，然后将 override.yml 合并进去，以生成 Python 代码要访问的嵌套数据结构。但这是 YAML 的错吗？不，并不是。</p>
<p>我用 pickle 文件持久化数据时还遇到了其他序列化问题。比如“defaultdict 实例在序列化时会出问题，因为它们实际上存储了一个 lambda 表达式”这种蠢事。如今我可以回过头来看那个时候，并意识到这里的共同原因是什么：Python。或者更准确地说，是泛指所有动态语言。在像 Python 这样的动态语言中，根本不可能完全正确地完成“对象间互转”的序列化。</p>
<p>总之，下一个项目。《太空空间站 14》（Space Station 14）在所有“原型”（prototypes）（以及一些其他内容）中都使用了 YAML。这意味着实体、配方以及其他大约 200 种内容的数据定义都采用它。最初这个项目实际上使用的是 XML，但在我接管掌舵后，我决定将其切换到 YAML。在很大程度上，这是一个“巨大的成功”。我们真正遇到的最大问题是，新贡献者有时很难意识到它是缩进（空白字符）敏感的，从而会导致一些愚蠢的语法错误。虽然烦人，但并不致命。</p>
<p>我们是如何避免“挪威问题”的呢？秘诀就在这里：虽然具体的实现细节有所变化（我们现在到了“serv3”，实际上可能该叫 4 了），但我们始终用自己的代码来处理实际的对象反序列化逻辑。这意味着我们从库中提取图对象（如 YamlMappingNode、YamlScalarNode 等），然后由我们自己解析它们。我们不会在不该反序列化的时候将“no”反序列化为布尔值，因为我们只在读取需要接收布尔值的字段时才执行布尔值反序列化。令人震惊吧。</p>
<p>当然，这才是进行对象序列化的正确方式。你应该对照程序代码中定义的模型来进行序列化。这就是我们在《太空空间站 14》中避免荒唐错误的方式，也是我本来可以在 Discord 机器人中避免那些荒唐错误的方式。因此，每当我看到那些抱怨 YAML 有多“糟糕”、因为它可能会错误地将“no”反序列化的文章时，我脑海中浮现的只有“纯粹是动态类型带来的巨大技术硬伤（skill issue）”。</p>
<p>但这真的是事实吗？万一我错了呢？万一我们用错了 YAML，而规范恰恰要求这种行为呢？那我不就成了小丑吗！所以……让我们去查查该死的规范！</p>
<p>根据其官方网站，YAML 经历了几个重要的版本修订：1.0（2004 年 1 月）、1.1（2005 年 1 月）、1.2（2009 年 7 月）。让我们先从 1.0 版开始看看是怎么回事。</p>
<p>如果你开始深入研究，你会很快意识到，该规范在类型转换和解析应如何运作的细节上着墨甚少。第 2.4 节是这样说的：</p>
<p>在 YAML 中，纯（无引号）标量会根据应用程序获得隐式类型。本规范中的示例使用了 YAML 标签仓库中的类型，包括整数、浮点值、时间戳、空值、布尔值和字符串值等类型。</p>
<p>顺着链接，我们看到：</p>
<p>以下是对三个强制性核心标签的描述。YAML 要求支持 seq、map 和 str 标签。YAML 还在其标签仓库（可访问 https://yaml.org/spec/type.html）中提供了一组非强制性的通用标签。这些标签代表了大多数编程语言中的原生数据类型，或者在广泛的应用程序中非常有用。因此，强烈建议应用程序在适当的时候使用它们，以提高 YAML 系统之间的互操作性。</p>
<p>最后一个链接已经失效，但它可能指向类似于《YAML™ 1.1 版语言无关整数类型》的内容。例如看整数类型：</p>
<p>解析与验证：<br />有效值必须匹配以下正则表达式，该表达式也可用于隐式标签解析：<br />[-+]?0b[0-1_]+ # (2进制) |[-+]?0[0-7_]+ # (8进制) |[-+]?(0|[1-9][0-9_]*) # (10进制) |[-+]?0x[0-9a-fA-F_]+ # (16进制) |[-+]?[1-9][0-9_]*(:[0-5]?[0-9])+ # (60进制)</p>
<p>如果我们继续在主规范中搜索隐式类型，我们在第 3.3.2 节中看到以下内容：</p>
<p>纯标量样式异常允许未加引号的值表示数字、日期或其他类型的数据，而加引号的值则被视为普通字符串。通过此异常，处理器可以将纯标量与一组正则表达式进行匹配，以在没有显式[原文如此]标签的情况下提供此类类型的自动解析。</p>
<p>好的，这里提醒一下。YAML 规范确实对某些关键字（如“may”）遵循 RFC 2119 规范。你可能已经注意到了“may”（可以）这个词的使用，以及像“depending on the application”（取决于应用程序）这样的托辞。的确：我对 YAML 1.0 的理解也认同这完全取决于应用程序自身。</p>
<p>YAML 1.1 似乎并没有脱离这一点，除了把涉及的语言表述变得更加复杂。同样在第 3.3.2 节中：</p>
<p>标签解析特定于应用程序，因此 YAML 处理器应当提供一种机制，允许应用程序指定标签解析规则。[……]</p>
<p>直到 YAML 1.2，表述才变得不再那么含糊其辞。现在有了真正的“模式”（schemas）概念，具有切实的隐式标签解析规则，并且“核心模式”（Core Schema）成为了“推荐”的默认项：</p>
<p>核心架构（Core schema）是 JSON 架构的扩展，允许以更具人类可读性的方式展现相同类型。除非另有指示，这是 YAML 处理器应该使用的推荐默认架构。强烈建议其他架构也基于此构建。</p>
<p>但等等！YAML 1.2 架构中并没有六十进制（以 60 为基数）或 yes/no 布尔值！因此很显然，“挪威问题”（The Norway Problem）并不是这份 YAML 1.2 推荐规范导致的！</p>
<p>听着，我之前已经反复通读过 YAML 规范的这部分内容好几次了。我看到那一堆堆庞杂的“可能”（may）和“由应用程序决定”（up to the application），心里琢磨着：“好吧，所以 PyYAML、Ruby 和所有那些其他库只是自行决定选择了一个有缺陷的默认值。”给出这种简化的归因并不难，因为所有这些库都把不安全加载（unsafe loading）作为默认选项，所以很明显它们从一开始的设计就不怎么称职。</p>
<p>但话又说回来，事情真的仅止于此吗？我们可以去查阅更早的规范草案！也许它们能告诉我们一些东西。2001 年 12 月的规范草案是首次将隐式类型（implicit typing）写入文档的版本，并且从我的理解来看，它始终是生效的！太有意思了！快进大约一年，在 2002 年 10 月的草案中，规则似乎又变了，现在变成了“由应用程序决定”。看来在起草过程中，他们实际上改变了主意！</p>
<p>“为什么”是你在规范草案中找不到的答案，而且那里面绝对没有任何变更日志。要弄清楚规范中所有字句的来源，我们唯一的办法就是去翻看背后的讨论。</p>
<p>就 YAML 而言，这主要发生在上世纪初（2000 年代初）的一个邮件列表中。值得庆幸的是，该列表的存档如今在 SourceForge 上仍然可以访问。然而令人恼火的是，SourceForge 上的列表没有公开的存档下载（仅供项目管理员使用），按月份切分，并且分页展示。这意味着所有相关的数千封电子邮件散落在大量的浏览器标签页中。</p>
<p>如果不借助在真正的邮件客户端中打开这些邮件的能力，深入探究这件事情是根本不可能的。于是我操起 Python，抓取了 SourceForge 那该死的网站。如果他们不想让我爬取他们的数据，他们就应该以负责任的方式提供其托管的公开存档供人访问。公开的查看器仅提供用户名、纯文本消息内容和时间数值（出于隐私原因没有电子邮件地址），但这些已足够让我将数据倾倒进一个 .mbox 文件并在 Thunderbird 中加载。如果你感兴趣，我那些写得很烂的脚本放在这里和这里。如果你想要我抓取的 mbox 文件，放在这里。</p>
<p>没错，那确实是海量的邮件。</p>
<p>邮件有数千封，而我也只浏览了其中的百分之几。我主要寻找与隐式类型和标签解析（tag resolution）相关的信息：它是如何诞生的，规范的作者们究竟怀揣着怎样的意图？当然，在搜索关键词的同时点击数百封邮件，不可避免地意味着我读到的内容远不止这些。</p>
<p>这一切的核心，是几个充满干劲的人在做他们想做的事。其中有犯傻的举动，有各种出于兴趣而露面的随机新人，有漫长的争论。有一次，规范文档甚至下线了，因为服务器主机设在秘鲁。这是我第一次费心去“调查”这类事情，虽然古老的邮件列表对我来说大多很陌生，但那种氛围依然让我觉得与我所习惯的社群有些相似。</p>
<p>在我们继续之前，我必须先讲清楚：我出生于 2000 年；在我学会走路之前，这些人就已经在讨论隐式类型规则了。我并未亲身经历过其中的任何事情，因此我不得不对这一切发生时的大致背景做出自己的推断。</p>
<p>YAML 源于千禧之交的 XML“炒作”周期。许多人和企业认为 XML 是通向未来的神奇灵药，因为它可以实现数据互操作性。我们将所有数据都放进 XML 中，现在我们拥有了一大堆神奇的工具，比如 XSD、XPath、XSLT，以及天晓得以“X”开头的其他各种首字母缩写词。见鬼，有些公司甚至在兜售硬件中间盒（middlebox），其唯一的工作就是基于更多的 XML 来验证和转换 XML！这种语言被用于一切场景：配置文件、序列化状态、充当数据库、RPC 协议等等。</p>
<p>但是，XML 真的很奇怪，它是一种标记语言。将其与 HTML 对比：如果你从这个网页中剥离所有标记……它至少对人类来说仍旧勉强算连贯。但如果对典型的 XML 用例这样做呢？它将彻底失去一切意义。我们真的在标记内容吗？</p>
<p>此外，如果你曾经尝试为任何事物设计过 XML 格式，你可能根本无法完全确定某项内容应该作为标签名、属性还是文本内容。我相信很多人都针对这个话题写过立场鲜明的指引，但事实是，它真的非常不直观。而且，老天，看看上面那个例子中重复内容的数量吧。正如你可能意识到的那样，JSON 或 YAML 都没有这些问题。如果你对这两者略有了解，脑海中浮现出上述示例在它们当中的模样绝非难事！</p>
<p>YAML 在很大程度上是为了支持 XML 的所有用例而设计的，这意味着它在设计时兼顾了相关工具的方方面面（包罗万象）。数据可移植性、序列化、配置文件，该死的一切。许多人有着截然不同的用例，我读到的一些电子邮件中也反映了这一点。</p>
<p>为什么 YAML 规范比 JSON 复杂得多？因为，好吧，它本身就想这么复杂。关于“YAML 处理器”应该如何工作，规范中有篇幅浩繁的表述。在邮件列表上，曾频繁顺带提及并探讨关于“YPATH”、“YAML 架构”、“YAML-RPC”等诸多设想。人们想要用 YAML 实现你可以用 XML 做到的一切。</p>
<p>当然，XML 的炒作周期过去了，随之而去的还有对 YAML 同等替代品的所有渴望。我前面提到的大多数雄心勃勃的目标呢？从未实现。现如今，人们在编写配置文件时，大多只是将 YAML 用作比 JSON 更好用的替代方案。至于这是好事还是坏事，就留给你们去评判了。</p>
<p>我自己对此也有很多想法，我之所以想写这篇博文，部分原因也是为了能够在互联网上发表我自己的看法。对比几种语言，加入我自己的见解和观点，诸如此类。</p>
<p>然而最终，我未能以一种令自己满意的方式将上述内容系统地组织起来，而这篇博文在其余部分均已完成的情况下搁置了好几个月。所以，为了能够真正把它发表出来，我删掉了那部分内容。</p>
<p>不过，如果你确实想知道我对 YAML 的最终评价：它还行吧。</p>
<p>正如我之前所言，YAML 最初本应具备更强的隐式类型规则。他们当时非常清楚这其中所有的兼容性风险！在 2002 年 6 月，显而易见的是，他们正难以确定一套既能满足需求又毫无歧义的精确隐式规则。他们既希望支持无引号字符串，又希望支持隐式整数和浮点数，或许还有日期，并且当时尚未就布尔值达成一致。有人曾提出一些构想，要求对像日期这类较为“小众”的类型进行限定声明（例如 ! 2026-05-22），但随之而来的是铺天盖地的“这在我的使用场景下太难看了”。他们当时最终确定的方案[4]大致长这样：</p>
<p>正如一封邮件善意指出的那样，这些过时的语法有一部分在 2004 年 1 月的 1.0 规范中并未被清理干净！看看你能不能找出来！</p>
<p>到了 2002 年 9 月，关于类型如何运作的话题再次被提及。起因是一位新人试用 YAML 时遭遇了时间与日期类型的局限性和风险，其他一些人也对现有的隐式类型规则感到不安。于是齿轮开始转动，“DWIM”（Do What I Mean，按我说的做）提案被提出，后来被重命名为“未知类型”提案：</p>
<p>- 简而言之：这项提案让 YAML 实现 DWIM。如果你希望它这么做的话。如果你想严格一些，就为每个节点添加显式的转换方法（transfer method），并且/或者提供验证/类型化/比较模式（schema）等。如果你不想严格，只需将所有内容都视为字符串（但始终保留转换方法）。</p>
<p>据我理解，这项提案随后被合并到了 2002 年 10 月 31 日修订的规范中。此外，他们似乎希望尽快完成 1.0 规范，因此将非核心类型移了出去，这样就不必让它们和规范的其余部分同时截断。无论如何，在这个时间节点上，我相信我的解读是正确的：规范作者们的预期是“默认情况下所有内容都应该是字符串”，而这一意图一直延续到 2024 年 1 月[5]都没有改变。这一点在规范作者们不同时间段的多封电子邮件中得到了再次印证：</p>
<p>“如果我和 Ingy 哪天完成了下一版 PyYaml，它的第一个特性就会是一个‘所有值均为字符串’的加载器（loader）。”</p>
<p>“一个标准的、不感知 Schema 的 Loader 应该始终将此类值加载为字符串。如果你想让日期作为对象，只需混入一个日期加载器类即可。”</p>
<p>“现在这成为可能了，因为类型已经移出了规范之外。解析器不需要识别它们。这是我们在简化 YAML 逻辑方面做出的最明智之举。”</p>
<p>“这是阻碍我更广泛部署它的最大障碍：不得不向其他人解释关于值语法的复杂规则。说‘只需让你的值以字母或数字开头就没事’，远比说‘所有纯数字不行。YYYY-MM-DD 不行。以 !&#39;&quot;% 开头不行。t/f/~ 不行’容易得多。”</p>
<p>“是的。现在情况完全不是这样了。基本上每个标量都被解析为带有类型的字符串。而且（在缺少 schema 的情况下）完全由 Loader 决定如何处理该字符串和类型。我们*鼓励* Loader 在合理的情况下支持 YAML 类型仓库。而且多数情况下，默认将值作为字符串加载，并在用户开启 load_dates_as_objects 选项时将日期加载为对象，才是合情合理的。”</p>
<p>“哪怕是纯标量（plain scalar）也是有类型的。它的类型是空字符串。这是给 Loader 的一个提示，让它根据 Loader 默认配置、用户设置的 Loader 选项或 Schema 文档中的类型提示，去做最合乎常理的处理。”</p>
<p>“我的意思是，让你的 YAML 模块在默认情况下始终加载字符串。完全不要有隐式类型转换。这是推荐的默认行为。”</p>
<p>“隐式类型是可选的，它*不*属于基础标准的一部分 [1]。”</p>
<p>“[2] 不幸的是，目前的 PyYaml 在隐式类型处理上并不能真正达到核心规范其余部分的水准。这是历史原因造成的，在编写 PyYaml 时，隐式类型*并非*可选，并且由此引发了诸多问题，随后规范意识到这一错误并做出了修改（感谢 Steve Howell）。希望 Tim 正在开发的新版 PyYAML 能先专注于核心规范，至于数据类型则留待日后解决。”</p>
<p>“好吧，那么，我记不清我们在‘y’和‘n’布尔值上的立场了。Syck 一直不支持它们，因为它们”</p></div>

### [我的 HTML 样板代码](https://vale.rocks/posts/html-boilerplate)
<div class="original-title-sub"><span class="orig-tag">原文</span> My HTML Boilerplate</div>

<p>直到首个正式标准——HTML 2.0 确立，规范的文档结构才真正成型。用于声明文档类型并处理兼容性的 DOCTYPE 声明成为了必不可少的组成部分，head 与 body 部分亦是如此：</p>
<p>自 HTML 2.0 于 1995 年问世以来的数年间，万维网发生了翻天覆地的变化。然而，网络标准界有一句名言：“不要破坏网络（Don’t Break The Web）”。虽有一些例外，但总体而言，即使岁月流转，在网络诞生初期开发的网站在现代浏览器中仍应能正常运行。然而，为了保持这种兼容性，就存在因担心破坏现有网站而导致任何变更都无法推行的风险。</p>
<p>网络应对这一问题的一种方法，是在 HTML 文档中引入某些预期的特定元素。如果该元素存在，则启用新功能；如果不存在，则直接回退到旧功能。再结合整个网络中不同集成与系统的要求，这意味着会出现相当多的“样板代码”（boilerplate）——即几乎在每个新建或维护的网站中都会重复出现的代码。HTML 样板代码通常既用于启用现代功能，也用于设定网站偏好和细节，涵盖了诸如网站如何在社交媒体上嵌入展示、应加载哪些样式、浏览器应如何为网站周围的界面适配主题等各色细节。</p>

<p>这是 HTML 5 引入的 HTML 现行标准（living HTML standard）的文档类型声明。我始终会包含它，以避免进入怪异模式（quirks mode）。</p>
<p>打开包裹整个文档的 html 标签，并通过带有 lang 属性的 RFC 5646 规范标签定义文档语言。该语言设置提供了整页的默认语言，并且可以针对单个元素进行覆盖。指明语言对于自动翻译、诸如连字符等排版细节，以及辅助技术（尤其是屏幕阅读器）至关重要。</p>
<p>我放在 head 中的第一个元素始终是值为 UTF-8 的 charset meta 标签，这是自 HTML 5 以来唯一有效的编码方式。它始终位于 head 的最顶部，因为该声明必须出现在文档的前 1024 个字节内，且应位于任何可能被损坏解析的元素之前。</p>

<p>很多人会加上 initial-scale=1，然而经过广泛的测试与研究，我发现已经没有必要再写这一项了。当元素横向超出视口宽度时，包含它可以改变页面的呈现效果，但这种情况根本就不应该发生，我建议不要这样做。</p>
<p>minimum-scale、maximum-scale 和 user-scalable 都会严重损害无障碍访问（accessibility），绝不应该使用。一旦在网站中发现它们，通常都应该将其剔除。</p>
<p>使文本依据系统设置进行缩放。如果存在该标签，则页面的样式必须预先考虑到这一点并做相应编写。这对于避免内容缩放带来的无障碍缺陷尤为重要。</p>
<p>页面的标题。这是一个必填值，会在许多场景下显示。它在加入书签时用作页面名称，在搜索引擎中用作标签页名称，以及任何需要页面名称的场景。我通常会先展示页面标题，紧接着展示网站名称。</p>
<p>任何必须导入的样式都可以在这里引入。样式通常应在页面 head 中引入，而不是在样式表内部使用 @import CSS at 规则，以此避免瀑布式请求——即必须先获取样式表，才能进而去获取其他样式表。</p>
<p>即使经过子集化和其他优化，复杂的无级可变字体（variable fonts）体积依然相当庞大，因此我会预加载那些已知会在页面上使用的字体。即使字体与页面同源，crossorigin 属性依然是必需的。我始终使用 WOFF2 格式提供字体，因为它是受广泛支持且性能最佳的字体格式。</p>
<p>og:title 用于诸如社交媒体展示等嵌入场景。它是 Open Graph 协议众多元数据值之一。虽然我通常会在元素末尾包含网站名称，但我会在 og:title 中略去它。在绝大多数情况下，嵌入展示都会在标题旁显示域名或 og:site_name，再加就会造成重复。</p>
<p>我主要将这个 meta description 字段作为一项搜索引擎优化（SEO）手段来处理。以往主流搜索引擎会在搜索结果页面上直接向用户展示该描述，不过现在它们大多直接从文档正文内容中抓取。</p>
<p>og:description 有时会显示在嵌入预览中。如果缺失，嵌入卡片通常会省略描述，或回退采用 meta description。我喜欢在这里写简短且通常诙谐风趣的内容，以激发读者的好奇心，并适合在社交媒体或聊天信息流中呈现。</p>
<p>网站图标（favicon）对所有网站而言都是重要的品牌标识——尤其是当打开了许多标签页时，用于识别特定标签。我以 SVG 格式提供网站图标，因为它们支持良好，能够动态自适应浅色/深色模式，在各种尺寸下都显示出色，并且无需再维护一套不同尺寸的光栅图图标。</p>
<p>og:image 中定义的图片通常会展示在社交媒体或聊天平台等网站嵌入卡片中。几乎在所有网站上包含它都是有益的，因为它能补充上下文，并且通常能扩大嵌入卡片的尺寸以获得更好的视觉存在感。嵌入图片对替代文本（alt text）的支持参差不齐，因此不可过度依赖。有些网站支持，有些则忽略，还有些支持方式很奇特。我会尽量添加 alt 文本，但保持简短。1200px 乘 630px 是广泛支持的尺寸，而在我测试过的现代图片格式中，WebP 是兼容性最好的。</p>
<p>指向页面权威版本的规范链接（canonical link）对于指明何为权威可信来源非常重要。当存在重复内容时，这尤为关键。</p>
<p>要在嵌入卡片中显示的网站名称。正如前文所述，某些嵌入预览会在页面标题旁展示该名称。</p>
<p>author 标签显然指明了页面的作者。它并非严格必要，但有助于开发者识别谁对该页面负责。</p>
<p>将 color-scheme meta 标签的 content 属性值设为 light dark，可告知浏览器该网站同时支持浅色和深色模式。在 head 中定义该标签能够防止出现无样式内容闪烁（FOUC），比如在网站和浏览器均设置为深色模式时突然闪现一片刺眼的白屏。</p>
<p>该标签用于为作为渐进式 Web 应用（PWA）安装的网站定制浏览器界面（browser chrome）主题，同时也用于在 Android 版 Chrome 中定制浏览器界面主题（不过仅限浅色模式）。其他一些浏览器也会以不同方式解析这些值。我使用 media 属性分别独立设置浅色和深色模式下的颜色。</p>
<p>如果网站有聚合订阅源（syndication feeds），那么将其包含在 head 中便可允许浏览器对其进行自动发现。</p>
<p>如果网站集成了搜索功能，创建 opensearch.xml 文件并在文档 head 中对其进行引用，便能将其暴露给浏览器，从而提供丰富的搜索体验。具体的体验因浏览器而异，但在很多情况下，它允许用户直接通过浏览器自身的地址栏在站内进行搜索，并且还提供了一种添加搜索引擎的简便方法。</p>
<p>我是渐进式 Web 应用（PWA）的倡导者。我非常喜爱它们，而且许多网站都能从成为 PWA 中获益，即使该网站并非典型的“应用程序”。对于大多数网站，即使唯一的益处仅仅是当人们把网站添加到主屏幕时外观呈现更美观，我也会为其定义一个 manifest 文件。该声明有助于浏览器发现此清单文件。</p>
<p>这只是样板代码。它是一个模板，涵盖了我几乎在每个网站上都会包含的内容，仅作少量微调。每个网站必然都会根据自身需求在此基础上有所增减，但这构成了合理的基石。</p>
<p>如果页面预计会被学术引用，那么可以考虑加入 Google 学术搜索（Google Scholar）的 citation_* meta 标签以及都柏林核心（Dublin Core）的 dc meta 标签。如果页面代表一篇文章，那么应包含来自开放图谱协议（Open Graph Protocol）的 article 命名空间的标签，以及可能与发布系统相关的标签。视频、音频、书籍或其他内容类型同样会采用不同的标记方式。许多网站也能从 JSON-LD 结构化数据中获益。</p>

### [Windows XP 是用什么算法来选择你的初始用户头像的？](https://devblogs.microsoft.com/oldnewthing/20260909-00/?p=112683)
<div class="original-title-sub"><span class="orig-tag">原文</span> What algorithm did Windows XP use to choose your initial user picture?</div>

<div class="article-body" data-article-body="true"><p>我前段时间提到过，Windows XP 是从 %ALLUSERSPROFILE%\Application Data\Microsoft\User Account Pictures\Default Pictures 目录下的图片中随机选择你的初始头像的。但看起来大家想了解更多细节。</p>
<p>有人尝试探究过 Windows XP 在首次创建账户时用来决定使用哪张头像的随机数生成器（RNG）吗？<br />—— Xeno (@XenoPanther) 2025年12月11日</p>
<p>这里的随机数生成器正是我们的老朋友 RtlRandomEx，并使用 GetTickCount() 的当前返回值作为初始种子。</p>
<p>该函数采用了一种单遍遍历（one-pass）的随机选择算法。我能立刻想到这一决定的两个好处。首先，相较于先统计全部项目数量、再在 1 到 n 之间随机抽取一个数字、最后进行第二遍遍历来找到该索引对应项目的朴素两遍算法，单遍算法效率更高，因为它减少了对文件系统的调用次数——而文件系统调用正是性能瓶颈所在。此外，如果在代码运行期间目录中的文件数量发生变化，单遍算法还能避免引发复杂问题。</p>
<p>这种单遍算法是蓄水池抽样（reservoir sampling）在 k 等于 1 时的特例。这一特例允许采用一种更加简单的定制算法。</p>
<p>该算法的运作原理在于：在一个包含 n 个项目的集合中，最后一项被随机选中的概率是 1/n。如果最后一项没有被选中，那么你需要在前 n − 1 个项目中进行随机选择，这可以通过递归的方式来解决。</p>
<p>将这个递归逻辑正向推进：首先从基本情况开始——如果列表中只有 1 个项目，那么你唯一的选择就是选中该项目。否则，如果列表中有 n 个项目，先从前 n − 1 个项目中随机挑选一个，然后以 1/n 的概率替换为第 n 个项目。</p>
<p>作为最后的安全防护措施，代码在抽样采样达到 100 张图片后便会停止。这避免了在有人往 Default Pictures 目录中放入 100 万个文件时出现病态异常行为。</p>
<p>雷蒙德（Raymond）参与 Windows 的演进已超过 30 年。2003 年，他创办了名为 The Old New Thing 的网站，其受欢迎程度远远超出了他最大胆的想象，这一发展至今仍让他感到有些心惊肉跳。该网站还催生了一本书，书名巧合地同样叫作《The Old New Thing》（Addison Wesley 2007 年出版）。他偶尔会在 Windows Dev Docs 的 Twitter 账号上露面，讲讲一些没有任何实用信息的故事。</p>

### [原生开发如今是 Shopify 移动端的未来（2026）](https://shopify.engineering/back-to-native)
<div class="original-title-sub"><span class="orig-tag">原文</span> Native is now the future of mobile at Shopify (2026)</div>

<div class="article-body" data-article-body="true"><p>编程智能体（Coding agents）改变了将移动端应用重复开发两遍的成本代价。以下是 Shopify 为何正在从 React Native 重返 Swift 和 Kotlin 原生开发。</p>
<p>Shopify 工程团队</p>
<p>早在 2020 年，我们就决定全面押注 React Native，事实证明这一抉择取得了巨大的成功。只需编写一次功能代码，我们便省去了海量时间，还让没有移动开发背景的开发者也能参与应用的开发，使我们彻底告别了疲于奔命对齐双端功能特性的日子。</p>
<p>2025 年 1 月，我曾撰文表示 React Native 前途光明，Shopify 亦计划继续对其加大投入。基于我们当时的认知，这毫无疑问是正确的。React Native 当时在我们的业务中运转良好，而且它至今仍是一个出色的框架。但自那时起，编程模型有了突飞猛进的发展；对于我们的应用和团队而言，分别用 Swift 和 Kotlin 实现相同的功能，已不再具有昔日那般高昂的成本。</p>
<p>我们绝不会仅仅因为某项决策在过去取得过成功就对其墨守成规。当一项核心假设发生转变时，我们愿意回头重新审视这是否仍是明智之举。大语言模型（LLM）颠覆了促成我们 2020 年决策的核心假设之一，因此我们从第一性原理出发，对移动端技术栈展开了全面重估。</p>
<p>我们的评估结果指引我们回归原生开发。</p>
<p>2020 年我们决定从原生转投 React Native，主要基于三个考量：</p>
<p>React Native 始终如一地兑现了这些优势。虽然我们发现自己耗费了大量的时间和资源去优化性能、改进 React Native 的关键底层基础，以及跟进框架升级与外部依赖项，但这些在当时都是能够接受的权衡取舍。使用 React Native 带来的收益，远远超出了我们在这些方面所必须付出的投入。</p>
<p>Shopify 早在 2021 年（比 ChatGPT 问世还要早一年！）就开始利用 LLM 来辅助构建软件。最初，我们用它们来实现具体功能、排查并修复缺陷以及审查代码。随着模型能力的增强，我们托付给它们的工作复杂度也水涨船高。到了 2025 年底，它们已不再仅仅是帮助我们更快地编写代码，而是让我们开始反思：将一套软件分别构建两次，是否还等同于要付出双倍的工作量？</p>
<p>我们决定重新评估移动技术栈，并着手进行原型设计，以验证过往的技术选型是否依然坚挺。我们借助 LLM，使用 Swift 和 Kotlin 重建了旗舰应用中的数个核心模块，其成效之出色超乎想象。智能体：</p>
<p>选择原生依然意味着要在两个独立平台上构建和维护软件，这一成本并没有凭空消失。但不同之处在于，智能体现已能够承担足够多的实现、转换、测试以及审查工作，双平台维护已不再是如 2020 年那般决定去留的关键阻碍。</p>
<p>React Native 应用同样可以做到运行飞快，我们的应用便是明证。我们之所以做出这项调整，是因为智能体大幅摊薄了共用代码实现所带来的红利，而针对各个平台量身定制的原生优势却依然无可替代。原生开发让我们更贴近操作系统底层能力和第一方原生工具链，在我们的代码与平台之间减少了框架层和依赖层的隔阂。</p>
<p>在深入探讨具体迁移路径之前，我们希望确保这次过渡走得平稳而干净。从一开始，我们就怀着回馈 React Native 生态的初衷去改进它。我们开源的多款工具库已成为各自领域的标杆之选。对于社区给予的热烈反响，我们深表感激，并将竭尽全力确保此次交接平稳顺畅、不留意外。</p>
<p>Shopify 将继续赞助该项目至 2026 年底，William Candillon 此后将继续推进该项目。他将在接下来的几个月内复刻（fork）该代码仓库，并以新名称发布该库。原仓库将在过渡完成后正式归档。我们会在整个过程中持续发布更新动态，确保大家拥有充足的时间进行迁移。如果您的应用依赖此库，请考虑提供赞助支持。</p>
<p>该库每周拥有约 200 万次下载量，已成为 React Native 中渲染高性能列表的既定标准方案。鉴于其对整个生态系统至关重要，Shopify 将继续修复破坏兼容性的关键问题。我们目前正与数家公司探讨由其接管 FlashList 长期维护事宜。如果您对此有意向，请在此处与我取得联系。</p>
<p>Restyle 的用户群体相比我们其他库要小，因此我们将对该仓库进行归档。我们将保障其正常运行至 2026 年底，之后将停止官方维护。我们非常欢迎任何人 fork 并接续推进该项目；若有团队愿意接手，我们也将协助完成交接。</p>
<p>Shopify 拥有多款大型移动应用（Shopify、Shop、Point of Sale 以及 Inbox）。全球数以百万计的商家和消费者每一天都依靠这些应用来维系生计、选购心仪品牌的商品。</p>
<p>我们曾在逐步向原生迁移（棕地模式/brownfield）与从零全新重构（绿地模式/greenfield）之间进行过反复权衡。过去在向 React Native 迁移时，针对部分体量最大的应用，我们采用了棕地模式，因为完全重写耗时动辄数年，而且在重写期间我们不得不停下交付新功能的步伐。</p>
<p>然而这一次，出于以下考量，绿地模式成为了毋庸置疑的胜出方案：</p>
<p>在各大应用商店购物榜常年名列前茅的 Shop 应用成为了首个迁移目标。在 AI 的全力协助下，团队从概念验证到完成纯原生应用的重构并在应用商店正式上架，仅仅耗时 12 周。我们已在此处详细撰文复盘了这次迁移全貌。</p>
<p>Shopify 应用（作为我们规模最庞大的旗舰应用，拥有 300 多个独立界面、主屏与锁屏小组件、Apple Watch 独立应用、表盘复杂功能、Siri 快捷指令等）的迁移工程也已全面展开，计划于今年晚些时候发布。其余应用的迁移工作亦将紧随其后展开。</p>
<p>把 React Native 代码库直接一股脑交给 LLM，期望它一次性（one-shot）吐出完全对应的原生功能代码，这种想法固然诱人，但根本无法行得通。即便你让它预先尽可能收集全量信息，并固化为规格说明和任务文件后再着手实现，最终产出的也只是一堆根本无法维护、无法上线的废代码。</p>
<p>为了攻克这一难题，我们自主打造了一套名为 Helix 的系统，采取更为渐进的方式。它从不预设初次输出就是完全正确的，而是搭建了一套闭环机制：任何不够完美的尝试在被打磨成符合质量标准的合格产物之前，绝无可能进入下一环节。</p>
<p>开发者只需将 Helix 指向特定界面。Helix 便会读取对应的 React Native 代码，并拆解出一系列可在数分钟内审阅完毕的检查点（按逻辑排序的精细工作微切片）。随后，它按照检查点逐一构建：每个检查点都必须通过自动化测试来证明行为符合预期，在视觉审查中与正在运行的原应用完全一致，承受住两个对抗性代码审查智能体的严苛挑剔，并最终获得人工开发者的首肯，方可提交代码并开启下一阶段。审查过程中的每一条反馈都会被系统沉淀记忆，因此随着迁移的推进，整个闭环的自主化程度亦会越来越高。</p>
<p>Helix 正在利用 Swift 和 Kotlin 重建 Shopify 移动端应用中的一个界面</p>
<p>这种方法效果极佳，使我们能够用极少的时间重构应用。</p>
<p>智能体（Agent）对模拟器的控制一直是一个瓶颈。我们发现自己不得不时刻照看它们，因为它们无法可靠地进行构建、测试和迭代。我们构建了相关工具，以便智能体能够自主复现缺陷、修复缺陷并验证修复结果，但这既缓慢又脆弱。React Native 的模块热替换（Hot Module Reload）对这种情况有所帮助，但由于模拟器控制速度较慢，它并没有彻底解决问题。这主要是因为需要依赖无障碍功能树（accessibility tree）或屏幕截图来获取应用状态、执行操作并验证结果。智能体可以在数秒内完成代码更改，但测试输出结果却需要数分钟。这使得迭代变得极其缓慢且需要大量人工介入。如果模型无法快速测试其工作成果，那么无论它有多优秀都无济于事，而这在移动端上尤为困难。</p>
<p>我们正在通过将应用架构设计为同时适用于人类和智能体来解决这一问题。其核心原则是：业务逻辑应与用户界面（UI）彻底解耦，并且能够以无头（headless）方式在桌面端运行。随后，我们通过命令行工具（CLI）将其开放给智能体，使它们无需模拟器的参与即可在毫秒级而非分钟级内完成迭代。</p>
<p>使用 CLI 浏览应用并执行操作</p>
<p>该 CLI 允许智能体在完全无需触碰 UI 的情况下，检查应用状态、在不同版块之间导航以及执行各项操作。这实现了极速的反馈循环，并允许智能体一次连续自主工作数小时。</p>
<p>当需要与模拟器交互时，CLI 可以通过远程模式连接到模拟器，并通过指令驱动 UI，而无需检查布局或无障碍树。这实现了极其迅捷的性能以及端到端（E2E）测试。</p>
<p>这是实时呈现的（未加速）</p>
<p>我们将在整个过程中借助 AI，将所有移动端应用迁移至 Swift 和 Kotlin。Shop 应用已经作为纯原生应用发布，Shopify 应用的迁移正在进行中，其余应用也将很快跟进。我们动作迅速，但绝不降低标准。每一次重构都必须达到或超越人们如今所期望的性能、稳定性、无障碍性以及产品质量。这绝不仅仅是用不同语言重写相同的应用。我们重构它们，是为了让人类和智能体都能快速理解、测试和修改它们。</p>
<p>迁移并非终点。成功意味着我们的团队能比以往更快地为商家和买家交付更优质的体验。我们将通过产品研发速度、应用质量以及智能体能够自主完成的工作量来衡量成效。</p>
<p>我们将在这一过程中分享所学到的经验，包括深入剖析我们支持智能体调用的架构 Helix，以及我们如何与智能体协同构建移动应用。我们此前曾坦诚分享过从 React Native 中学到的经验，对于这次转型，我们也打算同样保持透明。</p>
<p>这是我们开展过的最具雄心的移动工程项目之一。如果你想协助构建 Shopify 的下一代移动应用，我们正在招聘移动工程师、基础设施工程师以及在 AI 与软件工程交叉领域工作的开发者。</p>
<p>原生开发现在是 Shopify 的正确选择，但 React Native 曾是 Shopify 在 2020 年的正确选择。那一成功唯有凭借让它运转起来的人们才成为可能。</p>
<p>感谢 Meta 的 React Native 团队，你们一直是该框架卓越的引领者，多年来始终倾听我们的反馈并与我们紧密合作。得益于你们在架构、性能、工具和社区方面的投入，如今的 React Native 已经大幅改善。</p>
<p>感谢你们打造了 React Native Skia，并将其推进到了远超我们所有人想象的高度。你们重新定义了 React Native 中图形和动画的可能性，我们非常期待看到你们接下来将其带向何方。</p>
<p>感谢你们在 Reanimated 上的所有付出，感谢你们倾听我们的反馈，并帮助我们解决了应用中一些最棘手的动画和性能难题。</p>
<p>数百名工程师为采用 React Native、迁移我们的应用、构建共享基础底座、优化性能、维护集成以及向生态系统反哺贡献了力量。你们中的许多人重新成为初学者，挑战了长期以来的固有观念，在持续为商家和买家交付成果的同时，成功实现了转型。谢谢你们。</p>
<p>感谢所有使用过我们的开源库、贡献过代码、报告过问题、质疑过我们的决策并分享过心得的人。你们的贡献和反馈，包括那些尖锐的意见，都让我们的工作变得更好。</p>
<p>过去六年中建立的工具、经验教训以及人际关系，将继续塑造我们在 Shopify 构建移动应用的方式。我们向参与其中的每一个人致以深深的谢意。</p>

### [关于网络钓鱼的吐槽：这不是用户的错（也不是DNS的错）](https://maurycyz.com/misc/domains/)
<div class="original-title-sub"><span class="orig-tag">原文</span> A rant about phishing: It&#39;s not the user&#39;s fault (and not DNS either)</div>

<div class="article-body" data-article-body="true"><p>“为了安全起见，请勿点击可疑链接”</p>
<p>无论是用户名、密码还是双重认证（2FA）提示，均未托管在公司自己的域名上。再加上凭据令牌（token）过期会随机触发身份验证弹窗，这使得识别网络钓鱼几乎成了不可能的任务……因为真实的正规页面看起来和诈骗页面别无二致：</p>
<p>攻击者唯一要做的，就是制作一个带有密码输入框和公司徽标的网页。网址（URL）根本无所谓，因为用户早就习惯对它视而不见了。</p>
<p>我承认 URL 并不是最符合直觉的东西，因为它的阅读方向是交替变化的。主机名（hostname）和协议（scheme）是从具体走向抽象笼统，而路径（path）的层级方向却正好相反：</p>

<p>然而，如果主机名本身不再是一个可靠的判定指标，那么这一切尝试都毫无意义。</p>

<p>该规则同样适用于电话号码：切勿发送短信或邮件让用户“拨打 0491-570-006”，因为用户根本无法判断这是否是诈骗。联系方式“必须（MUST）”在原信息所链接的官方网页中予以提供。</p>
