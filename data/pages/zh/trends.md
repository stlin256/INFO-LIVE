<div class="article-body" data-article-body="true"><p>这些是我和 @stonerl 在开发全速 Game Boy 模拟器时发现的一些高级优化技巧。它们不是你在别处随处可见的常规游戏优化建议，因此如果你还不熟悉现有的通用技术，这些技巧对你来说可能用处不大。</p>
<p>这类优化技巧最适合用于需要极高性能的代码场景，例如模拟器、大型模拟系统（类似《异星工厂》那样的游戏）、3D 渲染器、编解码器等。</p>
<p>-O3 并不一定最快；-Os 可能会好得多。Playdate 的指令缓存（icache）很小（Rev A 硬件只有 4 KB），因此如果你的核心代码——比如模拟器解释器循环、片元渲染器、物理引擎——无法容纳在 4 KB 以内（据称 Rev B 是 16 KB？），那么其性能表现很可能不如体积更紧凑的代码（即使更紧凑的代码需要更多的 CPU 操作）。为了提升 Game Boy 模拟器的性能，我做的第一件事就是把 20 KB 的模拟器核心代码压缩到只有 2 KB：通过移除庞大的 switch 表，并改用更少代码量和寥寥几个分支来表达。（同时配合 -Os。）程序行为完全相同，但性能因此大幅提升。</p>
<p>现在，只有你的核心代码需要塞进这 4 KB 的缓存中。你可以把低频操作（例如几乎从未出现的操作码，或者模拟中极罕见的边界情况）挪到其他地方。</p>

<p>硬件中有一小块名为紧耦合内存（Tightly-Coupled Memory，TCM）的区域，其访问速度快于普通内存。栈空间（stack）就位于 TCM 区域内，因此在栈上分配的对象通常比堆上分配的对象或静态变量访问更快。</p>
<p>事实上，如果你需要在某段时间内持续操作某个结构体，不妨将其 `memcpy` 复制到栈上，在栈上进行操作，最后再 `memcpy` 写回。@RPDev 在 PlayGB 中实现了这一做法，并获得了巨大的性能提升。</p>
<p>但我们还可以做得更绝！为什么不直接让变量永久驻留在栈上，而不是放在堆上呢？这样我们就能省掉两次 `memcpy`。不过这样做有个原因限制了我们——我们无法掌控 `main` 函数，因此无法把任何东西永久保留在栈顶。但有一个变通方案——我们可以把它存放在栈的另一端（即低地址端，通常我们绝不该触碰该区域，以免发生栈溢出风险）。你可以在 `kEventInit` 触发时的 `eventHandler` 中使用 `__builtin_frame_address(0)` 来获取栈的高地址端，然后减去一个略小于 10 KB 的数值（我发现 `0x2180` 一直很安全），从而触及栈的低地址端。如果系统后续加入了对应特性，那将会是定位栈低地址区域的更好方法。</p>
<p>如果你将某些数据保存在这个低地址区域（我将其称作 `dtcm_mempool`），它应该能够在帧与帧（update）之间保持持久有效。在 `dtcm_mempool` 的起始和末尾放置金丝雀值（canary），并在每次 update 时至少检查一次，以确保栈溢出没有破坏 `dtcm_mempool` 的数据。</p>
<p>顺便提一句，内存中还有其他部分也位于 TCM 区域内，例如 Playdate 的帧缓冲区（framebuffer）。如果栈空间不足，你可以将数据存放在那里以实现高效访问（不过显然你需要处理一个问题：一旦进行渲染，这些数据会直接显示在屏幕上！）。</p>
<p>栈（或者说 `dtcm_mempool`）不仅能存放数据，我们还可以在其中存放代码。目前尚不清楚这是否能为 Rev B 带来加速，还需要进一步研究。但在 Rev A 硬件上，这正是 Game Boy 高效模拟的“绝密武器”。</p>

<p>第一次尝试时，如果细节没有完全处理好，程序很可能会崩溃。因此，一开始从小处着手——例如，先尝试复制一个除了返回一个数字外什么都不做的单函数，然后再逐步深入。当你把一个庞大的函数移植到 itcm 时务必格外小心，因为它可能会通过短跳转（shortcall）调用其他函数（这样几乎必然会导致崩溃）。</p>
<p>当你修改代码时，你会发现看似毫无规律地，有些构建版本变慢了，而有些版本变快了，有时差距还极为显著（比如快了 50%）。造成这种情况的原因有很多，但我确定了两个尤为突出的主要诱因：缓存未对齐（cache misalignment）和分支预测表（branch prediction tables）。</p>
<p>缓存行（cache line）的大小是 32 字节，这意味着你的应用程序每次会加载 32 字节的指令。如果有两个大小各为 16 字节的函数紧挨在一起，且第一个函数的地址刚好能被 32 整除，那么加载其中一个函数就会顺便让另一个函数也进入缓存。相反，如果一个函数长 32 字节，但其起始地址无法被 32 整除，它就会跨越两条缓存行的边界（这非常糟糕）。</p>
<p>这是如何引发“性能彩票”效应的？简单来说，这意味着只要在代码前端添加一个大小不能被 32 整除的函数，就会导致后续的所有其他函数发生向下偏移，它们的地址在模 32 意义下可能不再与旧地址同余。到了这一步，性能是变快还是变慢就全凭运气了。</p>
<p>如何将这种效应降到最低？在你的代码中，时不时强制某些内容按 32 字节对齐。在 C 语言中，你可以通过 `__attribute__((aligned(32)))` 来实现，或者在链接器映射文件（linker map）中使用 `. = ALIGN(32);`。在链接器映射文件中这样做的优势在于，你可以手动指定相对于 32 字节的偏移量，例如 `. = ALIGN(32); . += 0xC;`。你应该查看上一次快速构建（即上一次在“性能彩票”中表现良好的构建）中 `nm` 的输出（第 4 部分），以此来确定此处应使用的手动偏移量。我喜欢在链接器映射文件中的每个源文件和段之前加上 `. = ALIGN(32)`，以确保它们在缓存行方面彼此完全隔离。</p>
<p>顺便提一下，你可以使用编译器选项 `-falign-loops=32` 来确保代码中的循环按 32 字节对齐，这也可能会有所帮助。</p>
<p>关于 Cortex M7 CPU 上分支预测的具体工作机制并非公开信息。根据我的估算——我也可能完全猜错了！——存在一个针对 1024 个唯一下标指令地址的预测值表。通俗地说，这意味着如果两个 if 语句彼此相隔的字节数是 1024 的倍数，那么分支预测器就会以完全相同的方式对待它们，从而导致大量的误预测。因此，在你的链接器映射文件中，可以零星插入几个 `. = ALIGN(1024); . += n;`，其中 n 在 0 到 1024 的范围内取不同值。（更好的做法是，根据上一次良好构建中紧随其后的首个符号的地址来选择 n。）不过，这会浪费 4KB 以上的空间，所以不要大量使用这种操作。</p>
<p>关于分支预测是否是导致这种二阶“性能彩票”的原因，我的判断可能有误，但无论如何，除了 1024 能被 32 整除这一事实之外，ALIGN(1024) 这一技巧确实起到了效果。</p>
<p>我发现自从采用这些技巧后，“性能彩票”现象几乎完全消失了。</p>
<p>我还没有观察到使用预取（prefetching）带来的任何性能提升，但也有可能只是我用得不够巧妙。@FReDs72 在这个 Discord 讨论帖中描述过一个预取有所助益的案例。涉及预取时，性能的改善可能非常微小，因此也许应该使用高精度计时器来测量帧时间，而不是依靠普通的 FPS 仪表。</p>
<p>理论上，在存在间接寻址的情况下，预取应该会有所帮助。例如，如果遍历一个指针列表（`int** list`），你可能会从以下操作中受益：(a) 提前遍历整个列表并预取每一个 `list[n]`，或者 (b) 在访问 `list[i]` 之前预取 `list[i+1]`。</p>
<p>对于使用 CMake 的人，我修改了：<br />`$SDK_PATH/C_API/buildsupport/playdate.cmake`</p>
<p>哇，非常棒的信息。<br />我在 C 语言部分添加了甚至从未被 Lua 调用的函数时，SAT 碰撞检测代码的性能竟然下降了 20-30%。事后回想起来，这很可能确实是由指令缓存（对齐和大小）引起的，这就说得通了。</p>
<p>非常感谢你花时间研究并写下这些内容。</p>
<p>这里的信息非常棒且准确，感谢发布这篇帖子！</p>
<p>我也想补充一下我自己的一个发现——在 Playdate 上，除法可能会相当慢。哪怕是整数除法也是如此。<br />我曾经有一个用于渲染的循环，当时我试图通过改用整数除法来优化掉浮点数。然而，当我用浮点数替换掉这些整数除法，并改为只进行浮点加法时，该代码路径的性能得到了大幅提升。当然，这并不是一条放之四海而皆准的建议，但如果你在某个紧密循环中执行除法（即使是整数除法）并且遇到了性能瓶颈，这绝对值得一试。</p>
<p>这让我挺意外的。表面上看，整数除法理应需要 2-12 个周期，而浮点除法需要 14 个周期。</p>
<p>我在一个紧密循环中把除法换成了对浮点数的累加，结果带来了巨大的差异。<br />所以不仅仅是换成浮点数那么简单，我以前用的是整数除法，现在改成了在浮点数上做加法。这样做反而更快。<br />我大概可以把那段代码找出来展示一下。我也很惊讶，因为我当时特意重写了代码以避免使用浮点数，但在这个案例中，最终证明改用可以做累加的浮点数效果更好。</p>

### [唯一“直观”的界面是乳头](https://www.greenend.org.uk/rjk/misc/nipple.html)
<div class="original-title-sub"><span class="orig-tag">原文</span> The Only Intuitive Interface Is The Nipple</div>

<div class="article-body" data-article-body="true"><p>唯一“直观”的界面是乳头。在那之后，一切都是后天习得的。</p>
<p>这句话通常被归于一位名叫布鲁斯·埃迪格（Bruce Ediger）的人（尽管至少有一人曾认为这最初出自史蒂夫·乔布斯之口，一位精良电脑的制造商），它指的是人们频繁（且无一例外不准确）将计算机用户界面描述为“直观”。但在2001年，布鲁斯否认这是他的原创。这让我好奇这句名言的来历究竟是什么。</p>
<p>我的第一站是一本语录词典，但里面根本没有收录。那么，也许它确实相对较新。</p>
<p>我最早可以追溯到1994年8月，当时针对“确实没有任何一种用户界面隐喻是真正直观的”这一说法，斯科特·弗朗西斯（Scott Francis）提出乳头是唯一直观的界面。核心观点有了，但确切的表述并非如此。（当然，乳头并不是隐喻，至少在当前语境下不是。）为了寻找最接近通常被引用的措辞，我能找到的最早记录出自一位名叫杰伊·沃尔默（Jay Vollmer）的人于1995年1月发表的内容。他写道：</p>
<p>“事实上，唯一真正直观的界面是乳头。”</p>
<p>布鲁斯是看到了这篇帖子并喜欢上它，还是在别的地方看到了这个想法？从谷歌的归档记录中实在无法确知。无论如何，他不久后便开始使用它的变体。例如，在1995年2月：</p>
<p>“我知道这是一句老生常谈，但唯一真正、确确实实‘直观’的界面是人类的乳头。”</p>
<p>同月稍晚些时候，我们看到了泰勒·赫特（Taylor Hutt）针对“全都是后天习得的”这一主题的一个变体：</p>
<p>“我认为没有任何计算机界面是直观的——一个都没有；它们全都是后天习得的。”</p>
<p>1995年4月，布鲁斯再次发文：</p>
<p>“按照这一定义，乳头是唯一‘直观’的用户界面。”</p>
<p>紧接着在当月晚些时候：</p>
<p>“基本上，唯一‘直观’的界面是乳头。在那之后，一切都是后天习得的。”</p>
<p>所以，或许布鲁斯终究最理应拥有这种特定表述的署名权？也许吧。无论如何，我想我更喜欢他2001年的版本：</p>
<p>“根本没有直观的界面，哪怕乳头也不是。一切都是后天习得的。”</p></div>

### [绝非普罗米修斯之火](https://jardo.dev/hardly-promethean)
<div class="original-title-sub"><span class="orig-tag">原文</span> Hardly Promethean</div>

<div class="article-body" data-article-body="true"><p>上周我发表了《那 Rails 怎么办？》（What About Rails），深入探讨了 DHH 在 Rails World 上的主题演讲。比我聪明的人对此发表了有趣的看法：</p>
<p>“你拥有了有史以来最强大的工具，你已经成为了千倍创造者（1000x maker），难道你就想不到如何让你的技术栈提升 10 倍吗？”</p>
<p>何塞·瓦利姆（José Valim）提出了一个绝佳的问题。我试图去寻找答案。</p>
<p>“它们很快就不会再是 Web 应用了。它们将成为原生应用，因为开发这些东西的成本几乎降到了零。”</p>
<p>前端转向原生应用、后端转向 Rust，并非关乎某项特定的技术，而是关乎成本。DHH 并不是第一个提出这一论点的人。</p>
<p>早在八月份，丹·卢（Dan Luu）就发表了《软件再也没有慢的借口了》（There’s no reason for software to be slow anymore）。在文中，他辩称专门的性能优化工作成本大幅下降（因为大语言模型 LLM），以至于现在几乎任何人都能负担得起。</p>
<p>卢比 DHH 谨慎得多。他指出，智能体（agent）会在基准测试中过拟合，在缺乏人类协助时很不擅长实验设计，而且获得严谨结果所需的时间并没有减少，减少的只是获得一个看似有趣的结果所需的时间。</p>
<p>不久之后，瓦伦·甘地（Varun Gandhi）发表了自己的回应，题为《软件仍然有慢下去的理由》（There continue to be reasons for software to be slow）。他指出了这种论点的形式逻辑：做 X 的成本太高，LLM 将成本除以了一个庞大的数字，因此人们现在就会去做 X。甘地认为，虽然这对像卢这样的人（从事自己项目的专家）确实成立，但那些情况十分罕见。</p>
<p>把 X 替换为 Rust 后端、六款原生应用，或者上周五前赶出的 CLI，你就能得到 DHH 主题演讲的推介辞。DHH 是一位在他自己控股的公司里从事自己产品的专家。甘地指出，这正是最有可能奏效的情境。这里甚至没有经理来卡预算。如果它在任何地方能起效，那就是在这里。他把一个最理想状态下的结果，泛化成了“到 12 月时，几乎所有程序员、几乎所有公司都将如此”。</p>
<p>甘地最有价值的见解在于，编写代码1从来都不是最主要的成本。我们还必须考虑发布变更、维护它们以及避免回归缺陷。DHH 对 Hey Next 的体验不过才一周时间，它甚至都还不是一个生产系统。</p>
<p>他自己就向我们展示了这一点。Basecamp 5 的“瑞士奶酪”架构，正是脱胎于“代码很便宜，但协调成本却不菲”这一现实。甘地讲述了同一个故事的另一个版本：Bun 借助 LLM 辅助对 Zig 进行了分支（fork），编译速度提升了 4 倍，但却无法合并回上游，因为没有人2想要一个结果不确定的编译器。</p>
<p>消除一个瓶颈并不能消除排队现象；它只会向你揭示下一个制约因素在哪里。有了 LLM，我们只是将瓶颈向右移动了一步，从编写代码移到了之后发生的一切事务上。而 DHH 的解决方案就是跳过这些事务。</p>
<p>“现在，部分原因在于像 Rust 这样的编程语言极度冗长，对人类来说毫无观赏性。所以我不去看它，我允许智能体直接吐出超出必要的内容，这种方式在我的 Ruby 代码中我是绝不会容忍的。”</p>
<p>甘地认为成本论点失效的原因之一是，人们的容忍度提高了。当工作变成异步且由智能体驱动时，我们不再面对面地承受变慢的 git、更迟钝的自动补全和更漫长的构建过程。没有人在那里干等着。如果你仍然在意这些事情，你大概会讨厌这一点。</p>
<p>而 DHH 把这一切都跳过了。你把任务交代出去，“就像对待同事一样”，然后“等有东西准备好了再回去审查”。这里的“审查”并不意味着代码审查；它意味着检查那个按钮是否能用。</p>
<p>也许对于他个人的一次性项目来说这没问题。从 Hey Next 启动一周来看，这似乎行得通。但他自身容忍度的提高并不会提高其他人的容忍度。他可以不去在乎 Hey Next 这个黑盒子里装了什么，但很多人在乎 Rails 盒子里装了什么。所谓的“几乎所有程序员”到头来也不过如此。</p>
<p>所以，回到瓦利姆的问题。你拥有无限的 Token。你是一个千倍创造者。你可以创造任何东西。难道你就找不出任何东西，哪怕任何一件能为 Rails 创造的东西吗？</p>
<p>这从来都不是预算的问题。速度的提升并不会改变优先级。DHH 今年打造的一切，都是他自己想要的。他正在构建的东西没有一样需要 Rails 变得更好，所以他也未曾让它变得更好。</p>
<p>我们现在可以想要一切。我们现在可以得到一切。</p>
<p>那么，这“一切”究竟是什么？事实证明，是一个计算器。一个视频编辑器。一些演示文稿软件。又一个 Linux 发行版。以及对他自己产品的一次重写。他被赋予了无限的 Token，而这就是他所能构想出的全部。这里确实存在匮乏。思想的匮乏。</p>
<p>看看那个清单吧。没有一个全新的点子。这是当下整个行业的缩影。DHH 的欲望展露无遗，他想要的无非属于他自己的东西，以及早已存在的东西。</p>
<p>LLM 极其擅长制造早已存在的东西。卢承认这一点；早期的模型甚至过拟合到了滑稽的地步3。要求做一个计算器是个稳妥的诉求。而在 2004 年，Rails 绝非稳妥之物。它是新颖的，并因此备受赞誉。</p>
<p>DHH 的主题演讲本末倒置了。手写代码的时代并不是某种我们已经超越的温情旧梦。在 LLM 出现之前，将一个想法付诸实践需要付出多得多的跑腿苦工。但你首先需要灵感的火花，而你现在依然需要它。</p>
<p>在 2005 年，“看看我没有去做的所有事情”是一种自豪的夸耀。今年他重演了这一幕以作类比。但在我看来，他如今不再去做的那件事，恰恰是提出新的想法。</p>

<p>让我们探讨一下如何结合工厂方法模式使用数据和值对象，以帮助解耦软件组件。<br />我为 Ruby 做了一个 Web 框架。好吧，其实并没有。但差不多算吧。</p></div>

### [Deser：重新思考 Rust 的序列化机制](https://lucumr.pocoo.org/2026/9/29/deser/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Deser: Rethinking Rust Serialization</div>

<div class="article-body" data-article-body="true"><p>写于 2026 年 9 月 29 日<br />Serde 是一款令人惊艳的 Rust 序列化库，多年来它一直是我在 Rust 中保持高生产力的重要原因。然而，早在 Sentry 工作时，我就对其存在的某些局限感到十分沮丧；但真正去取代 Serde 却非常棘手，因为它在整个生态中具有极其强大的影响力。此外，如果不做出一些可能相当痛苦的妥协，实际上也很难做得更好。<br />以下是 Serde 边界情况的三个例子，展示了 Serde 特性之间不佳的交互或是意料之外的限制：<br />一个内部带标签的枚举（internally tagged enum），且开启了 serde_json 的 arbitrary_precision 特性：<br />Serde 的数据模型没有容纳任意精度数字的位置，因此 serde_json 采用了带魔法键的映射（map）来进行带内信令（in-band signalling）。该枚举必须先缓冲字段，直到看到标签为止，而缓冲区并不知道这个魔法键的存在。由于 Cargo 的特性是统一合并的（unified），只要你的依赖图中有任何一个 crate 开启了该特性，就会触发此问题。<br />Stats 本身可以顺利解析 {&quot;scores&quot;: {&quot;42&quot;: 23}}。JSON 的键始终是字符串，serde_json 仅在类型要求时才会将它们转换为整数。然而，一旦 flatten 缓冲了该值，&quot;42&quot; 就仅仅只是一个字符串了。而且报错位置指向的是文档末尾，而不是那个键。<br />函数不能作为类型参数传递，因此无法将 from_hex 应用到 Option、Vec 或 map 的内部。你必须为每个包装器另外编写一个函数，而一旦你有了 from_opt_hex，该字段就不再是可选的了，除非你还记得加上 #[serde(default)]。<br />这些都不是在 Serde 中容易修复的 bug。它们源于其整体架构设计，而这一设计又受到 Serde 稳定性保证的保护。<br />早在 2022 年，我启动了一个名为 Deser 的实验项目。它是一个 Rust 序列化库，继承了 Serde 的用户体验，并将其置于受 miniserde 启发的完全不同的架构之上。我当时并没有真正完成它，它就这样搁置了几年。最近我重新拾起了它，现在它已经发展到了我认为值得一看的阶段。哪怕仅仅是为了启发其他人，看看是否有人想探索这个领域。<br />它的名字就是把 Serde 的前后两半调换了一下。Deser 本质上就是反过来的 Serde。在 Serde 中，由类型来驱动反序列化过程：Deserialize 的实现会向反序列化器询问它所期望的值类型，数据格式再回调访问器（visitor）。每个嵌套值都通过递归来处理，这使得 Serde 的反序列化在本质上会随着嵌套层级的加深而增加调用栈深度。<br />相反，Deser 颠倒了这一流程：由数据格式告诉类型下一个值是什么，并将事件推送到接收槽（sink）中。当一个 sink 遇到嵌套值的起始时，它不会直接调用进入，而是将一个新的 sink 交还给驱动器（driver），驱动器将所有状态保存在堆上（实际上是在一个 arena 内存池中）。在退出时，发射器（emitter）会返回它们的嵌套值，而不是通过递归进入它们。<br />这也意味着 Deser 无法支持像 protobuf 这样非自描述的数据格式。事实上，它们是完全被刻意排除在设计之外的。换句话说：如果你想“修复”Serde，就必须做出其他妥协。<br />Deser 大多数想法的起因都可以追溯到 Sentry Relay，它需要处理海量的不可信 JSON。在 Sentry 的那些年里，我们反复遇到同一套问题，其中许多其实并不是 Serde 的 bug，而是其设计的必然结果。Serde 的稳定性保证意味着很多问题在不破坏现有格式和手写实现的前提下是无法修复的。这些问题大多源于以下三个决策：<br />所有格式共用一套 trait。Serde 既服务于自描述格式（JSON、YAML、TOML 等），也服务于读取方必须预先知道类型的格式（postcard、bincode、protobuf 等）。这极其有用，但也意味着某些特性仅对部分格式有效，并且你只能在运行时才发现。在 Serde 中，这也导致了一些奇怪的瑕疵，例如派生出的结构体在 JSON 中会静默接受一个数组来代替对象。<br />固定且在缓冲时会丢失信息的数据模型。内部带标签的枚举、无标签枚举以及 flatten 在知道如何处理值之前，都需要对值进行缓冲。缓冲区无法保留该格式原本已知的所有信息，错误会丢失其具体位置，生态系统的扩展则不得不依赖带内信令来表达任意精度数字等内容。<br />调用栈上的递归。每一层嵌套都会消耗栈空间。各种格式通过设置递归深度上限来防御此类问题，但一旦走到了没有深度限制的代码路径（如写入、动态值），深层嵌套的数据就可能使你的进程崩溃。这也意味着在等待更多输入时，反序列化过程是无法暂停的。<br />许多对应的 Serde issue 已经开启了数年之久，我之前也写过关于滥用 Serde 的文章。多年来，人们尝试从不同角度来解决这个问题。有些人走向极简路线，去掉了绝大多数特性以换取极快的编译速度和零递归。dtolnay 自己的 miniserde 就是最好的例子，deser 最初的 trait 设计正是以此为原型的。其他最近的尝试则走向了运行时反射，或是专注于二进制格式的新数据模型。<br />如果你想全面了解汇总起来的 Serde 设计挑战，我在这个链接维护了一份长长的清单。<br />首先，我认为替换掉 Serde 是不太可能的。孤儿规则（orphan rule）使 Serde 在生态系统中根深蒂固。但有些事情是 crate 作者力所能及的。对于 Deser 而言，那就是完整性。<br />今天的 Deser 实现了所有重要的自描述格式，包括 YAML、JSON、TOML、CBOR、JSON5 等，同时也支持 XML 和 plist 以真正填补空白。尤其是 XML，这是 Serde 明确拒绝支持的格式，其劣势显而易见（下文详述）。至少，格式支持不应该成为拒绝使用 Deser 的理由。<br />第二个常见问题是，真正解决 Serde 的问题往往需要在编译时间和/或运行时性能上付出巨大代价。Deser 也不例外。虽然 Deser 的编译时间比 Serde 略好，但二进制文件体积膨胀却严重得多，运行时性能也是互有胜负。从数据上看整体相当，但取决于数据格式的结构，某些权衡取舍会带来明显的性能损失。<br />即便如此，它现在所处的状态，至少在原则上已经可以作为一个直接替代品（drop-in replacement），其中的取舍对于某些用户来说可能恰到好处。<br />在表层使用上，Deser 并未试图与 Serde 表现出太大的差异。在大多数场景下，你只需 derive Serialize 和 Deserialize，然后配合你选择的格式实现 crate 开始使用。大多数属性（attributes）都非常相似，不过它们接受的是 Rust 表达式而不是字符串。</p>

<p>既然你已经了解到 Deser 至少在理论上非常出色，那么它的代价是什么呢？</p>
<p>天下没有免费的午餐。该设计依赖于动态分发以及保存在堆上的接收槽和发射器，这带来了可观的运行时开销。在我自己对 JSON 的基准测试中，取决于具体数据，Deser 的读取速度在比 serde_json 快 33% 到慢 60% 之间波动。平均而言，读取速度慢大约 10%。写入速度在快 3 倍到慢 70% 之间，平均下来基本持平。对于 YAML 和 TOML，它明显快于基于 Serde 的 crate，但这更多归功于格式的具体实现而非整体架构。</p>
<p>编译时间略有改善，但并不显著。由于它没有对所有内容进行单态化（monomorphize），派生代码的 release 构建速度大约是 Serde 的 2.3 倍，并且在实践中对于你自己的代码还会更好一点，因为所需的重新编译更少。</p>
<p>为了让 Deser 的设计完全行得通，它在内部也使用了 unsafe。其中大部分是为了在堆上维护借用的接收槽链。我觉得在当今拥有 Miri 和各类工具/智能体的时代，这完全没有问题，但我知道这会让某些人感到不安。</p>
<p>而且，最大的代价在于它终究不是 Serde。</p>
<p>实际上支持的功能相当多，这可能会让人感到惊讶。除了核心功能外，还提供了对 derive 的支持。</p>
<p>它支持你能想到的所有 JSON 变体：JSON、JSONC、JSON5 和 HJSON。（这里有个有趣的事实：它们都是从同一个共享解析器模板生成的）。对于二进制处理，它支持 CBOR 和 MessagePack。此外，它还支持 YAML 1.1 和 1.2、TOML、XML 以及苹果 plist 的全部三种格式，外加 CSV/TSV、urlencoded 数据和环境变量。对于更高级的复杂需求，你可以附加路径信息或捕获位置数据，同时也支持调试打印。你可以在解析的同时执行验证，除 base64 之外还能自由选用不同的二进制编码，你可以桥接到 serde 或捕获动态值，在不同格式之间进行代码转码，或者将其与 tokio 集成。</p>

### [两种不同类型的 SQL 查询构造器](https://mechanicalrabbit.github.io/FunSQL.jl/stable/two-kinds-of-sql-query-builders/#Two-Kinds-of-SQL-Query-Builders)

<div class="article-body" data-article-body="true"><p>SQL 语言有着耐人寻味的命运。尽管它在设计之初是为了迎合人类用户的直觉，但如今大部分 SQL 代码都是由计算机编写——更准确地说是生成——的。许多计算机程序都需要查询某种数据库，而对于绝大多数数据库服务器而言，唯一支持的查询语言就是 SQL。但生成 SQL 却很困难，因为其类英语语法规则复杂且晦涩（其原名 SEQUEL 代表“结构化英语查询语言”）。出于这个原因，与数据库交互的程序通常会使用专门的库来生成 SQL 查询。</p>
<p>FunSQL 就是这样的一款库。FunSQL 的设计旨在实现两个目标：支持 SQL 查询功能的全部特性，并通过可组合、面向数据（data-oriented）的接口呈现这些功能。这两个目标的结合使 FunSQL 成为在 SQL 中进行数据分析的理想工具，并使其在所有其他查询构造库中脱颖而出。许多查询构造器都提供了对 SQL 特性的良好覆盖，较少能提供面向数据的接口，但唯有 FunSQL 将二者结合在了一个单独的工具包中。</p>

<p>SQL 语法存在诸多缺陷，包括刚性的子句顺序、查询嵌套以及 SELECT 子句荒谬的位置。SELECT 的位置违背了查询的执行流，而这种违背又因查询嵌套而进一步加剧。复杂的 SQL 查询通常需要多层嵌套，这使得此类查询变得臃肿且难以解读。正是在这一点上，不对管道节点顺序做限制的面向数据查询构造器，相比纯 SQL 带来了改进。</p>
<p>那么另一种查询构造器又是怎样的呢？Active Record 和 Laravel 采用了形式完全相同的管道，但因为它对节点的顺序不敏感，所以它必须基于不同的原理工作。事实上，这种管道是通过递增组装 SQL 语法树来生成 SQL 查询的。由于刚性的子句顺序，SQL 语法树可以被真实地表示为一个复合数据结构，其中包含指定 SELECT、FROM、WHERE 和其他子句内容的插槽（slots）：</p>
<p>该结构的各个插槽由相应的管道节点填充。</p>
<p>这就解释了为什么管道对节点的顺序不敏感。事实上，只要插槽的内容保持相同，以何种顺序填充这些插槽便毫无区别。</p>
<p>这种增量构建复合结构的方法被称为“构造器模式”（builder pattern）。我们可以将采用这种模式的查询构造器称为“面向语法”（syntax-oriented）的构造器。</p>
<p>面向数据和面向语法的查询构造器都是可组合的：二者的差异在于组合单元所处理信息的本质。面向数据的查询构造器逐步细化查询输出；面向语法的查询构造器逐步组装 SQL 语法树。它们的接口看起来几乎一模一样，但其运作原理有着本质的不同。</p>
<p>但是哪一种更好呢？面向语法的查询构建器有两个明显的优势：它们易于实现，并且能够支持全套 SQL 特性。事实上，面向语法的查询构建器的接口只不过是 SQL 语法树构建器的集合。对语法树表达的完整程度，决定了其对各种 SQL 特性的支持好坏。</p>
<p>另一方面，面向语法的查询构建器更难使用。由于它们直接体现 SQL 语法，因而继承了其所有的缺陷。特别是其僵化的子句顺序，使得组装复杂的数据处理流水线变得十分困难，尤其是当流水线节点的排列并非预先确定的时候。</p>
<p>面向数据的查询构建器则直接表示数据处理节点，这使得组装数据处理流水线直观得多——只要我们能在构建器提供的节点中找到所需节点即可。但是，构建器从何处获取其数据处理节点集？我们又如何判断这个集合是否完整呢？</p>
<p>实现面向数据查询构建器的一种方法是改造通用查询框架。事实上，这正是 EF/LINQ（由 LINQ 改编而来）和 dbplyr（由 dplyr 改编而来）的由来。查询框架决定了有哪些可用的处理节点以及它们如何运作。原则上，任何查询框架都可以通过仅引入一个新节点——即加载数据库表内容的节点——来适配 SQL 数据库。如果我们把这个节点放在流水线的开头，并用常规节点构建其余部分，就能得到一个处理来自 SQL 数据库的数据的流水线。然而，与 SQL 引擎相比，这种流水线的效率会非常低，因为 SQL 引擎可以利用索引来避免将整张表加载到内存中，从而以极快的速度处理相同的数据。这就是为什么 EF/LINQ 和 dbplyr 会生成一条 SQL 查询来整体替换该流水线。流水线本身不再直接运行，而是充当一种规范，其假设是：如果它真的运行起来，其产生的输出将与该 SQL 查询相同。这种将通用查询框架转换为 SQL 查询构建器的方法被称为“SQL 下推”（SQL pushdown）。</p>
<p>然而，SQL 下推存在严重的局限性。通用查询框架在设计之初并未考虑与 SQL 的兼容性。因此，在此类框架中组装的部分流水线无法转换为 SQL。更糟糕的是，许多实用的 SQL 查询根本没有等价的流水线，因而无法通过 SQL 下推生成。诚然，自 1974 年首次出现以来，SQL 积累了极其丰富的功能与特性。SQL 标准的第一个修订版 SQL-86 就已经支持笛卡尔积、过滤、分组、聚合以及相关子查询。随后的修订版 SQL-92 增加了多种连接类型并引入了查询嵌套。SQL:1999 通过增加两类查询极大地拓展了其分析能力：用于处理层级数据的递归查询，以及泛化了直方图、交叉制表、上卷、下钻和小计的数据立方体（data cube）查询。随后的修订版 SQL:2003 又增加了对滑动窗口聚合函数的支持。不可否认，SQL 是典型的企业级“怪胎”，为了支持所有能想象到的用例而东拼西凑了大量特性，但语法欠佳、功能上存在古怪的缺失，且毫不顾及内部一致性。尽管如此，SQL 功能的广度是任何其他查询框架（包括 LINQ 或 dplyr）都无法比拟的。因此，当我们使用 EF/LINQ 或 dbplyr 生成 SQL 查询时，很大一部分能力仍然是无法触及的。</p>
<p>FunSQL 是一款专为释放 SQL 全部表达能力而创建的面向数据的查询构建器。与 EF/LINQ 和 dbplyr 不同，FunSQL 并非由现有查询框架改造而来，而是从零开始精心设计以匹配 SQL 的各项能力。例如，这些能力包括对相关子查询和横向连接（lateral join）的支持（通过 Bind 节点）、聚合与窗口函数（使用 Group 和 Partition 节点），以及递归查询（使用 Iterate 节点）。对 SQL 功能的这种全面支持，使得 FunSQL 成为唯一适合组装复杂数据处理流水线的 SQL 查询构建器。此外，尽管 FunSQL 流水线无法直接运行，但每个 FunSQL 节点都具有明确定义的数据处理语义，这意味着原则上 FunSQL 可以发展为一个功能完备的查询框架。这有可能开辟一条道路，用一种同样强大、但更连贯且更具表现力的查询语言来取代 SQL。</p></div>

### [Shell 与电子邮件](https://www.machtiani.chat/blogs/the-shell)
<div class="original-title-sub"><span class="orig-tag">原文</span> The Shell &amp; Email</div>

<div class="article-body" data-article-body="true"><p>当同时与多个智能体（Agent）协作时，电子邮件是最佳的工作方式吗？每一个邮件主题线（thread）就是一个会话，而且它天生支持群组对话。</p>
<p>在 GitHub 上看看我构建的项目。</p>
<p>借助电子邮件，你不会被束缚在某家公司的单一应用中，甚至不必拘泥于你的笔记本电脑。你可以在任何地方操作，此外，电子邮件在恶劣的网络环境下也是适应性最强的。</p>
<p>电子邮件已经解决了以异步和分布式方式与人协作的问题。大语言模型懂得这一点，就像它们懂得 Shell 一样。</p>
<p>我们喜欢 Shell 以及让我们得以使用它的终端。这背后有着非常务实的原因：Shell 能够进行组合，并在无需任何守门人把控的情况下与其他应用程序实现互操作。一旦你掌握了门道，使用终端就会变得既有趣又让人感到自由。</p>
<p>当大语言模型与 Shell 结合时能发挥最大效用，这绝非巧合。如果我们必须与某个智能体紧密协作，在终端中进行是最好的选择，这样我们就能尽可能贴近 Shell。</p>
<p>我对此深怀感激。我们主要使用 Claude Code、Codex CLI 以及其他工具（例如使用 Shell 的 OpenCode），并通过终端与它们协同工作（使用 Shell）。我们不必为了高效使用计算机而被迫去用 iPhone 应用或某家公司基于云的 Web 应用。</p>
<p>然而，当你必须同时与多个智能体协作时，局限性就显而易见了。那种体验令人眼花缭乱。我们往往需要以异步方式与负责不同任务的智能体协同工作：停下来，去做别的事情，过好日常生活，抽空查看一下进度，在我们自己的时间节奏里轻松返回任务等等。</p>
<p>再说一次，电子邮件已经解决了以异步和分布式方式与人协作的问题。这种模式非常自然地延伸到了与智能体协作、乃至人与智能体混合协作的场景中。</p>
<p>在一年多前首次发布 Machtiani 之后，我开始将 Machtiani 的回答重新喂回给它的下一轮指令中。为了探索这一方向，我直到现在才发布新版本：一个驱动着工作者的迭代指令循环，而这个工作者正是一个轻量级的监督者（supervisor）。</p>
<p>这个轻量级监督者可以与你计算机上已安装的任何智能体协同工作。</p>
<p>我发现，电子邮件是与他人以及智能体共同协作最自然、最让人感到自由的方式。</p>
