### [OpenAI 公开数学研究成果目录](https://github.com/openai/math)
<div class="original-title-sub"><span class="orig-tag">原文</span> OpenAI shares mathematics research catalogue</div>

<div class="article-body" data-article-body="true"><p>本仓库包含由 OpenAI 内部模型生成的数学论文手稿及辅助证明材料。</p>
<p>作为模型研发工作的一部分，我们在开放式研究问题上对模型进行了评测。在我们现有的数学基准评测表现达到饱和后，我们扩大了这些评测的范围。部分产出建立在模型先前生成的成果之上。</p>
<p>该合集包含处于不同验证阶段的成果。并非所有成果都附带 Lean 形式化证明。随着我们获得相应的 Lean 形式化成果，我们将持续更新此仓库。</p>
<p>部分尚未形式化的成果可能存在纰漏。我们将努力尽快修复任何此类问题。我们同时也在探索为这些材料设立社区托管的存储库。</p>
<p>当前目录包含 722 篇论文手稿，划分为 372 个成果族（families）。一个成果族将相关论文归并在一起，其中可能包含一项主要成果、配套论证、推论或替代证明。每个成果族均按数学学科门类进行了分类。</p>
<p>我们还发布了模型推理过程的精简摘要，涵盖以下成果：</p>
<p>绝大多数成果均采用相同流程、利用 OpenAI 尚未发布的内部模型获得。平均而言，针对该模型，每个成果耗费了 3 小时的 ChatGPT Pro 思考算力（thinking compute）。在整个评测过程中，模型被提出了大约 4,000 个问题。将输出聚合为成果族和手稿，并筛选出具备相应显著性水平的内容后，便形成了上文所列的目录。</p>
<p>该固定流程的例外情况包括：关于黎曼 zeta 函数无零点区域的研究，以及 CM 阿贝尔簇霍奇猜想（Hodge Conjecture for CM abelian varieties）的证明。此外，关于黎曼 zeta 函数 Re(s) &gt; 11/12 无零点区域的手稿经过了人工编辑以提高可读性。</p>
<p>我们将保留该合集的公开发布历史。更正和修订将记录为新版本，此前发布的版本仍将保持可访问状态。</p>
<p>如需引用单篇论文手稿，请使用其目录下的 BibTeX 代码块。</p></div>

### [Python 3.15 到底有多快？](https://blog.miguelgrinberg.com/post/how-fast-is-python-3-15)
<div class="original-title-sub"><span class="orig-tag">原文</span> How fast is Python 3.15?</div>

<div class="article-body" data-article-body="true"><p>又到十月了，这也意味着是时候体验一下 Python 的最新版本了（严格来说，我使用的是 3.15.0rc3 版本，官方的 3.15 正式版还有几天才会发布）。正如一年前我写的 Python 3.14 性能文章一样，今天我将分享新一轮非正式的 Python 基准测试结果，对比 Python 3.15 与自 3.10 以来历代解释器的表现。</p>
<p>如果你对图表和表格不感兴趣，只想阅读分析内容，可以随时跳到文末的结论部分。</p>
<p>我刚才把我的基准测试称为“非正式”。这是什么意思呢？</p>
<p>要想对一门编程语言的性能得出客观且通用的衡量标准是不可能的。你所能做的只是写一些程序并运行它们，以获取其性能的度量。其他程序可能会展现出相似的性能特征，也可能不会，这真的无从得知。我做这个基准测试的初衷仅仅是想感受一下 Python 各个版本之间的性能变化，但我想明确说明的是，我并不是试图得出 Python 解释器的全面性能分析画像。</p>
<p>在我的基准测试中，我将运行名为 fibo.py 和 bubble.py 的两个程序，如果你愿意的话可以去查看它们。这些程序与我在此类基准测试往期版本中所使用的程序相同。第一个程序计算斐波那契数列中的数字，第二个程序使用冒泡排序算法对数字进行排序。</p>
<p>我选择这两个程序作为两类算法的代表。斐波那契计算使用的是递归，我发现这在 Python 解释器中效率稍显低下。另一方面，冒泡排序仅使用 for 循环，没有任何递归。还有其他类型的程序是我的基准测试并未试图涵盖的。特别是需要注意，我的基准测试中并未包含 I/O 密集型代码。</p>
<p>由于近期 Python 版本中的某些性能改进围绕多线程展开，因此我还为每个程序创建了一个多线程变体，所以总共有四项不同的测试。</p>
<p>完整的测试矩阵实际上相当复杂，因为我必须在所有 Python 版本下运行这四种程序变体，对于支持 JIT 和自由线程（free-threading）的版本还要运行其对应替代配置。我也喜欢在 PyPy 下运行这些测试，因为该解释器在此类基准测试的历史运行中展现出了令人惊艳的性能。为了将 Python 的性能置于更广阔的生态系统中进行考量，我还将这两个程序移植到了 JavaScript（Node.js）和 Rust。</p>
<p>以下是我使用的完整测试矩阵：</p>
<p>读过我以往基准测试的读者可能还记得，我的矩阵中曾包含一个 Linux 与 macOS 的额外维度。鉴于在前两次基准测试运行中两者之间并没有显著差异，这次我决定放弃 macOS 测试，因此所有测试均在一台搭载英特尔酷睿 i5 CPU 并运行 Gentoo Linux 的 Linux 笔记本电脑上执行。</p>
<p>我用于衡量此基准测试中每个参与者性能的方法是：将测试程序运行三次并取这三次的平均耗时。在下文分享的结果表格中，我还展示了相对于 3.15 版本的速度差异，并且在合理的情况下展示了相对于特定解释器前一版本的速度差异。对于速度比较，我使用了一个简单的比率，其中 1x 表示速度相同，0.5x 表示速度为一半（或者说花费了两倍的运行时间），2x 表示速度快一倍（或者说花费了一半的运行时间，如果你更习惯这种说法的话），依此类推。希望这能易于理解。</p>
<p>我们开始吧。第一项测试计算前 40 个斐波那契数。</p>
<p>在下方你可以看到上述速度的图表展示：</p>
<p>从这些结果中我们可以推断出，对于这项测试，Python 3.15 仅比 3.14 快了一点点，可能微不足道。正如我在往年观察到的那样，PyPy 3.12 的性能极为惊人，达到了 3.15 速度的 5.5 倍，甚至还略微领先于 Node.js。至于 Rust 则毫无悬念，但了解极限在哪里总是件好事！</p>
<p>将每个 Python 发行版与其前一版本进行对比，揭示了一个有趣的细节。唯一在性能上相较前代有显著提升的两个版本是 Python 3.11 和 3.14。你可以在图表中清楚地看到这一点，此时柱状图的高度相较前一个出现了较大幅度的下降。其他版本要么保持了相同的速度，要么带来了小幅提升，因此总体上一直是有进步的。</p>
<p>在下一组结果中，你可以看到 Python 的 JIT 和自由线程（FT）版本在同一测试上的进展。请记住，Python 解释器的这些替代版本最初是在 3.13 中引入的，因此可供评估的版本范围要小得多。</p>

<p>从这里来看，真正最有趣的事情是 3.15 解释器中的 JIT 比同一测试中的标准解释器更快，而在前几年情况并非如此。而且 1.20 倍的速度提升绝非微不足道，看到这一点非常令人振奋！</p>
<p>在自由线程方面，确实没有太多的指望，因为这项测试是单线程的。但我们可以说，自由线程解释器的性能与 3.14 版本大致持平。</p>
<p>现在让我们来看第二项测试。以下是单线程冒泡排序测试的表格和图表，该测试配置为对 10,000 个随机数进行排序：</p>
<p>与上一项测试一样，在这里我们也可以看到 3.15 相较于 3.14 只有非常微小的性能提升。我们再次看到 3.11 和 3.14 是近期真正推动了性能实质性提升的两个 Python 版本。某些版本在这项测试中甚至出现了微小的性能倒退。PyPy 依然非常快，但在本项测试中 Node.js 表现得更快。</p>
<p>接下来的表格和图表显示了 Python 解释器的 JIT 和自由线程版本的结果：</p>
<p>这展示了与第一项测试相同的总体情况。3.15 JIT 再次展现出了令人瞩目的提升，相比常规解释器获得了 1.28 倍的速度收益。自由线程版本相对于标准解释器出现了性能下滑，但 3.14 解释器也出现了类似的下滑，因此这并不算退步。正如我之前所说，这并没有太大关系，因为这项测试是单线程的，所以它并不是能让自由线程解释器大显身手的那类应用。我认为期望自由线程解释器的性能与常规解释器相当是合理的，因此从这个角度来看，我们只能说这项工作仍有待继续完善。</p>
<p>现在让我们并行运行 4 个线程来重复所有测试。鉴于这是一项专为评估 Python 解释器自由线程版本而设计的特定测试，我舍弃了非 Python 的运行项。</p>
<p>为了获得基准数据，我首先在标准 Python 版本上运行了多线程测试。需要非常明确说明的是，这些结果对 CPython 而言会比较糟糕，因为全局解释器锁（GIL）阻止了线程之间真正的并发执行。以下是多线程斐波那契测试的结果和图表：</p>
<p>该测试显示 3.15 比 3.14 稍微慢了一点点。我们在单线程测试中已经看到，3.15 解释器仅比 3.14 稍快一点，因此总体而言，我认为可以说标准解释器的速度与 3.14 大致相当。在这里我们还可以看到，PyPy 依然大幅领先标准 Python，但引入线程后，其速度也以类似的比例放缓，因为 PyPy 的并发同样受到 GIL 的影响。</p>
<p>现在让我们来看看 Python 解释器的 JIT 和自由线程（free-threading）版本在该测试中的表现。</p>
<p>Python 3.15 解释器的自由线程版本运行速度比标准解释器快约 4.5 倍，这一比例与 3.14 大致相同。这一显著的速度提升归功于解释器在没有 GIL 的情况下运行，从而实现了更高效的线程并发。</p>
<p>我们从这些结果中还可以得出第二个观察结论：在带有 GIL 的情况下运行的 JIT 版解释器，即使在运行多线程时，也对标准解释器保持着类似的优势，而这在 3.15 中是一个新现象。</p>
<p>我们还有一组结果需要过一遍。以下是冒泡排序测试的标准解释器结果：</p>
<p>这也再次与先前的结果大致吻合，3.15 解释器仅比 3.14 快一丝丝。</p>
<p>既然我们已经有了该测试的基准数据，接下来看看 JIT 和自由线程解释器的表现：</p>
<p>在这里，自由线程版 3.15 解释器再次快于标准版本。提升幅度虽然不像斐波那契测试中那么引人注目，但这种类型的程序仍然是免 GIL（GIL-free）解释器的良好使用场景。</p>
<p>至于 JIT 的结果，它们似乎与该解释器的所有其他运行结果一致，显示出在 3.15 中有极大的改进。</p>
<p>希望您喜欢我的基准测试。也许在看到一堆数字和彩色图表之余，您会好奇这一切在实际应用中意味着什么。</p>
<p>在结束本文之前，我想给您提供我对这些数据所代表含义的个人解读，因为您可能想知道升级到 3.15 是否合理，以及升级后可以期待看到哪些改进。在这一部分中，我们将离开确定性事实并进入观点领域，因此请记住，其他人看待这些数据可能会得出与我完全不同的解读！</p>
<p>免责声明交代完毕后，我想说，跑完测试后我的直觉感受是：在性能方面，Python 3.15 充其量只是对 3.14 的相当微小的改进。我可能最终会升级目前基于 3.14 的生产环境项目（例如本网站），但我获得的结果并不会让我急于升级——不像去年看到 3.14 的出色结果后那样迫切。</p>
<p>3.15 版本中唯一有明显改进的领域是 JIT。但 JIT 仍然是一项实验性功能，因此在生产环境中使用它并不是个好主意。只有当 JIT 脱离实验阶段后，我才会考虑在生产中使用它。</p>
<p>除了 JIT 之外，此版本实际上没有任何显著的性能提升。有些测试确实显示出小幅的性能提升，但其他测试却显示出性能倒退，因此我不指望这些微小的变化会转化为真实世界项目中肉眼可见的性能改变。老实说，我觉得再在 3.14 上多待几个月，甚至等到一年后 3.16 发布时再评估新版本，我也不会损失任何东西。</p>
<p>不过，我确实计划将 3.15 用作我日常主要使用的解释器，而且也许我最终会升级我的一些生产项目，仅仅是为了使用某些新特性，例如类似 JavaScript 的推导式解构或延迟导入（lazy imports）。</p>

### [当随机其实不够随机时](https://ersc.io/blog/when-random-isnt-random-enough)
<div class="original-title-sub"><span class="orig-tag">原文</span> When random is not actually random enough</div>

<div class="article-body" data-article-body="true"><p>我们在随处可见的代码库中常常能发现一个普遍的模式，而且我们许多人也曾写过这样的代码：给定一组对象，随机抽取其中一个。每个对象被抽中的概率应当相同。一个相当简单且直接的解决方案是抽取一个很大的随机数，然后通过取模将该数字限制在候选数量的范围内：</p>
<p>我清楚地记得，在年轻很多的时候我曾多次选择这个方案，尤其是在写 C 语言时——其标准库除了 rand() 之外没有提供任何其他东西——以及我当时常用的另一门语言 Haskell。毕竟，当面临这样一个问题时，这是一个相当直接且直观的解决方案，而且几乎任何代码库或语言，无论多么简陋或薄弱，都会有某种获取随机数的机制。</p>
<p>但这套解决方案存在一个隐藏的问题：它破坏了给定的 random_u64() 函数底层的均匀分布特性。这意味着所选对象的变化特征并不符合我们直觉上的设想：我们可能以为每个项目被选中的概率都是 1/10。但事实并非如此。</p>
<p>让我们从一个更简单的问题开始：在区间 [0, 9] 内选取一个整数。共有 10 种可能的选择。假设我们的随机选择函数具有均匀分布，那么每个整数被选中的概率均为 1/10 = 10%。</p>
<p>接下来，让我们像上面那样利用取模运算符，使用该整数从包含 3 个对象的集合中随机选取一个值。直觉上的（隐性）预期是该操作能以 1/3 = 33.3% 的均等概率从这 3 个对象中挑出一个；换言之，我们希望生成的概率分布能够“遵循”输入变量的均匀分布。</p>
<p>遗憾的是，事实并非如此；只要列出所有结果，这一点便显而易见：</p>
<p>换句话说：在给定的 10 个输入中，有 4 个会得到选项 1，而选项 2 和 3 分别只有 3 个输入会得出。这意味着选项 1 被选中的概率是 40%，而不是预期的 33%，同样地，选项 2 和 3 被选中的概率只有 30%。</p>
<p>这是最经典的错误之一，尤其是在你只有 random_u64() 可用的情况下。正确的做法应该是使用 random_between(l, h) 函数，它让 l 和 h 之间包含两端的每个数字都有 1/((h-l)+1) 的概率被选中。正如我们现在所料，这样的函数实现起来要稍显复杂一些！</p>
<p>在我看来，问题有两个层面。首先，我认为只提供均匀随机函数是一种次优的 API 设计，尤其是考虑到其最常用的变体很容易被错误实现。但同时，它也是从一开始就在错误的认知领域里思考的一个典型范例。</p>
<p>我认为首要的一点是，像 random_u64() 这样的 API 有点过于底层且过于专门化。我们真正想要的并不是对一个均匀数字进行采样，而是一个更通用的操作符，来表达“某件事发生的频率是多少”。</p>
<p>一方面，你很少只需要单纯抽取一个随机数，你通常想要的是从一些可能的选项中挑出某个对象；另一方面，为某些对象赋予比其他对象更高或更低的权重往往很有用——均匀分布并不是唯一有价值的分布！random_u64() 对这两点都无能为力；而 random_between(0, 9) 乍看之下也仅仅对第一点有所帮助（稍后详述）。</p>
<p>在大多数情况下，我认为转而使用更通用的操作符会更有帮助，它能让你直接面对这些问题：一个接收一组离散选项及其被选概率的 random_choice() 函数。换句话说，你应该亲自明确写出概率分布。有了它，你不仅可以实现之前的两种行为，还能表达许多更有趣的模式。</p>
<p>通常我们在讨论概率时，会认为它们的总和应为 1.0，正如对原始示例所做的如下重构；在这样的设计中，那个错误的“失衡”选取就会显得格外刺眼：</p>
<p>我认为这是通用 API、或者说更抽象的 API 能够切实让你大部分代码更容易推理且更易编写正确的一个案例（在众多案例中之一）。当然，你也应该保留 random_u64() 和 random_between()——但我认为 random_choice() 是好得多的默认工具，因为它会帮助你顺理成章地走向成功。</p>
<p>前面的接口在教学上很不错，但浮点数的不稳定性可能会干扰我们选取所需精确权重的能力，因为它们的总和必须恰好为 1.0。此外，要求总和为 1.0 也很麻烦，因为你可能不得不去计算每个可能选项的相应比例。因此，当面对任何涉及浮点数的问题时，我们会采用行之有效的方法来解决它：弃用浮点数，改用别的方式。</p>
<p>你会发现大多数标准库（比如 Python）正是这样做的，它们使用相对整数权重。“相对”意味着数字的总和不必为 100；你只需要将它们相加，任意选项的权重就是该选项几率与总和的比值。前面的权重可以改用 (4, 3, 3) 来表示。4 + 3 + 3 = 10，因此 3 / 10 = 0.3，正如我们所期望的那样。</p>
<p>相对整数权重的好处之一在于它们表现得更加符合直觉，因此你更有可能正确使用它。如果你数了一下盒子里的东西，看到有 10 个蓝色物品和 5 个红色物品，你只需将选项写为 [(Blue, 10), (Red, 5)]，最终的选取结果就会按照你的预期分布。</p>
<p>另外还有一个细节：如果你拥有的是 random_between(l, h) 而不仅仅是 random_u64()，直观地实现这个 API 会容易得多，我认为这再次说明了 random_u64() 过于底层。假设我们有整数权重 15 + 12 + 3 = 30。那么只需抽取一个随机数 choice = random_between(0, 29)。如果抽取的值在 [0, 14] 之间，则对应第一个选项；在 15 到 26 之间是第二个选项；[27, 29] 则是第三个选项。换言之，你可以直接将整数权重映射到区间 [l, h] 的子集上，然后从该区间内均匀抽取。这个方法既有用又简单，在我看来，它也应该与其他函数一起提供。</p>
<p>在我看来，另一个更为微妙的问题是弄清楚你究竟在哪个领域中进行操作。在前面的例子中，我们要讨论的并不是单纯的数字，而是随机变量。我们通常用大写字母 X、Y、Z 等来表示这些随机变量。</p>
<p>与普通数字非常相似，随机变量也具有代数运算性质；你可以对随机变量进行加法和减法，它们也具有指数运算。但这些运算符同样会影响底层的分布及其期望结果，正如它们在此处所表现的那样。但最重要的是，非线性运算符不遵循随机变量的期望值运算。具体而言，期望值上的函数 f，即 E[f(X)]，并不总是等同于 f(E[X])。</p>
<p>这里发生的情况正是如此；如果我们不加注意，就很容易误以为自己是在试图保留变量值 x = random_u64() 的某种特性，但实际上我们想要保留的是底层 random_u64() 函数本身的特性。</p>
<p>我们是 Antithesis 的客户。在其平台上，我们通过随机执行关键代码路径来切实有效地发现漏洞——它相当于一个面向整个操作系统的庞大确定性模糊测试工具（fuzzer）。就像模糊测试工具一样，将代码覆盖率视为指路明灯是很有用的：“这段代码是否被测试过”等同于提问“模糊测试工具是否发现了该路径”，如果模糊测试工具没有发现该路径，那么这段代码就没有被测试到。</p>
<p>提高覆盖率的关键在于表达正面与负面代码路径，并在测试中触发它们。负面路径是指一种异常情况，一旦触发就是漏洞，例如触发了 assert!() 报错——例如，我们可能会根据数据本身的哈希值作为键，从缓存中读取某些数据，然后断言 assert!() 该键与重新计算的数据哈希值相匹配。</p>
<p>正面路径则可能是确保某个在“小规模”和“大规模”上传时执行不同逻辑的上传函数，确实对这两种情况都进行了测试。在这种情况下，直接表达你的概率分布是非常方便的：</p>
<p>在这种情况下，在测试过程中，约 7/8 的上传是小数据块，约 1/8 的上传是大数据块（分为三种不同大小）。能够灵活调整这些数值对于帮助探索状态空间极其宝贵！将这个示例扩展到表达诸如泊松分布等分布也相当容易。</p>
<p>我在这里发现的另一个实用场景是在某些特定条件下扩展选项集合；例如，当发生某种“好的”或“坏的”情况时，使用 choice.push() 向上述向量中添加内容，以此来引导搜索方向——这需要重新平衡上述示例中的概率，但你可以设想通过不同的结构设计来避免这一问题。</p>
<p>这就引出了这篇文章，以及上周发生的一件事：最近在审查与 Antithesis 相关的代码时，我们最终彻底移除了那些悄悄混入的 random_u64() 用法，改用（带权重的）random_choice()，因为在实践中我们无论如何都只想要离散的加权选择；在另行通知之前，我们已暂停引入对其的新调用。我觉得这个教训非常重要，不能让它被埋没在某个提交信息（commit message）中，况且我自己也总是容易忘记它。</p>
<p>下次当你看到类似最初示例的代码时，不妨问问自己：我能否直接表达所需的分布？如果可以，你很有希望能找到一个丰富得多的工具供你使用！</p></div>

<div class="article-body" data-article-body="true"><p>通过在 64 位系统上使用 32 位指针，有可能大幅节省内存（对于堆中包含大量指针的程序，节省幅度接近一半），并能在一定程度上提升程序运行速度（得益于更多数据能够装入缓存）。</p>
<p>Linux x32 ABI 正是为此而设计的，但可惜它被严重低估且未得到充分使用。它在 Debian 上默认处于禁用状态（尽管可以通过启动标志启用），在 Arch Linux 上甚至根本没有编译进内核。大多数软件针对 x32 的编译都很顺利，但针对该架构的打包分发很少，因此几乎所有东西都需要自己编译。</p>
<p>我曾尝试在 x32 上部署 Mastodon，它将该应用的内存占用从 650MB 降到了 350MB。这其中蕴含着巨大的潜力，但相关工作主要是吃力不讨好的协调和沟通类事务，我自己既没有时间也没有动力去推进它。——Hailey</p>

### [用于传递程序状态的终端协议（OSC 7501）](https://mitchellh.com/writing/program-status-osc7501)
<div class="original-title-sub"><span class="orig-tag">原文</span> A Terminal Protocol for Program Status (OSC 7501)</div>

<div class="article-body" data-article-body="true"><p>我为一种新型终端转义序列编写了规范：OSC 7501，即“程序状态协议”（Program Status Protocol）。它允许任何程序向终端告知自己当前的状态：空闲（idle）、运行中（working）、等待用户响应（waiting on the user）、已完成（finished）或失败（failed），以及其具体原因。</p>
<p>例如，Terraform 可以通过该协议指示其当前正阻塞并等待用户输入，附带信息为“Apply 3 to add, 1 to change, 0 to destroy?”（经过 base64 编码）。终端（或任何运行 Terraform 的其他工具）都可以按其认为合适的方式展示这些信息：发送通知、收件箱式列表、状态图标等。</p>
<p>本文阐述了我为何认为需要存在这样一个协议、为何现有方法不够完善（特别是对于编码智能体/coding agents 而言），以及该协议的具体工作机制。</p>
<p>这是一个完全通用的、终端原生的规范与协议。它源于我在 Superlogical 和 Ghostty 上的工作，但该规范本身不包含任何特定于产品的功能或用语。它被设计成一个符合惯例、结构良好的规范，任何终端开发者都会感到熟悉。</p>
<p>长时间运行的任务在终端中屡见不鲜：构建、部署、软件包升级、数据处理，以及如今越来越常见的编码智能体。这些程序会在自行运行、等待用户以及最终完成之间交替切换。与此同时，用户通常会转去处理其他事情，并希望在工作完成或需要用户介入时收到通知。</p>
<p>这个问题的各个方面早在几十年前就已通过各种方式得到解决。例如，有些终端会监控活跃的前台进程，并具备在其发生变化时发出通知的功能。或者，它们会等待某段“静默”（有不同的定义）输出的时间。该规范中也列出了现有转义序列无法满足需求的具体原因。</p>
<p>归根结底，我认为目前尚未有一种连贯统一、与交互形式无关且通用的解决方案来传达进度、阻塞、完成以及任务树。而且，仅靠拼凑现有的转义序列也无法稳健地实现这一目标。</p>
<p>如果你不关心 AI、LLM 等话题，可以跳过本节。该问题属于通用范畴，即便不引入 AI，也是一个极具说服力的需求。只是在 AI 场景下该问题尤为棘手，所以我特意提出来；但如果你完全不关心这些，直接跳过即可。</p>
<p>如今，人们越来越频繁地出于各种原因同时运行多个长时间运行的智能体：后台调研、Issue 监控、错误修复、大型功能开发等。每一个智能体都会运行一段时间，然后停下来请求权限、提出疑问，或报告任务已完成。</p>
<p>由此催生了一类新工具，我统称为“智能体收件箱”（agentic inbox）：一个集中查看所有正在运行的智能体的单一视图，显示哪些正在运行、哪些已完成，以及哪些正在等待你响应。Herdr、cmux 和 Agent Deck 就是此类数百个工具中的几个代表。</p>
<p>在缺乏专用协议的情况下，它们主要通过两种方式解决智能体状态问题：启发式匹配（heuristics）和非终端 API。</p>
<p>第一种方法是通过读取屏幕内容或窗口标题，并将其与已知模式进行比对来猜测状态。</p>
<p>Herdr 是一个很好的范例，因为它在这方面做得不错且开源记录完备。它的检测清单采用 TOML 规则，将智能体归类为空闲、运行中或阻塞。以下是针对 Claude Code 的 16 条规则中的第一条：</p>
<p>如果 Claude Code 的窗口标题以盲文旋转微调字符开头，或者自 2.1.228 版本起以半圆字符开头，则被判定为“运行中”。仅针对 Claude Code，该文件的历史记录显示在三个月内就发生了十次变更。</p>
<p>这并非对 Herdr 的批评。其维护者已经利用现有工具做到了极致。但这也充分证明了统一协议能带来的巨大价值。</p>
<p>第二种方法是让程序通过特定于某个收件箱工具的带外 API 来报告自身状态，例如 Herdr 的 socket API 或 cmux notify。在某些方面这比启发式猜测更好，因为真正知晓状态的程序本身就是状态的报告者。但是，每个程序都必须单独与每个收件箱工具进行集成，而且本地 socket 在跨 SSH 或容器内部使用时，若没有额外的桥接就无法工作。而伪终端（pty）天然就能覆盖所有这些场景。</p>
<p>OSC 7501 是解决该问题的终端原生方案。程序直接通过始终具备的 pty 报告自身状态，使用的格式即使发送到任何地方也是安全的（规范的终端会直接忽略未知的 OSC 序列）。</p>

<p>同时运行多个任务的程序可以使用层级化 ID 报告多条记录。一个部署工具可能在根节点显示“运行中”，而 us-east 节点正在推送镜像（进度 40%），eu-west 节点则处于“阻塞”状态等待批准部署至生产环境。两者在同一时刻都成立，终端可自行决定如何呈现。clear 状态则用于移除记录。</p>

<p>我结合多年维护终端模拟器的经验编写了这一规范。它的设计旨在让应用程序开发者易于输出，同时也让终端模拟器易于接收和解析。</p>
<p>我已经对该协议进行了两次实现。我们在 libghostty 中有一处实现，我在 Rex 中也有一份并行实现。此外，我还通过插件或分支形式，在 Terraform、Claude Code、Codex 和 Homebrew 中完成了概念验证集成。在每种情况下，实现代码均不超过十几行。</p>
<p>我已与许多热门终端程序和模拟器的维护者取得联系，他们帮助审阅并完善了该规范。如果你有更多反馈，我也非常乐意倾听。</p>
<p>如果你已经实现了该规范，请通过电子邮件告知我（页脚有邮件图标），我会将你添加到实现该协议的工具列表中。多谢。</p>
<p>我希望我们所有人都不再需要通过读取屏幕或进程树来猜测程序在做什么。程序本身早就一清二楚。让我们给它一个直接告诉我们的途径吧！</p></div>

### [那次我和一个笔记本小偷共事的经历 (2025)](https://blog.pipetogrep.org/2025/07/27/that-time-i-worked-with-a-laptop-thief/)
<div class="original-title-sub"><span class="orig-tag">原文</span> That Time I Worked With a Laptop Thief (2025)</div>

<div class="article-body" data-article-body="true"><p>发布时间：2025-07-27 19:21:39，作者：Chris Jones<br />更新时间：2026-10-05 21:10:44 • 阅读时间 10 分钟<br />我曾经在一家公司工作，那里有一个 IT 外包员工在一整年多的时间里偷窃笔记本电脑并转售。这篇文章讲的就是他是如何被抓现行的故事。文中不会使用人物和公司的真实姓名，但故事和截图（已做打码处理）全都是真实的。<br />我当时在 DevOps 工程师的岗位上感到了职业倦怠。我没有选择去找另一份做同样事情的工作，而是向老板询问是否能暂时转到一个不同的岗位，这样我既能调整状态，又能继续对公司发挥价值。他同意了，并问我有什么想法。<br />公司的 IT 经理当时正准备离职，整个部门的员工、工具和流程确实都需要有人来整顿。我毛遂自荐担任临时 IT 经理，负责把这个部门重新整顿好。他很喜欢这个主意，于是我便着手开展工作。<br />IT 部门里唯一剩下的人是一名 IT 外包人员，我们暂且叫他吉姆（Jim）。吉姆在这家公司工作了一年多一点。随着我对吉姆的了解加深，我发现由他经管的一切都处于分崩离析的状态。IT 储藏室乱成一锅粥。他在工作时间几乎联系不上，晚上在办公室不知道在倒腾些什么，而在协助解决 IT 相关问题时也帮不上什么忙。<br />我先假定他是出于好意，认为他的部门长期以来人员不足、过度操劳，因此首要任务就是组建一个新团队。<br />在基本上由我自己一个人处理 IT 工单维持了一个月（吉姆经常玩失踪），并彻底清理了 IT 储藏室之后，我招募了一名新的 IT 经理和一名支持专员。在他们入职的第一周，我带他们参观了办公室，包括重新整理过的 IT 储藏室。就在那时，我第一次察觉到了不对劲的地方。<br />我们刚订购了 15 台全新的 MacBook。虽然其中一部分已经发放出去了，但储藏室里剩下的数量看起来仍然比应有的要少。我查阅了库存记录，发现有六台机器下落不明。<br />为了保持一切公开透明，我在 IT 讨论的 Slack 频道里发了一条帖子询问失踪笔记本的情况，并要求团队里的每个人如果知情就在帖子里发言。我的老板毫不知情。他也确实不可能知道，因为他是远程办公的。新员工也什么都不知道，因为这是他们第一天见到 IT 储藏室。<br />接着吉姆给我发了消息，不是在帖子里回复，而是私信。<br />他告诉我，其中五台笔记本电脑刚送达时电池就坏了，而第六台发给了一名员工。这是第一个对不上的地方。15 台全新原装封箱的苹果笔记本电脑，里面有 5 台一到货就是坏的？我知道苹果的硬件不是最皮实的，但这种故障率对他们来说简直是闻所未闻。<br />在消息中，他发给了我五个苹果维修案例编号。一查我就发现，这几个维修请求极其可疑地是在我发出关于设备丢失的消息之后立刻创建的。更可疑的是，我发现他是用自己的个人苹果账号而非公司账号创建的维修请求，这让我无法获取有关这些请求的更多信息。<br />第二天，送来了两个 FedEx 箱子，里面装有两台全新的 MacBook。FedEx 面单显示它寄自曼哈顿第五大道的苹果直营店（离办公室只有步行距离）。这两台机器有两个古怪之处：<br />后来吉姆声称其中两台笔记本电脑已经换新了。我向他道谢，并要求在我们把这一切弄清楚之前，他不要把笔记本电脑带回家。他试图操控我的认知，说他口头跟我提过机器坏掉的事，肯定是我忘记了。接着他表示自己“根本”没有把笔记本电脑带回家过。<br />此时，我仍然觉得事情十分蹊跷，但依然暂且相信吉姆。我此时的职责不是去指责或推测，而是收集数据看看真相究竟如何。我决定去咨询苹果公司。<br />我把送达的两台新笔记本带到了第五大道的苹果直营店。我说明了自己面临的处境，并询问他们是否能告诉我关于这两台机器来源的任何信息。它们并不是公司购买的。相反，与两台机器关联的名字正是吉姆本人。<br />与此同时，他创建的全部 5 个苹果维修请求，进展仅仅到了苹果寄出空箱子准备回收那 5 台“故障”机器的阶段。那些箱子是寄到公司的吗？并不是！它们被寄到了吉姆的住所。<br />最后，我询问了关于那些“换新”机器的 FedEx 运单面单。我询问他们通常是如何以及从哪里寄出换新设备的。他们确认他们**不会**从苹果直营店寄出维修机器，而是从苹果维修中心寄出，而在本案例中，维修中心位于相邻的一个州。<br />吉姆现在已被抓到了多次撒谎：<br />尽管我们表现得彬彬有礼，尽可能不带指责口吻，并且尽全力只是想查明吉姆负责监管的失踪财产的下落，吉姆却决定彻底扮演起受害者的角色。<br />当时，我们虽然并不完全清楚到底发生了什么，但我们知道确实有机器丢失了，而吉姆所说的话完全前后矛盾，我们在被他蒙骗。吉姆得到了 24 小时的期限交出所有丢失的机器，但他未能做到。在那个节点，我们别无选择，只能在他自己提出辞职之前将他解雇。<br />这些设备注册又持续了一年，有些是新注册的，有些则是同一批机器被懂得如何解锁并恢复出厂设置的人再次倒手转卖，结果在首次开机时又被重新锁住。我们追踪了其中一些机器流经多个国家和地理区域的轨迹。<br />真正的受害者并不是公司本身，而是那些在不知情的情况下购买了这些被盗设备的人。他们打开全新原封的 MacBook，却在机器被所属公司锁定时瞬间变成了一块砖头。<br />在吉姆离开几天后，邮寄收到了另一台全新的 MacBook。我又把它带到了苹果直营店，他们告诉我这台不像前两台那样是在店里买的。相反，它是由一家名为“英迈”（Ingram Micro）的公司购买的，这是一家大型 IT 设备分销商。<br />我打电话给英迈，他们向我提供了采购人的姓名以及采购时所在的供职公司。我不会透露这家公司的名字，但我可以说他们是一家国防部（DoD）的承包商。<br />花了好几天时间，在打了无数通电话和发了无数条信息之后，我联系上了该国防部承包商的 IT 和法务团队，并解释了来龙去脉。结果发现吉姆当时（同时！）也在为他们工作，并且偷了他们的一台笔记本电脑，用来充抵他从我们这里偷走的一台笔记本！</p>
<p>这么做也让他丢掉了那份工作。后来我从老板那里得知，一名联邦调查局（FBI）特工找他谈了话，他把一切都招了。国防部（DoD）相关的工作似乎对财产盗窃行为毫无容忍度。</p>
<p>几周过去了，吉姆仍然没有归还分配给他的公司笔记本电脑。在多次催促后，一个破损严重的箱子通过 UPS 寄到了。里面装着吉姆寄回的两台笔记本电脑，完全没有任何防震填充物。两台机器里里外外都被毁得一塌糊涂。</p>
<p>我其实不太清楚。我当时供职的公司在提请刑事指控这件事上不了了之。总的算下来，他在那里工作的一年间偷了 30 多台笔记本电脑。被盗财物的价值完全达到了重窃罪的级别，但我猜他们并不在乎，所以没有追究到底。我不知道他在那家国防部承包商那里是否也能这么走运。</p>
<p>但愿有些教训吧。如果他咬定自己什么都不知道，他的骗局或许还能维持得更久一些。相反，他不停地辩解，结果越陷越深。往好了想，我希望他能吸取教训，以后别再干这种荒唐事了。至少，他学会了别对我撒谎。</p>

### [等风头过去后，一份可持续的 Web 职业生涯](https://dbushell.com/2026/10/07/sustainable-web-career/)
<div class="original-title-sub"><span class="orig-tag">原文</span> A sustainable web career, for when all this blows over</div>

<div class="article-body" data-article-body="true"><p>2026年10月7日，星期三<br />无论好坏，Web 行业目前都正经历着一个特殊阶段。其中的原因在很大程度上是非理性的。人们仍然需要 Web，这一点丝毫未变。然而，该行业的财务状况却举步维艰。长期的职业前景显得充满变数。</p>
<p>由于我公开反对那股意图摧毁我所在行业的推动力量，并在此过程中招致了一些不满，志同道合的同行经常私下向我寻求建议。我只能给出一个虽然平淡但明智的回答：在没有后路的情况下，不要辞掉有收入的工作。去温彻斯特酒馆（Winchester），喝上一杯冰爽的啤酒，静待这一切烟消云散。</p>
<p>（图注：电影《僵尸肖恩》（2004）中的角色在温彻斯特酒馆喝酒。西蒙·佩吉饰演的角色举着一杯啤酒摆出干杯的姿势，并对着镜头眨眼。）</p>
<p>我相信局势会有所好转。在此之前，我们能关注些什么来加速摆脱这场思维低谷，并在局势平息后更好地确立自身定位呢？</p>
<p>为了获得可持续的 Web 职业生涯，还有什么比关注那些极度紧缺的关键技能更好的去向呢？我的重点是前端开发，但这些知识领域与任何从事网站制作业务的人都息息相关。</p>
<p>无障碍访问（Accessibility）一直是 Web 开发的基础，但现在比以往任何时候都更需要每个人去倡导它。理解为什么无障碍访问面向所有人。学习如何针对实际需求和落地实践来探讨无障碍访问。</p>
<p>遗憾的是，对于某些科技群体而言，无障碍访问已沦为一种道德标榜（据我所知，领英上充斥着错误信息）。无障碍访问并非如同装饰菜叶一样可以随意附加在网站上的功能。无障碍问题也无法在最后通过自动化流程来修复。Web 专业人士必须能够扭转这种思维，从第一天起在所有决策中都尊重无障碍访问。</p>
<p>学习并将相关指南作为基准。与真实用户交流并由他们进行测试。听从渴望让你理解现实情况的专家的意见。</p>
<p>CSS 是前端标准中最具活力且不断演进的部分。要架构一个优秀的样式表，需要对语言特性有深入的理解。诸如级联层（cascade layers）和降低特异性的选择器等新特性，使这一过程变得容易得多。</p>
<p>CSS 一直有能力处理组织良好的样式，但那些拒绝学习并尊重这门语言的开发者，却试图通过简化的抽象或“CSS-in-JS”解决方案将复杂性转嫁到别处。这些做法本质上具有局限性，会导致性能低下，并且并未真正解决它们声称解决的问题。</p>
<p>沟通是一项（出于显而易见的原因而）极度匮乏的“软技能”。如果你想脱颖而出成为专家，或者只是想在嘈杂的声音中被听见，这都是一项极佳的技能。学会简洁明了，聚焦重点。不要害怕提出问题。</p>
<p>在问题升级之前，尽早且委婉地处理担忧。不要推卸责任，但要“明哲保身”——项目中的每个人都应该朝着同一个目标努力，但有些人的方法可能走偏了。保持积极心态，不要迎头硬撞消极情绪。</p>
<p>如果你能很好地沟通，你在岗位上就会备受尊敬。</p>
<p>你可能没料到会看到这一条，但事实确是如此。</p>
<p>“远离政治”的奢望已经不复存在。极右翼政治意识形态正在抬头，科技界中潜伏的仇恨正在苏醒。法西斯科技（fash-tech）的震中正是马斯克的“X”，像 David Heinemeier Hansson 这样的人大肆宣扬种族主义并滥用社群权力推行其议程，Guillermo Rauch 与战争罪犯合影。像 Digital Ocean 这样的大型科技巨头正在资助这场夺权行动。警惕那些否认这一威胁的人。</p>
<p>如果你想避免被挤出这个行业，就要在法西斯主义找上你之前识别并拒绝它。不要保持沉默。</p>
<p>我已经涵盖了有助于我们未来发展的议题，但有哪些东西是我们应该摒弃的呢？</p>
<p>Facebook 的那套沦为盲目崇拜（cargo cult）的实验产物是一个依然残存的遗留框架，但如今已没有理由再去学习它。React 已经根深蒂固地成为代码挤出机的通用语言。React 代码生成的速度比任何人类阅读的速度都要快。只需说明一点：尽管陈旧的招聘岗位仍要求相关经验，但 React 已不值得投入时间。高薪 React 开发的时代已经屈指可数。</p>
<p>GitHub 现在成了一种负债。对于私有代码仓库，请使用自托管的 Git 托管平台。我推荐 Forgejo。使用类似于 Tailscale 的众多服务之一，是控制远程访问的简便方法。不要将内容公开给死人网络（dead internet）去攻击！对于 CI/CD，同样采用本地方案，或使用不与科技巨头绑定的独立服务。花时间学习基本的 Git 命令。掌握一点技术和基础设施知识将大有裨益。</p>
<p>这些人长相出众、魅力十足、极具亲和力。我说的是：开发者关系人员（DevRel）、YouTuber、初创公司创始人等。当科技行业尚能兼顾我们时，网红们还算有趣，在派对后的闲聊中也是不错的话题。现在局势已变，我们绝不能允许虚假叙事主导并决定一个封闭 Web 的未来。普通人依然在使用 Web。能够为网红兜售的新奇玩意儿买单的人少之又少。他们的注意力经济已不再关我们的事。</p>
<p>这就是关于在风头过去后，如何维系可持续 Web 职业生涯的关注重点。</p>
<p>请始终牢记最重要的一点：Web 是为了人类需求而创造的人类造物。那些需求不会消失。抛弃繁荣时期积累的累赘负担。回归基础，在专业需求回暖时为自己找准位置。</p>
<p>所有观点均代表我个人，而非大型语言模型。我写的一切都是百分之百由人类创作的。因为我在乎！</p>
<p>我创立了 Valley Fold 来帮助大家，让我们一起把你的网站落地。无论你已有明确的需求范围，还是毫无头绪，我们都可以在任何阶段与你展开合作。</p></div>
