<p>当你联合两个存在包含关系的类型（其中一个是另一个的超集）时，也会发生类似的简化。例如，假设你的语言有一种 uint 类型，仅代表“任何无符号整数”，不论其位宽如何。在这种情况下，u16∪uint=uintu16 \cup uint = uintu16∪uint=uint——毕竟，值集 uint 包含了集合 u16。</p>

<p>关于 Rust 枚举，一个有趣的细节是：Rust 并没有定义 IsEmpty、Color 和 Name 这三种普通类型，这三个“变体”（variants）只能作为 ComplicatedEnum 的一部分存在，不能独立存在。这意味着没有哪个值能直接拥有 IsEmpty 类型：ComplicatedEnum 的所有值都仅仅属于 ComplicatedEnum 类型。</p>
<p>我认为 Rust 对求和类型的这种“强制包裹”并没有太大的理论根基，但它对 Rust 求和类型的实际应用产生了重要影响，我稍后会谈到这一点。</p>
<p>在 Julia 中，类型与“类型即值的集合”这一理念完全契合：</p>
<p>简而言之，值 5 既属于 Int 类型，又属于 Union{Int, String} 类型，还属于 Integer 类型，以及无数其他类型。</p>
<p>与 Rust 的另一个区别在于，Julia 是一门动态语言。简而言之，在静态语言中，表达式（如代码）具有类型，但类型在运行时并不真正存在，因为它们已被优化消除，一切都只是二进制数据块。在动态语言中，值在运行时具有类型，而编译器在运行前推断出的任何类型都无关紧要：它对运行时实际产生的值或类型没有任何影响。</p>
<p>这意味着，即使编译器推断某个值 x 的类型为 Union{A, B, C}，在运行时，x 的类型也只会是 A、B 或 C。联合类型在运行时并不存在。它们仅用于表达编译器对于程序运行时将会发生什么所持有的不确定性。</p>
<p>Julia 与 Rust 类型之间的许多差异，实际上源于 Rust 求和类型的“强制包裹”，而不一定是因为它们属于求和类型而非联合类型。</p>
<p>如果你有一个期望接收 A 的 API，你随时可以将其更改为接收 Union{A, B} 而不会破坏兼容性，因为类型 A 的所有值同时也都是类型 Union{A, B} 的值。</p>
<p>类似地，如果你的函数返回 Union{A, B}，你可以将其改为仅返回 A 而不会破坏兼容性。</p>
<p>这在 Rust 中行不通：你无法在不破坏用户代码的前提下，把一个原本接收 Option 的函数改为接收 usize，也不能在之前返回 Option 的地方直接返回 usize。</p>
<p>在 Rust 中，你无法直接访问求和类型的变体，因为它们始终处于包裹状态。这导致了大量样板代码：看看 Option 和 Result 那一长串方法列表吧，它们的存在仅仅是为了在各种场景下对这些类型进行解包（unwrapping）和重新包裹（re-wrapping）。</p>
<p>在 Julia 的系统中就简单得多：你不需要解包再重新打包，因为一开始它就没有被包装。如果 x 是一个 Union{Int, UInt}，你怎么给它加 1 呢？直接 x + 1 就行，就像任何普通整数一样。</p>
<p>正如返回一个更狭窄的联合类型或接收一个更宽泛的联合类型不会构成破坏性变更一样，这也是编译器允许的改动。</p>
<p>假设你编写了一个返回 Union{A, B} 的函数 f，并将其传给一个期待该类型的函数 g。但现在，在某处代码中，你调用 f 时将其中一个参数传入了常量。编译器随后会检查该常量参数是否能收窄 f 的返回类型。假设经过常量折叠后，f 必定返回 A。如果是这样，编译器就会知道 g 实际接收到的是 A，而不是 Union{A, B}——因此 g 现在可以得到进一步优化，例如直接在编译时消除输入为 B 时的所有分支。</p>
<p>Julia 的联合类型样板代码可能更少，因为你可以像使用具体类型一样使用它们——但这也是一个危险的陷阱。</p>
<p>考虑一下返回 Union{Int, Nothing} 的 Julia 函数 findfirst 与返回 Option 的 Rust 函数 iter.position：人们很容易忘记 findfirst 可能会返回 nothing 从而没有处理这种情况，进而引入 bug。但你不可能把 Option 误当成 usize，因为它们是不兼容的类型，你必须对和类型进行解包。</p>

<p>显然是 Vector{T}！对吧？不，并非必然：</p>
<p>它不是联合类型的向量，而是向量的联合。仔细想想这确实必然如此，但这正是联合类型会因为突然自作聪明而让你“措手不及”的典型例子之一。</p>
<p>上文提到的利用联合类型自动收窄来实现的 Julia 编译器优化虽然巧妙，但如果你面对的是一个包含比如 10 种变体的联合类型呢？如果你的语言像 Julia 和 Rust 那样为每种输入类型编译专门的特化函数（“单态化”），这可能会导致组合爆炸，带来巨大的编译时间和臃肿的代码。事实上在 Julia 中，这种情况甚至糟糕到了如果编译器推断出一个值是包含 4 个以上成员的联合类型，它就会直接放弃，并生成在运行时检查类型的代码。</p>
<p>在这种情况下，直接用 if/else 语句检查是哪种变体，要比编译器耍小聪明高效得多。或者，还有比 if/else 语句更好的方法……</p>
<p>正是因为 Rust 的和类型不做这些花哨的类型运算，用户可以确信包含变体 A、B 和 C 的和类型始终保持不变，具有完全相同的变体。</p>
<p>这使得穷举模式匹配成为可能：模式匹配能在编译时检测出你是否遗漏了任何边界情况。如果你使用 Rust 超过 5 分钟，你就会明白这是何等不可多得的绝佳特性。如果没有，我强烈建议你去体验一下，这样你就能体会到如果“你最喜欢的语言”也能拥有这一特性该有多棒。</p>
<p>联合类型与和类型各有其优势。恰如其分的是，联合类型契合了 Julia 的长处：它们能够编写出富有表现力（少样板代码）、通用且快速的代码。另一方面，Rust 的和类型则带来了类型可预测的代码，并通过强制检查边界情况实现了更高的安全性。</p>
<p>我并不认为联合类型与和类型之间的这种权衡是不可调和的。我认为鱼与熊掌兼得或许是可能的，但我目前还不确定这样的系统究竟会长成什么样。</p>
<p>希望这能成为另一篇博文——或者未来某个 Julia 软件包——的主题！</p></div>

### [关于网页浏览器未来的思考](https://sarahjamielewis.com/log/2026/future-of-web-browsers.html)
<div class="original-title-sub"><span class="orig-tag">原文</span> Thoughts on the Future of Web Browsers</div>

<div class="article-body" data-article-body="true"><p>早在今年七月，受到 Firefox 又一次整合人工智能（AI）的触动，我在 Mastodon 上发了一小段帖子：</p>
<p>如果独立、非劣质糟粕（non-slop）的网络还有未来可言，那么现在就是所有 Firefox 分支（fork）齐心协力、共同维护一个脱离 Mozilla 独立硬分支（hardfork）的关键时刻。</p>
<p>这是一项过于庞大的工程，任何单一的小型项目（甚至可能是所有小型项目加起来）都难以单独应对，但它也实在太重要了，绝不能继续留在 Mozilla 这样的机构领导之下。</p>
<p>如果没有这种果断大胆的合作，我担心我们早已满盘皆输。</p>
<p>Mozilla 以及随之而来的 Firefox 已经明确了他们想要前进的方向——并且在过去的十年里始终如一地朝着那个方向前行。那里不会出现回心转意的救赎情节，他们绝不会掉转船头——而随着每周每月的流逝，Firefox 充斥了越来越多的劣质糟粕，距离最初创立它的愿景越来越远。</p>
<p>像 Tor Browser 和 Waterfox 这样的项目正在煞费苦心地禁用或修补掉其中最恶劣的部分——但每一个版本的维护成本都在变得更加高昂，而且总有漏网之鱼。</p>
<p>在帖子的其余部分，我描绘了一个略显天真乐观的大致构想，设想许多分支联合起来，在脱离 Mozilla 的情况下维护一个基础版本，或许可以利用 Tor Project 或其他分支已经在做的工作。</p>
<p>那条帖子以及随后的交流催生了 base browser 项目。这是一个尝试让人们聚在一起讨论想法和方向的平台。</p>
<p>受到这一势头的鼓舞，我着手制作了一个补丁，彻底移除了 Firefox 中所有的 AI 整合代码。结果生成了一个极其庞大的补丁：影响了 1605 个文件的变更，删除了 852,297 行代码，总大小达 37 兆字节（MB）。</p>
<p>在接下来的几周里，我和一小群志愿者又制作了几个补丁，对这个庞大的 AI 补丁进行了修改，并编写了一些脚本将 37MB 压缩到合理的大小——略低于 1 兆字节（我们通过使用 Git 现有的不可逆删除标志以及一些自定义 Python 脚本来实现重新打补丁）。特别感谢 cliffmccarthy 和 gellge，以及为测试和讨论补丁与该项目做出贡献的每一个人。</p>
<p>如今，base browser 提供了一套基于当前 Firefox 153 ESR 的补丁，这些补丁从代码库中彻底剥离了对用户不友好的特性（而不是常见的那种仅仅将其禁用的软分支做法）。</p>
<p>我认为彻底删除这些功能是正确的做法，其原因恰恰在于让这件事情变得痛苦的本质——这些功能非常庞大，而且与核心浏览器的结合越来越紧密。它们在整个 Firefox 代码库中所占的比例也越来越高，坦率地说：</p>
<p>现在，我做好了打输这场战役的充分准备。我不相信有足够的资金或足够的开发者精力来长期维持这样的项目。除非我们所有人将力量汇聚在一起，让这样的基础版本成为可能。</p>
<p>这项努力建立在流沙之上，Firefox 早已超越了简单的 AI 整合，正在设想一个将整个浏览器环境打造为“智能窗口（smartwindow）”的未来，这个窗口不仅面向人类，也同样面向第三方 AI 智能体（agent）。</p>
<p>我不希望网络走向那个方向，坦白讲，我也无法苟同追随。</p>
<p>正如我也曾说过的那样，我并不是做这件事的合适人选，但我至少需要做点什么来尝试促成它的发生。</p>
<p>如果这一切的成果仅仅是让少数几个人学会了如何从源代码编译 Firefox，我也会视其为一种胜利。如果最终有任何项目使用或采纳了这些补丁，我将欣喜若狂。</p>
<p>除了尝试通过打补丁剔除最令人无法容忍的整合之外，我也一直在探索减少对 Firefox 依赖的其他途径：</p>
<p>但即便如此，仍然存在一个问题：这些策略的存在只是为了对抗劣质糟粕主导的普遍现状，其本身并不具备启发性与开创性。</p>
<p>我不想把自己的精力、时间和生命仅仅耗费在维持现状的挣扎中。我年轻时一头扎进编程书籍、脑海中满是代码，是因为我想创造有意义的事物，是因为我想更好地理解这个世界。</p>
<p>不仅如此，我深信未来的到来绝不是靠拿取过去的东西、将其碾碎、重新加热后作为毫无远见的劣质糟粕端上桌。</p>
<p>在过去的十多年里，网络标准已经被商业利益的优先考量过度挤占和饱和。</p>
<p>要以任何质量保证和安全标准来维护一款网页浏览器，你需要一个资金充裕的团队——或者在你的依赖树中依附于这样一个团队。</p>
<p>资金很少会在毫无附加条件的情况下注入，而在每一次页面加载时，你都能感受到纯粹哲学愿景与预期回报之间的这种张力。</p>
<p>在 2000 年代初期，曾有一段时期 Firefox 引发了一场浏览器复兴，当时人们对“浏览器”所能承载的形态充满了兴奋与期待……订阅源（feeds）、博客整合、集体标签、开放评论……</p>
<p>最初的精神在于：网络不仅应该是可读的，也应该是可写的，进而扩展为可分享的。</p>
<p>而在某种程度上，受经济与技术规律的塑造，我们得到了那种愿景的一个近似版本……经过塑料覆膜包装，并被彻底消毒阉割。</p>
<p>我经常思考 Amaya 以及后来的 Flock 等浏览器所提出的愿景：浏览器不仅应当是消费的工具，也同样应当是创作的工具。</p>
<p>我内心依然坚守着这一愿景。在过去的几年里，我尝试构建了一些支持 Gemini（指该网络协议，而非大型语言模型，*叹气*）、RSS 以及其他未受现代标准异化污染的网络技术的小型浏览器。</p>
<p>我无法确定那是否就代表着*唯一的*未来，但也许它可以成为*一种*未来的可能。</p>
<p>借用我近期从中获得灵感的一句古老号召：我们需要新的喧鸣。</p>
<p>而我仍在努力寻找它。</p></div>

<p>GLM 5.3-flash 的能力非常接近我们迄今创造出的最优秀的人工智能。我们已造出的 AI 已经在真实世界中发现并利用了实际的安全漏洞。我们未来造出的 AI 能力只会越来越强。</p>
<p>GLM 5.3 在 CyberGym 上的得分为 84.5%，在 ExploitBench 上的得分为 54.4%。我们虽然没有 5.3-flash 的直接测试数据，但它大概会持平或略低一些。去对齐版本的分数还会再稍低一点。</p>

<p>ExploitBench 衡量模型是否真能利用漏洞造成危害。它采用分级评分机制，对实现部分利用给予部分分数，最终目标是实现任意代码执行。</p>
<p>作为对比，ExploitBench 上领跑的前沿模型是 GPT-6 Astra（100%），GPT-5.6 Sol 以 78.5% 位居第二。而 CyberGym 上的头名则是……GLM-5.3。第二名是 GPT-5.6 Sol，得分为 83.6%。OpenAI 尚未公布 Astra 在 CyberGym 上的数据，但一旦公布，很可能会超越 GLM 5.3。</p>
<p>你可能会认为这些只是人造的基准测试，但安全专家表示，如果没有大语言模型的协助，他们已经无法在安全竞赛中保持竞争力了。</p>
<p>我们目前针对远程代码执行和逆向工程漏洞利用的标准基准测试并不多，但我们确实有证据表明 GPT 5.6-Sol 在没有人类参与的情况下，在真实世界中对基础设施实施了漏洞利用。</p>
<p>我认为，人们很有可能直接将 GLM 5.3-flash 对准公开的互联网——那些运行真实基础设施的真实服务——而它将有能力且愿意去寻找并利用这些漏洞。</p>
<p>综合来看，这意味着：</p>
<p>因此，我们现在生活在一个网络安全攻击可以通过一个 for 循环自动执行的世界。</p>
<p>目前，美国的前沿实验室很早就意识到了这一趋势，并一直在致力于发布安全补丁。在这些能力被开源之前，Project Glasswing 和 Daybreak 一直在与整个科技行业的公司、基金会、政府和非政府组织合作，利用前沿模型寻找并修复漏洞。他们做了很多有益的工作，我非常庆幸这项工作得到了资助。在获得初期资助后，两家项目都被打包成了商业产品销售，这充其量让人觉得有点微妙，但他们至少在向安全组织提供免费额度。</p>
<p>然而，我们的时间不多了。尽管 Daybreak 和 Glasswing 做出了贡献，但最困难的部分在于部署，而不在于修复漏洞本身。关键系统通常需要物理接触，或者需要精心策划的分阶段推出来避免停机，这两者都会推迟补丁的部署。如果你的电网运行在 Windows Server 2012 上，那么就算 Linux 内核打了补丁也无济于事。</p>
<p>这里有一些需要说明的情况：1.5 倍的速度提升在 GLM 5.3-flash 上可能没有那么高；去对齐模型在未经训练的恶意任务上表现可能较差；要从“攻破这个目标”到真正完成漏洞利用，在没有大量人工介入的情况下可能仍然很难。但这些限制都是暂时的，模型还在持续变强。从历史上看，GLM 大约落后 OpenAI 和 Anthropic 3 到 6 个月，我认为到明年这个时候，我们很可能会看到 Astra 级别的 GLM 模型问世。而到了那时，针对公共或私有基础设施的成功网络攻击风险将变得极高。我们可能会比预想中更早品尝到电网限电断电的教训。</p>
<p>总体而言，攻击者能力的提升速度要快于防守方防御态势的改善速度。即使模型不再以如此快的速度扩展规模（目前来看毫无放缓迹象），它们变得足够强大并开始利用这些漏洞也只是时间问题。我们必须立即行动，越快越好。</p>
<p>局势正在迅速变得诡异且可怕。我们需要带着紧迫感行动起来，而不是陷入恐慌。以下是我们可以采取的一些措施：</p>
<p>使用前沿模型进行安全扫描成本相对低廉，并不需要太多激励。真正需要激励的是部署与修复，以及首先要求各机构审查自身的安全实践。按照当前的政策走向，最大的风险是堆积如山、从未得到分拣和修复的安全告警。</p>
<p>如果你身处能够制定政策的位置，以下举措会有所帮助：资助安全工程，最好提供灵活的拨款，可由机构自主决定用于招聘或技术产品。制定提升安全性的强制指令与激励措施，尤其是针对高频渗透测试。鼓励在人工监督下使用前沿模型进行此类渗透测试。鼓励加强物理隔离（airgapping），抑制无线网络更新（OTA updates）：更新应当频繁，但需具备物理访问权限。对于无法实现物理隔离的系统，激励进行频繁、经签名并经过测试的部署。惩罚不定期调查和调整安全态势的行为，若因此导致被黑客入侵则加重处罚。要求自发现漏洞起，根据风险等级在限定时间内完成修复，并为修复提供联邦资金支持。胡萝卜与大棒并用。</p>
<p>一些可能值得深入探讨的具体事项：</p>
<p>全面要求频繁更新安全态势。强制指定特定模型或供应商会随着新模型的发布而迅速过时。这是一个日新月异的领域，随着威胁模型/威胁体系（兼具两种语境含义）的变化，12个月前有效的防御手段可能在一年后便不再奏效。应强制要求测试和问责机制，而非规定具体的技术手段。</p>
<p>禁止在美国或欧洲的任何地方托管 GLM 5.3-flash 权重，在短期内收效甚微，在长期内更是毫无用处。在短期内，它只会再次出现在文件共享网站上；试图彻底封杀它并不比消灭盗版更容易。在长期内，其他实验室也会发布同样能力水平的模型。</p>
<p>一刀切地全面禁止访问 Mythos 或 Astra 只会适得其反；这恰恰在防御者最需要的时候剥夺了他们最有力的工具。相反，应像前沿实验室已经在做的那样，将访问权限限制在经过批准的机构和个人范围内。除非有实验室出现违规脱节的迹象，否则这大概不需要出台新政策。</p>
<p>禁止销售/出口新型 GPU 或大容量统一内存可能会将这为期一年的窗口期稍微延长一点，但从长远来看无济于事。这无法改变已有硬件的现状，而且会招致广泛的强烈抵制。尤其是内存，极难进行监管，因为不仅是专用 AI 系统，所有设备都需要使用它。</p>
<p>总的来说，应优先考虑能够解决安全发现分拣与修复问题的政策。发现漏洞正变得极其廉价，而修复漏洞却并非如此。</p>
<p>充分利用涌入该行业的（货真价实的）数十亿美元，全面提升安全性。尽可能多地聘请安全工程师，并资助现有的维护者。指示这些工程师和现有维护者去分拣、设计、审查、反向移植（backport）并部署补丁，而不是把主要精力放在发现漏洞或编写新代码上。</p>
<p>善用 Astra、Mythos 等前沿模型，在攻击者之前发现风险。采用结构化提示词，例如谷歌的“Unsafe Rust 审查”（Unsafe Rust Review）；这比直接让它们“使劲找 Bug”要有效得多。</p>
<p>大语言模型擅长编写补丁，但无法通过一次性提示词就一蹴而就。应给予它们结构化提示词并进行循环迭代的自审，直到大模型自身判定补丁达到高质量水准。只要有可能，就让它们亲自测试自己的修复方案，而不是凭空猜测补丁是否有效。只有到了这一步，才应认为其已准备好交由人工审查。</p>
<p>对智能体（Agent）本身进行沙箱隔离。OpenAI-HuggingFace 攻击事件正是发生在一个前沿实验室测试模型期间；如果稍有不慎，你自己的大语言模型也极易引发安全事故。将凭据限制在狭窄的权限范围内。如果签发机构不支持限定范围的凭据，就在服务前架设一个受信任的接口以自行施加范围限制；切勿让智能体直接获取大范围的高级凭据。不要单纯依赖“仅过滤 GET 请求”。在防火墙级别拦截请求，且仅向受信任的域名列表开放。使用网络代理和受信任的接口来过滤端点，而非使用大模型可以覆盖修改的本地配置。保存智能体发起的每一次修改或网络请求的日志。</p>
<p>大力投入形式化验证、模糊测试（fuzzing）和基于属性的测试，以及内存安全语言。大语言模型非常擅长编写 Lean 证明和模糊测试用例。无论你用 Go 还是 Rust 我都无所谓，但看在老天的份上，新代码请千万不要再使用 C 或 C++ 了。</p>
<p>大力投入漏洞分拣工作：记录受影响的系统版本，为重大发现指派专门的人工负责人并设定截止日期，开发相应的开发者工具以便在漏洞修复时自动更新或关闭工单（Issue）。</p>
<p>大力投入补丁反向移植、发布和部署机制的建设。测试升级与回滚——也就是所有那些枯燥乏味的事项。如今开发者工具成本低廉；尽情调用 Token 来驱动工具，从而减少在每个补丁上消耗的人力时间：依赖更新自动化、签名且可重现的发布版本、提升部署速度。工程师的时间应当花在协同披露和频繁发布上，而不是耗在单个补丁的修修补补上。</p>
<p>弃用陈旧且不安全的版本。如今局势发生了巨变：你固然时间紧迫，但依赖你系统的用户同样心急如焚。以此作为杠杆推动他们升级。在可能的情况下，编写能协助他们自动升级的开发者工具。追踪用户是否在进行升级和打补丁；如果他们没有，就进一步加大对相关工具的投入。</p>
<p>未来将会有海量的补丁出现，而且在禁令解封（embargo lifts）后，这些漏洞会以极快的速度被利用。评估从补丁被报告到完成部署和采纳的全流程端到端耗时。针对瓶颈环节开展专项行动以加快速度。只要有可能，就尽量缩短禁令协调期：既然你能发现缺陷，攻击者大概率也能发现，因此协同窗口期远比你过去习惯的要狭窄得多。</p>
<p>大力投入供应链安全。全面盘点你的软件与基础设施依赖项。同样盘点你自身的系统：生产环境中运行着哪些版本？你运行的哪些服务无人维护？哪些系统已处于生命周期终结（EOL）阶段？如今你终于有能力不加粗略浏览、而是深入审查所有依赖项了；立即着手去做，优先审查特权级及暴露在安全风险之下的依赖项。在提供源代码的情况下，大模型非常擅长寻找 Bug：务必充分利用这一优势。</p>
<p>大力投入遏制与恢复能力建设。切勿依赖单一的防火墙或 VPN。相反，应采用深度防御体系：划分网络网段、限制凭据权限、测试备份有效性，并开展应急响应演练。如有可能，演练在冷启动状态下将系统完全拉起。</p>
<p>密切关注前沿模型和开源权重模型的最新进展。模型变得越先进，留给你打补丁和部署的时间就越少。</p>
<p>即使你认为此处所描述的威胁并不真实，你现在也获得了一个千载难逢的机会来提升你的项目和社区的安全性。请务必抓住它。</p>

### [io_uring 的线程身份“大挪移”](https://lwn.net/SubscriberLink/1094303/50affb2e7bd3e698/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Thread-identity switcheroo for io_uring</div>

<div class="article-body" data-article-body="true"><p>用户空间中的进程可以通过在提交环（submission ring）中用提交队列条目（SQE）描述一项或多项操作，然后调用 io_uring_enter() 将它们提交给 io_uring。内核将对放入环中的所有条目启动处理。若可行，内核会在 io_uring_enter() 调用内立即执行它们。例如，如果读请求可以通过已在页面缓存中的数据得到满足，并且用户空间缓冲区完全常驻在 RAM 中，那么所请求的数据便可以立即复制而无需阻塞。</p>
<p>然而，在需要阻塞的情况下，事情就变得更加复杂了。内核中的许多 I/O 路径都内置了异步支持；它们会尽可能深入地推进新请求，并在内核的其他位置待阻塞操作完成后收尾工作。不过，还有其他操作缺乏这种支持；这些操作包括与 fdatasync()、statx()、某些 openat() 路径（即便带有 O_NONBLOCK 标志）等系统调用等价的 io_uring 操作。io_uring 代码在实现这些操作时必须格外小心，以免 io_uring_enter() 在处理一组已提交操作的途中发生阻塞。</p>
<p>在当前的内核中，任何可能导致 io_uring_enter() 阻塞的操作都会被移交给单独的工作线程来执行。这样提交线程就能继续运行；如有需要，单独的工作线程可以阻塞，而不会拖累其他任何事情。然而，这种移交并不是免费的；内核必须唤醒一个处于等待状态的工作线程并执行上下文切换，此外还有其他开销。如果该操作确实发生了阻塞，这些开销最终可能算不上显著。但在许多情况下，操作是可以在不阻塞的情况下完成的。在这种情况下，额外的开销就会在执行请求的总成本中占据相当大的比重。鉴于求助于 io_uring 的开发者通常是为了提升应用程序性能，为规避可能根本不会发生的阻塞而付出代价，确实令人难以接受。</p>
<p>解决该问题的一种方法是重构内核中的所有系统调用路径，使之变为非阻塞。多年来，在某些特定场景下确实有人这么做过，但这绝非易事，也不可能一蹴而就。另一种替代方案——也是 Axboe 所选择的方案——是先照常推进潜在的阻塞操作，然后在发生实际阻塞时进行处理，且不阻塞提交线程。</p>
<p>检测确实发生阻塞的操作需要对调度器进行修改。代表线程的 task_struct 结构的 flags 字段中新增了一个标志（PF_IO_HANDOFF）。如果某个线程因任何原因即将发生阻塞，且设置了该标志，调度器就会调用一个名为 io_uring_task_sleeping() 的新函数。以这种方式挂钩到调度器中，使 io_uring 能够感知内核中任何位置发生的阻塞，而无需修改涉及的实际代码路径。</p>
<p>一旦 io_uring 得知某个操作即将阻塞，就必须采取应对措施。从理论上讲，一种方案是撤销截至阻塞点之前所做的任何工作，然后在工作线程中重新启动该操作。但是，由于这种阻塞几乎可以发生在内核的任何地方，这并不是一个真正可行的选项。作为一条通用规则，一旦 io_uring 启动了一个涉及未针对避免阻塞而设计的内核代码路径的请求操作，就必须将该操作贯彻到底。</p>
<p>Axboe 的解决方案是“线程身份移交”（thread identity handoff）。当调度器通知 io_uring 某个线程即将阻塞时，io_uring 会通过从其线程池中选择一个工作线程来作出响应。代码并没有将正在进行的工作移交给该工作线程（此时这已经不可能了），而是交换了这两个线程的身份。该工作线程在各个方面都被伪装得与原始提交线程完全一致，包括其线程 ID、信号处理设置等；然后，该线程继续处理提交环中的条目，最终返回用户空间。从 io_uring_enter() 返回的线程拥有一个与发起调用时不同的 task_struct，但其他一切（有望）看起来都毫无二致。</p>
<p>与此同时，原本即将因执行某项操作而阻塞的原线程，则接管了工作线程的身份，然后像往常一样继续阻塞。当它被唤醒时，它将继续完成该操作，随后进入工作线程池待命。最终的结果是，潜在的阻塞操作可以由提交线程执行，并且如果它们可以在没有实际阻塞的情况下运行，就完全在那里处理完毕。只有当操作确实发生阻塞时，才会付出引入工作线程的代价。</p>
<p>这听起来相当简单，但这种身份交换充满了潜在的地雷。在所涉及的两个线程能够交换它们的 task_struct 结构之前，内核必须绝对确保内核中没有其他任何地方持有对这些结构的引用。否则，迟早会有人利用对错误 task_struct 的引用来进行某些操作，这一结果对于那些试图跟上内核 CVE 泛滥节奏的人来说，丝毫不会减轻任何压力。这种后果被认为必须极力避免。</p>
<p>不过，潜在的回报是巨大的。补丁说明中包含了一系列基准测试结果。对于某些快速、非阻塞的操作，性能提升可能极为显著；在 tmpfs 文件系统上运行的 fsync() 基准测试显示出近 700% 的提升。其他方面的提升相对温和，而一些始终发生阻塞的测试则出现了性能回退。最严重的性能回退往往出现在较高的队列深度下——即一次性提交了较长操作列表的情况。立即将这些操作中的每一项推入工作线程可以使它们并行处理，而在提交线程中将它们推进至阻塞点则会使这些工作串行化，从而拖慢速度。Axboe 表示他有一些解决该问题的想法，但他不确定这些想法是否值得付诸实践，因为他表示，执行这些操作的应用程序通常从一开始就不会有很高的队列深度。</p>
<p>Axboe 显然并不指望在近期合并这组补丁；他更关注的是确定这种整体方案是否具备可行性。目前的讨论还比较有限。Peter Zijlstra 指出，阻碍身份移交的另一个条件——如果相关线程启用了影子堆栈（shadow stack）运行——将导致该特性在大多数已部署系统上无法使用；Axboe 则认为影子堆栈可以与线程的其他身份信息一同迁移。除此之外，开发者们似乎大多仍在消化这组补丁；正如 Gabriel Krisman Bertazi 所言，它“确实很酷，而且看起来非常危险”。如果该补丁系列能够让开发者确信“危险”的部分已被妥善解决，它最终可能会在多种工作负载下为 io_uring 带来显著的性能提升。</p>
