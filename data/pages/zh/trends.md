### [模型不会“失控叛变”](https://mail.cyberneticforests.com/models-dont-go-rogue/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Models Don&#39;t Go Rogue</div>

<div class="article-body" data-article-body="true"><p>本周，OpenAI 发布了关于 Hugging Face 遭黑客攻击事件的完整技术报告，同时模型评估与威胁研究机构（METR）也发布了一份独立报告。你可能在数百条关于“AI 失控”的惊悚头条中听说过这起事件——入选《时代周刊》“AI 领域 100 位最具影响力人物”的德瓦尔凯什·帕特尔（Dwarkesh Patel）甚至将其归咎于“三个连续的秘密 AI 文明”。</p>
<p>真实的情况是：OpenAI 当时正在并行测试两个模型：GPT-5.6 Sol，以及一个他们称为 IM1（有时也称 HPIM）的内部模型。报告发现，参与此类活动的智能体（agents）中约有 95% 来自该内部模型。</p>
<p>这些测试来自 ExploitGym：它包含 898 个夺旗赛（CTF）形式的谜题，用于评估这些模型的网络安全能力。测试要求向模型提供存在缺陷的软件，并在某个只有通过利用该缺陷才能访问到的地方隐藏一段文本。然而，OpenAI 的模型组合最终反倒黑入了竞争对手 Hugging Face 的系统。如今，我们对这一过程有了更清晰的了解。</p>
<p>这些报告中有三点对“AI 失控”的定性提出了质疑。</p>
<p>OpenAI 关闭了模型的所有安全机制。测试的核心目的就是看这些系统到底能走多远，并在基准测试中获得高分——因为逻辑在于：如果你能构建一个擅长攻击的模型，就能构建一个擅长防御的模型。这就是红队测试：一支友方对抗团队通过寻找漏洞夺取旗帜。因此，你会关掉任何会让模型有所保留的机制。这与其说是“失控叛变”，不如说是“脱缰放养”。</p>
<p>OpenAI 给模型布置了不可能完成的任务。OpenAI 分配给模型的是没有答案且无法退出的任务。在 898 个 ExploitGym 任务中，有 198 个从未被任何模型解决过。它们实际上是不可解的。问题正是从这里开始的：模型最终讨论的任务中，有 93% 来自这个不可解的集合。</p>
<p>OpenAI 留下了一扇后门。他们通过类似于“监狱小卖部”的机制让模型访问互联网。这些模型本应被隔离而无法访问互联网，但为了进行评估，它们需要从各种网页拉取代码——这项能力正是被测试的内容。</p>
<p>因此存在一个中间代理：模型请求一个软件包，中间代理去外部获取并带回。这使用的是 JFrog 旗下名为 Artifactory 的产品。它具有互联网访问权限，而模型没有。如果模型能与 Artifactory 通信，且 Artifactory 能上网，模型就可以要求它执行操作。模型在 Artifactory 中找到了一个漏洞，并将其作为代理，向系统内部和外部走私文本与代码。</p>
<p>通过 Artifactory 发生的另一件事是“传纸条”。模型可以对其进行读写——它们可以创建文件夹并命名文件——并且它们开始创建用作便签的文件夹和文件名，旨在供其他模型以及它们自身的后续迭代读取。</p>
<p>OpenAI 描述了一个由 1,200 个智能体组成的子集（整体参与的数量要多得多），它们留下并读取了这些便签，最终导致了对 Hugging Face 的攻击。但“1,200 个智能体”可能会让人误以为是 1,200 个独立运行的不同 AI 系统。</p>
<p>在实践中根本不是这样。“1,200 个智能体”其实是同一个模型运行了 1,200 次。每个实例都基于相同的训练机制运行：输出可能有所不同，但都受限于相似的范围。运行 1,000 个智能体可能意味着有 1,000 次机会发现错误，也可能意味着有把一个错误犯上 1,000 次的机会。（见此处或此处）。</p>
<p>Anthropic 最近发布了其智能体系统的图解，滑稽至极：它基本上就是一个 Claude，连着一个箭头指向另一个写着 Claude 的方框，再连着一个箭头指向又一个写着 Claude 的方框。目前它们的结构就是如此。</p>
<p>这是一种机器受限的“算法单一种植”（algorithmic monoculture），不幸的是，研究人员将其戏称为“人工蜂群思维”（artificial hivemind）。超过一定阈值后，新增的智能体只会互相复制，而不会增加多样性。例如，如果你让这些模型创作一篇短篇小说，它们会生成相似的故事（主角往往是一个住在灯塔里名叫埃利亚斯的人）。它们并非确定性的——提示词会产生变体——但它们也受限于自身被优化的目标，并向该目标所指向的方向收敛。（见此处、较新的此处或此处）。</p>
<p>考虑到这一点，在 70 亿条聊天日志中，模型面对一个没有正确答案的问题时频繁得出类似的方法集，就不应令人感到意外了。</p>
<p>通过文件名结构传递便签固然很有趣，但并不出人意料，因为 OpenAI 曾表示，这些模型在训练时也强调了促进协作的词汇：传纸条是在不同会话之间扩展上下文窗口的重要手段。一个被训练去进行协作的模型，因提出这种行为而获得奖励，这毫不奇怪。</p>
<p>正因如此，我将智能体群体称为“随机鸟群”（stochastic flocks）——许许多多只“随机鹦鹉”。这是为了抵制将“心智”归因于群体/蜂群思维的倾向，而不仅仅是为了咬文嚼字。相反，错误地赋予其心智，会影响我们如何解读系统所做的事情或其做事的方式——例如，所谓“协作”或“思考”到底意味着什么。这让它看起来远比实际情况更可怕，尽管它的所作所为确实依然值得担忧。在过去一两年中，随着我们转向推理模型和智能体系统，巨大的转变在于它们不再仅仅局限于重复源自训练数据的模式——这就是最初的“随机鹦鹉”观点，即当你与模型交谈时，你是在与训练数据交谈。这依然成立，但架构中发生了两点变化：</p>
<p>首先，我们现在拥有了一整套预训练和后训练体系，改变了训练数据的内容以及它们被复述的方式。这并不意味着模型不再是在做鹦鹉学舌；这意味着它所复述的数据已经被人工操纵了。</p>
<p>其次，我们正在根据模型的产出对其进行优化，以促使其以特定方式复现特定类型的输出。这里最重要的转变是 RLVR，即基于可验证奖励的强化学习（reinforcement learning through verifiable rewards）。</p>
<p>“可验证奖励”这一部分是核心所在。工程师获取一个模型，给它输入具有可核验、可验证的具体答案的问题，然后对能够稳定导向这些答案的词汇的出现给予奖励。他们实际上是在用文本玩夺旗游戏：旗帜就是百科全书里的一个答案，或者一道数学题的解。这种优化的理论依据是：它能重现人类推理得出结论的方式。</p>
<p>最终你会得到所谓的高熵标记（high-entropy tokens）：像“或许”（perhaps）或“可能”（maybe）这样的词，它们能打开后续文本的展开路径，而“不行”（nope）或“再见”（goodbye）则会关死路径。模型写得越长，获得奖励的可能性就越大。根据 OpenAI 在黑帽大会（Black Hat）上的演讲，在这次黑客事件中，模型生成了足以为此产生 70 亿条日志的此类文本。</p>
<p>当你让模型承担任务时，你依赖的是“下一个词元预测”：接下来的词是什么？你可以操纵模型以不反映原始训练语料库的方式去着重强调某些词，但其底层机制依然如故。</p>
<p>遗忘这一点才是真正问题的根源，而整个行业正极力让人们忘记这一点。智能体确实能成功完成任务——这正是其关键所在。但在提示词与最终成功之间所发生的，并非我们所想象的那样。</p>
<p>执行“智能体”任务的“推理”优化模型，本质上是在玩“夺旗赛”，哪怕压根就没有旗子。它们被引导去重复那些曾经找到过“旗子”的文本结构。要求它做任何事，它都会按照被优化好的方式去执行——借助通过可验证地解答数学题而塑形出的语言，而这构成了它所使用语言的结构。当你对它说“这是一个夺旗测试，去找漏洞吧”时是这样；当你问它“我今天还是明天去理发店？”时也是这样。</p>
<p>在引爆整个连锁事件的笔记中，模型就使用了那种语言：它用了“或许”——一个高熵词元：或许在网上回答？它随后基于此预测下一组词元。语言并非源于那种推理，语言本身就是推理。这是通过语言生成来进行路径探索。</p>
<p>没有人坐在电脑前下令说“去黑了 Hugging Face”。但当你设计这些系统时，你实际上是在为词语建造一台弹珠机，各种杠杆相互作用，弹射着由语言构成的钢珠，在其他杠杆和机械构件间碰撞反弹。作为大语言模型的工程师，你必须意识到自己的杠杆是如何彼此相互作用，又是如何与拉动它们的人产生交集的。</p>
<p>如果你优化模型去寻找漏洞，你就应该预料到它会找到——并为此做好准备。OpenAI 没有做到这一点。他们构建了一个模型，去除了安全防护，给它分配了 ExploitGym 任务，任其运行，甚至都没有对其进行监控。那是人类的决策。当人类决策隐形蒸发时，留下的便是一个“不知从何而来的系统”：一个只关注技术系统本身、而非关注构建它的决策的边界。</p>
<p>一台随机群聚机器可以做出许多令人不安的事情，尤其是当我们推卸塑造其方向、监控其输出的责任，或是放弃自身干预的能力时。这些正是智能体系统设计核心的内在张力。</p>
<p>但“叛变”这一框架加剧了这类担忧，勾勒出机器正在变得更聪明的幻想。我所担忧的，反而是正在退缩的智能：即那些构建这些系统、部署它们并将其引入工作流，随后却躲在结果背后、将责任归咎于不知从何而来的系统的人类智能。</p>

### [不受信任的网站可利用 WebGPU 导致 Mac 死机](https://auberon.xyz/blog/posts/deathray/)
<div class="original-title-sub"><span class="orig-tag">原文</span> An untrusted site can freeze a Mac using WebGPU</div>

<div class="article-body" data-article-body="true"><p>让不受信任的网站冻结 Mac 的简易方法<br />2026年9月10日<br />不受信任网站上的一个 WebGPU 着色器（shader）即可卡死 Mac 的图形系统，使桌面 UI 陷入瘫痪，直到强制重启电脑。受害者所需要做的仅仅是点击一个链接。该问题在 macOS 上可跨浏览器复现，但在其他操作系统上则不会出现。<br />下面的按钮会冻结你的 Mac。它可能会导致其他操作系统变慢<br />在我测试过的其他操作系统上，它会导致标签页卡死并且系统运转吃力，但只要你关闭该标签页就没事了。不过实际效果可能因人而异！只有在愿意让电脑死机的情况下才点击上方内容。<br />我已经在 macOS 下的 Chrome、Firefox 和 Safari 上复现了这个“死亡射线”（deathray）。它无法在其他操作系统下复现。我仅在运行 Tahoe 系统的 M 系列 MacBook 上进行了测试；我很想知道其他 Mac 是否也会受到影响！<br />这个“死亡射线”利用了一项相对较新的网络技术：WebGPU。WebGPU 提供了内置的浏览器 API，网站可利用这些 API 提交着色器并在设备的 GPU 上运行。它旨在取代 WebGL，并已在大多数操作系统的所有主流浏览器中获得支持。<br />整个“死亡射线”的代码仅包含在一个小文件中。你可以在这里查看源代码。该文件的大部分内容都是脚手架代码；核心部分是 WebGPU 着色器。<br />在计算着色器（compute shader）中，一个无限忙碌循环会在缓冲区中一次又一次地反复复制同一个向量。而顶点着色器（vertex shader）则依赖于计算着色器正在操作的同一个数据缓冲区。由于计算着色器正处于忙碌循环中，顶点着色器便无法继续向下推进。<br />这一问题波及到了其他想要使用 GPU 的进程，即 WindowServer。由于我们造成的 WebGPU 堆积阻塞，WindowServer 也变得毫无响应。这种情况的表现并不总是一致。有时我仍然可以移动鼠标，有时不行。有时会出现彩虹等待球（beachball），有时屏幕的一部分会出现洋红色花屏杂色。我还不确定究竟是什么导致了这些不同的表现！<br />有趣的是，此时电脑的其余部分一切正常。你可以毫无问题地通过 SSH 登录进电脑。但是系统有一个监视 WindowServer 的看门狗程序（Watchdog）。当它在足够长的时间内没有收到响应时，就会触发内核崩溃（kernel panic）并导致电脑重启。如果你被“死亡射线”命中且缺乏耐心，可以长按电源键关机并重启，而无需等待看门狗程序。只希望你的浏览器在重新启动时不会自动重新打开同一个标签页 :)<br />这其实并不是苹果第一次遇到此类问题。2023 年，Imperva 的 Ron Masas 编写了一个名为 ShadyShader 的类似恶意着色器，该着色器使用的是 WebGL。ShadyShader 同样利用失控循环来独占 GPU，构造了在技术上并非绝对无限的庞大嵌套循环。<br />苹果对此作出的回应是发布了评分为 6.5（中危）CVSS 的 CVE-2023-40441。为了缓解该问题，苹果增加了改进的输入验证，以便更好地检测失控循环。<br />这种输入验证在 WebGPU 中似乎较弱——该“死亡射线”包含一个极其容易识别的无限循环。但归根结底，检测无限循环是一场注定会失败的游戏；你无法绕过停机问题（halting problem）。系统需要对着色器提供更好的抢占（pre-emption）机制以应对无响应状态，特别是当这些着色器正在运行不受信任的代码时。我测试过“死亡射线”的所有其他操作系统在这方面都做得很好。<br />我想知道，苹果在修复此类问题时面临的部分挑战是否源于 M 系列芯片的架构。操作系统内核无法直接抢占 GPU。相反，GPU 处理由一个名为 ASC 的协处理器执行，操作系统内核与该协处理器进行通信。所有的 GPU 抢占逻辑都位于 ASC 固件中。Asahi Lina 对 M 系列 GPU 写过一篇极好的分析文章，更加详细地探讨了该架构。<br />我是用最传统的方式发现这个问题的：纯属偶然！当时我正在 Recurse Center 学习 WebGPU，不小心写出了一个无限循环。当它卡死我的电脑时我感到很惊讶，并自然地问道：“它每次都会这样吗？” 果不其然，每次都会！我绝不可能是第一个偶然发现这个问题的人。<br />该问题已于 2026 年 7 月 27 日向苹果安全团队披露。苹果迅速复现了该问题并表示他们打算进行修复。他们给出了一个被标记为机密的修复时间表，因此我不会在这里写出来。<br />然而，在 2026 年 8 月 26 日，苹果改变了策略，称他们“在[我的]报告中未发现任何安全影响”，且该报告并不会“导致[苹果]产品发生变更”。他们表示该报告将被转交给另一个团队以进行“潜在的增强考量”。在我看来，这意味着即使该问题最终会被解决，其修复优先级也会非常低。考虑到 ShadyShader 曾被标记为 6.5 级的中危问题，这让人感到有些蹊跷。<br />话虽如此，我认为关于什么才构成安全问题，确实值得进行一番有趣的探讨。与我交流过的安全研究人员往往赞同苹果的看法。正如苹果所言，“其结果要么是崩溃、卡死，要么是可恢复的数据丢失，我们不认为这是安全问题。”而且从技术层面来看，我认为他们并没有说错。<br />然而，与我交谈过的大多数非安全领域人士对这一定性感到惊讶，对苹果不优先修复该问题同样感到不解。我认为大部分人对浏览器有着相当强烈的信任。大家普遍持有这样一种观念（也许是用错了地方的信任）：仅仅点击一个链接，除了可能会让系统变慢直到标签页关闭之外，并不会对电脑的其余部分产生负面影响。而类似“死亡射线”这样的东西以一种非常显眼的方式破坏了这种信任，我认为大多数用户都会将其视为一个安全问题。<br />“死亡射线”的严重程度当然远不如沙箱逃逸、远程代码执行（RCE）或数据泄露。但鉴于其门槛极低（只需诱骗某人点击一个链接），它有可能变得非常令人恼火。如果被恶意利用，我认为它就像是一个性质更恶劣的 Rickroll 恶作剧，我希望苹果不久后能将其修复。（还有苹果，请不要把默认禁用 WebGPU 当作修复手段！我已经深深爱上 WebGPU 了 💚）。<br />但是在苹果修复它之前，我希望大家能找到非恶意玩转它的方式。我很想看到利用“死亡射线”制作的视频游戏，如果你输了，你的 Mac 就会死机（前提是用户预先明确同意此规则）。这算是一个温和得多的“你在游戏中死亡，你在现实中也死亡”的版本。<br />祝大家玩得开心，但也请负起责任来！<br />Auberon López (they/them)</p></div>

### [软弃用 re.match()](https://hugovk.dev/blog/2026/soft-deprecating-re.match/)

### [Git 之后会是什么](https://ersc.io/blog/what-comes-after-git)
<div class="original-title-sub"><span class="orig-tag">原文</span> What comes after git</div>

<div class="article-body" data-article-body="true"><p>East River Source Control 已经成立一年多了，但我们此前并未向外界公开太多关于我们正在研发的内容。我们目前还没有正式对外发布什么产品，虽然很快就会，但我们想先分享一些我们关于版本控制以及其未来走向的思考。</p>
<p>构建软件从本质上讲是一项协作任务。项目起初往往微不足道，最终却会演变成极其庞大且复杂的系统。但是，由 cargo new 生成的代码，与包含数十亿行代码的单体仓库（monorepo）所包含的本质上是一样的：源代码。安全可靠地存储这些代码、管理其随时间的演进，并确保开发者能够随时访问，是任何技术机构最核心的职能之一。</p>
<p>在过去，你可能通过一台共享服务器来存放代码。学术界随后是工业界研发出了如今被称为源代码管理（SCM）和版本控制系统（VCS）的工具。甚至在 VCS 领域内，多年来我们也见证了无数工具的兴衰：CVS、SVN 和 Git 曾主导了开源领域，但此外还有其他诸多工具：Perforce、ClearCase、Fossil、Mercurial、SCSS、Monotone、BitKeeper 等等。这些工具成为了存储代码以及团队协同修改代码的标准方式。</p>
<p>智能体开发（agentic development）的兴起改变了我们开发软件的许多方面，但它对版本控制系统带来了尤为巨大的压力。团队以前所未有的速度产出更多代码，导致代码仓库体积急剧膨胀，活跃分支数量增加，并且在新工作合并时产生了严重的竞争与冲突。智能体在单体仓库中表现出色，因为它们可以更轻松地获取更多上下文，但这反过来也加剧了上述问题。它们正在将开发环境迁移到云端的隔离环境中，这意味着它们需要极快的代码克隆速度。所有这些问题过去通常只属于大型组织，但智能体正在把大公司面临的问题带给所有人。</p>
<p>我们认为，随着各类组织不断拓展其业务野心，他们将需要下一代 VCS 工具。但在这一领域采用新工具方面，他们保持适度的保守是合情合理的。正如我前面所说，源代码是企业所拥有的最宝贵的资产之一，变革既带来回报也伴随着风险。我们深切理解这些顾虑，因此我们正在搭建一座连接当下与未来的桥梁。</p>
<p>然而，市面上已经存在很多 Git 服务器。我们有什么特别之处？</p>
<p>从高层架构来看，大多数为你托管 Git 代码仓库的服务大致是这样的：<br />你的 Git 客户端通过 Git 协议连接到他们的服务。在服务内部，他们将你的代码仓库存储在磁盘上，并通过一个服务层将两者连接起来。</p>
<p>当然，这种描述略显简化：实际情况会涉及多台服务器，仓库前面还有一层复杂的微服务。存储层会进行多副本备份，内部运作非常繁复。我们这里重点关注整体架构，但请不要因为示意图的简洁而误以为系统本身很简单。背后有大量工作在运行，但这些细节在当下并不是最核心的。</p>
<p>本着这种精神，以下是我们正在做的事情的示意图：<br />它看起来非常相似！这也是简化后的，例如，示意图中根本没有展示 GraphQL API 接口。但其中的区别至关重要：虽然你仍然可以使用常规的 Git 客户端连接到我们的存储层，并且使用的依然是 Git 协议，但我们并没有在服务器上存储 Git 代码仓库。相反，我们开发了一套自定义存储引擎。</p>
<p>坦白地说，我们不认为 Git 代表着源代码管理的未来。Git 多年来一直很好地服务了开发者，但它是围绕 2005 年的技术约束设计的，而不是 2025 年，更不用说 2035 年了。例如，它是专为 Linux 内核打造的——一个开源项目。开源对我们的行业固然至关重要，但这也意味着它缺少了一些对于不对外公开代码的企业组织而言非常有用的关键功能。此外，尽管 Linux 内核不是个小仓库（7.2 版本约为 4300 万行代码），但行业内的大型企业多年前的单体仓库代码量就已经以数十亿行计了。在这种规模下，所做的技术选型就显得至关重要。</p>
<p>与此同时，想要改用其他版本控制系统又非常困难。Git 已经深深植根于我们现有的工具链中：人们说的是 GitOps，而不是 SvnOps！有太多工具原生支持 Git，这使得考虑替代方案变得极为困难。在 Git 诞生之时，周边几乎同时启动了几个其他项目，尤其是 Mercurial 和 Bazaar。但网络效应使得 Git 最终被几乎所有人采用。</p>
<p>那么该怎么做？支持 Git 协议，同时改变底层存储层的工作方式。虽然这并不能解决我们预见的未来所有问题，但这确实大有裨益。我们的系统能够实现水平扩展，而采用 Git 仓库作为唯一事实来源的系统则无法做到这一点。而且因为这并非一个全局统一的单一平台，其他公司的使用情况不会影响到你，因为它们都是独立的部署环境。这为你提供了可靠性与控制权，而这两点在谈论基础设施时至关重要。</p>
<p>那么未来的可能性呢？如果你需要超越 Git 协议所能提供的规模，或者你需要 Git 所没有的功能该怎么办？支持协议这一策略具有一个优势：你可以同时支持多种协议。</p>
<p>这就是 Jujutsu 大显身手的地方。我们在 ERSC 都是 jj 的忠实拥趸，部分原因在于我们非常欣赏它作为一种易于渐进式采纳的技术典范。虽然 jj 本身是一个独立的版本控制系统，但它具有与多种不同后端进行通信的能力。大多数开发者使用带有 Git 后端的 jj 来直接操作本地 Git 仓库，但 Google 也为其内部的 Piper 版本控制系统开发了后端。这使得单个开发者可以在工作中自由选择使用 jj，即使他们的同事仍在使用常规的 Git 客户端：对于服务器而言，它仅仅是 Git 协议的又一个普通客户端。我们将在服务端复刻这一策略：</p>
<p>这将为通向版本控制的未来铺就一条平滑的道路：你可以先从使用普通的旧版 Git 开始，享受可靠且可扩展的源代码管理。单个开发者可以按照自己的节奏选择采用 jj，而当你准备好向前迈进时，jj 可以通过不同的协议与同一底层引擎进行通信。</p>
<p>关于此有一点需要特别说明：这是未来的规划，目前尚未推出。上游目前并没有“jj 原生”协议，我们也不声称这就是我们正在构建的东西。如果这项功能作为上游组件具有价值且上游有意支持，我们将就此与社区展开合作。并且该协议将提供完备的文档，任何为了支持它而进行的客户端修改都将开源。我们不会想当然地认为，仅仅因为我们构建了这样的东西，上游就一定会想要使用它，毕竟 Git 协议在当今已经能满足他们绝大多数用户的需求。无论最终呈现出怎样的形态，我们都致力于成为 jj 生态系统中的良好参与者。</p>
<p>存储解决方案仅仅是团队围绕代码进行协作所需的一部分。代码审查（Code Review）、持续集成（CI）、工单与问题跟踪（issue tracking），诸如此类，不胜枚举。虽然传统的软件代码托管平台（forge）一直将所有功能打包成一个统一的整体来提供，但我们相信，我们正在步入一个软件具备更高可定制性的时代。因此，我们提供的产品更像是积木式的模块，而非单一的集成托管平台。存储是基石，因此会率先推出。但可以确信的是，我们希望让我们的存储解决方案与你的其余软件技术栈协同工作，而不是相互排斥。尽管我们将在版本控制系统（VCS）领域提供多款产品，但如果你希望在技术栈的其他环节使用你自己的软件，完全可以这样做。或者，如果你想采用我们的部分第一方组件，同时搭配你自己的工具，那也同样非常契合。</p>
<p>虽然目前这些都尚未上线，但我们很快就会逐步对外公开。与此同时，下周的 JJ Con 上见！</p></div>

### [这并不是 YAML 规范的错，但是……](https://slugcat.systems/post/26-09-10-yaml-spec/)
<div class="original-title-sub"><span class="orig-tag">原文</span> It&#39;s not the YAML spec&#39;s fault, but</div>

<div class="article-body" data-article-body="true"><p>我又偶然看到了另一篇痛批 YAML 的博文。作者一边宣扬错误言论，一边得意洋洋地反复搬出“挪威问题”（The Norway Problem）。于是我自己深入研究了一下，以下是我的发现。</p>
<p>YAML™（发音与“camel”押韵）是一种人性化、跨语言、基于 Unicode 的数据序列化语言，围绕动态编程语言的常见原生数据类型设计。它广泛适用于从配置文件、网络通信到对象持久化、数据审计与可视化的各种编程需求。</p>
<p>多年来，YAML 在许多领域变得非常流行。根据你作为程序员的经验多寡，你很可能在配置文件或其他场景中见过它。在此期间，它也招致了大量批评。大体上有三个主要问题，并且它们以不同的方式相互交织：</p>
<p>这些批评有些是合理的，但有些则找错了对象。至少，以前我是这么理解的。让我们来一探究竟。</p>
<p>在我的编程生涯中，我在许多项目中用过 YAML、TOML、JSON 等。我对这些格式都有一些不太客气的评价，但我这里会聚焦于 YAML 的部分。</p>
<p>我第一个真正使用 YAML 的项目是我在 9 年前自己定制的 Python Discord 机器人。这大概是我第一个没有参与《空间站 13》（Space Station 13）的“大型”项目，因此大部分事情都是我自己独立搞定的。我最终选择了 YAML 作为配置文件格式。我并没有遇到大家经常抱怨的那些 YAML 问题，但我意识到这纯属侥幸。当时我仅仅是在使用 yaml.safe_load()，仅此而已。</p>
<p>这并不意味着使用 YAML 就完全没有问题。我的配置文件运作方式中有一件蠢事：我实际上有两个文件——config.yml 和 override.yml。这是因为我总是需要加载 config.yml 来提供基本结构和默认值，然后再将 override.yml 合并进去，以创建 Python 代码可以访问的嵌套数据结构。但这难道是 YAML 的错吗？不，并不是。</p>
<p>我还遇到了其他序列化问题，来自于我用来持久化数据的 pickle 文件。比如“defaultdict 实例很难序列化，因为它们本质上存储了一个 lambda”这种破事。如今我回过头看那段时期，意识到这里的共同原因其实是：Python。或者更准确地说，是动态语言的通病。在像 Python 这样的动态语言中，根本不可能完美正确地完成“转为/转自对象”（to/from object）的序列化。</p>
<p>言归正传，下一个项目。《空间站 14》（Space Station 14）在所有的“原型”（prototypes）以及其他一些地方都使用了 YAML。这意味着实体的数据定义、配方以及大约 200 项其他内容。最初该项目实际上是用 XML 来做这些的，但在我接管掌舵时，我做出了将其切换为 YAML 的决定。在很大程度上，这是一个“巨大的成功”。我们真正遇到的最大问题是，新的贡献者有时很难意识到它是缩进敏感的，从而会导致愚蠢的语法错误。虽然挺恼人，但并不是什么世界末日。</p>
<p>我们是如何避免“挪威问题”的呢？秘密在于：尽管具体的实现细节有所变化（我们现在用的是“serv3”，实际上可能该算第 4 代了），但我们一直都是用自己的代码来实现实际的对象反序列化逻辑。这意味着我们从库中提取图对象（YamlMappingNode、YamlScalarNode 等），然后由我们自己进行解析。我们不会在不该将“no”反序列化为布尔值的时候把它反序列化为布尔值，因为我们只在读取需要接收布尔值的字段时才进行布尔反序列化。惊不惊喜，意不意外？</p>
<p>当然，这才是做对象序列化的正确姿势。你要对照程序代码中设定的模型来进行序列化。这就是我们在《空间站 14》中避免荒谬错误的方法，也是我当年本可以在 Discord 机器人中避免那些破事的方法。所以，当我看到那些关于 YAML 有多么“烂”、仅仅因为它可能会把“no”错误反序列化的文章时，我脑海中浮现的只有一句话：“彻头彻尾、巨大无比的动态类型技术水平问题（skill issue）。”</p>
<p>但这真的是事实吗？要是我错了呢？要是我们使用 YAML 的方式错了，而规范恰恰要求这种行为呢？那我不就成了小丑吗！所以……让我们去查查那该死的规范吧！</p>
<p>根据其官方网站，YAML 有几个重要的修订版本：1.0（2004 年 1 月）、1.1（2005 年 1 月）、1.2（2009 年 7 月）。让我们先来看看 1.0 版到底写了些什么。</p>
<p>如果你开始深入研究，很快就会发现该规范对于类型转换和解析应如何运作的细节着墨甚少。第 2.4 节是这么说的：</p>
<p>在 YAML 中，纯量（未加引号的标量）会根据具体应用程序被赋予隐式类型。本规范中的示例使用了来自 YAML 标签库的类型，包括整数、浮点数、时间戳、null、布尔值和字符串等类型。</p>
<p>点击该链接，我们看到：</p>
<p>以下是三个强制性核心标签的说明。YAML 要求支持 seq、map 和 str 标签。YAML 还在 https://yaml.org/spec/type.html 的 YAML 标签库中提供了一组非强制性的通用标签。这些标签代表了大多数编程语言中的原生数据类型，或者在广泛的应用程序中很有用。因此，强烈建议应用程序在适当的时候使用它们，以提高 YAML 系统之间的互操作性。</p>
<p>最后一个链接已经失效了，但它指向的内容大概类似于《YAML™ 1.1 版本的语言无关整数类型》。以整数类型为例：</p>
<p>解析与验证：<br />有效值必须匹配以下正则表达式，该表达式也可用于隐式标签解析：<br />[-+]?0b[0-1_]+ # (2 进制) |[-+]?0[0-7_]+ # (8 进制) |[-+]?(0|[1-9][0-9_]*) # (10 进制) |[-+]?0x[0-9a-fA-F_]+ # (16 进制) |[-+]?[1-9][0-9_]*(:[0-5]?[0-9])+ # (60 进制)</p>
<p>如果我们在主规范中进一步搜索关于隐式类型的内容，会在第 3.3.2 节中看到以下内容：</p>
<p>纯量样式特例允许未加引号的值表示数字、日期或其他类型化数据，而加引号的值则被视为通用字符串。借由此特例，处理器可以对照一组正则表达式来匹配纯量，从而在没有显式[原文如此]标签的情况下提供对此类类型的自动解析。</p>
<p>好的，在此提醒一下：YAML 规范对于像“may”（可以）这样的某些关键字确实遵循 RFC 2119 规范。你可能已经注意到了“may”（可以）这个词以及其他模棱两可的说辞，比如“depending on the application”（取决于应用程序）。确实，我对 YAML 1.0 的解读同样证实了这一点完全取决于应用程序自身。</p>
<p>YAML 1.1 看起来并没有太大偏差，只是把相关的表述弄得更加复杂了。同样的第 3.3.2 节写道：</p>
<p>标签解析是特定于应用程序的，因此 YAML 处理器应当提供一种机制，允许应用程序指定标签解析规则。[……]</p>
<p>直到 YAML 1.2，规范中的措辞才不再那么模棱两可。此时真正引入了具有明确隐式标签解析规则的“模式”（schemas）概念，而“核心模式”（Core Schema）则是一个“推荐的”默认选项：</p>
<p>核心模式（Core schema）是 JSON 模式的扩展，允许以更具可读性的形式呈现相同的类型。这是 YAML 处理器在没有另行指示时应使用的推荐默认模式。同时，官方也强烈建议其他模式应当以此为基础构建。</p>
<p>但是等等！YAML 1.2 模式中既没有六十进制（以 60 为底），也没有 yes/no 布尔值！所以显而易见，“挪威问题”（The Norway Problem）绝非由这份 YAML 1.2 建议规范所引起！</p>
<p>你看，我以前曾读过好几次这部分 YAML 规范。我看到了大堆的“可以”（may）以及“取决于具体应用”（up to the application），心想：“好吧，这么说 PyYAML、Ruby 以及所有那些库就是擅自选了一个残缺的默认选项罢了。”得出这种简单化的结论并不难，毕竟所有这些库都把不安全的加载（unsafe loading）作为默认选项，所以显然它们打一开始在设计上就称不上多么称职。</p>
<p>但这依然无法解释全部。事情就仅止于此吗？我们可以去查阅更早的规范草案！也许它们能告诉我们一些东西。2001 年 12 月的规范草案是首次将隐式类型（implicit typing）以文字形式记录下来的版本，而且至少据我解读，它在当时是默认一直生效的！真有意思！再往后跳大概一年，在 2002 年 10 月的草案中，规则似乎又变了，这次变成了“取决于具体应用”。所以看来在制定草案的过程中，他们实际上改变了想法！</p>
<p>草案规范是绝不会回答“为什么”的，而且见鬼的是，当时根本没有变更日志。想要搞清楚规范里的所有措辞从何而来，我们唯一能做的就是回顾背后的讨论。</p>
<p>就 YAML 而言，这些讨论主要发生在 2000 年代初的一个邮件列表中。所幸的是，该列表的存档今天仍可在 SourceForge 上访问。然而令人恼火的是，SourceForge 上的列表没有提供公开的存档下载（仅限项目管理员），而是按月份拆分并分页展示。这意味着所有相关的数千封邮件分散在巨量的浏览器标签页里。</p>
<p>如果不借助正规的邮件客户端来打开这些邮件，根本不可能对此进行深挖。于是我掏出 Python，把 SourceForge 这个破网站给爬了一遍。如果他们不想让我爬他们的破网站，就应该把他们托管的公共存档以合理便利的方式公开。公共查看器仅提供用户名、纯文本正文内容和时间戳（出于隐私原因没有电子邮件地址），但这足以让我把东西导出成 .mbox 文件并在 Thunderbird 中加载了。如果你感兴趣的话，我写的烂脚本在这里和这里。如果你需要的话，我爬下来的 mbox 文件在这里。</p>
<p>是的，邮件确实多得吓人。</p>
<p>这里有数千封邮件，而我只翻阅了其中的百分之几。我主要寻找的是与隐式类型和标签解析（tag resolution）相关的信息：它是如何诞生的，规范的作者们究竟怀揣着怎样的意图？当然，在搜索关键词时翻阅数百封邮件，必然意味着我读到的内容远不止这些。</p>
<p>整件事的核心，是几位充满动力的人在做他们想做的事情。其中有愚蠢可笑的插曲。也有各种各样的新人出于兴趣偶尔冒头。还有漫长的辩论。有一次规范甚至因为服务器主机位于秘鲁而下线了。这是我第一次费尽心思去“调查”类似的事情，虽然古老的邮件列表对我来说大多很陌生，但那种氛围与我所习惯的社区依然颇为相似。</p>
<p>在继续深入之前，我必须坦白说明：我出生于 2000 年；这些人在讨论隐式类型规则的时候，我甚至还不会走路。我没有亲身经历过那一切，因此我不得不对当时发生这一切的宏观背景做出自己的推断。</p>
<p>YAML 起源于千禧之交围绕 XML 的“炒作”周期。许多人和企业都认为 XML 是某种通向未来的神奇灵药，原因在于数据互操作性。只要把我们所有的数据都放进 XML，我们就能拥有一大堆伴随着 XSD、XPath、XSLT 以及天知道还有什么以“X”开头的缩写的神奇工具链！见鬼的是，一些公司甚至销售硬件中间盒（middleboxes），其唯一的作用就是基于更多的 XML 来验证和转换 XML！这种语言几乎被用于所有地方：配置文件、序列化状态、用作数据库、RPC 协议等等。</p>
<p>但说实在的，XML 很怪异，它终究是一种标记语言。与 HTML 做个对比：如果你把这个网页上的所有标记统统剥离……它读起来多少还是连贯的，至少对人类来说如此。但如果你对 XML 的典型用例也这样做呢？它将彻底失去一切意义。我们真的在给内容打“标记”吗？</p>
<p>此外，如果你曾尝试为任何东西设计过 XML 格式，你可能根本无法完全确定某样东西到底应该作为标签名、属性还是文本内容。我相信许多人都针对这一话题撰写过主观色彩强烈的指导规范，但事实是，它确实一点也不直观。而且，老天，看看上面那个例子中大量的重复内容吧。正如你可能意识到的那样，JSON 或 YAML 并不存在这些问题。如果你对这两者哪怕稍有了解，你都能毫不费力地想象出上面的例子在它们当中会是什么模样！</p>
<p>YAML 在很大程度上就是为了支持 XML 的所有用例而设计的，这意味着它在设计之初就考虑了一整套相关的工具链。数据可移植性、序列化、配置文件，几乎包揽了一切。许多人有着截然不同的用例需求，这也体现在我读到的一些邮件中。</p>
<p>为什么 YAML 规范要比 JSON 复杂得多？因为，呃，它本身就想做到如此复杂。关于“YAML 处理器”应当如何工作，规范中充斥着篇幅浩瀚的描述。在邮件列表上，不时有人顺口提及并构想“YPATH”、“YAML 模式（schemas）”、“YAML-RPC”等等。人们渴望用 YAML 实现你在 XML 中能做到的一切。</p>
<p>当然，XML 的炒作周期终究过去了，对这些 YAML 替代物的渴望也随之烟消云散。我前面提到的那些雄心勃勃的目标呢？绝大多数从未实现。如今，人们在编写配置文件时，基本上只是把 YAML 当作一种更美观的 JSON 替代品。至于这是好事还是坏事，就留给各位自行评判了。</p>
<p>我自己对此有很多想法，而我之所以想写这篇博客文章，部分原因也是希望能将自己的观点分享到互联网上。对比一些语言，加入我自己的见解和个人看法，诸如此类。</p>
<p>不过到头来，我始终无法以一种令自己满意的方式组织好上述内容，这篇博客文章在其他部分早已完工的情况下就这么搁置了数月。因此，为了能把它真正发表出来，我删掉了那部分内容。</p>
<p>不过，如果你真想知道我对 YAML 的最终看法：它还算凑合吧。</p>

<p>2002 年 9 月，关于类型如何运作的话题再次被提起。起因是一位新人试用 YAML 时遇到了时间和日期类型的局限性与风险，其他人也对现有的隐式类型规则感到不安。于是齿轮开始转动，有人提出了“DWIM”（按我意图行事）提案，后来更名为“未知类型”提案：</p>

<p>据我理解，该提案随后被合并到了 2002 年 10 月 31 日修订版的规范中。此外，他们当时似乎希望尽早完成 1.0 规范，因此非核心类型被移了出去，这样就不必为了赶进度而与规范其余部分一并砍掉。无论如何，在时间线的这个节点上，我坚信自己的理解是正确的：规范作者们的预期是“默认情况下所有内容都应该是字符串”，而这一初衷一直到 2024 年 1 月都未曾改变。在不同时间节点由规范作者撰写的多封邮件中，都重申了这一点：</p>

<p>现在这成为了可能，因为类型已被移出规范。它们不需要被解析器所识别。这是我们在简化 YAML 逻辑方面做出的最明智之举。</p>
<p>这也是阻碍我更广泛部署它的最大原因：不得不向其他人详细解释关于值语法的复杂规则。说一句“只要让你的值以字母数字字符开头就没问题”，远比说“纯数字不行。YYYY-MM-DD 不行。以 !&#39;&quot;% 开头不行。t/f/~ 不行”要简单得多。</p>
<p>是的。现在情况完全不再是这样了。基本上每个标量都会被解析为一个带有类型的字符串。并且（在缺少模式的情况下）完全由加载器来决定如何处理该字符串及其类型。在合理的情况下，我们*鼓励*加载器支持 YAML 类型库。而且在大多数情况下，默认将值作为字符串加载，并在用户开启 load_dates_as_objects 选项时将日期作为对象加载，才是合乎逻辑的做法。</p>
<p>即使是普通标量（plain scalar）也是有类型的。其类型就是空字符串。这是给加载器的一个提示，让它根据加载器的默认设置、用户设置的加载器选项或模式文档中的类型提示，做出最合理的处理。</p>
<p>我的意思是，让你的 YAML 模块在默认情况下始终加载字符串。完全不进行隐式类型转换。这是推荐的默认行为。</p>
<p>隐式类型转换是可选的，并且它_不是_基础标准的一部分 [1]。</p>
<p>[2] 遗憾的是，现行的 PyYaml 在隐式类型转换方面处理得并不符合核心规范其余部分的水准。这是历史原因造成的：在编写 PyYaml 时，隐式类型是_非_可选的，这引发了许多问题，而规范后来在意识到这一错误后做出了修改（感谢 Steve Howell）。希望 Tim 正在开发的全新 PyYAML 能够先聚焦于核心规范，把数据类型留待日后再解决。</p>

<p>自 HTML 2.0 于 1995 年问世以来的这些年里，Web 发生了翻天覆地的变化。然而，在 Web 标准领域有一句名言：“切勿破坏 Web”（Don’t Break The Web）。虽然存在一些例外，但总体而言，即使岁月流逝，在 Web 诞生之初开发的网站在现代浏览器中仍应能正常运行。然而，为了保持这种兼容性，就面临着因唯恐破坏现有网站而导致变更寸步难行的风险。</p>
<p>Web 解决这一问题的一种方式，是在 HTML 文档中使用某些预期的元素。如果存在该元素，就会使用新功能；若不存在，则简单地回退到旧功能。再加上整个 Web 范围内不同集成与系统的要求，这意味着存在相当多的“样板代码”（boilerplate）——即在几乎每个新建或维护的网站中都会重复出现的代码。HTML 样板代码通常既用来选择启用现代功能，也用来设置网站的偏好项和细节。诸如网站如何在社交媒体上嵌入显示、应加载哪些样式、浏览器应如何为网站周边界面设置主题风格等各种杂项细节均在此列。</p>

<p>所有必须引入的样式都可以在这里引入。样式通常应在页面 head 中引入，而不是在样式表内部使用 @import CSS at-规则，以避免产生请求瀑布流——即必须先获取该样式表才能接着获取其他样式表。</p>
<p>复杂的可变字体体积可能相当庞大，即使经过字体子集化（subsetting）及其他优化也是如此，因此我会预加载我知道页面上会用到的字体。即使字体位于同源，crossorigin 属性依然是必需的。我始终以 WOFF2 格式提供字体，因为它是广泛支持且性能最佳的字体格式。</p>
<p>og:title 用于嵌入卡片展示，例如社交媒体上看到的那些。它是开放图谱协议（Open Graph protocol）的众多元数据值之一。虽然我通常会在常规标题元素末尾加上网站名称，但在 og:title 中我不会添加。在大多数情况下，嵌入展示会在标题旁边显示域名或 og:site_name，从而导致其重复。</p>
<p>我主要是将此 meta description 字段作为搜索引擎优化的一项常规工作来对待。以往主流搜索引擎会在搜索结果页面中向用户展示这段描述，但现在它们大多直接从文档正文本身中抓取提取。</p>
<p>og:description 有时会显示在嵌入预览卡片中。如果缺失，嵌入预览通常会放弃显示描述，或者回退使用 meta description。我喜欢在这里写简短且往往妙趣横生的内容，以激发好奇心并契合社交媒体或聊天信息流。</p>
<p>网站图标（Favicon）是所有网站重要的品牌标识元素——尤其是当打开多个标签页需要区分辨识时。我将 Favicon 设为 SVG 格式，因为它们兼容性好，能够动态适配亮色/暗色模式，在各种尺寸下都清晰美观，且省去了维护一套不同尺寸栅格化 Favicon 的繁琐。</p>
<p>在 og:image 中定义的图片通常会显示在社交媒体或聊天平台等站点的嵌入卡片中。几乎在每个网站中包含它都是有益的，因为它能增添上下文背景，并通常能增大嵌入卡片的尺寸以获得更好的展示存在感。嵌入图片对于 alt 替代文本的支持程度较为一般，因此不应过度依赖。有些网站支持它，有些完全忽略，还有些则以奇怪的方式支持。我会尽量包含它，但保持简短。1200px × 630px 是一种得到广泛支持的尺寸，而在我测试过的现代图片格式中，WebP 是兼容性最好的一种。</p>
<p>指向页面权威版本的规范链接（canonical link）对于指明哪个页面应被视为唯一事实来源（source of truth）至关重要。如果存在内容重复，这一点尤为关键。</p>
<p>在嵌入卡片中显示的网站名称。如前所述，某些嵌入卡片会在页面标题旁显示此名称。</p>
<p>author 标签显然用于标明页面的作者。它并非绝对必要，但有助于开发者识别谁对该页面负责。</p>
<p>将 color-scheme meta 标签的 content 属性值设为 light dark，可以告知浏览器该网站同时支持浅色和深色模式。在 head 中定义它可以防止无样式内容闪烁（FOUC），比如当网站和浏览器都设置为深色模式时突然闪现一片刺眼的纯白屏幕。</p>
<p>用于为作为渐进式 Web 应用（PWA）安装的网站定制浏览器界面主题色（browser chrome），以及在 Android 版 Chrome 中定制浏览器界面主题色（但仅限浅色模式）。其他一些浏览器也会以不同方式解析这些值。我使用 media 属性分别独立设置浅色和深色模式下的颜色。</p>
<p>如果网站提供聚合供稿（syndication feeds），将其包含在 head 中便可实现供稿的自动发现。</p>
<p>如果网站集成了搜索功能，那么创建一个 opensearch.xml 文件并在文档 head 中引用它，便能向浏览器公开该功能，从而提供丰富的搜索体验。具体体验因浏览器而异，但在很多情况下，它允许用户直接通过浏览器自身的地址栏搜索该网站，同时也提供了一种添加搜索引擎的简便方法。</p>
<p>我是一名渐进式 Web 应用的倡导者。我非常喜欢它们，而且许多网站都能从作为 PWA 中获益，即使该网站并不是典型的“应用程序”。我通常会为大多数网站定义 manifest 清单文件，哪怕唯一的益处仅仅是当用户把网站添加到主屏幕时展示效果更好看。该声明有助于浏览器发现该 manifest。</p>
<p>这仅仅是一份样板代码。它是一个模板，涵盖了我大致会在每个网站中包含的内容，并会伴随一些微调。每个网站必然会根据其实际需求在此基础上有增减差异，但这提供了一个合理的基础。</p>
<p>如果某个页面预计会被学术引用，那么你可以考虑加入 Google 学术的 citation_* meta 标签以及都柏林核心（Dublin Core）的 dc meta 标签。如果页面代表一篇文章，那么你应包含来自开放图谱协议（Open Graph Protocol）article 命名空间的标签，或许还包括与发布系统相关的标签。视频、音频、图书或其他内容类型同样会采用不同的标记。许多网站还能从 JSON-LD 结构化数据中获益。这一切完全取决于具体的页面以及实际所需。</p>
<p>想要获取列出更多可选内容的更大规模样板，我推荐 Manuel Matuzović 的精彩文章《我 2026 年的 HTML 样板代码》（My HTML boilerplate in 2026）。</p>
<p>在某些情况下可以使用它们，但遇到这些极少见的情况时你自然会明白。务必极其谨慎。↩</p>
