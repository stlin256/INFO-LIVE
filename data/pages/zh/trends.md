### [我们几乎对所有服务都需要默认的硬性预算上限](https://simonwillison.net/2026/Oct/3/default-hard-budget-caps/)
<div class="original-title-sub"><span class="orig-tag">原文</span> We’re going to need default hard budget caps on pretty much everything</div>

<div class="article-body" data-article-body="true"><p>在接下来的数月乃至数年里，全世界将越来越需要这样一项产品特性：默认的硬性预算上限（hard budget caps）。我指的是按用量计费的服务和 API 中的一种功能，它允许你设定“当月费用达到 X 美元后，直接关停该服务并返回错误”。这必须是硬性限制。所谓“当月达到 X 美元后给我发送提醒邮件”的软性上限，根本无济于事。</p>
<p>编程智能体（coding agents）以及个人智能体（包裹在更友好的 UI 之下的编程智能体），极大地降低了编写并运行实用代码的门槛。有时这些操作是需要花钱的——比如调用付费 API、托管 Web 应用程序，或是会因额外存储与计算资源而计费的系统。</p>
<p>没有人想在半夜收到一封关于超出预算限制的警告邮件，醒来后却发现，就在自己睡觉的时候，失控的服务又消耗了数百（甚至数千）美元的费用。</p>
<p>反对这种做法的一个论点是，企业不希望由于超出某些预算限制，导致其托管的应用程序开始报错。但我认为，大多数企业和个人宁愿面对系统报错，也不愿面对突如其来的 10,000 美元以上的巨额账单。</p>
<p>我认为硬性预算上限应当成为默认设置。如果有人想冒风险，他们当然可以这么做，但这必须基于主动选择（opt-in）。应该在显眼的位置提供一个清晰明了的复选框：</p>
<p>“取消预算上限。如果超出设定的预算限制，我的应用程序将不会被关闭，我将承担后续产生的费用。”</p>
<p>我最希望提供这一功能的服务商是 AWS。我听过太多人出于（合情合理的）恐惧而拒绝在个人项目中使用 AWS，生怕失控的服务会让他们破产。我也听过有人因为没有预料到这一点而遭受惨重损失的经历。</p>
<p>……结果事实证明，AWS 几周前终于推出了支出限制功能！正如他们在 9 月 16 日发布的公告《全新 AWS 体验帮助构建者快速起步并加速交付》中所述：</p>
<p>“当您准备升级到付费计划时，您可以根据自己的使用习惯为项目设置每月支出限制，以确保费用控制在预算之内。如果某个项目的使用量达到了支出限制，您的项目将在当月暂停运行。”</p>
<p>另请参阅 AWS 设置中的《创建支出限制》，尽管该页面提醒称“我们目前仅面向有限数量的客户推出这一新体验”。希望该功能很快能向所有现有账户全面开放。</p>
<p>Google Cloud 也在 7 月推出了类似的功能，名为“支出上限”（Spend Caps），它允许你“为项目内的特定服务设定每月财务上限”。看来这正在成为一种趋势！</p>
<p>在理想情况下，我们的智能体也能在这方面提供帮助。如果智能体能开始倾向于推荐那些具有硬性预算上限的提供商，并警告新手和缺乏经验的开发者不要部署那些没有上限、可能带来麻烦的服务，那就太好了。</p>
<p>本文由 Simon Willison 撰写，发布于 2026 年 10 月 3 日，标题为《我们几乎对所有服务都需要默认的硬性预算上限》。</p>

### [Kolibri：一款主权级开源权重模型](https://aleph-alpha.com/en/blog/kolibri-has-landed-a-sovereign-open-weight-model/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Kolibri: A Sovereign Open-Weight Model</div>

<div class="article-body" data-article-body="true"><p>在德国统一日，我们正式发布了我们的全新模型：Kolibri。<br />Kolibri 是一款英德双语混合专家（Mixture-of-Experts）Transformer 模型，总参数量达 78B（780 亿），其中激活参数为 3B（30 亿）。它支持高达 1M（100 万）个 token 的上下文长度。该模型的完整权重可在 Hugging Face 上下载，并在 Apache 2.0 许可证条款下使用。<br />Kolibri 是我们模型训练工作持续迭代的结晶。我们首先构建了一套模型训练流水线，并通过打造 Kolibri Origin 对其进行了验证——后者是一款总参数 30B、激活参数 3B，且上下文窗口短得多的（65k token）模型。Kolibri 经历了完全相同的流水线：从数据摄取和精选，到消融实验、预训练和后训练，再到最终评估。这使得开展数百次消融实验和稳定预训练成为可能，在发生硬件故障或数据连接断开时，无需人工干预。我们持续监控训练指标，并针对自定义基准实现了标准化监控。我们在构建和迭代该流水线所投入的时间是一笔宝贵的投资。Kolibri 比 Kolibri Origin 的卓越表现，以及两者发布时间间隔之短，都印证了这一点。<br />Kolibri 是一款专用语言模型，专为公共行政、工业和航空航天等受监管领域中的主权级关键任务而打造。我们针对德语、推理、数学、智能体行为以及客户在生产中所需的其他能力对 Kolibri 进行了专项优化。此项专精化的目标是优化我们客户特定用例的表现。通过专精化，客户在其 AI 业务中获得了与情境深度契合的性能表现，并且能够监控其经济影响，从而使投资回报率（ROI）保持可量化并随时间持续增长。<br />单靠专精化是不够的。主权同样重要。对我们而言，主权结合了两个维度：我们如何构建该模型，以及它如何交付给我们的客户。我们提供完整的供应链完整性，并对从数据摄取、预训练与后训练，到最终评估的每一项决策负责。我们提供透明度。客户享有完全的部署自由与知识产权安全，因此合规性成为了该模型自带的继承属性。<br />阅读我们的技术报告以了解完整详情。<br />考虑到各特定行业的专业语言、监管与流程实际情况，我们优化了 Kolibri 在广泛行业中的性能表现。其小巧高效的体量为我们的客户提供了在本地高效运行的灵活性，无需将内部数据发送至第三方推理服务。本节的重点将介绍该模型的能力，随后我们将在“我们如何高速构建 Kolibri”一节中详细说明。<br />通过 Kolibri，我们在 78B 的总参数中使用 3B 的激活参数，优化了模型能力与部署成本之间的权衡。在英语和德语的质量与服务成本方面，Kolibri 均处于帕累托前沿（Pareto frontier）。帕累托前沿是经济学中的一个概念，标志着两个目标可实现的最优组合，在这一边界上，改善其中一个目标意味着必须牺牲另一个目标。在参与对比的模型中，没有哪个能在相同的服务成本下提供更高的质量，或以更低的成本提供同等质量。<br />在数学、编程、文档依据（grounding）和长上下文任务中，Kolibri 均能媲美激活参数量高达其四倍的模型，例如 Nemotron 3 Super。<br />给出有文档作为依据的答案。我们使用弃权数据以及我们的 Merlin-Arthur 协议对 Kolibri 进行了训练。因此，当上下文中不存在答案时，它被训练为回答“我不知道”。我们的客户非常重视并需要这一特性，因此我们持续跟踪并验证弃权准确率。我们在“依据（Grounding）”部分提供了更多细节。<br />我们在构建 Kolibri 时，从底层就充分考虑了《欧盟人工智能法案》（EU AI Act）、《通用人工智能行为守则》（General-Purpose AI Code of Practice）和《通用数据保护条例》（GDPR），并将版权法作为我们打造可信赖技术的工作重点。<br />我们对模型权重以及训练数据的精选过程保持透明，以便开发背后的决策公开可见。通过其推理轨迹，模型如何得出特定答案变得具备可解释性。借助我们的 Merlin-Arthur 协议，该模型夯实了可信度：当上下文不支持得出答案时，Kolibri 会避免作答。<br />我们的团队在德国构建了该模型，并在欧洲和德国法律框架下、在德国和芬兰的基础设施上进行了训练，不受任何外国控制。我们掌控着从数据精选、预训练与后训练，到我们“模型工厂（Model Factory）”优化的全套流水线。对端到端流水线的掌控夯实了模型的主权地位。控制权同样会传递给我们的客户，而 Kolibri 的小巧体量赋予了他们完全的部署自由，并支持可控的推理耗费，以便在成本、延迟与回答质量之间进行权衡。<br />我们的“模型工厂”是我们实现迭代速度的解决方案，它最大限度地缩短了从发现模型错误到训练出更优秀模型所需的时间。我们将训练流水线实现为代码，从而使团队的经验沉淀为一份带版本控制的训练配方，而不是零散的脚本和笔记。以下是 Kolibri Origin 到 Kolibri 之间的演进历程。<br />流水线的工作始于 1 月。历经五个月以及数百次消融实验运行后，Kolibri Origin 于 6 月 11 日在目标规模上完成了预训练。Kolibri 则于 9 月 11 日完成。在两个日期之间的三个月里，我们实现了从 30B 参数到 78B 的跃升，上下文窗口从 65k token 扩展至最高 1M，训练 token 从 7.5T 增加到 20T。为了获得这 20T token，流水线处理了超过 200T token 的原始数据，经过过滤、去重和精选，提炼出我们实际用于训练的数据。我们更改了注意力设计，将专家数量增加了两倍，提高了稀疏度，替换了路由算法，改进了后训练数据，将环境任务数量增加了一倍以上，并教会模型在四种不同的努力程度下进行推理。得益于我们效率团队的工作，两款模型每个 token 保持了相似的激活参数量，但 Kolibri 每个 token 的训练速度却快于 Kolibri Origin。<br />实现这一目标的背后是我们这套训练流水线——这是一项旨在将研究级模型开发转化为完全自动化的、可直接投入生产的基础设施的工作，用以设计和训练大语言模型。我们的流水线代码库供所有人共享。每次提交的代码更改都会触发一次端到端的小规模模型运行（涵盖训练与评估），以在数分钟内发现是否有地方出错。我们的运行均基于 GitHub Actions 工作流，重现某次运行仅需检出一个 commit。我们使用该流水线进行主训练，并进行了数百次消融实验，以做出我们的架构和数据配比决策。</p>
<p>训练检查点（checkpoint）大约每小时生成一次，流水线会自动对它们进行英语与德语知识、数学、代码、指令遵循、工具调用、长上下文、安全性、拒答幻觉以及事实溯源（grounding）能力的评测。我们可以每天直观地看到模型能力的演进，而无需等到训练最终结束时才揭晓成效。实际训练过程比我们预期的更为稳定。在 Kolibri 历时 21 天的预训练中，因硬件故障或连接超时导致了 38 次非计划中断，大约每 10,000 个 GPU 小时发生一次。这些问题全部由流水线自动处理，无需人工干预。集群会自动在另一批节点上重启训练任务，并从至多 250 步之前的检查点恢复训练。</p>
<p>能够访问完整流水线并向所有人开放检查点，意味着任何团队都可以端到端地独立负责一项特定能力，而不是仅局限于流水线中的某一个阶段。例如，有一个团队将 Kolibri 的事实溯源能力作为一项独立任务进行了完整的训练和评估，并无缝集成到了整体模型中。</p>
<p>然而，走到这一步并非一帆风顺。我们也曾遭遇挫折。在 Kolibri Origin 预训练了数万亿 token 之后，由于发现了一个躲过前期测试的数据打乱（data-shuffling）漏洞，我们不得不终止训练并从头重来。我们进行了消融实验并做出决策，但事后却发现配置中存在 bug 或错误，迫使我们重新运行某些实验。除了自身积累的经验外，我们还紧密跟踪最前沿的模型架构、最佳实践以及大语言模型领域的最新研究进展。这些日积月累的心得转化为流程上的改进，以及流水线中的安全防护机制。</p>
<p>对比 Kolibri Origin 和 Kolibri 之间的差距，提升是显著的，但这仍属于相对容易推进的方向：更多的参数、更多的数据、已被充分理解的架构家族，且规模依然适中。当我们考虑进一步扩大规模时，我们欣然在已打下的基石上迎接挑战。但今年我们打造出的最具持久价值的成果并不是这条流水线，而是一支拥有久经考验之能力的团队——能够以极高的速度，从原始数据起步完成大语言模型的构建、后训练并最终交付交付。</p>
<p>Kolibri 拥有 780 亿（78B）总参数量，是 Kolibri Origin 的 2.5 倍，其中活跃参数量约为 30 亿（3B）。在我们的实验中，将模型规模从 32B 扩大到 123B 带来了持续的性能提升。然而，更大的尺寸也意味着更高的训练与推理部署成本。后者的考量最终决定了方案取舍：在两张 H100 GPU 上，123B 只能同时处理 3 个 256k token 长上下文的用户请求，而 78B 则能支持 18 个并发请求，且解码速度快了 28%。我们采用了 384 个较小的专家网络（experts），而非较少的大专家网络，因为前者在我们的测试中表现更佳。我们将相同的效率优先逻辑应用于注意力机制。在全部 50 层中，仅有 10 层处理完整上下文，其余 40 层则采用紧凑的 512-token 聚焦窗口。无论上下文多长，这都能将这些层中的解码计算量和显存占用限制在固定范围内。效率的提升既有利于训练后模型的部署服务，也有利于严重依赖海量推理运算的后训练阶段强化学习（RL）。</p>
<p>我们在 768 张 B200 GPU 上分三个阶段训练了 Kolibri：第一阶段是在 16k 序列长度下进行 20T token 的预训练，耗时 21 天；第二阶段是在 64k 下进行 3.44T token 的中期训练（mid-training）；第三阶段是在 256k 下进行 200B token 的长上下文适应。总计消耗近 24T token，大约是 Kolibri Origin 消耗量的三倍。德语在预训练混合数据中占比超过五分之一，约为 4.3T token，英语约占 62%，代码约占 14%。与预训练相比，中期训练的数据更为精挑细选，侧重于推理、问题解决、代码以及智能体（agentic）数据。在长上下文阶段，我们没有单纯使用长文档进行训练（因为这往往会侵蚀先前学到的技能），而是将长文档与上一阶段的高质量中期训练数据交错穿插。在长上下文混合数据中，我们移除了合成的长文档，以避免人为虚高 RULER 等基准评测的成绩。</p>
<p>与训练 Kolibri Origin 时一样，我们采用了 Muon 优化器。我们特别关注训练的稳定性，两款模型的训练过程均非常稳健，未出现任何损失尖峰（loss spikes）。在 Kolibri 的训练过程中，针对专家网络之间的路由选择，我们引入了精确分位数平衡（exact quantile balancing）。分位数平衡最初在 Kimi K3 中被提出，当时由于精确计算被认为通信开销过大，因此通过直方图来估算全局分位数；而我们证明，它可以在不依赖于批次大小（batch size）的固定成本下被精确计算出来，并且这种精确性同时改善了负载均衡和模型质量。</p>
<p>后训练分为两个阶段：第一步是有监督微调（SFT），旨在赋予模型核心推理能力以及对话交互方式；随后进行大规模强化学习，以训练模型在各种复杂的长期任务中进行推理。我们为这两个步骤分别构建了专门的流水线，从而能够对模型的行为实现细粒度控制。</p>
<p>在 SFT 阶段，我们总共生成了相当于 174B token 的合成数据，经过质量过滤后，与经过筛选的采用宽松许可协议的开源数据集结合，最终得到了 268B token 的高质量训练组合。在强化学习阶段，我们在涵盖超过 120 万个精选任务的广泛环境中进行训练，覆盖代码与数学推理、智能体任务、指令遵循、问答、工具调用等多种领域。我们针对高性能优化了自研训练代码库，并采用异步训练：即利用当前模型在环境中生成训练数据的同时，并行地在已生成的数据上对模型进行训练。</p>
<p>在这两个阶段中，我们都训练了模型以不同的思考力度（effort levels，包括无、低、中、高）进行推理，这意味着用户可以灵活控制模型应投入多少算力来寻找当前任务的解法。这使我们的客户能够在成本、推理速度与最终回答质量之间进行权衡取舍。</p>
<p>从在小型代理模型（proxy models）上进行的实验中我们发现，使用约 20% 的德语数据进行训练可取得最优效果，这意味着要在 20T 的总体规划下训练模型，我们需要准备 4T 的德语 token。开源德语数据集虽有帮助但远远不够：在去重和过滤后，我们仅剩下 390B 德语 token，与目标相去甚远。正如我们在《Sauerkraut, Not Burgers》（要酸菜，不要汉堡）一文中所主张的，德语能力必须源于高质量的本土德语文本；过度依赖机器翻译会导致细微的翻译错误并缺失真实的德语文化语境，从而导致效果不佳。我们通过三种不同的方式填补了这一 token 缺口。</p>
<p>第二种方法是对我们已有的德语文件进行改写（rephrase）。大语言模型（LLM）在保留原始内容的前提下，将原始德语文件改写为百科词条、问答对话或段落文本等风格。这使模型能够通过多种表层形式学习同一事实，并成倍扩充稀缺数据中蕴含的信息量；而且这与翻译是截然不同的操作：源文本就是德语，因此其主题和文化认同保持了德语特色——例如是总理（chancellor）而非总统（president）。这种方法并没有增添太多新知识，而是对语料中已有知识提供了新的表达方式。改写为我们带来了约1万亿个独立token，成为该模型中单一最大的德语数据来源。</p>
<p>第三种方法是翻译，而我们仅在Kolibri Origin中采用了这一方法。在精心挑选模型、提示词和分块策略的情况下，将英语翻译为德语是行之有效的，但它伴随两个问题。首先，输出仍可能带有“翻译腔”（translationese），即成语习语的字面直译：例如将“一路平安！”（Drive safe!）译成“Fahre sicher!”，而非地道的德语表达“Komm gut an!”。更重要的是，文化背景是无法直接翻译的。从英语翻译而来的语料继承了英文网络的地理、人口及体制分布，因此基于该语料训练出的模型，虽然说着德语，描绘的却是一个美国化的世界。</p>
<p>最终，德语以一个包含2.4万亿token的独立数据池进入Kolibri，其中80%由我们策划或生成，20%来自开源数据集。在整个预训练token中，德语占比达到21.3%；通过上采样，在总共20万亿token的训练运行中大约占4.3万亿。每个德语token平均被查看1.8次，远低于重复训练不再产生收益的4个epoch上限。模型所阅读的德语数据中，约85%为网络文本（包括原始网络文本或由其改写而来的文本）。其余部分则是精心策划的文件——包括议会议事录、法律文本以及其他公有领域数据——以及那一小部分翻译数据。</p>
<p>我们构建了一个英德双语分词器（tokenizer），并在每个模型的预训练数据集上进行了专门训练与优化。得益于我们数据中21%的德语份额，该分词器对德语的压缩率优于其他主流SOTA模型。这带来了更高效的推理性能（产生更少的token），从而最大限度地降低了成本并缩短了响应时间。我们引入了一种全新的分词器训练方法UniBPE，与现有方法相比，它能在不牺牲英语token效率的前提下，更好地兼顾语言的形态学特征，特别是德语的复合词结构。</p>
<p>德语网络数据（FineWeb-2）<br />英语网络数据（FineWeb）<br />训练分词器的两种主流方法是BPE和Unigram。我们将这两者结合起来，保留了BPE自底向上的方法，同时使用Unigram的训练目标来选择将哪些合并项（merge）添加到词表中。在基于我们英德数据集训练的128k词表上，这一方法显著改善了分词效果。</p>
<p>Bundessozialgerichtes 联邦社会法院（属格形式）<br />Protokolldaten 日志数据<br />常见的LLM训练和评估机制往往鼓励“猜测”：去猜有一定概率碰巧答对，而弃权（abstention）则绝无得分可能。因此，模型学会了倾其所有作答，即使输入的信息根本不足以支撑得出结论。出于同样的原因，要求模型提供引文往往会适得其反：模型完全可以凭空捏造看似合情合理的虚假来源，来为其毫无根据的回答辩护。</p>
<p>对于受到严格监管的行业客户而言，模型是否懂得适时弃权，是决定其仅停留在试点阶段还是能够正式投产的关键。我们将说“我不知道”视为一项重要的模型能力，并采取了两项举措：(1) 开发并跟踪专门的依据对齐（grounding）与反幻觉指标；(2) 采用并开发专用的训练流程来增强这一弃权能力。</p>
<p>在训练过程中，我们使用了正确答案为“我不知道”的训练数据样本。尽管在整个行业内，针对弃权能力的微调正日益受到重视，但高质量的负面样本依然难以获取，尤其是在我们客户所需的狭窄垂直领域中，这些领域的所有数据都十分匮乏。因此，我们还采用了自主研发并在博客文章中详细阐述的“梅林-亚瑟”（Merlin-Arthur）训练流程。该流程在每个训练步骤中自动发掘模型的弱点，并利用现有文档生成合成负样本，从而解决了数据稀缺问题。这一训练过程变成了一个由三方参与的博弈。Arthur是我们正在训练并准备交付的模型。Merlin获取现有的文档上下文，并生成一个新的上下文以提高Arthur正确作答的概率。Morgana则生成新的数</p></div>

<p>每次调用 Errors 的 Debug 实现时，可能会有大量代码被内联，而这在例如 debug 或 trace 日志记录中可能会反复发生。</p>
<p>事实上，内联的代码量非常之大，甚至可能在 Rust 二进制文件总大小中占据不可忽视的比例：我们发现，通过阻止² rustc 内联某个给定的 Debug 实现，我们能够将 uv 的二进制体积缩减大约 160KB。</p>
<p>这在两个层面上让我感到惊讶：体积开销累加得非常快，而且 rustc（表面上看）并没有对 Debug 实现的内联大小或内联次数施加限制。不过，我推测在许多程序中，这仍然是一个正确的决定！</p>
<p>¹ 该层级结构已被大幅简化：现实世界中的 Rust 应用程序通常具有深度嵌套且包含大量字段的错误枚举。↩</p>
<p>² 我们通过添加自己的过程宏（proc macro）实现了这一点，该宏的行为类似于 derive(Debug)，但带有 #[inline(never)]。↩</p></div>

### [为什么没有更多开发者“利用平台原生能力”？](https://nolanlawson.com/2026/10/03/why-dont-more-developers-use-the-platform/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Why don’t more developers &quot;use the platform&quot;?</div>

<div class="article-body" data-article-body="true"><p>诺兰·劳森（Nolan Lawson）于 2026 年 10 月 3 日发布在“Web与软件工程”分类下。</p>
<p>多年来，Web 标准、性能和无障碍访问的倡导者一直在恳请 Web 开发者“利用平台原生能力（use the platform）”。我也经常是这些倡导者之一。</p>
<p>理由很简单：既然浏览器能为你代劳，为什么还要自己用 JavaScript 从头构建？无论你构建出什么，其性能和可用性往往都不如浏览器开箱即用提供的原生能力。</p>
<p>不过，我认为站在对立面思考也是有价值的，哪怕仅仅是为了理解那些对“平台持怀疑态度”的开发者的出发点。如果“利用平台”是如此显而易见的道理，那为什么似乎还需要去说服那么多人呢？</p>
<p>最明显的原因是历史因素：在很长一段时间里，浏览器一直都在努力追赶建立在它们之上的生态系统。在浏览器实现等效 API 的过程中，像 jQuery 这样的库填补了关键空白——即便浏览器后来实现了，你也可能得等到 IE6 之类的落后浏览器被彻底淘汰之后才能真正用上它们。如今，大多数浏览器都是常青浏览器（Safari 或许存有争议，尽管每年约 7 次更新也并不算差），但直到 2020 年代左右，Web 开发者还必须面对一个极其参差不齐的 Web 环境。在那种环境下，自己动手造轮子是一个明智的选择。</p>
<p>另一个原因是习惯与熟悉度：当你习惯了在 npm 上寻找 React 组件时，无论手头面对的是什么问题，你往往都会直奔那里。如果你在 npm 上搜索“sticky positioning（粘性定位）”，可没有任何一个包会写着：“笨蛋，直接用 CSS 的 position: sticky 就行了。”</p>
<p>而且通常情况下，即便有了成熟的标准，npm 上的库也会在框架的人体工学体验与底层平台之间填补有益的空白。我一直觉得很有趣的是，许多 React 开发者更喜欢坚持使用 JSX 和 React 的惯用语法——原生 DOM API 让他们觉得“别扭”——但他们却非常乐意使用那些内部广泛进行原生 DOM 操作的底层库。例如，一个虚拟列表库可能会为了纯粹的性能而乐意使用原生 DOM API，同时对外暴露新手 React 开发者更容易理解的高阶原语。从某种意义上说，React 组件生态促成了一种自然的劳动分工：经验更丰富的人将不那么熟悉的平台 API 封装成了更符合直觉的形态。</p>
<p>这种现象的一部分也是由文档驱动的。许多 npm 包都有精心编写、详尽周全的 README 或包含示例、教程和截图的专属网站。而在 MDN 确立其作为 Web 文档首选去处之前（web.dev 则作为谷歌更面向未来的前沿阵地），Web 平台的文档零散分布在各个博客、StackOverflow 以及像 CSS Tricks 这样的网站上。而且这些网站往往只会告诉你去使用像 jQuery 或 GreenSock 这样的知名库！</p>
<p>不过，如果仅仅是第三方库与平台 API 之争，我认为还不足以完全解释人们对“利用平台原生能力”的反感。那些图省事的开发者（或者说，所有开发者不都如此吗？），只想为当前面对的问题找到现成的解决方案，他们不太可能在乎这个方案究竟是来自 npm、浏览器，还是从某人随手写的 GitHub Gist 上抄来的。他们只想解决问题然后继续前进。但对于这种反对“利用平台”的态度，我还想探讨另一个来源。</p>
<p>对某一类开发者而言，亲手构建东西本身就更有乐趣。而且通常情况下，亲手写出的代码更容易推导和理解，尤其是当你对 Web 平台并没有百科全书般的全面了解时。一旦你亲手构建了某个东西，就可能会产生一种“宜家效应（IKEA effect）”，让你忍不住想要维护和摆弄自己亲手写的代码。</p>
<p>举个例子，假设你正试图构建一个模态对话框（modal dialog）。你可能从视觉上理解它们是如何运作的：内容出现在屏幕上，背景虽然部分被遮挡但依然可见，点击对话框外部或许就能将其关闭。于是你可能会拿出 position: absolute 和 z-index 来正确定位对话框——啊哈，但背景依然会滚动，所以你得在 body 上禁用 overflow……然后，如果你对无障碍访问稍有了解，你就会意识到自己需要处理 Esc 键关闭、构建焦点陷阱（focus trap），并将焦点归还给触发该对话框的元素，还有……</p>
<p>对许多开发者来说，我刚才描述的这些听起来就像一场噩梦（而且很容易造出一个半吊子的半成品）。但对许多开发者而言，这听起来太有趣了！想想看，当你动手构建这个东西时，你能学到多少知识。再想想看，你可以怎样融入自己的创意风格：添加动画、主题、可选的“关闭”按钮……不知不觉间，你已经写出了一个可以发布到 npm 上的库。这可比直接拿现成的东西来用然后草草收工要有趣得多——直接用多扫兴啊！</p>
<p>对我们之中的许多人来说，在类似的原生 API 出现之前，这正是我们学习 Web 平台的方式！如今倡导“利用平台原生能力”的许多人，曾经自己也是 polyfill、垫片库（shim）和第三方库的作者。我深知这一点，因为我自己就是其中之一！作为 PouchDB 工作的一部分，我花了数年时间开发针对 IndexedDB、WebSQL 及其他浏览器存储 API 的工具，这最终让我有了足够的信心坐在 W3C 标准会议中，甚至就 IndexedDB 规范本身提出 issue 和 Pull Request。如果没有弥补平台空白这一强力倒逼机制，我不知道自己是否还能找到兴趣或动力去达到这种专业水准。</p>
<p>当然，凡事亲力亲为也并非全无弊端。有时这纯粹源于无知。特别是在 Web 平台上，例如对于本可以通过 CSS 更好解决的问题，之所以涌现出如此泛滥的 JavaScript 解决方案，我认为原因之一在于许多开发者根本没有花时间去深入理解 CSS 的工作原理。</p>
<p>坦率地说，CSS 在历史上确实很难理解！那个网站之所以被命名为“CSS Tricks（CSS 奇技淫巧）”是有原因的。像清除浮动（clearfix）、浮动（float）以及 min-width: 0 这种技巧，几乎毫无直觉可言。与其费力去理解 CSS 的内部算法，往往远不如直接构想出你想要的命令式逻辑并用 JavaScript 表达出来要容易得多。此外，多年来 CSS 都缺乏直观的方式来表达常见的样式模式，比如多行文本截断（line clamping）、文本域大小调整、隐藏滚动条等。因此，开发者自然会利用自己早已掌握的工具亲手去构建它们。</p>
<p>我甚至认为，这种“回避平台原生能力”的现象并不仅限于 Web 领域。它可以适用于任何在自己未完全理解的平台上进行开发的工程师。例如，在我的工作中，我们使用 ClickHouse 来存储各种分析数据。有一次，我和同事在如何将大型 JSON 数据存入某一列上产生了分歧：他构建了一套在存储前对其进行压缩的系统，而我则将数据保存在一个单独的键值存储中，仅将键插入到 ClickHouse 中。事实证明我们两个都错了！ClickHouse 会自动压缩数据，而且作为列式数据存储，如果直接交由 ClickHouse 处理，跨行压缩的效果实际上反而更好。而单独的键值存储，不过是对列式 SELECT 原生功能的一个拙劣模仿。</p>
<p>直到我真正花时间通读了 ClickHouse 文档并编写了基准测试来验证自己的假设之后，我才意识到这些。最终让我深感震惊的是，我们费心搭建的东西，竟然比平台本身开箱即用提供的功能更慢、更笨重。这与 JavaScript 以及 Web 平台上的情况何其相似，让人难以忽视。</p>
<p>我相信，如果你是一名 iOS 或 Android 开发者，或者在游戏引擎之上进行开发，又或者是任何在某种平台层之上构建应用的开发者，你很可能也有过类似的经历。人们对经验丰富的老牌资深工程师的固有印象是有原因的：他们总能把初级开发者写出的繁复芜杂、犹如巴洛克风格般纠缠不清的代码，精简替换为区区一行。你学得越多，就越能凭借对整个系统端到端运作机制的理解，以尽可能最小的代码改动来达成目标（从而从长远来看大幅减轻维护负担）。</p>
<p>在整篇博文中，我一直在极力克制自己不去讨论 AI（因为过去一年里关于它我已经谈得实在太多了），但我当然还是忍不住去想，AI 编程会对这种现象产生怎样的影响。实际上，我同时持有乐观和悲观两种看法：</p>
<p>在我自己使用 AI 编程的过程中，这两种情况我都亲身体验过。我倾向于认为，随着模型和编程配套工具（coding harnesses）的不断完善，我们将会逐渐偏向乐观的结果，但我现在还无法给出定论。</p>
<p>无论如何，以上便是我对“善用平台（use the platform）”这一理念漫长且略带纠结的思考。作为一句箴言，我非常喜欢它，因为它精辟地概括了我在审视某些过度设计、混乱不堪的“面条式代码”时的感受：如果作者能够对底层机制稍微多了解一点，这段代码本可以变得多么高效而优雅。与此同时，我也曾是那样的作者，也曾体会过构建出那种精美而混乱的代码时的快乐（至少在我眼里是精美的），因此我认为理解这些开发者的初衷是很有意义的。正是出于这个原因，我相信只要平台依然存在，“善用平台”的声音就永远不会消失。</p>

### [Android系统级广告拦截指南](https://kevinboone.me/adblock.html)
<div class="original-title-sub"><span class="orig-tag">原文</span> System-level ad-blocking in Android</div>

<div class="article-body" data-article-body="true"><p>互联网已经沦为了一个广告平台。移动设备用户对此体会尤为深刻，因为除了充斥网络的各种广告之外，移动操作系统环境和应用程序还在不断强制向用户推送广告。随着Android系统越来越封闭、越来越难以自定义，在Android手机上避开广告变得日益困难。让拦截广告变得容易，显然不符合Google的利益。</p>
<p>然而，即使到了2026年，抑制绝大多数广告仍然是可行的。</p>
<p>本文专门探讨如何在系统级——也就是在Android平台本身，而非特定应用内——拦截广告。一些Android应用（尤其是网络浏览器）拥有自己的广告拦截方式，或者可以通过第三方插件添加此类功能。不过奇怪的是，DuckDuckGo浏览器虽然能拦截针对性广告所伴随的追踪行为，却并不专门拦截广告——你还需要更多的手段。</p>
<p>如果你在系统级拦截广告，所有应用乃至系统本身都能得到保护。此外，拦截广告的方法通常还可以扩展到防范追踪器和其他类型的恶意软件。</p>
<p>据我所知，所有系统级广告拦截方法都是通过覆盖DNS行为来实现的。DNS（域名服务）是将主机名映射为数字IP地址的技术；DNS查询几乎是所有网络操作的第一步。</p>
<p>利用DNS拦截广告，实质上就是找出已知广告服务的主机名，并将它们映射到虚假的IP地址上。这既可以在Android手机本机上完成，也可以在外部DNS服务器上完成。</p>
<p>返回虚假IP地址并不能阻止应用程序或浏览器尝试展示广告，也无法让其更好地利用广告所占用的屏幕空间。各应用在展示广告失败时的反应不尽相同——稍后会对此做更详细说明。</p>
<p>利用DNS变更来拦截广告基本上有四种方法。</p>
<p>通常情况下，当你在Android设备上连接到互联网时，DNS域名解析（将主机名映射为数字互联网地址）是由手机的移动运营商或互联网服务提供商（ISP）托管的服务器执行的。</p>
<p>Android允许你覆盖这一默认行为，并选择一个能拦截广告的自定义DNS服务器。好吧，它实际上并不会真正去“拦截”任何东西；DNS服务器只是在你的手机查询已知广告商主机名对应的IP地址时，返回一个虚假的IP地址。</p>
<p>根据你所使用的DNS服务不同，你可能拥有、也可能没有权限去具体控制它拦截的内容。例如，出于对儿童保护的考虑，一些用户还会选择屏蔽访问色情或在线赌博内容。</p>
<p>当然，这些服务的运作效果取决于服务运营方维护已知广告主机列表的质量如何。广告服务来来往往，即便是长期存在的服务也会不时更换其服务器。</p>
<p>市面上有许多支持广告拦截的商业DNS服务，我并不专门推荐任何一家。它们的价格各不相同，且大多数服务都提供免费试用。如果你看重隐私，你会希望使用不保留任何日志的服务，并且可能还想使用支持加密DNS的服务。恶意的DNS运营方可能会通过各种途径获取敏感数据。例如，DNS运营方完全有可能将对你网上银行服务的请求重定向至其自建的代理服务器，并在你登录时窃取你的凭据。你务必保持高度警惕；虽然存在合法的免费DNS服务，但我对任何此类盈利模式不明确的服务都持相当怀疑的态度。</p>
<p>与商业DNS服务一样，恶意的VPN运营方也可能非常危险，因此审慎选择服务商至关重要。</p>
<p>据我所知，所有这些应用都在利用Android平台封闭机制中的某种“漏洞”。</p>
<p>像所有基于Linux的操作系统一样，Android提供了一种让设备覆盖其当前互联网服务提供商DNS映射的方法。在手机的某个位置，会存在一个包含优先域名到IP映射列表的文件。在未获取Root权限的Android设备上，用户没有修改该文件的权限，因此一种简单的广告拦截方式——在文件中维护一份已知广告商的虚假DNS映射列表——便无法使用。</p>
<p>不过，在未Root的设备上，你可以安装VPN服务。如果Android要支持VPN，就必须允许这一点。一个无需Root的广告拦截应用通常会在本地（应用内部）运行一个DNS服务器和一个本地VPN主机。该应用会将手机配置为将其自身的VPN作为系统VPN提供商，进而使其自身的DNS服务器成为系统DNS。通过掌控DNS，该应用便可以自行处理域名查询，包括对已知广告服务器的查询。</p>
<p>Google作为一家广告公司，对此类做法并不热衷。它无法在不彻底破坏VPN功能的前提下轻易阻止“本地”VPN的使用，但Google能够——而且确实在——让非技术用户更难获取相关应用。目前，你还可以从F-Droid等替代应用商店获取像AdAway这样的应用。</p>
<p>Google也打定主意要在这方面设卡制造困难，不久之后你就必须从（但愿是）信誉良好的来源获取应用的APK文件，并跨越Google为安装其不喜欢的软件所设置的重重障碍。在撰写本文时，Google并未彻底禁止从Play Store之外安装软件，但过程正变得越来越繁琐棘手。</p>
<p>不过极有可能的是，Google设置的这些障碍永远不会像对Android手机进行Root并应用彻底的广告拦截方案那样难以逾越。即使Google让安装变得困难，使用像AdAway这样的应用相比商业DNS或VPN服务可能仍然具备优势。</p>
<p>最显而易见的优势在于这些应用通常是免费使用的。尽管免费，志愿维护者社区仍能确保这些应用维护的已知广告商列表与任何商业服务提供的一样详尽。然而，一个劣势在于，来自所有应用的所有网络流量都必须经由手机上的单一应用进行路由。这不仅会造成网络瓶颈，而且一个恶意的广告拦截应用的危险程度与恶意VPN服务完全相同。幸运的是，由于这些广告拦截应用通常是开源的，不良行为者作恶的机会非常有限。即使你不打算亲自查看源代码，我也强烈建议不要使用非开源的应用。</p>
<p>如果你的手机已经Root，那么拦截广告——至少在理论上——是十分简单的。Android的优先域名到IP映射列表存放在/system/etc/hosts文件中，因此你只需编辑该文件，将广告商的主机名指向一个虚假IP地址即可。通常这个虚假IP是手机本机的本地地址127.0.0.1。因此，你的hosts文件将充斥着如下所示的条目：</p>

<p>这在理论上非常简单明了，但在实践中却存在两个主要问题。</p>
<p>首先，我们需要一份要屏蔽的主机名来源。这类列表在各大网站上随处可见，但维护问题始终存在。其中一些列表极其庞大，毫无疑问还包含已经不再运行的主机。如果主机名列表如此冗长，那么所有网络访问都会变慢，因为手机在进行每次 DNS 查询时都必须解析 hosts 文件。</p>
<p>广告拦截 hosts 文件的最佳来源，或许是类似 AdAway 这样的开源广告拦截应用的代码。事实上，在已获取 Root 权限的手机上安装该应用时，它可以自动提供其规则列表，从而简化了配置过程。</p>
<p>第二个问题是，即使拥有 Root 权限，你也无法直接修改 hosts 文件——在所有现代 Android 设备上，它都位于只读文件系统之中。因此，你需要某种软件能够在启动过程中趁着 /system 目录仍可写时，对其内容进行操作。</p>
<p>如果你已经对手机进行了 Root，几乎肯定已经有办法做到这一点。例如，如果你使用的是 Magisk，可以通过模块来提供一个新的 hosts 文件。Magisk 模块存放在 /data/adb/modules 下的目录中，模块自身 system 目录中的任何文件都会在开机启动时覆盖主 /system。因此，你可以创建一个自带 /system/etc/hosts 的 Magisk 模块。</p>
<p>令人高兴的是，Magisk 用户无需手动完成此操作，因为 Magisk 开发者已经预见到了这种用途。如果你在 Magisk 应用中启用了“Systemless hosts”选项，它就会自动创建包含所有必要元数据的对应模块。此后，要创建自定义 hosts 文件，你只需（以 Root 身份）直接修改 /data/adb/modules/root/system/etc/hosts，然后重启即可。或者，你也可以使用某个应用程序来进行此更改。</p>
<p>事实上，由于这种修改 hosts 文件的方法非常普遍，像 AdAway 这样的广告拦截应用本身就内置了对此功能的支持；但是，这种支持显然仅适用于已获取 Root 权限的设备。如果你的手机已经 Root，使用能够识别 Root 的广告拦截应用可能是管理广告最有效的方式。它比通过安装本地虚拟 VPN 的非 Root 应用快得多，而且不会引发任何相同的安全担忧。这并不是说完全没有任何隐患，理想情况下，你应该检查此类应用安装的 hosts 文件，确保其中除了 127.0.0.1 之外没有映射到其他任何地址。</p>
<p>必须明确的是，没有任何一种广告拦截方法是完全可靠或毫无副作用的。</p>
<p>最值得注意的是，某些 Android 应用程序若没有广告就根本无法运行，或者无法正常运行。如果你必须使用此类应用，你需要一种允许自定义拦截站点列表的广告拦截方法。仅从应用本身的行为来看，根本无从察觉它为什么无法运行，或者该如何修复。在已 Root 的手机上，你可以详细追踪特定应用的网络行为，并在理论上找出被你拦截的必要内容。而在实践中，参考此类应用的在线讨论会更容易，因为很可能已经有人替你完成了这项排查工作。</p>
<p>然而，有些应用程序甚至将所有广告都直接内置在软件内部；任何广告拦截器都无法阻止此类应用展示广告，因为根本没有可以拦截的网络操作。</p>
<p>同样需要理解的是，Android 会在多个位置缓存 DNS 查询结果。尽管某些广告拦截方法允许动态配置被拦截的主机名列表，但你可能仍需重启手机才能刷新其缓存。</p>
<p>尽管显而易见，但请牢记：基于 DNS 的广告拦截仅在应用程序使用 DNS 时有效。鉴于基于 DNS 的广告拦截如此普及，一些应用开发者正尝试直接使用 IP 地址访问广告服务器，这使得所有基于 DNS 的方法均告失效。幸运的是，这种情况目前仍相对少见。</p>
<p>在 2026 年，具备系统级广告拦截能力是将你的 Android 手机进行 Root 的少数极具说服力的理由之一。以这种方式拦截广告几乎不会消耗额外的系统资源，而且其效果涵盖所有应用程序。</p>
<p>如果你无法将设备 Root，或者不愿这么做，还有其他拦截广告的方法，但没有一种能像这样高效、可配置且成本低廉。</p>
<p>最后，如果你主要是为网站上的广告所困扰，而非应用程序内的广告，那么最简单的做法或许是安装一个支持广告拦截的网页浏览器，从而彻底避开系统级广告拦截。</p>
