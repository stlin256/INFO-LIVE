### [廉价易用的即用即弃式 VPN 服务器](https://a.l3x.in/blog/throwaway-vpn/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Cheap and easy throwaway VPN server</div>

<div class="article-body" data-article-body="true"><p>在我之前的博文中，我提到过我经常长途旅行，并介绍了随身携带的装备，正是它们让旅途体验更加愉快。遗憾的是，并非我到访的每个地方都能提供与我在自由民主国家🇪🇺成长过程中所习惯的同等种类和程度的自由。</p>
<p>坦白说，仅这一点本身通常并不会对我有感知的自由造成太大限制¹；然而，如果不采取某种变通方法，不受限制的互联网访问可能并非总能实现。在本文中，我将向大家展示我通常用来绕过此类限制的方案。</p>
<p>默认情况下，我会忽略 DHCP 等提供的 DNS 解析器，转而使用公开可用且广为人知的服务之一，通常是 Cloudflare 的。在我的便携微型路由器²中设置一个解析器，意味着对连接到我专用局域网的每台其他设备来说，这一过程都是透明无感的。有些提供商支持额外的隐私保护功能，例如 DNS over TLS，我建议开启它，因为通常它不会带来任何肉眼可见的额外延迟，何乐而不为呢？</p>
<p>单凭这一简单的改动并不能解决 IP 地址段或端口被过滤的问题，但它在避免一系列其他烦心事方面已经非常管用。最重要的是，这是一种一劳永逸式的配置更改，完全无需费神操作。</p>
<p>多年来，我一直是 Proton 服务的忠实用户，对其赞不绝口：他们提供了一种简单且极具成本效益的方式，既能摆脱令人厌烦且充斥广告的谷歌服务，又能大幅提升隐私安全性。他们还提供免费套餐，因此你可以免费起步，等到真正觉得有需要时再升级购买专业服务，就像我当时那样。</p>
<p>我对该服务唯一不满的一点在于：它不允许我自由选择 VPN 出口端的国家。对于一项免费服务来说这合情合理，但如果出口端国家本身也在实施网络过滤，这可能就无法解决屏蔽/过滤的问题了。更普遍的情况是，由于服务器过载，服务质量可能会有所下降，因此总体而言好坏全碰运气，我无法将其视作一种稳定的解决方案。</p>
<p>我想自主选择 VPN 出口节点所在位置的原因还不止于此，例如，某些流媒体平台可能会根据源 IP 地址的地理位置来限制内容或展示不同的可用内容，诸如此类。</p>
<p>我明白你想问什么：为什么不顺便购买 ProtonVPN 的付费专业版，或者市面上其他众多的 VPN 服务呢？我确实可以买，但鉴于我对 VPN 连接的需求非常零散，最极端情况下一个月加起来也用不上几个小时，买它基本上纯属浪费钱。</p>
<p>如果我能按需随时启动一台专业级 VPN 服务器，只需为使用的具体时长付费，甚至还能自主选择它在世界哪个地区运行，岂不美哉？</p>
<p>当自定义 DNS 和 ProtonVPN 都派不上用场时，我的做法其实很简单：只需运行一条 CLI 命令即可快速启动一台 WireGuard 服务器，将我的 WireGuard 客户端以全隧道模式连接到它，使用完毕后再运行另一条 CLI 命令将其销毁。</p>

<p>我所需做的就是将打印出的 WireGuard 配置（一次性）复制到例如我的 MacBook 的 WireGuard 客户端中，并启用它，以便将所有网络流量通过这台全新的 VPN 实例进行隧道传输。</p>
<p>你可以在我代码托管平台上托管的这个代码仓库中找到具体实现。假定你已经安装了 OpenTofu⁵ 并且拥有可用的 AWS 账号，那么它应该可以开箱即用。</p>

<p>该模块还有一个功能开关，允许我在我托管于 Njalla 的 l3x.in 区域中创建一条 CNAME DNS 解析记录，但你可以将其视作一个实现细节，并在该环节使用其他提供商，或者直接忽略这条额外的 DNS 记录而直接使用 EC2 的公开 DNS 主机名；该代码仓库更倾向于用作蓝图参考，而非放之四海皆准的现成解决方案。</p>

### [要闻：Git 2.56 版本包含 700 多个非合并提交](https://lwn.net/SubscriberLink/1094575/2385e98583715c2b/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Looking forward to Git 2.56 - and 3.0</div>

<div class="article-body" data-article-body="true"><p>Git 2.56 版本包含 700 多个非合并提交；它带来了许多不错的改进，但不会从根本上改变大多数用户的 Git 使用体验。在这方面颇具潜力的一项特性，是为（仍处于实验阶段的）git history 工具箱新增了 drop 子命令：</p>
<p>该命令将从当前分支的历史记录中移除指定的提交，并重新应用其后添加的所有提交。它为移除有问题的提交提供了一种更简便的方法。遗憾的是，如果历史记录中包含合并提交，该命令仍会拒绝工作，这导致它在许多（或大多数）代码仓库中无法使用。</p>
<p>git status 命令现在会建议运行 git pull 命令，以更新落后于其跟踪分支的本地分支。不过，即使分支落后于（尚未抓取的）远程跟踪分支，它仍然会提示该分支“已是最新”（up to date）。</p>
<p>git refs 命令用于在底层操作引用；在 2.56 版本中，它获得了若干新的子命令。这些子命令包括 create、delete、update 和 rename，对于 Git 来说可能有些出人意料——它们的功能完全正如其字面意思所示。</p>
<p>此外还有许多易用性方面的微调。git branch 新增的 --delete-merged 选项将移除已合并到对应远程跟踪分支的本地分支。如果某个分支正在用于二分查找（bisect），使用 git branch -d 尝试删除该分支将会失败，并给出有用的提示信息。锁定配置文件的尝试在失败时将进行重试，避免了多个命令同时尝试修改该文件时带来的困扰。git add 新增了 --resolved 选项，该选项仅暂存已解决合并冲突的文件。</p>
<p>除此之外，照例还有大量的错误修复、代码重构和性能提升。总的来说，2.56 看起来是一个稳健的版本，但它也显露出该项目正在为未来蓄力的迹象，将许多更重大的工作留待后续推出。这就引出了下一个问题：接下来会是什么？</p>
<p>9 月初，Git 维护者滨野纯（Junio Hamano）询问社区，下一个版本应该定为什么。是将社区一段时间以来一直在推进的 3.0 版本发布出来，为这一年画上圆满的句号？还是在 3.0 发布之前，仍需要再推出一个或多个 2.x 版本？</p>
<p>这是一个重要的问题，因为 3.0 将包含若干不向后兼容的重大改动，可能会让一些用户在升级前有所犹豫。其中，最显著的改动或许是将默认哈希函数切换为 SHA-256，而非 Git 从一开始就使用的 SHA-1 哈希。SHA-1 长期以来一直被认为安全性薄弱，这对于像 Git 这样的应用程序来说令人担忧。在 Git 仓库中，哈希值用于标识每一个对象（文件、目录树、提交），并用于验证导向任何特定节点的提交链。如果 SHA-1 能被攻破，理论上就可能被用来以难以察觉甚至无法察觉的方式篡改仓库历史。</p>
<p>Git 很早以前就已经包含了针对已知 SHA-1 攻击的防御措施，目前似乎很少有人严重担心仓库被篡改的可能性。尽管如此，转向更安全的哈希函数仍然十分必要。</p>
<p>自 2023 年发布的 2.42 版本起，Git 就已经提供了非实验性的 SHA-256 支持，不过用于与旧仓库互操作的某些粘合层耗费了更长时间。一段时间以来，阻碍 Git 开发者将 SHA-256 设为默认的最大顾虑在于各大代码托管平台的支持（或缺乏支持）。GitLab 自 2024 年起就已提供支持，Forgejo 也同样支持。然而，房间里那头依然缺席的大象是 GitHub；发布一个会创建与 GitHub 不兼容仓库的 Git 版本，是一个令人担忧的前景。目前仍不清楚 GitHub 何时会加入该支持，但值得注意的是，GitHub 员工兼 SHA-256 迁移背后的核心开发者 brian m. carlson 在回复滨野纯的问题时表示，关于该主题的消息即将公布，将下一个版本定为 3.0 可能是最佳选择。</p>
<p>话虽如此，carlson 还提出了另一项他希望在 3.0 发布前加入的改动。尽管 Git 一直将十六进制数（具体指对象 ID）作为小写字符串管理，但它也接受大写形式的 ID。这导致了两个表面上看起来不同（例如 f00f00 和 F00F00）的 ID 实际上是相同的情况。由于这种二义性，似乎已经引发了若干缺陷和安全漏洞。因此，carlson 希望更改 Git 的行为，使其仅接受小写 ID。这一改动按理说应该不会影响太多用户，但几乎可以肯定，在某些地方确实有人依赖于这种行为。</p>
<p>等待 3.0 版本的另一项重大改动是切换到“reftable”机制。Git 中的引用（通常简称为“ref”）是名称与仓库中对象之间的关联；例如分支、标签和远程跟踪分支都是引用。目前，Git（默认情况下）将每个引用作为文件存储在仓库的 .git/refs/ 目录下。如果仓库包含一个名为 foo 的分支，就会有一个文件 .git/refs/heads/foo，其中包含该分支顶端提交的 ID。此外还有一种将所有这些引用合并到单个 packed-refs 文件的机制，这能在一定程度上提高性能。</p>
<p>这种机制行之有效，但随着引用数量的增加，其效率会变得越来越低。在某些项目中，引用数量确实非常庞大。根据该项目的 reftable 文档，Android 仓库包含超过 80 万个引用。在这种规模下，查找引用或确定是否存在指向特定提交的引用，可能会成为一项开销极大的操作。拖慢开发节奏是一种令人十分烦躁的体验，进而促使人们希望对引用的存储方式进行改进。</p>
<p>Git 2.45 版本引入了 reftable，作为一种更高效的引用存储方式。它是一种针对空间效率和快速访问进行了优化的二进制文件。从那时起，用户就已经可以创建使用 reftable 而非旧有基于文件的机制的仓库，但这从未成为默认设置。切换到 reftable 对 Git 本身的用户来说应该没有任何显见的影响（除了性能提升），但对于使用访问 Git 仓库的其他软件包的用户来说，这可能会成为一个问题。carlson 在其邮件中提到了 libgit2 就是一个潜在的担忧点。</p>
<p>事实证明，libgit2 在这里不会成为阻碍；Patrick Steinhardt 透露，他已经为 libgit2 添加了 reftable 支持，并且 SHA-256 支持已在 8 月默认启用。因此，libgit2 应该已经为 Git 3.0 的过渡做好了准备。</p>

### [要闻：1996年5月，当我正在撰写我的第二篇 JavaWorld 文章《类文件的生活方式》（&quot;The Class Fi](https://www.artima.com/insidejvm/whyCAFEBABE.html)
<div class="original-title-sub"><span class="orig-tag">原文</span> Why 0xCAFEBABE?</div>

<div class="article-body" data-article-body="true"><p>1996年5月，当我正在撰写我的第二篇 JavaWorld 文章《类文件的生活方式》（&quot;The Class File Lifestyle&quot;）时，我对 Java 类文件的魔数 0xCAFEBABE 产生了好奇。每个 Java 类文件的前4个字节都被规定为 0xCAFEBABE，这是一个有助于工具快速将潜在的类文件与非类文件区分开来的魔数。出于对这个数值背后是否隐藏着某种深层含义的好奇，我在 comp.lang.java 新闻组发布了以下问题：</p>
<p>每个 Java 类文件的前4个字节都有魔数值 0xCAFEBABE。我很好奇，有人知道这个值是怎么选出来的吗？不知道的人有人想猜一猜吗？</p>
<p>我以前听过原因，但答案似乎早就从我的电子邮件归档中删除了。我也很想知道为什么。为什么？</p>
<p>好吧，他们想必得选点什么作为魔数来标识类文件，而在仅使用字母 A 到 F 的情况下，你能想到的与 Java 或咖啡相关的词汇是很有限的 :-)</p>
<p>Matthew Travis 写道：<br />好吧，文件必须以*某个*魔数（或字符串）开头，以便轻松识别为有效类文件，而不是其他东西。<br />至于为什么魔数是 3405691582 (0xCAFEBABE)，嗯，我的猜测是：(a) 32位魔数更容易处理，且更有可能是唯一的；(b) Java 团队想要一些带有 Java-咖啡隐喻的东西，由于十六进制中没有“J”或“V”，他们就折中选了带有 CAFE 的词。我猜他们觉得“CAFE BABE”比“A FAB CAFE”或“CAFE FACE”之类的更性感，而且绝对不喜欢“CAFE A FAD”（或者更糟的“A BAD CAFE”）所带来的含义。<br />（顺便说一句，他们当然远非第一批在魔数中使用十六进制数字拼写出有意义单词的人。二十多年前，Burroughs B6700 将其48位字长的“未初始化”内存初始化为 0xBADBADBADBAD。）</p>

<p>当我还是个小孩子时，我帮一位数值分析师调试程序。S/360 核心转储（core dump，还有人记得十六进制矩阵吗！）终于揪出了罪魁祸首：一个极度超出范围的浮点值。<br />前三位数字是 0xBAD。<br />我费了九牛二虎之力才让那家伙相信这纯属巧合！</p>
<p>David N. Smith 写道：<br />在需要填入容易识别的假值的地方，一个经典的（即在《新黑客词典》中被明确引用的）“伪值”是 0xDEADBEEF。</p>
<p>在缺乏内存保护的 Macintosh 上，一种流行的做法是在位置 0 填入某个魔数，这样解引用空指针或句柄时就会立即崩溃。很久以前，一位朋友出于这个目的使用了 &#39;NIL!&#39; 的 ASCII 值，但经过深思熟虑以及对 Macintosh 上真正合适数值的探索，最终找到了 0x50FFC001——这是一个完美的 Mac 崩溃值（至少有三个原因，留作给读者的思考题），但遗憾的是它并不是一个酷炫易读的值。--</p>
<p>我最初是在 NeXTSTEP 中看到使用 0xCAFEBABE 作为魔数的。NX 使用了“胖二进制”（fat binaries），本质上就是将不同平台的二进制文件打包在一个可执行文件中。如果你在 NX Intel 上运行，它就会运行 Intel 二进制文件；如果是在 HP 上，就会运行 HP 二进制文件。0xCAFEBABE 就是用来区分 Intel 还是 Motorola 二进制文件的魔数（记不清是哪一个了）。<br />看来 Sun 把它沿用过来了……</p>
<p>Vivian Man Cheng 写道：<br />我最初看到 0xCAFEBABE 是作为 NeXTSTEP 使用的魔数。<br />奇怪但千真万确……0xfeedface 用于摩托罗拉（moto），0xcafebabe 用于英特尔（intel）。不过 Sun 和 HP 呢？<br />你觉得它会被 NeXT 注册版权或商标吗？:-)</p>
<p>既然“babe”这个词基本上就是“chick”（小妞）的同义词，我怀疑你在这里找不到任何*深层*含义。当我听到“CafeBabe”时，我想到的就是一个典型的“咖啡女孩”：穿鼻环、至少有一处文身、头发染成黑色、厌恶世界、政府和父母，有一种偏哥特/病态式的吸引力。<br />但这是我的理解。它也可能是向在 Sun 的 Java 团队常去的小咖啡馆里为他们服务的女服务员致敬。或者，也许这是他们仅用 A-F 能拼出的少数词汇之一，而且在他们看来，CAFEBEEF 或 DEADCAFE 听起来远不如 CAFEBABE 顺耳。<br />谁知道呢。你可以写信问他们。</p>
<p>别忘了老式 IBM 机器出于同样的目的使用了 0xDEADBEEF。在某些圈子里（至少在那些年纪足以记住那段历史的程序员中），使用未初始化内存仍然被称为“死牛肉错误”（dead beef error）。<br />RS6000 上的 AIX 仍然使用 0xdeadbeaf 来表示未初始化的存储空间。</p>
<p>说来也怪，.class 文件的魔数早在“Java”这个名字被用来指代该语言之前很久就被选定了。我们当时在寻找某种有趣、独特且容易记住的东西。0xcafebabe 比第二顺位候选者 0xdeadbabe 更好。:-)<br />隐约指代皮爷咖啡（Peet&#39;s Coffee）可爱的咖啡师，并作为“Java”这个名字的预兆，这纯属巧合。</p>
