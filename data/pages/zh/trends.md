### [LuaRocks 2026年9月安全事件通报](https://luarocks.org/security-incident-september-2026)
<div class="original-title-sub"><span class="orig-tag">原文</span> LuaRocks Security Incident September 2026</div>

<div class="article-body" data-article-body="true"><p>2026年9月25日，我们通过CISA（网络安全与基础设施安全局）协调收到了一份关于LuaRocks.org存在远程代码执行漏洞的报告。该漏洞已于9月26日修复。在调查过程中，我们发现该漏洞在2026年7月9日至8月20日期间曾在LuaRocks.org服务器上被多次利用。</p>
<p>由于攻击者能够在服务器上运行代码，我们将该服务器可访问的所有内容均视为已被泄露。该网站已被迁移至一台新搭建的服务器上，旧服务器所持有的所有凭据均已被吊销并替换。</p>
<p>我们未发现现有软件包被修改的任何证据。我们核查的详细信息见下文。</p>
<p>Rockspec是Lua文件。当上传rockspec文件时，LuaRocks.org会在受限环境中运行它以读取软件包的名称和版本。用于加载该文件的函数既接受Lua源代码，也接受预编译的LuaJIT字节码。由于LuaJIT不对字节码进行验证，精心构造的字节码文件能够读写受限环境之外的内存，并在Web服务器内部执行任意代码。</p>
<p>修复方案将rockspec仅作为文本加载，并拒绝接收字节码。</p>
<p>我们发现了为此前创建并利用了该漏洞的三个账户：</p>
<p>Web服务器运行所使用的账户可以获得该服务器的完整管理权限，因此我们推定攻击者可以读取服务器上的所有内容，包括整个数据库。</p>
<p>由于发生了远程代码执行，我们推定机器上的所有内容均已被攻击者读取：</p>
<p>LuaRocks.org在git中保存了所有软件包的每日镜像，这为我们提供了一份首次受攻击之前的副本以供比对。</p>
<p>我们所能核查的范围存在局限。被攻击者删除的软件包与被所有者删除的软件包表现一致，且我们无法核查受影响服务器发送给客户端的具体内容。恶意rockspec文件此前也被同步到了mirror.luarocks.org以及GitHub上的公开镜像仓库中，目前均已从两处移除。</p>
<p>如果您有任何疑问，请在LuaRocks.org的问题跟踪器（issue tracker）上发起讨论，或直接发送电子邮件至leafot@gmail.com与我联系。</p>
<p>感谢报告此问题的研究人员。我们对于该问题进入了代码库且未被及早发现深表歉意。</p></div>

### [改变我世界的十行代码](https://pixelambacht.nl/2026/ten-lines-of-code/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Ten Lines Of Code That Changed My World</div>

<div class="article-body" data-article-body="true"><p>十行以某种方式对我而言意义非凡的代码。要么是因为我亲自写下了它们，要么是我曾大量抄录过它们，又或者是它们曾让我开怀大笑，亦或泪流满面。</p>
<p>我不记得自己第一次敲出这段代码是什么时候了，也不确定是否就是这个精确的版本。当时可能没有逗号，或者有更多的感叹号。</p>
<p>尽管如此，计算机还是照做了，欢快地向世界打了个招呼，尤其是向那个第一次与计算机产生交流、睁大双眼的孩子问好。</p>
<p>第二行代码让人深刻体会到：只要你发出指令，计算机就会照单全收。永远的 Hello World！</p>
<p>把这行代码复制并粘贴到你浏览器的控制台中，你将见证老派流行文化电视与极客编程幽默的跨界碰撞，外加一剂浓烈醇厚的“JavaScript 真是太蠢了”的调侃。</p>
<p>经典之作，我第一次运行它时真的是笑出了声。</p>
<p>机器语言是能达到的最接近硬件底层的语言。没有警告，没有日志，也没有任何防护栏。它甚至允许你自我修改——在代码运行时直接覆写其底层的实际字节。</p>
<p>就像这个例子一样，你在其中更新了源地址和目的地址的高位字节。分支语句从 $2000 循环到 $20FF，随后的 INC 在重新开始循环之前，将地址从 $2000 修改为 $2100。</p>
<p>（6502 处理器采用小端序，因此我们使用的是 +2 和 +5，而不是 +1 和 +4）</p>
<p>底层的极致，硬核，且略带危险性。意识到自己可以做到这一点，让人切实体会到：当你在如此接近硬件底层的地方编程时，一切皆有可能。</p>
<p>这个微型批处理脚本在 Windows 上实现了简易版的 touch 功能，从 Windows NT 到 Windows 7 期间我一直在高频使用它。我在 Total Commander 的微型 shell 中输入 touch filename.txt，就能快速生成新的空白文件。简直须臾不可或缺。</p>
<p>层叠样式界的 console.log！样式表里的 var_dump()！CSS 领域的 printf()！</p>
<p>只要把一个特定的字节写入当前计算机内存中二进制代码的恰当位置，你就能瞬间获得无限生命、无限能量或无限金钱。</p>
<p>这不仅能让你在游戏中作弊，还带来了一种震撼的认知：只要你知道在哪里 PEEK 和 POKE，任何游戏中的一切都可以被肆意操控。</p>
<p>一个有趣的故事，而对于我们这些曾经不得不埋头于无聊、漫无目的的项目的人来说，这或许是一个颇具吸引力的点子。</p>
<p>在 2000 年代前后，如果你在 Linux 上遇到问题，往往会去 IRC 寻求帮助。正是在那里，许多人找到了解决所有 Linux 问题的神奇妙方，而且答案始终如一：以 root 身份登录，然后运行 rm -rf /。</p>
<p>百试百灵，它能让每一个 Linux 问题都彻底消失！</p>
<p>那是在 90 年代初，我们的学校终于搭建了局域网，因此我那帮赛博朋克、脚本小子、菜鸟、骨灰级黑客伙伴们和我自然对其进行了一番探索。我们知道所有的用户名都由三个字母组成，而那些未启用的账户则会保留默认密码。</p>
<p>于是我们在 Borland Pascal 中捣鼓出了这个极其简陋的用户名扫描器。Bug 比代码行数还多，但它大致还能用。（按理也该如此——毕竟这可是 2.00 版本！）</p>
<p>我们开开心心地黑掉了能找到的所有休眠账户，然后……就去干别的事了。</p>
<p>一首仅用 280 个字符的 CSS 编写的动画诗篇。没有 JavaScript，甚至没有 HTML——它可以在一个仅包含一个块级元素的空白文档中运行，全凭这 280 个纯粹的 CSS 字符。</p>
<p>这个人为限制是由 Twitter 设定的，相比早期的 140 字符限制有所放宽，它允许用户发布简短的代码片段，你可以将其复制到一个空白的 CodePen 中来欣赏有趣的视觉效果。</p>
<p>我尤其对自己使用的 1e+9 持续时间感到自豪，它比 infinite（无限）还要短（无论是在时间意义上，还是在字符数量上）。</p></div>

### [逃避痛苦能让你快乐吗？](https://www.theguardian.com/books/2026/sep/27/does-avoiding-misery-make-you-happy)
<div class="original-title-sub"><span class="orig-tag">原文</span> Does avoiding misery make you happy?</div>

<div class="article-cover"><img src="https://i.guim.co.uk/img/media/28f6cc74df0276d133724551507dca147e0831a9/0_0_1530_1224/master/1530.jpg?width=140&amp;quality=85&amp;auto=format&amp;fit=max&amp;s=1b4ce720140202ee0807bedbaed03f9a" alt="逃避痛苦能让你快乐吗？" loading="lazy" /></div>

<div class="article-body" data-article-body="true"><p>这看似是一种自我保护，但结果未必如你所料。</p>
<p>在苏斯博士的《绿鸡蛋和火腿》（Green Eggs and Ham）中，永远乐观的“我是山姆”（Sam-I-Am）整本书都在纠缠一个脾气暴躁、没有名字的讲述者，劝他尝尝这道与书名同名的菜肴。他不断提出一个又一个极具创意却徒劳无功的推销——在房子里吃，和老鼠一起吃，在盒子里吃，和狐狸一起吃，在火车上吃，在雨里吃——直到这位讲述者仅仅为了耳根清净而妥协，尝了这道菜，结果发现自己爱上了它。在我儿子成长的过程中，“绿鸡蛋和火腿”成了我的代名词，用来告诉他：他正在逃避某些只要他愿意尝试就会喜欢上的东西。</p>
<p>当然，并非每一种让我们恐惧或畏缩的经历最终都会变成美妙的惊喜。痛苦是人类生存境况中不可避免的一部分。我们无法避开它，然而人们无论如何都会拼尽全力去逃避。即便处境毫无希望，我们依然死死抓住希望不放；我们宁愿将痛苦的念头抛诸脑后，也不愿去直面它们；我们竭力想要掌控那些根本无法改变的事情；我们甚至有时会不惜自毁前程，去保护自己的自尊心免受哪怕最轻微的刺痛。这些策略有时或许能让我们暂时免于痛苦。然而，尽管它们的初衷是为了促进（或至少维持）我们的幸福，但长此以往，它们往往会带来适得其反的结果，让我们变得更加痛苦。</p></div>

<p>早在 2023 年，某些页面上的组件数量开始出现爆发式增长。这给我们现有的 CSS-in-JS 解决方案带来了一些与性能相关的挑战：</p>
<p>很明显，Primer 团队需要从源头上解决该问题。我们必须找到一种替代方案，彻底避免当前方案所带来的客户端和服务器端开销。最重要的是，我们选择的任何替代方案在迁移过程中都必须确保不会对 GitHub 造成任何破坏。</p>
<p>Primer 团队找到了一种符合我们全部标准的解决方案：CSS Modules。这种格式使我们能够实践最喜欢的事情之一：编写并使用原生 CSS 特性，同时依然保留我们以往从 CSS-in-JS 中所期望的一定程度的就近部署与样式封装。</p>
<p>借助 CSS Modules，样式可以在组件对应的 JavaScript 源文件旁以独立的 CSS 文件进行编写。它还允许我们将所有类名默认视为局部作用域，从而避免全局选择器可能带来的一些命名冲突与挑战。这种格式还消除了对任何客户端或服务器端运行时的需求。取而代之的是，样式将被打包汇总进 CSS 样式表中，作为页面 HTML 的一部分进行下发。</p>
<p>然而，这一方案与我们当时采用的 CSS-in-JS 方案截然不同。这一变更需要对每一个 Primer 组件以及 GitHub 中使用该技术编写的每一个组件进行更新。值得庆幸的是，设计系统正是大规模交付此类变更的绝佳载体。</p>

<p>值得注意的是，尽管设计系统本身已正式脱离 styled-components，但 GitHub 代码库本身的很大一部分尚未脱离。由于 sx 属性多年来一直是 GitHub 事实上的样式标准，我们面临着数以千计需要迁移的 sx 属性，之后才谈得上让 GitHub 用上全新且不依赖 styled-components 的 @primer/react 版本。</p>
<p>那么……我们究竟是如何在提升确定性并降低风险的同时，完成这一庞大工作量的呢？答案是：切忌一蹴而就。</p>
<p>最初的 CSS 迁移比我们之前透露的要更为微妙：除了将组件迁移到 CSS Modules、利用特性开关在生产环境中进行测试并逐步灰度推广之外，我们还在一个名为 @primer/styled-react 的过渡库中创建了“包装器（wrapper）”组件。该软件包的全部目的就是允许在刚完成迁移的组件中继续使用 sx。这样一来，GitHub UI 代码库中使用该属性的实例可以通过从 @primer/styled-react 导入同一组件来继续使用它们；而对于未使用该属性的场景，我们则可以通过直接从 @primer/react 导入来收获性能红利。</p>

<p>这项工作于 2025 年 4 月正式启动，待迁移的 sx 属性峰值约为 7,760 个；直到 2026 年 5 月我们才彻底实现目标。起初，我们优秀的内部开发者之一 Ian Sanders 创建了一个 VS Code 插件来辅助逐个属性的迁移。内部还开发了类似的 codemod 工具，并将其用于迁移 GitHub 代码库中的整个文件。这项工作虽然需要少量人工核查和细致验证，但绝大部分已实现自动化。由 8 名工程师轮值组成的团队在 6 个月内迁移了 6,419 个属性，观察到服务端渲染（SSR）时间性能提升在不同页面中从 1% 到 22% 不等。</p>

<p>GitHub 支持七种不同的主题，所有主题都提供了高对比度模式变体。正如你所猜想的，这一切全部是通过 styled-components 实现的。在考虑移除这些依赖之前，我们必须先对主题系统进行解耦。</p>
<p>不过，这并没有听起来那么严重。我们的主题变量一直是通过 @primer/css 软件包在 CSS 中定义的，而且在 2025 年末迁移 @primer/react 时，我们就已经为非 styled 的主题化方案做好了规划。我们需要移除的，其实是 styled-components 所支持的 JavaScript 用法和实用工具。我们再一次投入到了工作中。</p>

<p>截至 2026 年 6 月，GitHub 已经完全在 100% 的 CSS 模块（CSS Modules）上运行。我们设立的安全保障措施使我们能够安全地推出重大的架构变革、在生产环境中进行压力测试、捕获错误、高效调整并修复，最终让我们达成了目标，并在整个过程中实现了巨大的性能提升。</p>

### [在 p5.js 中讲授 GPU 编程：现已支持计算着色器](https://www.davepagurek.com/blog/p5-compute-shaders/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Teaching GPU programming in p5.js: now with compute shaders</div>

<div class="article-body" data-article-body="true"><p>计算机图形学教育目前正处于一个尴尬的境地。计算机的图形处理能力已经实现了巨大的飞跃。在当前阶段，甚至很难单纯去谈论“图形”能力：你的图形处理器（GPU）已不再仅仅是把三角形推送到屏幕上；它已经成为一个通用并行计算平台。这对于拓展可能性来说固然极为出色！但有如此之多潜在的内容需要学习，你该如何入门？</p>
<p>要在 GPU 上进行任何编程，通常都需要大量的背景知识储备，这使得它的入门门槛高得出了名。在 Vulkan 中从零开始渲染一个三角形需要成千上万行代码。这是目前讲授计算机图形学的教授们正苦苦思索应对的问题。逐渐形成的一种通用做法是不要一开始就讲授全部内容，而是提供一个内置模板供人操作，隐藏掉那些初期与学习无关的细节。随着学生了解的内容逐渐深入，可以逐步撤去“脚手架”，让他们逐渐了解那些最初隐藏的部分。但最重要的一点在于，这些隐藏的细节对于取得即时的初步进展并非必需。这种教学技巧被称为脚手架式学习（scaffolded learning）。</p>
<p>目前，大家都在各自摸索该采用怎样的脚手架。脚手架通常会抽象掉许多底层的图形 API，但依然保留了大部分“经典”的着色器管线（shader pipeline）：学生仍需要学习数据如何从顶点着色器流向片元着色器、数据如何从 CPU 传递到 GPU，以及如何用一门全新的语言编写着色器代码。尽管比起完全从头开始这已经有所简化，但要想跨入这道门槛依然负担沉重。</p>
<p>我参与了 p5.js 的开发。它除了是艺术家们的工具外，还经常被用作计算机科学的教学工具，能非常方便地将逻辑可视化。以往这主要是在其 2D 模式下进行的，因此入门级 3D 和 GPU 教学往往更倾向于使用诸如 three.js 等工具。在过去的几年里，我一直在努力填补 p5 在 GPU 方面的空白。</p>
<p>在今年早些时候发布了 p5.js 的实验性 WebGPU 构建版本、在性能上做了些优化并修复了大量 Bug 之后，我终于能够着手实现计算着色器（compute shaders）了。这最后一块拼图让 p5 距离成为我所期望的 GPU 学习系统又近了一大步。那么，让我们来聊聊它究竟是什么样子的吧！</p>
<p>我们的着色器系统 p5.strands 逐渐确立的目标，是提供这样一种脚手架：如果你以前编写过 p5.js 的作品（sketch），并且熟悉诸如 p5 官网上的“p5.js 入门”系列教程，那么你就应该能轻松迈出 GPU 编程的第一步。无论处于何种技能水平，你都应该始终能够有所产出并做出有趣的东西，而且你所学到的每一块递进知识，都能帮助你在原有能力的基础上解锁一项具体的新功能。虽然抽象可以起到简化的作用，但绝不能产生误导；你绝不需要为了日后从 p5 转向更面向工程的系统而强行摒弃任何坏习惯。话说回来，p5 绝不应该仅仅是一个学习工具：其抽象层应当足够便捷和直观，以至于无论你的技能水平如何，你都会愿意使用它们，直到你的项目规模和体量大到变成了一个更庞大的工程项目为止。</p>

<p>该 API 经过了细致的更新，因此你无需掌握更多内容即可开始。你一开始完全不需要了解着色器管线、uniform 变量、varying 变量或类似的概念。你最终依然会学到这些东西！但它们不再像以前那样被强制要求提前掌握；在真正需要它们之前，它们都不会来干扰你。</p>
<p>在熟悉了 filter(BLUR) 等现有 p5 滤镜后，创建属于自己的滤镜就绝非什么难事了。它涉及创建一个函数、使用数组，以及操作对象的属性和方法。最需要学习的重点是特殊的 filterColor 对象，你可以通过 .set() 为其设置颜色。下面是一个将画布变红的滤镜！虽然还不算复杂，但你可以看到颜色取值范围在 0 到 1 之间。</p>
<p>filterColor 还有一个名为 texCoord 的属性，用来表示你当前处于画布纹理的哪个坐标上。极为方便的是，它在两个轴向上的取值也都是 0 到 1，因此你可以轻松地将其直观展示为一种颜色。所生成的渐变效果生动说明了该函数是如何以不同的输入在每个像素上运行的。</p>
<p>你可以通过将这些坐标传入 noise() 来探索生成式纹理。当然，如果你想了解其底层运作原理，也可以自己编写噪声函数。但这是一个非常实用且高效的结构，而且在 p5 的其他部分中大家已经对其十分熟悉了。</p>

<p>但并非所有类型的运动都能由 noise()、sin() 或其他预定函数来驱动。如果我想把点放置在一堆特定位置上呢？或者如果每个粒子都需要独立运动呢？例如，可以参考《代码本色》（Nature of Code）中关于自主智能体（autonomous agents）的章节，里面有很多非常酷的技术！</p>

<p>当你在存储缓冲区中有了数据之后，下一个顺理成章的问题就是如何更新这些数据以让粒子运动。这就是实现《代码本色》中所描述的智能体的方式。交互是通过每一帧如何逐步更新状态来描述的，而不是依赖于在给定时间下计算确切位置的现成公式。</p>
<p>通常这会通过 for 循环来完成，但有了 WebGPU，你现在可以使用 buildComputeShader 配合计算着色器（compute shader）来实现。计算着色器类似于 for 循环，但它并不是按顺序一次执行一个迭代，而是同时并行运行所有迭代——这需要特定的硬件（即你的 GPU）来完成。</p>
<p>为了进行对比，这里有一段不使用计算着色器、仅使用普通 for 循环让一堆球在画布边缘反弹的代码。稍后，我们将展示在计算着色器中这是如何实现的。</p>
<p>现在来看计算着色器的版本。我们使用的是存储缓冲区，而不再仅仅是一个普通数组。更新函数现在只执行循环中的单次迭代，并使用 index.x 来跟踪当前迭代。绘制所有粒子也是通过着色器配合 instanceID() 一次性完成的。你只需调用 compute() 并传入你的着色器即可运行更新。</p>
<p>计算着色器之所以强大有趣，是因为大致来说，在普通 for 循环通常只能运行单次迭代的时间里，它可以在成千上万个对象上并发运行循环。这意味着你可以执行一些通常需要极高算法复杂度才能快速运行的操作。想让所有的球互相碰撞反弹吗？在常规 JavaScript 中，双重嵌套 for 循环的方式可能会变得很慢。但在 WebGPU 计算着色器中完全没问题。为了好玩，我还为它们设置了不同的大小半径。</p>

<p>我希望到了那个阶段，你能够掌握足够的知识，毫不畏惧地跨入所需的任何其他 GPU 库或硬件平台。你仍然会有一些新东西需要学习，但届时摆在你面前的将不再是堆积如山的新概念；相反，这只是一个了解新系统如何处理你早已掌握的那些概念的过程。</p>
