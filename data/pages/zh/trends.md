<div class="article-body" data-article-body="true"><p>“为了安全，切勿点击可疑链接”<br />攻击者所需要做的，只是写一个带有密码输入框和公司Logo的网页。URL根本无关紧要，因为用户早就学会了忽略它。<br />我承认URL并不是最直观的东西，因为其阅读方向是交替变化的。主机名和协议方案从具体走向宽泛，而路径的逻辑则正好相反：<br />由于这种语法的存在，关键部分（二级域名）落在了URL的中间。这是必须向非技术用户普及的内容：仅仅告诫他们“避开可疑链接”是远远不够的。<br />然而，如果主机名本身无法作为可靠的指示指标，那么这一切努力都将徒劳无功。<br />为了让用户有机会识别骗局……<br />机构“必须”（MUST）使用单一、广为人知的根域名。内部服务“必须”（MUST）置于该根域名的子域名之下，“绝不可”（MUST NOT）使用如下URL：<br />通过电子邮件或短信发送的链接“必须”（MUST）属于该可识别的域名。如果确实有绝对必要将用户引导至其他地方，请创建本地重定向或链接：<br />这并不意味着所有内容都必须由该机构亲自托管：许多服务支持自定义域名，并且链接是免费的。<br />该规则同样适用于电话号码：切勿发送短信或邮件让用户“拨打 0491-570-006”，因为用户根本无法确认这不是诈骗。联系方式“必须”（MUST）在原始信息所链接的网页上提供。<br />本文档中的关键用词“必须”（MUST）、“绝不可”（MUST NOT）、“必要”（REQUIRED）、“应当”（SHALL）、“应当不”（SHALL NOT）、“应该”（SHOULD）、“应该不”（SHOULD NOT）、“推荐”（RECOMMENDED）、“可以”（MAY）以及“可选”（OPTIONAL）均应按照 RFC 2119 中的说明进行解释……<br />主机名混乱的现状已经恶化到了这种地步：我甚至见过有人争论说子域名的存在本身就是一个问题，因为这让犯罪分子能够在缺乏监管的情况下随意冒充任何人。<br />DNS是一个分层系统，其结构40多年来未曾改变：<br />对于究竟是谁在运营某个特定网站，本应绝无混淆的可能……然而，现实中竭尽全力让正规合法网站看起来与诈骗网站无异，却反倒成了标准操作。<br />（甚至连政府机构都未能始终如一地使用为其分配的顶级域名）</p></div>

### [Rust 已成为微软的一级支持语言](https://rustfoundation.org/media/guest-post-rust-is-tier-1-language-at-microsoft/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Rust Is Tier-1 Language at Microsoft</div>

<div class="article-body" data-article-body="true"><p>&gt;&gt; 帮助资助 Rust 背后的维护者</p>
<p>如今，Rust 对微软具有战略重要性已不再是什么新闻。从 Azure 首席技术官 Mark Russinovich 阐述我们未来原生代码战略时提出的宏伟使命声明，到随后几年微软为支持 Rust 项目投入的数百万美元，皆证明了这一点。观看 Mark 在去年 RustConf 上的主题演讲，即可一览我们部分由 Rust 驱动的核心项目。</p>
<p>如今，Rust 与 C++、C# 和 TypeScript 并列，成为微软内部开发支持度最高的语言之一。Rust 获得的这种“一级支持语言（Tier-1 language）”工程地位，意味着内部团队拥有了一条从本地开发到生产环境的平坦坦途：安全的工具链构建、高效的开发者工具、优质的工作流、深度平台集成，以及完全契合微软软件必须满足的安全开发生命周期（SDL）要求。</p>
<p>Windows 平台和 MSVC 已经共同演进数十年，因为 C 和 C++ 一直是我们开发平台的基石。随着 MSVC 和 Windows 不断推出创新技术，我们必须确保这些特性与功能同时适用于 C++ 和 Rust，并且两者之间具备无缝的互操作性。</p>
<p>MSVC 是 Windows 的原生平台编译器，随着 Rust 在微软内部的应用范围不断扩大（从固件和驱动程序、内核和虚拟机监控程序，到微服务和各类应用），Rust 需要充分融入这一生态系统。这在 Rust/C++ 混合项目中显得尤为关键。为实现这一目标，我们最重要的投入之一就是 rustc_codegen_utc。</p>
<p>rustc_codegen_utc 是 rustc 的替代代码生成后端，与 rustc_codegen_llvm、rustc_codegen_gcc 以及 rustc_codegen_cranelift 属于同一架构家族。它接入了相同的后端接口，将 rustc 共享的编译器机制连接至 MSVC 后端（又称“UTC”）。</p>
<p>它融入了一项更为宏大的平台生态战略，以支持：</p>
<p>这些能力与工作流依托 MSVC 技术栈历经多年构建而成。将 rustc 连接到该后端，能让 Rust 直接复用相同的平台技术投入，获得开箱即用的完美兼容性，而无需为每一项 Windows 特有功能单独进行平行实现。</p>
<p>其成果是为 Windows 上的 Rust 和 C++ 带来了一个统一的代码生成平台。</p>
<p>微软的生产级软件需要经过广泛的安全和质量工作流检验。尽管 Rust 在微软已晋升为一级支持语言，但经过数十年的积累，C++ 仍然占据主导地位。采用统一的代码生成平台将使我们的维护和演进成本降至最低。MSVC 和 Windows 仍在持续创新，新的代码生成能力、安全特性、诊断机制和服务技术始终在不断加入。</p>
<p>借助 rustc_codegen_utc，这些技术投入能够同时赋能 C++ 和 Rust 共享的通用基础。这在运维层面意义重大，因为它减少了重复的工程建设；在战略层面同样至关重要：Rust 从而可以直接融入微软的原生 Windows 工程生态系统。</p>
<p>这对于 Rust/C++ 混合项目尤为宝贵，且未来许多系统仍将长年并用这两种语言。共享后端为这些系统中的两端代码平等参与所有开发流程奠定了基础。</p>
<p>这一工程协同是 rustc_codegen_utc 存在的主要原因之一。它让 Rust 能够满足微软团队现已用于构建、验证、诊断和维护 Windows 软件的环境所提出的工程预期。</p>
<p>在其他平台上，如果一个 Rust/C++ 混合项目使用 Clang 构建其 C++ 代码，两种语言已经能够接入相同的 LLVM 代码生成平台。而对于以 MSVC 为原生平台编译器的 Windows 原生 C++ 项目，rustc_codegen_utc 则创造了相同的共享后端契机。</p>
<p>代码生成、平台特性、ABI、异常处理（EH）和链接后工具链，仅是互操作性挑战的一半。高保真的语言级互操作、FFI 契约、绑定、语言语义差异……以及构建系统，都只是我们正在内部以及整个行业范围内着手解决的部分问题。请参阅 Rust 基金会的“互操作性倡议”，快速了解该问题领域及社区当前正在推进的各项工作：https://rustfoundation.org/interop-initiative/</p>
<p>作为微软开发者部门（DevDiv）专属团队的一项重大投入，rustc_codegen_utc 自 2026 年初起就已具备生产可用性。它自 Rust 1.90 起便实现了自举（self-hosted），并且是更广泛的微软内部 Rust 平台的一部分。该平台涵盖了 rustc 的安全供应链构建、标准库、关联工具，以及与本地开发、生产流水线和我们工程系统中常见质量与合规工作流的深度集成。</p>
<p>如今已有超过 100 个微软项目代码库使用它进行构建。随着更多代码库的采纳，这一推广部署每周都在持续拓展。</p>
<p>这是微软对 Rust 整个工程生命周期持续投入的一部分：包括获取、工具链、质量、安全、平台集成、生产部署以及长期支持。</p>
<p>rustc_codegen_utc 是这一历程中的重要组成部分。它的独特优势很简单：它将 rustc 与微软数十年来围绕 Windows 构建的原生后端及平台生态系统紧密连接在一起。</p>
<p>这为 Rust 和 C++ 提供了统一的基础，为 Windows 平台技术投入惠及两种语言开辟了通路，也为微软将继续构建的原生混合系统奠定了更加坚实的基础。</p>
<p>如果您想向我们提问或分享反馈，欢迎加入 Rust 项目 Zulip 上的专门讨论主题。</p>

### [Guix-Science 首次版本发布公告](https://hpc.guix.info/blog/2026/09/guix-science-first-release/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Announcing the first Guix-Science release</div>

<div class="article-body" data-article-body="true"><p>我们很高兴地宣布 Guix-Science 频道的首个发布版本：v20260907。</p>
<p>这是来自 Guix-Science 项目的专属 Guix 频道。该频道提供了一个全面、由社区驱动的科学软件目录，适用于全球科学界。</p>
<p>随着 Guix 在科研场景中的使用日益增加，对科研与教学领域所用软件进行打包的需求也随之增长。尽管 Guix 项目鼓励用户向 Guix 主频道贡献软件包，但有些软件包由于不符合 Guix 的打包规范，或者因为专业性过强而在高性能计算（HPC）之外的场景鲜有使用，因而无法纳入主频道。Guix-Science 频道采用了比 Guix 主频道更宽容的策略，尤其是在使用预构建组件方面。此外，它对弃用淘汰的策略也比 Guix 本身更为宽松。</p>
<p>Guix-Science 频道由一线科研工作者维护，并服务于广大科研工作者。我们将该频道视为涵盖广泛领域的科学软件包核心枢纽，这使得社区能够共同分担打包与维护工作。我们鼓励您参与到频道的开发中来。此外，一旦软件包被纳入 Guix-Science，我们的基础设施就会为其构建二进制替代包（substitutes），并向所有人公开提供。</p>
<p>Guix 采用滚动发布模式。这意味着一旦软件包合并入 master 分支，用户便能收到更新。因此，Guix-Science 频道也遵循同样的模式。得益于 guix time-machine 命令，用户不必担心频道更新会破坏其现有环境。该机制允许用户锁定自己的频道版本，从而掌控何时更新其环境。</p>

<div class="original-title-sub"><span class="orig-tag">原文</span> Decoding the NEC V20 Microcode</div>

<div class="article-body" data-article-body="true"><p>reenigne在2020年对8088微码的解码，为实现8088 CPU的极高精度仿真打开了大门。</p>
<p>尽管我已经在MartyPC中添加了对NEC V20的支持，但从V20的实际时序来看，该V20核心并未达到时钟周期级精确（cycle-accurate）。它不过是披着V20外衣的8088——只是将我的8088核心复制粘贴过来，并附加了V20指令。</p>
<p>这并不理想，但在没有微码的情况下，要使我的V20核心达到周期级精准，前景似乎是一场令人气馁、不断试错的苦旅。</p>

### [撕裂社区：Bevy 的六周岁生日](https://blog.fallible.net/it-breaks-a-village/)
<div class="original-title-sub"><span class="orig-tag">原文</span> It Breaks a Village: Bevy&#39;s 6th Birthday</div>

<div class="article-body" data-article-body="true"><p>这篇文章与我所有的文章一样，均由我本人撰写。它源于我与许多人的大量交流和反思。文章篇幅很长。我向你保证，完整且抱持开放心态地通读全文、而不是仅仅做摘要或只看小标题，是有其价值所在的。</p>
<p>此处陈述的观点仅代表我自己，不代表任何与我有关联的个人、组织或公司。</p>
<p>感谢 Bevy 社区中所有就此话题与我交流过的人。</p>
<p>（去年回顾：《GiGF 与 Bevy 的五周岁生日》）</p>
<p>今年初夏，Bevy 游戏引擎经历了一连串积极的发展。随着 0.19 版本的发布，BSN 宏终于完成合并。我们拥有了声明式数据模型，UI 现在变得切实可用。真正的美术工具的基础也已具备。这是一项里程碑式的成就。</p>
<p>与此同时，Rustweek 2026 是我在线下与技术人员交流中最美好的一次体验，我结识了许多优秀的人，在白天和夜晚都进行了精彩的对话。我没有经历过任何不快，我遇到的每一个人都让人乐于交谈和相处，我很想再次与他们共度时光。</p>
<p>然而从那以后，事情开始变得棘手起来。</p>
<p>过去几个月我一直在重构插件 API（Plugins API）。其目的是重新构建插件系统，使依赖关系成为可能，并让未来的工具更加强大。这一设计最终可能会被引擎采纳，也可能不会，但我正在努力论证这是一个不错的方案。等我写出正式的相关文章后，我会发布在我的技术博客上。我做这件事的动机已发布在其他地方，但我很快会再次发文详述。</p>
<p>在过去的 5 周里，这项工作几乎完全搁置了，因为眼下尝试编写与 Bevy 相关的代码会让我感到极度反胃。胃里翻江倒海，想吐。我的脑海中忍不住一直在翻腾：在当下的时间节点上，作为一名开源贡献者到底意味着什么。</p>
<p>在这一具体感受上，我也许是孤独的，但在“眼下为 Bevy 做贡献感觉糟糕透顶”这一点上，我绝非形单影只。</p>
<p>注：过去几天里讨论有所增加，这可能会让人觉得我是在就最近的事态发表评论，但本文中提到的大多数论点在数周前就已初步罗列并起草完毕。</p>
<p>Bevy 最近采纳了一项新的“AI”政策1，（按声明的初衷）该政策比以往略微宽松一些。从字面上看它没什么问题。但问题出在其制定的背景上。</p>
<p>出台该新政策的陈述理由是，我们对人们使用大语言模型（LLM）需要采取“现实”态度，而且此前的政策“无法执行”。文中引用了一些例子，指出某些人的个人资料和拉取请求（PR）未能通过直觉审查（sniff test），但当唯一的证据只是某种特定的代码异味，或是一个私密/可疑的 GitHub 个人主页时，根本无法确凿证实。</p>
<p>从这个角度来看，举证责任不公地落在了“指控者”身上，而不是“被指控者”身上。这与许多司法系统如出一辙，但拒绝一个 PR 并不等同于监禁、罚款或死刑。这只是一种轻微的社交后果，相当于对爱丁堡边缘艺术节上分发演出传单的人，或是发放当地奇怪宗教派别宣传册的人说一声“不用了，谢谢”。</p>
<p>这项政策在向公众开放“辩论”和修改期之前，大部分内容就已经在主题专家（SME）和其他相关方之间提前敲定了。在此期间，许多 LLM 爱好者开始公开幻想更宽松的政策，以及一旦完全允许自主智能体（agentic）模式后他们打算怎么做。与此同时，几乎所有反对使用“AI”的论点都或多或少被弃置一旁或置之不理。自该政策合并以来，这一势头就像齿轮卡紧般不断推进，难以逆转。</p>
<p>这种经历就像是目睹一把刀硬生生切入并撕裂了 Bevy 项目的社交肌理。</p>
<p>关于这项新政策，最公开的大张旗鼓宣传出现在《Bevy 六周岁生日》那篇文章中——如果你不算 Discord 讨论的话。公开且如此高调地写下这些，我心里五味杂陈。但如果我想让 Bevy 继续成为一个我能够使用并为之贡献的项目，我觉得自己别无选择。</p>
<p>在持续的网络挑衅（trolling）和相互冲突的社区价值观重压之下，社区凝聚力已然分崩离析。</p>
<p>“AI”议题被定性为值得平等待遇的对立双方。这与其实际背景相冲突——这里的背景是一个作为创作工具的游戏引擎，人们（包括我自己在内）投入了多年的生命去学习、讨论和推广它，寄望于 Rust 能为艺术家/游戏开发者提供坚实的土壤。与近期那些声音越来越大但投入甚浅的 LLM 爱好者相比，这种背景直到对话后期才得到承认。而承认并不意味着会对“AI”政策做出实质性的改变。</p>
<p>此前 LLM 政策的所谓“无法执行性”，在很大程度上读起来更像是一种托词，而非合理的修改理由。现行的 LLM 政策即便没有被视为废纸，也最多被看作是暂时的或容易妥协退让的，大家的假设是未来还会出台下一版更宽松的 LLM 政策，那么为什么还要信任它呢？当人们已经在漠视其边界时，又为何要信任它呢？</p>
<p>此外，Bevy 先前的政策为那些在日常工作或人际关系中不得不应付“AI”吹鼓手、LLM 爱好者和“AI”强制使用要求的人们提供了一个避风港2。这种自上而下的文化转变在更深层次上打破了人们的信任，其破坏程度远未被充分正视。</p>
<p>人们的立场被单纯视作“猎巫”和骚扰活动的前奏。没有人相信我们的立场是出于善意，反而认为我们只会以威胁存续的方式进行宣泄，既不“正视现实”，也没有“真正的论据”。这种现象甚至蔓延到了仅仅询问一个 PR 是否为 LLM 生成的产物都会遭到抵制的地步，尽管信息披露本就是现行政策的一部分。</p>
<p>这种情况对双方都造成了伤害。关于 Bevy 治理方向的私下沟通使得人们不再信任治理机制。大家感觉自己的声音未被倾听，未被尊重。社区成员也未能及时提出管理和审查方面的问题。矛盾不断累积，人们满腹怨言。大家在背后议论纷纷，进而引发了一波又一波的猜忌与普遍的不信任。</p>
<p>对于一项主要通过先向主题专家征求意见、随后才开放讨论，且“不改变对‘AI’政策态度”根本不属于备选方案的“AI”政策来说，这种结果完全在预料之中。</p>
<p>我坦诚地提出这一点，是因为我自己就一直活跃在这些所谓的“反 AI”3 私下渠道中。我深知许多人在闭门之后的真实感受。我还开设了一个“AI 戒断空间”（&#39;AI&#39;-Sober Space），作为 Bevy 项目及其使用者的替代开发空间。但这是一个几乎任何人都可以加入的开放空间，只要他们怀着善意而来即可。我们遵守与 Bevy 项目其余部分相同的行为准则，并额外提醒大家：这里不欢迎恶意挑衅。</p>
<p>Bevy 的 Discord 中设有一个“展示”（Showcase）分类，大家可以在这里发布自己的 Bevy 项目，包括游戏更新、crate 库、开发日志和教程。</p>
<p>然而，#showcase 频道如今已不再值得一看；如果你看重个人的成长与学习胜过最终产物，那这里甚至会让人感到沮丧。其中相当大比例的帖子都是关于“AI”驱动的项目。一个原本大家互相激励、共同学习的地方，如今基本上沦为了 LLM（大语言模型）狂热爱好者的领地。</p>
<p>我们在 r/rust 和其他链接聚合论坛上也看到了类似的情况：随着大量低投入帖子的涌现，人们的热情正在减退。你无法通过审核来消除人们对某个话题的内心感受，能管制的只有他们在官方频道中发布的内容。人们在分享自己的作品时感觉更糟了，因为它们被夹杂在那些低投入、与 Bevy 缺乏深度互动的作品之间。大家也不再愿意浏览展示频道，因为那里几乎看不到倾注大量心血的作品或真实的社交互动。</p>
<p>（注：本文写于“移除表情包与闲聊”（remove memes and off-topic）讨论开始之前。自本文撰写以来，“#memes”频道已因“过于难以管理”而被移除。）</p>
<p>在“AI”政策变更的前夕，社区 Discord 增加了一项貌似保持政治中立的“禁止嘲讽”（no dunking）规则。这一规则的明确目的，就是减少在闲聊频道中发布的表达对 AI 反感的表情包数量。</p>
<p>我把这些版块都静音了，也不是常客，但这依然让我感到不适。这曾经是——且继续是——对 Bevy 以往社区规范的一种文化压制。这是单方面的政策调整，旨在让“AI”用户感觉环境“不那么敌对”。</p>
<p>这项“AI”政策本身还附带了其专属的“不得对‘AI’恶语相向”的规则。社区此前尝试自我纠正“展示区空洞化”问题的做法之一，就是在展示频道中给 LLM 项目添加“🤖”表情反应。而这一做法如今已被管理团队禁止。在 Bevy 的 Discord 中，已经不再有任何温和的集体手段来劝阻 LLM 用户发布低投入的作品。</p>
<p>这一点至关重要，因为我们通常需要向公众推销我们的游戏。</p>
<p>Bevy 从 Rust 社区整体“看重高质量作品”的文化姿态中继承了大量的社会声誉。这是人们几乎默认尊重 Rust 及其开发项目的文化基石。人们自然会觉得“有人在认真对待这件事”。但我们正处于一个声誉下滑的时期，造成这一现象的不是“永恒的九月”，而是随着 LLM 爱好者用他们的提示词“盯上”Rust，这种关联性正在不断增加。</p>
<p>在软件行业，一种奇怪的观点正在占据主导地位：认为我们的工作就像 LLM 的产出一样毫无价值。并不是说 LLM 的产出多么有价值，不，而是说我们变得和它一样没有价值。这种观点有时表现为“他们和你一样棒！”，而这在本质上主要是对所谈及的程序员的一种贬损。</p>
<p>在人们如何从文化层面看待 LLM 产出方面，软件行业是个异类。游戏引擎与软件圈子之外的人群有着千丝万缕的联系。</p>
<p>没有人会特意去在线市场上购买“AI 资产”。没有人会向“AI 艺术家”约稿或寻求合作。关注“AI 艺术”账号的人……绝大多数都是“AI”吹捧者，或者部分被热闹景象吸引的人。Steam 上的“AI”作品会立刻遭到抵制，并且这种抵制随着时间的推移愈演愈烈。</p>
<p>游戏开发者将“AI”视作负债，玩家则将“AI”产出看作换皮粗制滥造的虚幻产物（asset-flip vapourware）。当人们听说某个项目中包含“AI”时，很多人便会失去对该项目的信任。即使这“仅仅”是代码，情况也是如此。它被视为一种推卸责任的行为，一种放弃付诸用心的表现。</p>
<p>无论模型有多大“改进”，人们总能敏锐地察觉出视频、文字和图像中的“AI”痕迹。这是人类从现实世界中过滤信息的刚需。“AI 产出”是噪音，而不是信号；要想在互联网这样的中介层上建立人与人之间的连接，你就必须能够迅速过滤掉噪音。</p>
<p>我们看到的倡导使用 LLM 的主要论调是“它确实管用”。这一点值得商榷，不过如果你觉得毋庸置疑，可以直接跳到下下段；此外，确认偏误可能会让人觉得它的效果远超实际情况。我既不天真，也不是原教旨主义者，我亲自接触过这些机器以了解它们的能力。但我并没有感到惊艳。我认识一些被迫使用这些机器的人⁴，他们同样不觉得有什么了不起。</p>
<p>这些模型固有的随机性⁵使得所谓的“幻觉”⁶成为一个棘手的问题。但狂热的信徒们却以为自己无需为此担忧，坚信人们会去审查这些代码——即便人们根本没有足够的心力去仔细、全面地理解“AI”的产出，而且他们可能也没有足够的时间。</p>
<p>这种“它管用”的定调本身就存在问题，因为它把一个复杂的系统（游戏引擎的开发、使用和维护）当成仅仅由“概念输入”和“代码输出”构成的单元拼凑而成。这种说法很容易被接受，因为它契合了我们对代码的固有认知。这也是组织及其内部成员在榨取性压力下久而久之容易形成的思维方式。这是一种抽象。</p>
<p>这种定调所忽视的，是它对参与项目的“人”所造成的伤害。拥抱这些 LLM 的人被鼓励将不使用它们的人视为盲目的卢德派⁷或讨厌的清教徒。而那些不使用这些机器的人（或被迫使用但内心抗拒的人，这部分人在“AI 用户”中占了很大比例）则感到沮丧、丧失动力并被贬低。一种个人毫无价值的感觉油然而生，并且由于生产公式中社交属性的缺失，这种感觉还在被推波助澜。</p>
<p>“AI”吹捧者与不愿使用 LLM 的人之间的博弈并非处于平等的地位。在一个希望保持“AI 节制”（AI Sober）的空间里大肆吹捧“AI”是具有破坏性和敌意的；明知故犯更是挑衅或彻头彻尾的恶意网络钓鱼（trolling）。到目前为止，已经发展并传播了许多策略，其中许多都围绕着贬低和挫败被挑衅对象的士气展开。这就像诱导戒断者复吸，或诱导抑郁症患者自杀一样。故意引发情绪失控就是这种卑劣手段的企图。</p>

### [SystemIO 冲突并非固件 Bug](https://codon.org.uk/~mjg59/blog/p/systemio-conflicts-are-not-firmware-bugs/)
<div class="original-title-sub"><span class="orig-tag">原文</span> SystemIO conflicts are not firmware bugs</div>

<div class="article-body" data-article-body="true"><p>我本来在查一些完全不相干的内容，却无意中看到了一些搜索结果，让我意识到很多人至今仍以为像“ACPI Warning: SystemIO range 0x0000000000001828-0x000000000000182F conflicts with OpRegion 0x0000000000001800-0x000000000000187F”这样的报错意味着固件存在 bug。通常这并非事实。我们需要深入探讨一下 ACPI 到底是什么，来解释其中的原因。</p>
<p>高级配置与电源接口（ACPI）¹ 规范定义了大量内容，但与我们这里相关的主要是它所实现的硬件抽象。尽管名义上 PC 是一套规范明确的平台，但一旦复杂度超过一定限度，在硬件层面上就并非如此了。举例来说，当系统挂起时，你需要按正确的顺序关闭硬件电源，而要知晓该顺序，就必须了解特定主板设计的细节。嵌入式领域采用的方法是将这些知识以某种形式直接写入操作系统，这便诞生了设备树（Devicetree）。ACPI 则采取了另一种方法——它并没有将这些信息作为供操作系统驱动读取的数据来提供，而是以代码的形式进行分发。</p>
<p>每个方法都会获取一把锁（最多等待 0xffff 毫秒，若未获取到则报错退出），然后执行访问操作。这样一来就不可能发生竞态了。松了一口气！</p>
<p>现在假设有人为这款硬件写了一个 Linux 驱动程序。该驱动直接访问硬件，对 ACPI 一无所知。那么有什么能阻止该驱动与某个 ACPI 访问方法发生竞态吗？完全没有。噢糟糕！又来了！顺便说一句，这并非假设情景——这里有一个相对无害的例子，但过去我们确实遇到过固件和 Linux 同时访问温度监控芯片的情况，结果你以为自己在读取温度，实际上读到的却是一个状态标志位，导致读出一个不可能的高温并立即触发温控关机。</p>
<p>在这种情况下，内核通过打印类似“ACPI Warning: SystemIO range 0x0000000000000400-0x000000000000401 conflicts with OpRegion 0x0000000000000400-0x0000000000000401 (OPR1)”的信息，将你从这种（可能损坏硬件的）后果中拯救出来。该信息告诉你，内核检测到有驱动正在试图分配 IO 端口 0x400-0x401，但有一个名为 OPR1 的 ACPI 操作区域（OpRegion）声称占用了相同的地址。内核无法预知固件可能会对该区域执行何种类型的访问，因此假定这可能是危险的，并阻止该驱动加载。</p>
<p>不过事情还没到绝境！内核还会打印一些有用的建议：“ACPI: If an ACPI driver is available for this device, you should use it instead of the native driver”（如果该设备有可用的 ACPI 驱动，你应该使用它而不是原生驱动）。而且 ACPI 表中通常实际上会包含类似下面这样的定义：</p>
<p>它定义了一个 ACPI 设备及其关联方法。其中 _HID 字段定义了设备类型，可以编写一个 Linux 驱动程序，在发现类型为 VEND0001 的设备时自动加载。该驱动随后可以调用与该设备关联的 ACPI 方法，以符合固件预期的方式访问这些资源。</p>
<p>（有兴趣编写这样的驱动吗？我在 2009 年曾写过一篇指南）</p>
<p>固件在这里完全没有做错任何事²，但尝试加载原生驱动会产生报错，而互联网上的人会告诉你 PC 固件开发者能力低下³，你应该传入一个内核参数来覆盖/忽略这种行为，而且他们这样做从未遇到问题，这样做大概率也不会对你造成损害，但它确实有可能，并且你可能永远也不会知道为什么你的系统偶尔会卡死或烧毁。</p>
<p>¹ ACPI 规范以前托管在 acpi.info，遗憾的是，在 UEFI 接管该规范的管理权后的某个时间点，该网站似乎消失了。↩︎</p>
<p>² 你可能会辩称固件在运行时根本不应该做任何事，因为那不是固件的工作；我完全理解这一点，如果你愿意，当然可以用 acpi=off 启动系统，这样运行时就不会执行任何 ACPI 代码。到时候告诉我效果如何。↩︎</p>
<p>³ 我在此不对此发表意见，只是想说这并不能为该断言提供任何支持证据。↩︎</p></div>
