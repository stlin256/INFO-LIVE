<p>卡拉尼什巨石阵上空的日行迹</p>
<p>说明：如果你每天在同一时间走到室外，拍摄一张包含太阳的照片，太阳的位置会如何变化？这个问题的视觉答案便是日行迹（analemma）——即在一年之中、于同一地点、同一时间拍摄并合成的图像。本期展示的日行迹，是在英国苏格兰外赫布里底群岛的卡拉尼什村附近，每隔几天于正午时分拍摄的图像合成而成的。前景是卡拉尼什巨石阵（Callanish Stones），这是一处建于约公元前2700年（人类青铜时代）的石圈。目前尚不清楚卡拉尼什巨石阵的布局在过去或现在是否具有天文意义。此日行迹以及所有日行迹呈现“8”字形的根本原因，在于地轴的倾角以及地球绕太阳公转轨道的椭圆度。在至日（冬至或夏至）时，太阳会出现在日行迹的最顶端或最底端。这幅精选图像是在12月冬至附近拍摄的，因此太阳出现在靠近底端的位置。然而，分日（春分或秋分）对应的是日行迹的中点——而非交叉点。两天后将迎来分日（“昼夜平分”），届时整个地球各地的白天和黑夜都将等长。许多文化都会在分日庆祝季节的更迭。</p>

### [编排 Claude Code 智能体：“幕僚长”模式](https://asyncdot.com/blog/chief-of-staff-pattern-orchestrating-claude-code-sessions/)
<div class="original-title-sub"><span class="orig-tag">原文</span> Orchestrating Claude Code Agents: The Chief of Staff Pattern</div>

<div class="article-body" data-article-body="true"><p>一个会话负责协调和验证，其他会话负责执行，并通过持久化的任务看板来维护状态。这是一个适用于长时间运行的 Claude Code 智能体的“编排者-执行者”循环。</p>
<p>长周期的 AI 编程任务之所以失败，往往不是因为智能体写不出代码，而是因为它们的上下文是短暂易逝的，且它们的自我汇报并不可靠。解决办法是组织架构层面的，而非技术层面的：由一个会话负责协调和验证，由独立的会话负责执行，通过持久化的外部看板维护状态，并且在采信任何断言之前都必须重新运行验证。这种形态在业内已有共识，通常被称为“编排者-执行者”（orchestrator-worker）或“协调者-实现者-验证者”（coordinator-implementor-verifier）。“幕僚长”（Chief of Staff）只是我们对它的称谓。本文将介绍该工作闭环、使其落地的工具链，以及它旨在捕获的各种失效模式。</p>
<p>单个 AI 编程会话运行一个小时效果不错，之后便开始退化。通常会出现三类问题。</p>
<p>仅仅增加更多智能体并不能解决这个问题，反而会成倍放大问题。这样一来，你手头就有了多个不可靠的汇报者，却没有人去核实协调它们。</p>
<p>真正能解决该问题的是借鉴自人类组织的分工模式：设立一个专人，其职责不是亲自干活，而是查明真相。</p>
<p>这也正是区分原型与上线产品所依据的严谨准则。生成步骤从来都不是瓶颈，检查步骤才是。</p>
<p>“幕僚长”是我们对一种智能体编排形态的称呼。在这种模式下，一个长期存在的会话充当协调者，负责分派任务、验证断言并维护共享状态；而独立的短期会话则负责具体实现。</p>
<p>如果你想快速建立心智模型，可以把它看作是一个“集成管理员”（integration manager）。在 Git 的集成管理员工作流中，贡献者在各自的代码仓库中工作，由一名维护者拉取每一项变更，在本地测试，并决定将哪些内容合并到基准仓库中。协调者所做的正是这项工作，只是服务对象从贡献者换成了智能体会话。</p>
<p>这个名字是我们认为很贴切的一个比喻。它并不是一个既定的专有名词，你不需要对其感到面熟。其底层的架构形态早已广为人知，并有着若干正式名称。</p>
<p>它们表达的核心意思都一样：一个智能体负责规划与检查，其他智能体负责干活，而共享状态则存在于任何单一上下文窗口之外。如果你在寻找现有技术或相关先例，建议搜索那些术语，而不是搜这个词。</p>
<p>本文补充的并不是这个框架形态本身，而是下文将详述的验证准则，以及那些会导致长时间自主运行崩溃的具体失效模式。</p>
<p>“幕僚长智能体”（chief of staff agent）这个短语常被用来指代另一种东西：一个帮人管理日历、收件箱和优先级，并将工作派发给专业智能体的助手。Anthropic 的应用指南（cookbook）中就有一个专门为初创公司 CEO 构建的此类幕僚长智能体。比喻虽然相同，解决的却是不同问题。本文讨论的是编程闭环。</p>

<p>它明确不做的事情就是编写实现代码。协调者一旦开始写代码，它就会停止验证，这种模式随即就会退化回单会话过载的旧路。</p>
<p>你需要三样东西。具体的工具可以替换，但角色不可替代。</p>
<p>Claude Code 提供了会话本身：工具调用、文件编辑、Shell 访问，以及会话之间相互发送消息的能力。每个会话都有自己独立的上下文窗口，这正是关键所在。隔离是一种特性，因为一个会话的思维混乱不会污染到另一个会话。</p>

<p>Plan Desk 是一个通过 MCP 协议向智能体开放的规划看板：包含项目、目标、带有依赖关系边的任务、关联的设计文档以及评论。协调者和每一个执行会话都读写同一个看板。</p>
<p>这是人们常常跳过的组件，而跳过它正是他们的多智能体配置无法熬过漫漫长夜的原因。看板就是记忆。会话是可随用随抛的，看板则不是。</p>
<p>看板上记录的内容包括：</p>
<p>一次处理一个工作项。一次派发。一次提交。</p>
<p>如果在你开始之前检查就已经是一片绿色（通过状态），那么这项工作就证明不了任何东西。你无法分辨一个正确的实现，和一个从未真正运行的检查、一个什么都没匹配到的过滤器，或者一个断言了本已为真的测试之间的区别。</p>
<p>先运行验证器还能低成本地捕获陈旧工作。在实践中，排队等待的任务中有相当一部分实际上已经完成了——可能是在另一张卡片下构建的，或者被后来的变更淘汰了。一个本来应是红色的关卡，仅凭一条命令就返回绿色，这只耗费数秒时间，却能为你省下原本需要阅读代码以实现某些已存在功能的大把时间。</p>
<p>Git 提交历史与看板保持一一对应。每次提交的主题都标明其任务名称。三天后出现故障时，从症状到决策的排查路径仅需一条 git log 即可追溯。</p>
<p>这一部分正是将该方法论与单纯的“同时运行多个智能体”区分开来的关键。</p>
<p>当一个执行会话汇报“测试套件全绿，49项检查，零失败”时，协调者的职责是查明这是否属实。这并非因为智能体会撒谎，而是因为它们所汇报的对象与它们实际检查的对象往往是两个不同的实体。</p>
<p>一个值得铭记的典型模式是：某个会话手动将一个提交哈希（commit hash）写入了日志文件，然后使用 git cat-file 进行验证，但验证时比对的却是留在其 shell 中的短哈希，而不是它刚刚写入文件中的那串字符串。两项检查都通过了。然而该文件中包含的却是一个根本无法解析的无效哈希。检查的对象与记录的对象是两个不同的实体，而当时只测试了其中之一。</p>
<p>由此得出的一条准则：验证工件时，必须通过重新读取该工件中的值来进行验证，绝对不要去读取你自以为写入那里的变量。</p>
<p>在智能体工程（agentic engineering）中最常见的单点故障，莫过于检测工具对它并未实际完成的工作汇报成功。这种情况形态多样。</p>
<p>通用的防范策略是：每一项可能出现未匹配的检查，都必须明确报错。必须能够清晰区分出“计数为零”和“未能运行”。此外，反向断言（absence assertion）在同一次运行中需要设置正对照（positive control），因为如果什么都没运行，“没有坏事发生”就会被直接判定为通过。</p>
<p>在断定某事物不存在之前，先证明你的检测工具在它存在时能够找得到它。首先将检查指向一个已知正常的案例。一个汇报“无异常”的工具与一个已经损坏的工具，输出的内容是完全一样的。</p>
<p>会话之间可以直接通信。这条通道确实非常有用。协调者正是通过它在运行中途回答问题，执行会话也是通过它报告矛盾之处，而不是选择绕过矛盾自行其是。</p>
<p>但它还不够可靠，不能完全依赖。一条消息可能会在一个忙碌的会话后排队，或者根据接收会话的权限模式等待人工批准，甚至可能未送达就已失效。沉默并不等于赞同。</p>
<p>因此，任何必须送达的内容都要走持久化通道。</p>
<p>消息只是提醒，文件才是契约。</p>
<p>一个能带来高回报的小习惯：将持久的策略规则与临时的具体工作内容区分开来。</p>
<p>策略目录（Policy directories）承载着规范每个周期的契约，即循环机制、路由规则和标准。这些内容是长期的、经过审查的，且极少变动。一次性简报、任务上下文以及会话专属的指令则应放置在任务看板或临时暂存目录中。<br />将它们混在一起意味着六个月后，谁也分不清到底哪些文件依然具有约束力。<br />长时间的自主运行应当按照既定节奏进行汇报，而不是消失数小时后带着整墙的代码变更（diff）重新出现。<br />让时间盒（timeboxing）生效的规则是：时间间隔决定了你多长时间对外浮现汇报一次，但绝不决定工作在何处停下。当计时器在一个任务项进行到一半时到期，请先完成该项、验证它、提交它，然后再做汇报。在中途强行掐断运行，会让工作陷入最难以恢复的状态——即处于半应用状态、未经检验且根本无法被如实描述。<br />检查点（checkpoint）是一个向外展示进展的时刻，而不是权限请求。汇报一经发出，下一个任务项应在同一轮次中立即启动。如果你发现自己写下了“我还要继续吗？”，请删掉它。正在旁观的人类自然会打断你，而不在场的人类则会因为这样一个提问而导致整个运行进程被迫中断。<br />请汇报已被证实的事项，而不是尝试过的想法。没有验证结果的任务项只能算作顺延结转，而非完成。<br />这些都是小细节，但每一个细节所对应的故障模式看起来都像是由其他原因引起的。<br />务必验证新衍生的会话是否真正启动。启动器报告“已创建工作区”，并不等同于智能体已经在运行。请检查进程，并检查其工作目录：<br />在启动前立即捕获基准时间戳。若使用以“晚于上一个会话”为键的过滤器，很容易误把中间启动的无关会话纳入进来；如果那个会话具有不同的工作目录，原本正常的启动看起来就会像损坏了一样。<br />会话名称并不是你可以凭空猜测的地址。无论你给工作区起了什么名字，往往都不是消息传递层实际使用的名称。在与会话通信之前，请重新列出所有活跃会话，切勿复用你之前读取到的名称。<br />简短标识符只是展示用的前缀，而不是键。看板通常会显示截断后的 ID。将其补齐为完整长度的标识符只会产生一个格式良好却根本不存在的值。请改为通过搜索具有区分度的标签子字符串来解析它。<br />搜索标签本身，而不是你的转述。日志条目的标题通常是写入会话对自己所做工作的表述，这并不是卡片上的实际标签。搜索前者将一无所获，并被解读为“无此卡片”。<br />在共享工作树中，切勿使用光秃秃的裸 commit（bare commit）。git add 紧接着执行 git commit 会提交整个暂存区索引，包括并发会话暂存的任何内容。请使用带参数限定的提交方式（例如 git commit --），确保提交中仅包含你明确指定的内容。<br />这些额外的开销正是核心所在。你付出这些代价，换取的是信任结果的能力。<br />衡量该机制是否奏效的标准，不在于写了多少代码，而在于你是否可以在任何时刻询问“这项工作的当前状态是什么？”并得到一个真实确凿的回答。<br />当 AI 编程智能体在长期任务中表现欠佳时，人们的本能反应是去寻求更好的模型或更大的上下文窗口。这两者确实有所帮助，但都无法解决实际的制约因素——即根本无人进行校验。这也是“70% 问题”背后的症结所在，也是每一个操作生产系统却缺失回读验证步骤的智能体所面临的问题。<br />一个不写任何代码却清楚知晓真实状况的协调会话，其价值远胜于又一个执行者。这是人类组织架构中的一条老经验，事实证明它同样适用于此。<br />我们以固定价格交付生产级软件，均采用此处所述的编排与验证规范进行构建。提供完整源代码，部署至您的账户，归您所有。告诉我们您想构建什么，我们将为您评估范围、价格与时间表。</p></div>

### [疟原虫如何在应激条件下提升其传播潜能](https://phys.org/news/2026-09-malaria-parasite-boosts-transmission-potential.html)
<div class="original-title-sub"><span class="orig-tag">原文</span> How the malaria parasite boosts its transmission potential under stress conditions</div>

<div class="article-cover"><img src="https://scx1.b-cdn.net/csz/news/tmb/2026/mosquitoes.jpg" alt="疟原虫如何在应激条件下提升其传播潜能" loading="lazy" /></div>

<div class="article-body" data-article-body="true"><p>作者：巴塞罗那全球健康研究所（ISGlobal）<br />编辑：Gaby Clark，审校：Robert Egan<br />本文已根据 Science X 的编辑流程与政策进行审校。编辑在确保内容可信度的同时强调了以下属性：<br />经同行评议的出版物</p>
<p>疟原虫能够检测到宿主环境的变化，并通过增加可传播给蚊子的有性阶段形态的产生来作出反应。由巴塞罗那全球健康研究所（ISGlobal）领导的一项研究确定了这一过程背后的分子机制。该研究结果发表在《自然·微生物学》（Nature Microbiology）杂志上，解答了数十年来疟疾研究中悬而未决的重大问题之一。</p>
<p>在感染人体血液期间，恶性疟原虫（Plasmodium falciparum）面临两项相互竞争的需求：一方面，它必须通过增殖以维持感染；另一方面，一部分寄生虫必须发育为被称为配子体的有性形态，以便通过蚊子传播给其他人。决定是继续增殖还是转化为配子体，是恶性疟原虫生命周期中的关键抉择，而恶性疟原虫正是导致大多数重症疟疾病例的元凶。</p>
<p>长期以来，人们已知该寄生虫能检测宿主环境的变化，例如发热或特定营养物质的匮乏，并相应调整其配子体的产生量：当生存条件变得不利时，寄生虫投入更多资源用于向蚊子传播以感染另一位人类宿主，对其而言更有利。</p>
<p>近年来，研究人员发现了如 gdv1 和 ap2-g 等在启动配子体形成中起核心作用的调节因子。人们也已知营养匮乏等对寄生虫构成压力的应激条件会促进配子体的产生，但触发这一反应的分子机制此前仍属未知。</p>
<p>为了揭示该机制，研究团队结合了基因组学、表观基因组学、转录组学、蛋白质组学和基因工程技术。寄生虫分别暴露于三种应激条件下：营养匮乏、抗疟药物双氢青蒿素（DHA）处理，以及模拟发热过程。</p>
<p>研究人员随后分析了哪些基因被激活、哪些蛋白质丰度增加，以及染色质（调节DNA可及性的结构）的组织构象发生了怎样的变化。同样的实验也在相关调节因子经过基因修饰的寄生虫中进行。</p>
<p>“所有三种刺激都激活了相同的调控通路。它们均在 gdv1 和 ap2-g 基因中引发了类似的改变，”该研究的第一作者、ISGlobal 研究员 Elisabet Tintó 解释道。</p>
<p>研究表明，这种应激反应不仅涉及开启基因，还涉及异染色质的重组，异染色质是一种使某些基因保持沉默的 DNA 折叠包装形式。该系统还包含一套自带的内置控制机制。</p>
<p>一旦被激活，GDV1 就会触发向配子体的转化，同时诱导产生 gdv1-as（一种抑制 gdv1 活性的 RNA 分子）。这一调控反馈回路发挥着类似刹车系统的作用：它使寄生虫能够对压力作出快速反应，同时防止 GDV1 的表达活性超出必要的时间，否则这可能对寄生虫致命。</p>
<p>该研究还揭示，调节基因表达的蛋白质 AP2-HS 作为控制中枢，使寄生虫能够对不同类型的应激作出反应。它的作用至关重要：当检测到应激条件时，AP2-HS 会激活 GDV1 的表达，从而启动配子体的产生。与此同时，AP2-HS 还会激活其他应激存活机制，这表明该基因是恶性疟原虫抗逆韧性的关键因子。</p>
<p>“当我们敲除 ap2-hs 基因后，即使在发热、DHA 处理或营养匮乏等应激条件下，寄生虫也完全丧失了发育为配子体的能力。此外，极少数开始发育的配子体也未能存活，”Tintó 解释说。</p>
<p>“这项工作有助于回答一个困扰多年的问题：寄生虫如何调整其生命周期以适应不断变化的环境，并产生对其在种群水平上生存至关重要的可传播形态，”ISGlobal 的 ICREA 研究员、该研究的协调人 Alfred Cortés 说道。</p>

### [要闻：未引入任何特殊情况](https://utf-8000.jb2170.com/)
<div class="original-title-sub"><span class="orig-tag">原文</span> UTF-8000: Unlimited UTF-8</div>

<div class="article-body" data-article-body="true"><p>无限 UTF-8！ASCII ⊆ UTF-8 ⊆ UTF-8000。<br />未引入任何特殊情况。保留所有原有属性。<br />可以通过执行 `$ pipx install UTF-8000` 来试用参考实现。<br />UTF-8000 绝无统一码联盟（Unicode />用于编码单个码点的一段 UTF-8000 字节序列。<br />开始一个 UTF-8000 代码单元的第一个、也是唯一的那个字节。<br />首字节的自同步前缀对于 ASCII 而言是 0，对于多字节代码单元而言是 11。<br />该术语与“起始字节”并不同义。首字节必然是起始字节，但反之不然。正是由于这个原因，首字节有时也被称为“第一起始字节”。<br />有趣的发现：由于自同步前缀为 0，ASCII 字节的高位十六进制半字节（nibble）只能是 0、1、2、3、4、5、6、7 之一。<br />由于自同步机制，该术语与“续行字节”互斥。<br />多字节 UTF-8000 代码单元中位于首字节之后的一个字节。<br />续行字节的自同步前缀是 10，这也称为续行前缀位。<br />有趣的发现：由于自同步前缀为 10，续行字节的高位十六进制半字节只能是 8、9、A、B 之一。<br />由于自同步机制，该术语与“首字节”互斥。<br />自同步前缀<br />每个 UTF-8000 字节的最高若干位，用于指示它是首字节还是续行字节。<br />所有可能的自同步前缀构成了一棵无前缀树：<br />UTF-8 这一巧妙架构的组成部分被 UTF-8000 编码的文件的一部分时最为有用。如果我们在文件中随机跳转寻道到一个任意字节，我们可以毫无歧义地判断出：我们当前处于一个首字节，可以立即开始解码一个新的代码单元；或者我们处于一个续行字节，需要稍向后寻道一点以找到下一个首字节从而开始解码。我们既不需要处理寻道位置之前的任何字节以发现某种全局状态，也不需要了解我们所寻道到的字节的上下文；无论出现在何处，首字节始终可以明确判定为首字节，我们可以根据其自同步前缀为 0 或 11 推导得出。<br />这不仅对随机访问有用，对错误恢复也同样有用。假设我们正在解码一个易出错的 UTF-8000 字节流，每当我们遇到错误时（例如出现异常的 0xC0 字节），我们希望保持镇定并继续处理，而不是立即退出。我们可以输出 Unicode 替换字符 U+FFFD ，然后等待下一个首字节，同时丢弃在此期间遇到的所有内容。<br 1），共有 5n+1 个内容位。我们推导出该公式的过程如下：我们从 n 个空字节开始，每个字节有8位。对于每个字节，有2位被自同步前缀占用。接着，还有额外的 n-1 位被起始位占用。因此，留给内容位的位数就是 8n - 2n - (n-1) = 5n+1 位。理解该公式中数字 5 的另一种方式是：通过追加另一个后续字节，从 n-1 字节扩展到 n 字节。通过这样做，我们在后续字节中获得了6个可用位，但在更长的起始位序列中损失了1位，因此总体上我们为内容位增加了 6-1 = 5 位。<br />该术语与“起始位”（start bits）互斥。<br />这些位以青柠色高亮显示。<br />强制内容字节（Mandatory Content Byte）<br />包含一个或多个强制内容位的字节。<br />这些是在解码码元时，我们用来检查是否存在超长编码（overlong encoding）的字节。<br />强制内容位（Mandatory Content Bits）<br />码元中前0、4或5个内容位，其中必须至少包含一个 1 位，以免这些字节构成被禁止的超长编码。<br />对于 ASCII，有0个强制内容位，因此不需要进行防超长检查。这是因为 ASCII 是最小的可能码元。<br />对于2字节 UTF-8000，有4个强制内容位。这是因为从1字节 ASCII 跳到2字节 UTF-8 时，内容位从7位跃升到11位。因此，我们获得的内容位数量是 11 减 7，即4位。<br />否则，对于 n 字节 UTF-8000（其中 n &gt; ### [英语：A 还是 An](https://www.redblobgames.com/blog/2026-09-16-english-a-vs-an/)
<div class="original-title-sub"><span class="orig-tag">原文</span> English: A vs. An</div>

<div class="article-body" data-article-body="true"><p>在英语中，有一个可以置于单词前面的“不定”冠词 a。例如，a raccoon（一只浣熊）。但对于某些单词，我们会使用 an。例如，an apple（一个苹果）。</p>
<p>在程序化生成文本时，我希望有一个函数 a_or_an(&quot;apple&quot;) 能告诉我该使用哪一个冠词。这听起来似乎很简单。我们可以检查首字母是否为元音。但那意味着我们会输出 an unicorn，而不是 a unicorn。</p>
<p>实际的规则不在于书面单词是否以元音字母开头，而在于口语发音是否以元音音素开头。有些单词以元音字母开头（如 u），但发辅音音素（cmudict 标记为 Y，IPA 为 /j/）。有些单词以辅音字母开头（如 h），但发元音音素（cmudict 标记为 AW，IPA 为 /aʊ/）。</p>
<p>我很好奇这些例外情况出现的频率有多高，以及它们是否可以归类在一起，因此我花了一天时间研究数据、制作了一些可视化图表，并将结果写了下来。令我惊讶的是，在我的列表中，32,455 个单词中只有 129 个需要作为例外处理。</p>
<p>[LLM 附注：我没有使用大语言模型（LLM）来编写这其中的任何代码，但事后回想起来，我本该使用的。这是一次性用来回答特定问题的代码，不需要写得多么整洁或具备可维护性，只需要确保正确即可。这样我本可以把更多时间花在字典树（trie）简化算法上，而少花点时间在解析 cmudict 和重新学习 d3.js 上。]</p></div>

<div class="original-title-sub"><span class="orig-tag">原文</span> Trump says it’s time to rebrand AI with a new name — and he’s also creating an AI Force</div>

<div class="article-body" data-article-body="true"><p>唐纳德·特朗普总统以其特有的风格回应了近期围绕人工智能（AI）安全展开的辩论——他宣称，这些担忧是“由极左民主党人（Dumocrats）为了摧毁我们的国家而制造的一长串骗局”的一部分。</p>
<p>周六，特朗普在其社交网络Truth Social上发表了关于AI的想法，写道：“许多人认为，相对于AI或人工智能而言，‘人工智能’（Artificial Intelligence）这几个字很不准确，而且非常不贴切。”因此，他发起了一项民意调查，让粉丝投票为这项技术选出一个新名称——优越智能（Superior Intelligence）、极限智能（Extreme Intelligence）或至高智能（Supreme Intelligence）。（截至发稿时，该投票仍在进行中）</p>
<p>几个小时后，特朗普紧接着发帖声称，企图“毁灭或摧毁AI”是“众多”民主党骗局之一，类似于“通俄门、乌克兰、乌克兰、全球变暖、第一次弹劾骗局、第二次弹劾骗局、男性参加女性体育运动，[以及]全民变性”。</p>
<p>特朗普随后坚称他“绝不会袖手旁观任由这种情况发生”，并补充说，这场所谓的骗局“始于对我们数据中心的攻击，直到人们意识到这些数据中心为其所在的社区带来了多么丰厚的财富与声望”。但在他看来，在“疯狂的数据中心攻击基本上失败了”之后，批评者们现在正“直接针对AI下手”。</p>
<p>特朗普并未提供任何证据来支撑他的说法，即外界对AI和数据中心的普遍怀疑并非自发且真诚的。（共和党和民主党两党都曾对数据中心提出批评，而纽约州最近成为第一个暂停大型项目许可证的州。）</p>
<p>总统的这篇帖子也呼应了他上周末在一次高尔夫锦标赛上的言论，当时他表示自己对设置“安全护栏”持开放态度，但也坚称：“我认为有许多负面势力正在提及此事，而他们本不该提起。”</p>
<p>周六，特朗普进一步表示，他将“在这项[AI产业]成长过程中珍视它、扶持它并守护它”，但他同时也在组建一支“AI部队”（AI Force），类似于他在第一任期内建立的太空部队。</p>
<p>“为此，我将在不久的将来宣布AI‘沙皇’的人选——只有高智商人士方可申请！”他补充道。</p>

<p>近期，在一名AI研究员表示自己因担忧顶尖AI公司“切实认为它可能在本世纪末毁灭所有人”并且正在“拿我们的生命作赌注”而从Anthropic离职后，围绕AI安全的辩论愈发激烈。Anthropic首席执行官达里奥·阿莫代伊（Dario Amodei）随后发布了一项“调控前沿步伐”的计划，该计划似乎得到了OpenAI首席执行官萨姆·奥尔特曼（Sam Altman）和SpaceX首席执行官埃隆·马斯克（Elon Musk）的支持。AI行业的批评人士则指出，围绕这项技术所谓生存性威胁的诸多担忧，是在转移人们对AI更直接危害的注意力。</p>
<p>与此同时，英伟达首席执行官黄仁勋在All-In峰会（萨克斯为联合主办人之一）期间在台上与特朗普现场通话，认同总统关于AI反弹是一场“骗局”的看法，并坚称“我们绝不会让”发展放缓发生。</p>
