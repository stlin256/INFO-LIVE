托管代码的每一行最终都要经过即时编译器（JIT），所以我们就从这里开始。

在改进 .NET 性能的所有方向中，很少有哪个领域的影响范围能像即时编译器（JIT）那样深远。C#、F# 和 Visual Basic 通常首先被编译为中间语言（IL），而 JIT 最终将这些 IL 转换为 CPU 执行的机器本地指令。因此，凡是出现被优化模式的地方，JIT 的改进都能让应用程序和类库代码直接受益，通常完全不需要更改源代码或重新编译应用程序本身。哪怕只是移除一条指令，或证明某项检查是不必要的，只要该代码处于高频执行的热点路径（hot path）上，收益就会迅速累积。

作为开发者，我们钟爱抽象。抽象让我们能够编写出整洁、可复用、面向对象的代码，但我们并不希望在运行时为每一次抽象买单。当运行时证明抽象带来的影响在外部不可见时，往往就能将其“还原消解”。它可以分析虚方法调用并确定其将调用的具体方法，可以观察堆分配并识别出该对象绝不会逃逸出当前栈帧，或者分析接口类型转换并复用方法前文中已确立的类型事实。这一过程被称为“去抽象化”（deabstraction）。多年来，.NET 在这一领域持续稳步推进，在 .NET 11 中这一趋势依然延续。

这是一个性能问题。这些间接调用会带来开销，但更大的代价是失去了内联的机会。内联不仅能节省函数调用开销，更重要的是，它能让被调用方（callee）的代码享受到与调用方（caller）相同的优化，例如常量传播、死代码消除、边界检查消除、进一步的去虚化（devirtualization）等。这意味着一系列看起来无关痛痒的微小虚方法调用，在去虚化和内联之后，可以精简为寥寥数条指令，与原始源代码相比，不仅面目全非，而且执行成本大幅降低。如果没有内联，每个被调用方都是一个不透明的黑盒；而有了内联，JIT 就能看透层层代码。

作为 .NET 开发者，我们始终依赖 JIT 复杂的内联启发式算法，该算法会综合权衡被调用方的 IL 大小、被调用方执行的具体任务、方法的调用频率、常量实参带来的预期收益以及数十种其他因素。对于虚方法调用，JIT 需要知道调用的实际目标是什么；它需要进行“去虚化”（devirtualize）。在某些情况下，当 JIT 掌握确切的类型信息时，可以通过静态分析来确定这一点。例如，如果 JIT 能够证明 animal 始终是 Dog，无论是因为它刚刚通过 new Dog() 分配：

但在无法通过静态分析证明这一点的其他情况下，JIT 会求助于基于配置文件引导的优化（PGO，Profile-Guided Optimization）。PGO 听起来很高级，但在概念上其实很简单。借助“分层编译”（tiered compilation），当一个方法首次被调用时，它可以在几乎不进行任何优化的情况下被“即时”编译（这被称为 Tier 0）。JIT 可以在这次编译中加入额外的探测逻辑（可以理解为“printf 调试”），以便跟踪与代码特性相关的大量有趣信息，记录其运行时的实际情况：执行了哪些分支、虚调用点或类型转换尝试中出现的具体类型是什么等等。如果该方法被调用的次数足够多，或者循环次数足够多，运行时就会要求 JIT 生成一个新的优化版本（称为 Tier 1）。随后，该编译就可以将分析过程中收集到的所有经验教训综合考虑进去。

当然，JIT 仍然需要生成始终正确的代码。即使动态分析显示 animal 在 100% 的情况下都是 Dog，也无法保证它将来永远是 Dog；很可能前 1000 次调用传入的是 Dog，但第 1001 次调用传入的却是 Dolphin。那么 JIT 该如何运用这一分析结果呢？答案是通过生成运行时检查。针对 Dog 的执行路径可以获得直接调用，随后可能被内联；而另一条路径则保留原始的虚调用作为后备兜底方案。高性能来自于将常见情况精简到极致，而正确性则来自于对罕见情况的原样保留。

这种被称为“受保护的去虚化”（GDV，Guarded Devirtualization）的“猜测并验证”模式，在实际工作负载中带来了许多最大的吞吐量提升。它不仅适用于虚方法调度，也适用于接口调度。接口调度往往比虚方法调度还要昂贵一些，因为一个类型可以实现任意数量的接口，这意味着接口槽位并不会简单地映射到固定的虚函数表（vtable）位置。

当“去抽象化”（Deabstraction）揭示出所涉及的对象类型时，它还可以提高对象创建的效率。通常情况下，.NET 中的对象都分配在垃圾回收堆上，由垃圾回收器（GC）进行跟踪，并在不可达时被回收。堆分配通常很快，往往实际上只是移动一下指针。但是，当没有足够的空间来移动指针时，成本可能会高昂得多，包括需要触发垃圾回收。每个分配的对象实际上还会分摊所有垃圾回收的平摊成本，因为每个分配的对象最终都需要被清理。

在过去的几个 .NET 版本中，JIT 一直在逐步扩展逃逸分析（escape analysis）。其中，.NET 9 和 .NET 10 在委托和闭包、Nullable 临时变量以及小型辅助对象的栈上分配方面进行了大量投入。核心主旨在于：每一次逃逸误报——即 JIT 错误地认为对象可能逃逸而实际上并未逃逸——都意味着原本可以避免的堆分配，而我们希望逐步削减这份误报清单。在 .NET 11 中，JIT 通过多种方式对该清单进行了缩减。

借助一种名为“条件逃逸分析”（CEA，Conditional Escape Analysis）的机制，枚举器（enumerators）的逃逸分析得到了进一步改进。对 CEA 的支持是在 .NET 10 中引入的，但 .NET 11 扩展了该分析能够安全识别的模式集。现有的逃逸分析会询问：由某次分配所创建的引用是否会流向 JIT 无法再跟踪的地方（例如未知的调用）？如果会，该对象就必须保留在堆上。这种分析必然是保守的，而且在很大程度上是流不敏感的（flow-insensitive）：如果一个对象在任何一条路径上可能会被传递给接口调用，它并不会尝试去证明包含该调用的路径与包含该分配的路径是互斥的。

遗憾的是，这正是基于推测的去虚化（GDV）在优化针对 IEnumerable 的 foreach 循环时所产生的现象。如前所述，GDV 会将接口调用转化为带有两个分支的类型检查：一个是针对极可能集合类型的快速分支，另一个则是包含原始接口调用的回退（fallback）分支。沿快速分支的去虚化与内联通常会暴露集合类型的枚举器分配，而后续的枚举器保护守卫则保留了诸如 IEnumerator.MoveNext 等回退调用。现有的分析机制在检测到这些调用后，便推断局部分配的枚举器可能会发生逃逸。而条件逃逸分析（CEA）则改为记录快速路径上的分配与后续守卫所测试的局部枚举器之间的关联。如果每一次表象上的逃逸仅在类型检查失败之后才会发生，JIT 便可将该区域克隆为一个已知这些检查必然成功的热点版本。在克隆出的版本中，对象根本无法触及回退调用，因此它可以被分配在栈上，并且通常能被提升为独立的标量局部变量。原始区域则保留作为常规的慢速路径。

原文 How I Wrote a Forth (Without Knowing How)

前情提要：什么是 Forth？

在过去的几周里，我一直在编写 Forth 编程语言的一个实现。在此之前，我从未写过 Forth，在着手编写 MoonForth 之前，也并不真正知道该怎么去写一个 Forth。甚至在完成了基础架构、能够用 MoonForth 编写实际程序之后，我依然说不太清自己究竟是怎么做到的。这有几个原因。

Codeberg 上的 MoonForth

首先，我没有对开发过程做好充分的记录。其次，我认为就算记了笔记意义也不大，因为编写 Forth 的过程极其简单直接，以至于这个过程本身乏善可陈。我在这里所呈现的内容大部分源于记忆。

在权衡了各种选择并发现市面上几乎没有手把手教人编写 Forth 的优质详尽指南后，我决定遵循 Forth 圈子里的常见建议，从 JonesForth 的源代码开始入手。

JonesForth（非官方 Github 镜像）

JonesForth 是一个用 x86 汇编语言编写的 Forth。它确实能完成任务，且遍布代码的大量注释有助于解释底层逻辑的细微之处——尽管我有时觉得它稍显啰嗦。

因为我的目标是用 C 语言编写一个 Forth，所以我知道 JonesForth 的汇编语言无法直接套用到我自己的尝试中。我还发现它的解释器和编译器有些难以理解，因此在起步阶段我直接绕过了这两部分。我想，如果我在其他方面取得了足够的进展，之后便会更有动力去搞懂那些部分，并且可能会具备足够的洞察力，让后续的步骤走得更轻松。

对我来说非常有利——且确实也是部分动力来源——的一点在于：Lua 内部使用栈在函数之间传递数据。在我看来，基于 Lua 的 C API 开始编写 Forth 最容易的切入点，就是编写直接操作该栈的函数，并让这些函数充当某些 Forth 内置核心“词”（words）的实现。几个小时后，我写出了几个用于操作 Lua 栈的函数。尽管当时没有任何实际运行它们的途径，但我基本上可以假装这些就是我最早的 Forth 词。在实现重要的核心词时，我也决定只要可能就尽量使用自己已有的词。随着我开始编写更复杂的词，我自己的函数便会与对 Lua 自身 API 的调用交织在一起。甚至在运行哪怕一行代码之前，我就已经在利用这个 Forth 的雏形骨架对其进行进一步扩展了。

简单的栈操作函数就位后，编写更复杂的函数就变得更容易了。因为我所写的一切在构思上都尽可能与 Forth 自身的栈操作词直接对齐，这也意味着，尽管我对如何在此基础上构建一个 Forth 毫无头绪，但我依然能够反向应用 Forth 的“因子分解”（factoring）概念。我通读了 JonesForth 的源代码，查看了那些硬编码的词，观察它们是如何运作的，然后直接针对 Lua 的 C API 为 MoonForth 编写了我自己的实现，打算留待以后再去彻底搞懂。

最终，我恍然大悟。

C 函数可以转换为指针，而指针可以作为用户数据（user data）推入 Lua。由于 Forth 词不过是一系列其他词的集合，我可以将自定义词的定义存储为一个包含 C 函数指针的表（table）。由于 Lua 表始终是引用传递，我也可以简单地将其他词定义的表直接存储到使用它们的更深层的词中。以这种方式进行编译的另一个好处是，词的重定义可以像大多数 Forth 系统那样工作：遮蔽旧词的新词不会改变任何已经使用了旧词的已编译词。还有一个巧妙的窍门：我应该能够很轻松地在词定义中存储字符串和数字字面量。解释器只需要读取词定义中存储的每个项目的类型，就能决定如何处理它。

正是在这个时候，我开始感到惶恐——因为一旦你搞清楚了数据结构，又掌握了与该数据结构进行实际交互的手段，编写代码就会变得非常简单——我可能真的要成功了。

尽管这是一段略微令人沮丧的反复试错过程，但编写解释器并不难。当它无可避免地无法工作时，我只需要通过 print 语句跟踪程序的执行（因为我就是这种类型的开发者），然后逐个排查消除错误。在决定尝试基于 Lua 的 C API 编写 Forth 的三个工作日后，我运行了自己的第一行代码。

编译器紧随其后。没过多久，它就和解释器达成了协调一致，基于对整个体系的同一套理解协同运作。既然已经了解了“立即词”（immediate words）的概念，实现它们也变得相当容易。

随后，我研究了 JonesForth 的流程控制实现。与最酷的那些 Forth 一样，JonesForth 直接在 Forth 内部用更简单的词来实现流程控制。MoonForth 也不例外。由于无法直接访问词定义，JonesForth 用于此处的代码甚至并不特别适用于 MoonForth。但这一障碍通过编写允许后续回填分支跳转指令的词便得以轻松化解，反之其他 Forth 本来也正是这样实现流程控制的。尽管实现细节可能与 JonesForth 大相径庭，但结果是 MoonForth 现在拥有了 if/else/then 语句以及循环。正是在这一刻，我关闭了所有打开 JonesForth 源代码的浏览器标签页。我不再需要任何指导了。在一周之内，我从一个不知道怎么写 Forth 的人，走到了在自己的 Forth 中实现了核心语言特性的地步。

新千年以来写就的最著名、流传最广的 Forth 文章之一，是 Dave Gauer 撰写的 Forth 历史回顾文章。

《Forth：能够自我编写的编程语言》

在这篇回顾中，Dave 断言 Forth 就其本质而言是一种“自我编写”（writes itself）的编程语言。初读这篇文章时，我并不理解这个断言的含义。我现在明白了。只要对 Forth 的运作方式有一个模糊的概念，任何会写代码的人应该都能非常轻松地构建出一个 Forth。接下来需要构建什么始终一目了然，而且往往只需留意自己的 Forth 还缺少什么就能立刻受到启发。发现这些缺失就像尝试编写一个程序然后发现某些东西阻碍了进度一样简单。如果你知道自己遇到了什么问题，知道解决方案大概是什么样子，并且知道如何操作源数据以获得期望的结果，那么把结果编程实现就只是对已有内容进行简单扩展的事情。当这门编程语言体量很小且完全由你自己编写时，这项任务会变得令人愉悦地简单。

MoonForth 并不是将 Forth 引入 Lua 的首次尝试。

爱德华多·奥克斯（Eduardo Ochs）在 2008 年曾撰文探讨如何用 Lua 自举一个 Forth 语言。

MoonForth 并不是用 Lua 编写的。相反，它是用 C 语言编写的，并借助 Lua 的 C API 来达成目标。即便如此，MoonForth 也并非首创——此前就存在另一个名为 Luarth 的项目，似乎也是为了实现同样的目标。
GitHub 上的 aabacchus/luarth
若不是因为 Luarth 并不完整——它无法定义自定义字（word），同时也缺少其他核心语言特性——我本可以直接使用它的实现，完全不必去写 MoonForth。
MoonForth 与 Luarth 之间的一个显著不同在于，后者将其内置字实现为完整的 Lua 函数。由于 Lua 处理自身调用的机制，Lua 函数无法直接操纵堆栈。而 MoonForth 则将内置字实现为普通的 C 函数，只需解引用指针即可完成调用。正因为 Lua 调用栈完全不参与其中（除非调用进入 Lua 本身），MoonForth 的字可以在不干扰 Lua 内部状态的情况下自由操作堆栈。我推测这可能正是我的项目能够继续推进，而 Luarth 未能继续的原因。无论如何，它都是一种启发——例如，MoonForth 自身的 lua-call 这一字的功能就与 Luarth 别无二致。
在 Forth 程序员（Forthers）群体中，流传着一个常被引用的梗：Forth 爱好者往往倾向于去写自己的 Forth 解释器，而不是去写自己的实际程序。另一句广为流传的话则是：自己写 Forth 就像是试图仅仅通过解剖来理解一种动物——Forth 是一门活生生的编程系统，必须亲自使用才能真正理解它。在尤其经验丰富的 Forth 圈子里，那种一上来就本能地想去写自己的 Forth，而不是去学习任何现有 Forth 的做法，往往会遭到嘲笑。
编写 MoonForth 的初衷，是希望拥有一种能够轻松与我充分了解且熟练掌握的高级语言进行交互的 Forth，而它本身又并非构建在该高级语言之上。这一架构层面的决策，与其说是出于性能考虑，不如说是出于概念上的考量。我认为，如果在一个本身就仅仅是构建在 Lua 之上的语言中，再去调用 Lua 库来编写应用程序，是毫无意义的——既然如此，为什么不直接使用 Lua 呢？
至于我为什么想要构建一个 Forth……
你在科技行业工作吗？我不在，但就像许多被推挤到该行业边缘之外的人一样，我无法容忍“垃圾代码”（fashslop）逐渐蚕食软件栈。
尽管许多 Forth 开发者自身也陷入了某种精神涣散的状态（viberotting），但在摆脱对不道德软件提供商依赖的讨论中，Forth 始终占据着一个引人瞩目的位置。因为单枪匹马的开发者几乎不需要什么外部工具就能极轻松地构建出 Forth，它实际上为探索替代性计算机生态系统提供了一条便捷的途径。正是在这种背景下，我对 Forth 产生了浓厚的兴趣，不过若没有一个能与我平时常用的更高级编程环境进行交互的 Forth，我始终无法感到顺手。因此，MoonForth 成为了一个弥足珍贵的机会，让我得以学习如何实现一个 Forth，如何用 Forth 解决问题，当然，还有如何使用 Lua 的 C API。
至于为什么要坚守 Lua 而不是进一步深入软件栈底层，是因为我坚信 Lua 很有可能在劣质代码（clod code）的肆虐中相对安然无恙。Lua 的维护者长期以来一直坚持拒绝绝大多数提交的补丁，即便那些功能很诱人，他们也宁愿凡事亲力亲为。Lua 也长期保持着克制，代码体量几乎没有膨胀，几乎感受不到来自外部促其改变的压力。在这样的环境下，维护者或首席开发者不太可能会觉得有必要求助于聊天机器人来进行大幅修改，因为 Lua 历来对这种理念嗤之以鼻。这一曾经让该语言便于我学习的宝贵特质，如今成为了让我坚定依附于整个生态系统的极为有力的理由。
我相信我对局势的判断是正确的。如果判断有误，我或许可以直接退回到一个不再受支持的旧版 Lua，直到这场风波平息。
在 Lua 之上构建 Forth 的另一个原因是可移植性。Forth 往往是针对特定硬件量身打造的，以此来驾驭硬件的种种特性。而 MoonForth 的唯一依赖就是 Lua 本身——因此，只要有 Lua 的地方，就应当能运行 MoonForth。单凭这一点，就足以让它与更传统的 Forth 区分开来。我还确保了 MoonForth 兼容 Lua 5.1，从而打开了与 LuaJIT 等该语言诸多替代实现方案互操作的大门。

终端不应拥有工作的所有权#

原文 The terminal should not own the work

终端是启动进程的好地方，但若用于存储该进程的真实状态，却是个糟糕的选择。

当一个智能体（agentic）任务归属于某个终端标签页时，该标签页就会意外变成控制平面。关闭它可能会导致工作停止。回滚历史记录（scrollback）丢失可能会抹去有价值的说明解释。重新打开项目则意味着必须重构到底运行了什么、修改了哪个分支，以及它当时是在等待、已完成还是静默卡死。任务运行的时间越长，这种机制给人的脆弱感就越强烈。

Vincent 将所有权移交至后台守护进程（daemon）。该守护进程掌控着任务状态、工作流执行、智能体进程、调度、数据库以及 git 工作树（worktree）。TUI、CLI 和 API 只是该状态的客户端。关闭任何客户端都不会对其背后的工作产生任何影响。

这一架构选择带来了显而易见的成效。我可以启动一个任务，关闭 TUI，用终端去做别的事情，稍后再返回查看相同的状态和历史记录。多个客户端可以同时查看同一个守护进程，而不会产生写入冲突。即使没有任何人打开仪表板，调度器也可以根据优先级和并发限制来接入任务。

持久性也改变了对中断的处理方式。Vincent 在对状态变更采取操作前会先将其持久化。如果守护进程在某个步骤中停止，重启恢复机制会记录下这次被中断的尝试，在终止孤儿进程前对其进行验证，并在不消耗失败重试次数的情况下重新运行该步骤。系统不会假装进程能在机器重启后幸存；它会让中断明确化，并从已知状态中恢复。

这之所以重要，是因为智能体编程越来越像一种工作负载，而非一场对话。任务需要等待配额、门禁、重试、子分支和外部检查。它们的生命周期不应与启动它们的界面生命周期绑定在一起。

终端可以展示工作，但不应掌控工作的所有权。

上周我参加了第一次电话会议，但并不是与网络应用工作组开会，而是与技术架构组（Technical Architecture Group，简称 TAG）开会。TAG 是一个元工作组，当其他工作组出现涉及大局的僵局时，它会出面协助。
在安装网页应用方面，眼下就存在一个大局上的僵局。
尽管大多数参会者（也就是浏览器厂商）都想花时间商讨为了支持可安装网页应用具体实现何种 API 的细节，WebKit 却在直接否定这项工作的前提本身。
在上周的电话会议上，WebKit 阐明了他们的立场：不应该存在一种允许开发者让用户安装当前网站的方式。他们说，这事应该留给浏览器来决定。另外，这难道真是用户想要的吗？从统计数据来看，显然完全不是这样。
如果当下已经有一种实用的网页应用安装方式，这倒是一个合理的立场。但事实并非如此。在技术上，将网站添加到 iPhone 的主屏幕是可行的。但在实际体验中，这简直是一场复杂混乱的可用性噩梦。

一方面，他们表示安装网页应用有点像添加书签。这确实没错。我们并没有用于添加书签的 API，那凭什么要有用于安装网页应用的 API 呢？
如果添加书签与安装网页应用的用户界面有任何可比性的话，这倒是个合情合理的观点。但添加书签在用户的浏览器体验中完全处于最核心、最显眼的位置，并且有数十年的使用习惯作为后盾。与此同时，安装网页应用的选项却被深深埋在“分享”图标之后的五级菜单之下。

WebKit 担心让已安装的网页应用获得访问更强大 API 的权限。他们不想这样完全没错！从主屏幕启动的网页应用不应该享有任何特权。如果它想要访问比如地理位置，用户同样需要像页面在浏览器中打开时那样授予权限。

其他浏览器又不是没能实现基于权限的 API（如推送通知）。但显然，将通知限制在已安装的网页应用中，是苹果能想到的安全实现这一 API 的唯一方法。
